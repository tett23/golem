# マニュアルの方針

この文書は、Golem の二つのマニュアル（使い手のマニュアル `manual/` と開発者のマニュアル `manual-dev/`）を書く人とレビューする人の基準である。
最初の中身は [ADR 0024](adr/0024-manual-audiences-and-policy.md) が決めた。
[ADR 0022](adr/0022-manual-as-typesetting-sample.md) のうち、Golem 自身で組むこと、フォントをリポジトリに入れないこと、CI で組んで決定性を確かめること、リリースのアセットに加えること、内容の範囲は、今も効いている。

マニュアルとこの文書の変更は、プルリクエストで決める。
読み手、内容の範囲、更新の検査、判型を変えるときも、ADR は要らず、この文書とマニュアルを同じプルリクエストで直す。
ADR を書くのは、メンテナーが求めたときだけである。
[ADR 0022](adr/0022-manual-as-typesetting-sample.md) と [ADR 0024](adr/0024-manual-audiences-and-policy.md) は、書いた時点の決定の記録として残し、書き換えない。
この文書と二つの ADR が食い違うときは、この文書に従う。

この文書は Golem の振る舞いを定めないので、`scripts/ci/needs-build.sh` のビルドが読む文書の一覧には入れない。

## 原稿と出力

| | 使い手のマニュアル | 開発者のマニュアル |
| --- | --- | --- |
| 原稿 | `manual/` | `manual-dev/` |
| 判型 | A5 の横組み | B5 の横組み |
| 版面 | 本文 13Q、行送り 22H、一行 32 字、29 行 | 本文 13Q、行送り 22H、一行 40 字、34 行 |
| 文体 | 敬体（です、ます） | 常体（である） |
| 出力 | PDF と HTML | PDF と HTML |
| リリースのアセット | `golem-manual-<タグ>.pdf`、`golem-manual-<タグ>-html.tar.gz` | `golem-dev-manual-<タグ>.pdf`、`golem-dev-manual-<タグ>-html.tar.gz` |

原稿は `.gm` のファイルだけである。
Markdown の版は持たない。
組んだものは、CI の `build` ジョブの成果物（`manual` と `manual-dev`）と、リリースのアセットで読める。

## 組み方

```sh
$ GOLEM=$(cabal list-bin -v0 golem) sh scripts/manual/build.sh            # 二冊とも
$ GOLEM=$(cabal list-bin -v0 golem) sh scripts/manual/build.sh manual-dev # 一冊だけ
```

`build.sh` は、組む前に `scripts/manual/build-info.sh` で `common/build-info.gm`（奥付の版とコミットのハッシュ）を書き、フォントを取得し、`golem build --target pdf --target html` で組む。
エラー、警告、お知らせのどれか一つでも出れば失敗とする。
マニフェストに `[diagnostics]` の `silence-notices` を書いてはいけない（`build.sh` が組む前に止める）。
`golem build` に `--no-notices` を付けて呼ぶこともしない。
お知らせの原因（コードのフォントの役割の欠け、折り返したコードの行、勧めない記法など）は、原稿の側で取り除く。
勧めない書き方を例として見せたいときは、コードブロックの中に書く。
コードブロックの中身は解釈されない。

`build-info.gm` は生成物であり、Git では管理しない。
これがないまま `golem check` や LSP でマニュアルを開くと、`@import` の先がないエラー（G0302）になる。
マニュアルを編集する前に、一度次を実行する。

```sh
$ sh scripts/manual/build-info.sh manual
$ sh scripts/manual/build-info.sh manual-dev
```

Git のリポジトリの外で組むときは、`GOLEM_MANUAL_COMMIT` と `GOLEM_MANUAL_TAG` の環境変数で値を渡す。

## 内容の範囲

二つのマニュアルに書くのは、採択して実装を終えた仕様だけである。
[docs/roadmap.md](roadmap.md) に載っている事項（未決事項を含む）と、提案の ADR は書かない。

使い手のマニュアルの例外は、付録 H「今後の予定」と付録 I「既知の不具合」だけである。
付録 H には、[docs/roadmap.md](roadmap.md) の項目のうち本を作る人に関わるものと、メンテナーが決めた予定の時期（v1 までのリリース候補、v2、v3）を、読み手の言葉で短く並べる。
付録 H の冒頭には、実装を約束するものではないことを太字で断る。
時期は「予定」として書き、「対応します」のような約束の言い方をしない。
本文の章と、付録 H のほかの付録には、今後の予定を書かない。
ただし、今の Golem にできないことを書く箇所（色の節の特色と二色刷りなど）から付録 H を参照するのはよい。

付録 I には、docs/specifications.md の「既知の不具合」の項目と、[docs/roadmap.md](roadmap.md) の v1.0.0 の項目のうち使い手が組版で出会いやすい不具合を、使い手から見える症状と分かっている対処の形で書き直して並べる。
内容は仕様書とロードマップに食い違わないようにし、どちらかの一覧を変えたときは付録 I も直す。
付録 I の冒頭には、そのマニュアルと同じバージョンの Golem についての記述であることを書く。
内部の型、モジュール、ADR、IR のように使い手が触れないものだけに関わる不具合（`golem inspect` の振る舞いなど）は載せない。

開発者のマニュアルの例外は二つある。
一つは「はじめに」の「自由ソフトウェアとしての Golem」の節で、プロジェクトの目標（v3 までに、書籍の組版で TeX と InDesign の代わりになること）と、数式の組版を v2 に回したことを書いてよい。
Golem に貢献する人が、プロジェクトの向かう先を知ったうえで手を入れられるようにするためである。
時期は目標として書き、個々の機能の予定は書かずに [docs/roadmap.md](roadmap.md) へリンクする。
もう一つは、第二部の「決定性を守る」の章の「見た目の回帰テスト」の節である。
この節には、[docs/roadmap.md](roadmap.md) の v2 の「見た目の回帰テスト」について、検討の材料（決定性の検査との違い、道具の候補、費用、考えられる進め方）を書く。
バイト列の決定性の検査が何を保証し、何を保証しないかは、Golem の利点を説明するのに欠かせないからである。
節の冒頭で、まだ実装していないことと、決定ではないことを断る。
ほかの節に同じような検討の材料を書くときは、先にこの方針を改める。

決定の正は ADR と仕様書である。
マニュアルは新しい決定をしない。
マニュアルと ADR や仕様書が食い違ったときは、ADR と仕様書に従い、マニュアルを直す。

## 使い手のマニュアル

### 読み手

一般的な組版の知識（版面、行送り、禁則、ルビ、トンボと塗り足し、入稿）を持ち、InDesign を使える編集者と DTP オペレーターである。
著者も読むが、組版の用語の説明は読み手の知識を前提にして省く。
逆に、プログラムを書く人には当たり前の事柄（ターミナル、テキストの文字コード、TOML、Git、CI）は、読み手が知らないものとして説明する。

### 文体

敬体で書く。
ADR の番号、モジュールの名前、内部の型と処理の段階は本文に出さない。
根拠として仕様書の節を示すときは、脚注にリポジトリの文書の URL を置く。

### 技術の説明の厚さと根拠

次の事柄は、手順だけでなく、なぜそうするのかと、その根拠を書く。

- ターミナルとコマンドの基本（作業中のフォルダ、終了コード、標準エラー出力）
- テキストのファイル（UTF-8、BOM、改行の LF、Unicode の正規化をしない理由、異体字セレクタ）
- TOML の書き方（テーブル、配列、文字列の二つの書き方、型の誤り）
- Git と CI（バージョン管理、差分、CI で毎回組むこと、決定性）
- フォント（OpenType の機能、埋め込みのライセンスと `fsType`、プロジェクトの中にフォントを置く理由）
- PDF/X-4、出力インテント、ICC プロファイル、トンボと塗り足し
- CSL と CSL-JSON
- LSP

根拠は、仕様や規格があればそれを示す。
仕様や規格へのリンクは脚注（`[note: ...]`）に置き、本文には規格の名前だけを書く。
規格の本文を読める形で公開していないもの（JIS X 4051、ISO 15930-7）は、規格の名前と発行元の案内のページを示し、Golem がどこまで従うかを仕様書の節で示す。
PDF/X-4 は、Golem 自身では適合を判定できず、入稿の前に商用のプリフライトで確かめる必要があることを書く。

### 言葉の選び方

読み手は、プログラムを書く人の言葉を知らない前提で書く。

- 「ディレクトリ」は、最初に出る箇所で「ディレクトリ（Finder やエクスプローラーで見るフォルダのことです）」のようにフォルダであると明示する。以後の地の文では「フォルダ」と書く。「ディレクトリ」を使うのは、コマンドの名前、オプションの名前、Golem やほかのプログラムが表示する文言を引くときに限る。
- 読み手は Git を知らない前提で書く。下の一覧の Git と CI の語は、最初に出る箇所で、何のための仕組みかを Git を知らない人の言葉で説明する。説明する前の語を、ほかの章で先に使わない。使う必要があれば、説明の箇所へ相互参照を付ける。
- 第 1 章と第 2 章は Git を使わずに読めるように書く。Git の語は第 8 章「バージョン管理と CI」で初めて説明する。
- 読み手がふだん使っている言葉を使い、定着した外来語や用語を、聞き慣れない和語に置き換えない。たとえば、computer は「機械」ではなく「コンピューター」、version は「版」ではなく「バージョン」（version control は「バージョン管理」）、tool は「道具」ではなく「ツール」、TOML の table は「表」ではなく「テーブル」、copy は「写す」ではなく「コピー」と書く。「版」は、本の版（edition）と印刷の版（plate）にだけ使う。
- フォルダの階層の上の端を「根」や「ルート」と書かない。「プロジェクトのフォルダの直下」「プロジェクトのフォルダのいちばん上」のように書く。エディタの設定の画面に出る「ルート」のように、ほかのプログラムが使う語を引くときは除く。
- 「シェル」の語は使わない。必要なときは「ターミナルの中で、打ち込んだコマンドを読み取って実行するプログラム」のように、役割で説明する。
- ホームのフォルダを表す `~` は、第 1 章「配布物を取得する」で説明してから使う。コマンドの例のほかでは、「ホームのフォルダの中の `.cache` のフォルダ」のように言葉で書く。
- 手元のコンピューターの性質に左右されないことを言うときは、「どのコンピューターで組んでも」のように書く。
- 「書体」と「フォント」は同じ意味の語として使わない。書体は文字のデザイン（明朝体、ゴシック体、ある書体の見た目）、フォントはソフトウェアが読み込み、埋め込み、取得し、ライセンスの条件が付く具体的なファイルとデータ（OTF や TTF のファイル、フォントにない字、ファイルを指すフォントの役割）を指す。箇所ごとにどちらの意味かで選ぶ。使い手のマニュアルでは、第 5 章「書体とフォント」と付録 G で違いを説明する。

下の一覧の語は、最初の説明の箇所より前に使わない。
付録 G「用語の一覧」にも同じ語を載せる。
どの語がこの扱いに当たるかは、この一覧で管理し、レビューで足す。

### はじめに

「はじめに」は、読み手が Golem を使ってみたくなる順に、次の節を並べる。
得られるものを先に書き、できないことと仕組みの説明は後に回す。

1. 冒頭（見出しのない部分）。InDesign で本を作る人が日々出会う手間から入り、Golem がそれを仕組みの側で引き受ける組版システムであることと、このマニュアルの読み手を書く。
2. Golem で得られるもの。InDesign から移って得られるものを、確かめられる事実に限って書く。どのコンピューターで組んでも同じ紙面になること（ビット、バイト、決定性の語をここで説明する）、一つの原稿から四つの形式を作ること、原稿と体裁がテキストであること、日本語の組版の規則と InDesign と同じ名前の機能が入っていること、プリフライトと日本語の誤りの知らせが組み込まれていること。決定性を保証する形式（PDF、HTML、プレーンテキスト）と、まだ保証しない形式（EPUB）を書き分ける。
3. 自由ソフトウェアとして無料で使えること。MIT License の自由ソフトウェアであること（自由ソフトウェアとプロプライエタリソフトウェアの語をここで説明する）と、それが本を作る人にもたらすもの（ライセンスの料金も月ごとの利用料もこれから先もかからないこと、契約が切れて道具やデータを使えなくなることがないこと、過去のバージョンを使い続けられること、原稿と設定の書き方が公開されていてデータが閉じ込められないこと、誰でも改変して配れること）、動く環境、使ってみて困ったことを配布元に知らせてほしいこと。プロジェクトの資金や目標の話は、使い手のマニュアルには書かない。
4. 読み手ごとの説得。編集者、DTP オペレーター、著者のそれぞれに向ける。著者には、組版から入稿のデータまでを一人で作れることと、入稿の前に印刷所の指定と商用のプリフライトで確かめる必要があることを書く。
5. Golem の仕組み。三種類のファイルとプロジェクト、`golem build`。
6. InDesign との違い。InDesign にあって Golem にないもの（画面の上で直接組むこと、個々の行やオブジェクトを手で動かす調整、雑誌のような自由なフレームの配置、特色、プリフライトの全体）を書き、付録 H と付録 I を参照する。
7. TeX との違い。TeX と比べて Golem を選ぶ理由を、確かめられる事実に限って書く。TeX にあって Golem にないもの（数式の組版、長い歴史とパッケージの蓄積）も書く。
8. このマニュアルについて。

主張の一つ一つに、根拠（仕様書の節、CI のジョブ）を脚注で示す。
次のことは書かない。

- 「InDesign と同じ品質」「TeX より美しい」のような、比べ方を定められない主張。
- 速さの比較。計測の記録（`docs/benchmarks/`）があるときに限り、その記録を示して書く。
- 「PDF/X-4 に準拠することを保証する」。

### 章立て

前付け、本文の章、付録、後付けの順に並べる。

- 前付け：はじめに（`@nonumber`、目次に載せる）、目次
- 第 1 章 インストールと最初の一冊
- 第 2 章 テキストで本を作るための基礎（ターミナル、フォルダとファイル、テキストのファイル、TOML）
- 第 3 章 原稿の記法
- 第 4 章 プロジェクトの設定
- 第 5 章 スタイルの設定
- 第 6 章 出力
- 第 7 章 検査と診断（お知らせと、その抑制を含む）
- 第 8 章 バージョン管理と CI
- 第 9 章 エディタと LSP
- 第 10 章 プラグイン
- 付録 A 記法、B マニフェスト、C スタイル、D preflight.toml、E 診断の一覧、F InDesign との対応、G 用語の一覧、H 今後の予定、I 既知の不具合
- 後付け：参考文献、索引、奥付

ノンブルは「はじめに」の最初のページから通しで振る。
各節では、その節で説明する機能を、その節の中で実際に使う。

### InDesign との対応

Golem の概念に InDesign の対応物があるときは、初出でその名前を示す。
付録 F に同じ表を載せる。

| Golem | InDesign |
| --- | --- |
| プロジェクト（`manifest.toml` と原稿と `style.toml`） | ドキュメントとブック |
| `style.toml` の `[page]` と `[page.grid]` | 新規ドキュメントとレイアウトグリッドの設定 |
| 段落スタイル、文字スタイル、`based-on` | 段落スタイル、文字スタイル、基準 |
| 正規表現スタイル | 正規表現スタイル（GREP スタイル） |
| アキ量のセット | 文字組みアキ量設定 |
| `kerning`、`tracking`、`proportional-metrics`、`baseline-shift` | カーニング、トラッキング、プロポーショナルメトリクス、ベースラインシフト |
| マスターページ（`[masters]`） | 親ページ（InDesign 2022 より前はマスターページ） |
| プロジェクトの `fonts/` | Document Fonts フォルダー |
| スウォッチ（`[color.swatches]`） | スウォッチ |
| `golem build` | 書き出し |
| `golem check` | 原稿と設定の検査（プリフライトの検査は含まない） |
| `golem preflight` | プリフライト |
| プリフライトの設定（`preflight.toml`） | プリフライトプロファイル |

対応は名前と役割の近さを示すもので、振る舞いが同じであることを意味しない。
振る舞いが違う箇所（たとえば、Golem の段落スタイルは行送りを持たず、本文は常に行の格子に載ること）は、対応を示した同じ節で違いを書く。
InDesign の操作の手順は説明しない。

## 開発者のマニュアル

### 読み手と構成

- 第一部「Golem で仕組みを作る」：Golem を使って仕組みを作る人（プラグインの作者、CI で自動の組版を組む人、エディタに LSP をつなぐ人）に向ける。
- 第二部「Golem を開発する」：Golem そのものを開発する人に向ける。

### 文体とリンク

常体で書く。
モジュールの名前、型の名前、ADR の番号は本文に出してよい。

Golem が報告する誤りや注意は、「診断」と書かず、英語の diagnostic で書く。
開発者は、LSP の Diagnostic やコンパイラの diagnostics でこの語を知っているからである。
一つ一つを指すとき、数えるとき、コードや重大度を言うときは単数の diagnostic（「diagnostic を出す」「diagnostic のコード」）、まとまりや並びを指すときは複数の diagnostics（「diagnostics の一覧」「diagnostics を JSON の配列で書く」）と書く。
コードの識別子（`Diagnostic` など）、ファイル名（`docs/diagnostics.md`）、ADR や文書の題を「」で引くときは、元の語のまま書く。
使い手のマニュアルは「診断」のままとする。
開発者のマニュアルの「はじめに」の「表記」で、この使い分けを断る。

リリースに付けるファイル（GitHub の Releases の assets）や、プログラムが使う辞書、図版、フォントのようなファイルを指すときは、「資産」と書かず、「アセット」と書く（「リリースのアセット」「辞書のようなアセット」）。
開発者は GitHub やビルドツールの asset でこの語を知っており、「資産」は会計の語と紛れるからである。
コードの識別子と、「」で引く題は元の語のまま書く。

diagnostic の重大度は、`error`、`warning`、`notice` の名前で書く。
使い手のマニュアルと docs/diagnostics.md が使う「お知らせ」は、開発者のマニュアルでは使わない。
開発者は「お知らせ」から重大度の `notice` を引きにくく、ログの水準の info と取り違えやすいためである。
docs/diagnostics.md の重大度の欄の値を説明するときに限り、その値として「お知らせ」を引く。

開発者のマニュアルは、docs/ の仕様書、各モジュールの仕様書、ADR、CONTRIBUTING.md をまとめ、その文書へリンクする。
リンクは脚注に置き、リポジトリの文書は `https://github.com/tett23/golem/blob/main/` から始まる URL で書く。
版やコミットを含む URL にはしない。
どのコミットから組んだかは、奥付の版で示す。

## 二つのマニュアルに共通する体裁

- 説明していない語を、いきなり使わない。用語、略語、外来語、コマンドやファイルの名前は、最初に出る箇所で何であるかを書いてから使う（使い手のマニュアルは使い手の言葉で、開発者のマニュアルは開発者が知らないかもしれない語に限って）。説明が長くなる語は、説明の箇所へ相互参照を付け、用語の一覧にも載せる。章の順に読まない読み手のために、各章で初めて使うときにも、必要なら説明の箇所への相互参照を付ける。
- 前付けの順（番号のない「はじめに」、目次）、索引の二段組み、奥付の版の表示をそろえる。
- 脚注の前に区切り線を引く。`style.toml` の `[notes.rule]` に、一行の字数の 4 分の 1 ほどの `length` と、前後の 0.5zw の間隔を書く（[golem-driver ADR 0024](golem-driver/adr/0024-rule-spec-and-footnote-separator.md)）。
- 奥付は `@import common/build-info.gm as build` で読み、「版：[= build.edition]」と「コミット：[code: [= build.commit]]」の二行を載せる。
- コードブロックは組み込みの段落スタイル `code` で組み、背景のスウォッチ（`{ cmyk = [0, 0, 0, 8] }` を出発点にする）と内側の余白を付ける。
- コードブロックの中のコマンドの行は、プロンプトに見立てた `$` と空白で始める。コマンドの出力の行には付けない。`\` で終わる行の続きや、`for` の中の行のように、一つのコマンドの続きになっている行にも付けない。コマンドのコードブロックの言語は `sh` とし、出力を交えて見せるときは `console` とする。使い手のマニュアルでは、コマンドが最初に出る第 1 章「配布物を取得する」で、`$` が打ち込む行の印であり、`$` と空白は打ち込まないことを説明する。開発者のマニュアルでは、はじめにの「表記」で断る。
- 本文の中のファイル名、コマンド、パス、キーは `[code: ...]` で書く。`[style code: ...]` は使わない。
- フォントの役割 `code` には、欧文に Source Code Pro の Regular、和文に Noto Sans JP の Regular を使う。
- フォントはリポジトリに入れず、`scripts/manual/fetch-fonts.sh` がバージョンを固定した URL から取得して SHA-256 を確かめる。どれも SIL Open Font License 1.1 である。
- 本文が拠りどころにする規格と文献は、最初に出る箇所で `[cite キー]` で引用し、巻末の参考文献（`@bibliography`）に載せる。書誌のデータは、各マニュアルの `references.json` に置く。リンクは今までどおり脚注に置く。参考文献の一覧は引用した文献だけを並べるので、脚注にだけ書いた規格は一覧に載らない。
- 開発者のマニュアルの図は、`manual-dev/images/src/` の SVG を原稿とし、`scripts/manual/render-figures.sh` で PNG にして、両方をコミットする。今の Golem は図版に PNG と JPEG を使い、SVG を扱わないためである。図の文字は、組版と同じ Noto Sans JP で描く。
- マニュアルは画面で読む PDF と HTML として配るので、印刷用の設定（塗り足しと出力インテント）を持たせない。出力インテントに要る ICC プロファイルは配布の条件のためリポジトリに入れられず、塗り足しだけを持たせても PDF/X-4 の要件は満たせない。
- 各マニュアルのルートの `preflight.toml` は、組み込みの `print` を元にして、印刷のための検査（図版の色空間と ICC プロファイル、塗り足し、PDF/X-4 の要件）を `off` にする。はみ出し、グリフの欠け、図版の解像度は検査に残す。
- 図版は、今は RGB の PNG のままにする。PDF と SVG の図版（[docs/roadmap.md](roadmap.md) の v0.1.0-rc3 の「PDF の図版」と「SVG の図版」）が使えるようになったら、図をベクターのまま置く形に改める。

## 更新の決まり

`scripts/manual/check-updated.sh BASE HEAD` が、ブランチの変更を次の規則で検査する。
`.githooks/pre-push` と、CI の `docs.yml` の `manual` ジョブが呼ぶ。

1. docs/markup.md か docs/specifications.md を変えたら、`manual/` か `manual-dev/` の下のどれかのファイルを変えていなければならない。
2. CONTRIBUTING.md か CONTRIBUTING.en.md を変えたら、`manual-dev/` の下のどれかのファイルを変えていなければならない。
3. どちらの規則も、範囲のコミットのどれかのメッセージに `Manual: unchanged` のトレーラーがあれば通す。

規則 1 は二つのマニュアルのどちらを直しても通る。
使い手から見える振る舞いが変わったら使い手のマニュアルを、開発者にだけ見える変更なら開発者のマニュアルを直す。
どちらを直すべきかはレビューで確かめる。
各モジュールの仕様書と ADR の変更は検査しない。
細部のずれはレビューで見つける。
