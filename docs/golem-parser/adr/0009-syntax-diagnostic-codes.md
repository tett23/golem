# ADR 0009: 構文の段階の診断コード

ステータス: 採択→G0119 の条件とメッセージは [ADR 0013](0013-splat-after-keyword-arguments.md)

## 文脈

[docs/diagnostics.md](../../diagnostics.md) は、Golem が出す診断のコードを一つずつ説明する。
構文の段階（`G01xx`）のコードのうち、G0123 を除く 17 個は「ADR なし」である。
[ADR 0002](0002-parser-on-peg-hs.md) は、読み込みの段階の検査と、ラベルから診断コードへの対応表を golem-parser に一箇所で持つことを定めた。
しかし、どのラベルにどの番号とメッセージを当てるかは書いていない。
[ADR 0003](0003-block-grammar.md) と [ADR 0004](0004-inline-grammar.md) はラベルと回復を表にしたが、コードは [ADR 0002](0002-parser-on-peg-hs.md) の対応表に加えるとだけ書いている。
[ADR 0007](0007-grammar-label-safety.md) は G0123 を定め、G0110、G0111、G0117、G0120、G0122、G0129 を既存のコードとして挙げるにとどまる。
番号の割り当ては、実装（`Golem.Parser.labelCode` と `Golem.Parser.Read.readSource`）にしかない。

この ADR は、次の 17 個のコードの条件、重大度、メッセージ、位置、段階を、実装を追認する形で定める。

- 読み込みの段階：G0101、G0102、G0103
- 解析の段階：G0110 から G0122、G0129（G0123 は [ADR 0007](0007-grammar-label-safety.md) が定めた）

あわせて、実装を読み、`golem check --format json` で確かめた結果、次の問題が見つかった。
それぞれについて、この ADR で扱いを決める。

1. 読み込みの段階の診断（G0101 から G0103）が、ファイルのパスを持たずに表示される。
   人が読む形式では `<unknown>:?:?:` と出る。
   読み込みに失敗するとプロジェクトの読み込みが `Left` で終わり、golem-driver が `brSources` を空にして返すためである。
2. 読み込みの段階を通るファイルが揃っていない。
   原稿（章と import したファイル）と `manifest.toml` は `readSource` を通るが、`style.toml` は `decodeUtf8Lenient` で読む。
   `style.toml` の BOM は G0306（TOML の誤り）になり、CRLF と不正な UTF-8 は黙って受理される。
3. LSP の編集中のバッファは、`readSource` を通らない。
   ディスクの上の原稿なら G0102 や G0103 になる BOM と CR が、エディタで開いている間は診断にならない。
4. G0120 が同じ位置に二度出ることがある。
   golem-parser はラベル `expr` に G0120 を出す。
   AST への変換は解析できなかった式を `EError` にし、golem-eval は `EError` の評価に同じ G0120 を出す。
   `EError` の位置は golem-parser の診断の位置と一致する（`[=]` ではどちらもバイト 2 から 2、`[f *[=]]` ではどちらも 5 から 6）。
   golem-driver は構文エラーのあるファイルを評価しないので、`golem build` と `golem check` では二度出ない。
   LSP がプロジェクトの外のファイルを扱う `Golem.Lsp.Workspace.loose` は、構文の診断と評価の診断をつないで返すので、二度出る。
5. `Golem.Parser.Lower.exprOf` は、式のノードが一つもないとき、`FileId 0` のバイト 0 を位置とする `EError` を作る。
   `FileId 0` は `manifest.toml` のファイルである。
   今は構文エラーのあるファイルを評価しないので表に出ないが、4 の LSP の経路では `manifest.toml` の先頭（プロジェクトの外のファイルでは、そのファイルの先頭）を指す診断になる。
6. G0111 のメッセージが条件と合っていない。
   メッセージは「タブ、または 2 の倍数でない空白」と言う。
   実際の条件は、そのブロックの深さの空白の後に、さらに空白かタブが続くことである。
   行頭の空白 2 個の段落（`"  二つ空け\n"`）は 2 の倍数だが G0111 になり、項目の続きの空白 3 個（`"- a\n   - b\n"`）は 2 の倍数でないが受理される。
7. G0117 のメッセージが、閉じ括弧があるときにも「] がありません」と言う。
   ラベル `close` は、式やコマンドの後に `]` が来ないときに送出される。
   `[= 1 ? 2]` では `1` の後の `?` で送出され、`]` は後にあるのに G0117 になる。
8. 必ず失敗する式に付けたラベル（`BadIndent`、`TooDeep`、`OrphanDef`、`BadBracket`）は、誤りの文字を読んだ後で送出される。
   そのため、診断の位置が誤りの文字の次から始まる。
   `"- a\n\tb"` の G0111 はタブの次から、`"#### x"` の G0112 は 4 つ目の `#` の次から、`"本文 [ だけ"` の G0121 は `[` の次から始まる。

ほかに、次のことを確かめた。
どれもこの ADR で直すことはせず、[トレードオフ](#トレードオフ)に理由を書く。

- G0129 には、今は到達しない。文法のすべてのラベルが `labelCode` に載っており、ParserSpec がそれを確かめている。
- G0122 にも、今の文法では到達しない。開始の規則 `File` はすべての選択肢が省略可能で失敗せず、`Blocks` の中のブロックの失敗はラベル `block` が受け止める。
- `[f *[x y]]` は G0117 を二つ出す（バイト 7 から 10 と、10 から 10）。閉じていない `[` が二つあり、位置も異なる。
- `本文 [=` で終わるファイルは、G0117 と G0120 を同じ位置（ファイルの終わり）に出す。式がないことと `]` がないことの二つである。
- G0115 の位置は、セルの数が違う行の終わりの幅 0 の位置である。G0116 の位置はファイルの終わりの幅 0 の位置である。どちらも開始の位置（行の頭、開きのフェンス）を指さない。

番号の区分は [golem-syntax ADR 0001](../../golem-syntax/adr/0001-source-spans-and-diagnostics.md) が定める。
この ADR が扱う 17 個は、すべて構文の区分（`G01xx`）に収まっている。

## 実装すること

### 共通の定め

- この ADR のコードは、すべて重大度がエラーである。プロファイルで重大度は変わらない（`profileDependentCodes` に含めない）。
- 段階は構文であり、golem-parser が出す。G0120 だけは golem-eval も出す（[G0120 の二重](#g0120-の二重)）。
- 位置はファイル先頭からの UTF-8 のバイト数で表す（[golem-syntax ADR 0001](../../golem-syntax/adr/0001-source-spans-and-diagnostics.md)）。
- 解析の段階の診断の位置は、peg-hs の `SyntaxError` の範囲（`syntaxErrorRange`）から作る（[ADR 0002](0002-parser-on-peg-hs.md)）。始まりはラベルを送出した位置、終わりは回復が読み飛ばした入力の終わりである。挿入の回復では幅 0 になる。
- メッセージの `<ラベル>` は、引数を埋める部分を表す。

### 既存の振る舞いの追認

この節は、今の実装をそのまま定める。
変える点は、次の[変えること](#変えること)の節に分けて書く。

#### 読み込みの段階

`Golem.Parser.Read.readSource :: FileId -> ByteString -> Either [Diagnostic] Text` が、パーサーに渡す前のバイト列を検査する。
次の順に検査し、最初に当てはまった一つだけを返す。
返した時点で、そのプロジェクトの読み込みは失敗し、ほかのファイルの診断は出ない。

| コード | 条件 | メッセージ | 位置 |
|---|---|---|---|
| G0102 | バイト列が `EF BB BF`（UTF-8 の BOM）で始まる | `ファイルの先頭に BOM があります。BOM を取り除いてください` | バイト 0 から 3 |
| G0101 | UTF-8 として復号できない | `UTF-8 として不正なバイト列があります` | 最初の不正なバイトの 1 バイト |
| G0103 | 復号できたバイト列に CR（`0x0D`）が一つでもある。CRLF の CR と、単独の CR の両方を含む | `改行に CR が含まれています。改行は LF に限ります` | 最初の CR の 1 バイト |

**BOM が先である理由**：BOM は正しい UTF-8 なので、UTF-8 の検査の前に見ないと検出できない。

**不正なバイトの位置**：先頭から UTF-8 の列を一つずつ読み、先頭のバイトが `C2` から `F4` の範囲にない、列が途中で切れている、または復号できない列の先頭のバイトを指す。

**G0103 の修正案**：`diagFixes` に、題が `golem fmt で LF に直す`、編集が空の修正案を一つ載せる。
編集を持たないのは、ファイル全体の書き換えを修正案の編集で表すと大きくなるからである。
[ADR 0002](0002-parser-on-peg-hs.md) は「CRLF を含めばエラー」と書いたが、実装は単独の CR もエラーにしている。
この ADR は実装に合わせ、CR を一つでも含めばエラーとする。

**検査するファイル**：章と import したファイル（golem-project の `loadSources`）と、`manifest.toml`（`loadProjectWith`）である。
`style.toml` は今は検査していない（[style.toml の読み込み](#styletoml-の読み込み)で変える）。

**BOM が途中にある場合**：先頭以外の `EF BB BF` は U+FEFF（幅のない改行しない空白）であり、読み込みの段階では拒まない。

#### 解析の段階

`Golem.Parser.labelCode :: Maybe Text -> (Text, Text)` が、ラベルを診断コードとメッセージに対応させる。
回復の規則は [ADR 0003](0003-block-grammar.md)、[ADR 0004](0004-inline-grammar.md)、[ADR 0007](0007-grammar-label-safety.md) が定め、`modules/golem-parser/grammar/Golem.peg` の `%recover` に書いてある。
次の表の位置は、今の実装で確かめたものである（8 の問題を直した後の位置は[変えること](#変えること)に書く）。

| コード | ラベル | 送出する条件 | メッセージ | 位置 |
|---|---|---|---|---|
| G0110 | `block` | `Block(ind)` のすべての選択肢（`BadIndent`、`OrphanDef`、ブロックコマンド、見出し、箇条書き、定義リスト、表、コードブロック、段落）が、ほかのラベルを送出せずに失敗した | `このブロックを解釈できません` | ブロックの先頭から次の空行の前まで |
| G0111 | `indent` | 行頭で、そのブロックの深さ `ind` 個の空白の後に、さらに空白かタブがある（`BadIndent`） | `インデントが不正です（タブ、または 2 の倍数でない空白）` | 余分な空白かタブの次の文字から次の空行の前まで |
| G0112 | `heading_level` | 見出しの `###` の直後に `#` が続く（`TooDeep`） | `見出しの階層は 3 までです` | 4 つ目の `#` の次から次の空行の前まで |
| G0113 | `def_orphan` | ブロックの位置（深さ `ind`）が `=:` で始まる。定義リストの用語の後の `=:` は `DefList` が先に受理するので、ここに来るのは用語のない `=:` だけである（`OrphanDef`） | `用語のない =: があります` | `=:` の次から次の空行の前まで |
| G0114 | `table_delimiter` | 表の 1 行目（`TableRow`）と改行の後に、区切りの行（`TableDelimiter`）が続かない。ファイルが 1 行目で終わる場合を含む | `表の 2 行目は区切りの行でなければなりません` | 2 行目の先頭から次の空行の前まで |
| G0115 | `table_cells` | 表の本体の行のセルの数が、1 行目のセルの数と違う | `表のセルの数が見出しの行と一致しません` | その行の終わりの幅 0 の位置 |
| G0116 | `code_close` | コードブロックの開きのフェンスと同じ深さの閉じのフェンスが、ファイルの終わりまでに現れない | `コードブロックが閉じていません` | ファイルの終わりの幅 0 の位置 |
| G0117 | `close` | インラインのコマンド（`InlineCommand`）、式文脈（`[= ...]`）、展開する引数（`*[...]`、`**[...]`）の後に `]` が来ない | `閉じ括弧 ] がありません` | `]` を期待した位置から段落の終わりまで。段落の終わりでは幅 0 |
| G0118 | `comment_close` | `%%` または `%%=` で始めたコメントが、段落の終わり（空行の前の改行、またはファイルの終わり）までに `%%` で閉じない。見出しと表のセルの中のコメントも同じである | `コメントが段落の中で閉じていません` | 段落の終わりの幅 0 の位置 |
| G0119 | `arg_order` | コマンドの引数で、キーワード引数（`key=value`）の後に位置引数がある | `キーワード引数の後に位置引数があります` | その位置引数の前の空白から、読み飛ばした引数の終わりまで |
| G0120 | `expr` | 式文脈（`[= ...]`）、展開する引数、`@set 名前 = 式` の `=` の後で、式が一つも読めない | `式を解釈できません` | 式を期待した位置から `]` の直前（`@set` では回復が読み飛ばした範囲）まで |
| G0121 | `bracket` | インラインの `[` の後に、コマンド名（`[a-z]` で始まる識別子）も `=` も続かない（`BadBracket`） | `[ の後にはコマンド名か = が必要です。本文の [ は \[ と書きます` | `[` の次から段落の終わりまで |
| G0122 | （ラベルなし） | ラベルを持たない構文エラー。開始の規則の後に入力が残る場合と、開始の規則が失敗する場合 | `解釈できない入力が残っています` | `SyntaxError` の範囲 |
| G0129 | 上の表と G0123 にないラベル | 文法にあって `labelCode` にないラベルで失敗した | `構文エラー（<ラベル>）`。`<ラベル>` はラベルの名前 | `SyntaxError` の範囲 |

G0117 と G0120 の区別は、式が一つも読めないか（G0120）、式やコマンドを読んだ後に `]` 以外が来たか（G0117）による。
たとえば `[= 1 +]` と `[= 1 ? 2]` は、`1` を読んだ後で失敗するので G0117 になる。

`@set x = 1 +` は G0110 になる。
`@set` のブロックコマンドの規則は、式の後に行末を求めるだけでラベルを持たないので、`BlockCommand` 全体が失敗し、`block` が送出される。

#### G0129 と G0122 の位置づけ

G0129 は、文法にラベルを足したのに `labelCode` に載せ忘れた場合の既定である。
ParserSpec の「every grammar label has its own diagnostic code」が、文法のすべてのラベルが G0129 以外に対応することを確かめるので、正しい実装では出ない。
G0122 は、[ADR 0002](0002-parser-on-peg-hs.md) の「ラベルを持たない構文エラーにもコードを割り当てる」に当たる。
[ADR 0002](0002-parser-on-peg-hs.md) は「開始規則の後に残った入力」と「開始規則の失敗」のそれぞれにコードを割り当てると書いたが、今の文法の `File` は失敗しないので、両方を G0122 にまとめる。
二つを分けるのは、`File` が失敗しうる文法に変えるときとする。

#### golem-eval の G0120

`Golem.Eval.Expr.evalExpr` は、`EError` を評価すると G0120 を `EError` の位置に出す。
`EError` は、AST への変換（[ADR 0005](0005-cst-to-ast.md)）が解析できなかった式に作る値であり、構文エラーのあるファイルにしか現れない。
golem-eval の G0120 は、評価が `EError` に値を与えないための防御であり、診断として利用者に見せるものではない。

### 変えること

#### 読み込みの診断の位置

1 の問題を直す。
ソースの読み込みが診断で失敗したときも、診断の表示に使うファイルの表を返す。
読み込みの失敗の型 `ReadFailure` を、golem-parser の `Golem.Parser.Read` に置く。

```haskell
-- | ソースの読み込み（readSource）の失敗。失敗したファイルも、行の索引を付けて表に入れる
data ReadFailure = ReadFailure
  { rfDiagnostics :: [Diagnostic],
    rfSources :: Map FileId SourceInfo
  }
```

- ファイルを読む処理は、どれかのファイルの `readSource` が失敗したら `ReadFailure` を返す。`rfSources` には、読んだすべてのファイルを、失敗したファイルも含めて入れる。行の索引は、そのファイルのバイト列を `decodeUtf8Lenient` で復号したテキストから作る。`manifest.toml` と `style.toml` も同じである。
- 不正な UTF-8 のファイルでは、復号で不正なバイトが U+FFFD に置き換わるので、それより後のバイト数はずれる。G0101 の位置は最初の不正なバイトなので、その位置より前の行と列は正しい。
- golem-driver の `build` は、`ReadFailure` の `rfSources` を `brSources` に入れる。LSP は、診断の FileId が `rfSources` で指すファイルに載せる。

`ReadFailure` は、ソースを読む段の失敗だけを表す。
プロジェクトの設定の誤り（`manifest.toml` と `style.toml` の値、import の循環など）の失敗は、提案中の [golem-project ADR 0006](../../golem-project/adr/0006-project-diagnostic-codes.md) の `ProjectFailure` が表す。
二つは別の型とし、どちらの ADR も他方の採否に依らずに実装できるようにする。
両方を実装したときは、`ProjectFailure` を返す処理が `ReadFailure` を受け取ったら、`rfSources` を `pfSources` に合わせ、`rfDiagnostics` を `pfDiagnostics` に加える。

これで、たとえば import したファイルの CRLF は `<unknown>:?:?:` ではなく `y.gm:1:2:` と表示される。

#### style.toml の読み込み

2 の問題を直す。
golem-driver が `style.toml` を読むときも `readSource` を通し、G0101、G0102、G0103 を `style.toml` の `FileId` の位置に出す。
これで `style.toml` の BOM は G0306 ではなく G0102 になり、CRLF と不正な UTF-8 も診断になる。
golem-fmt は `style.toml` を整形しないので、G0103 の修正案（`golem fmt で LF に直す`）は `style.toml` には付けない。

#### LSP のバッファの検査

3 の問題を直す。
golem-parser に、復号済みのテキストを検査する関数を足す。

```haskell
-- | 'readSource' のうち、復号の後に残る検査（BOM と CR）。
checkText :: FileId -> Text -> [Diagnostic]
```

- テキストが U+FEFF で始まれば G0102 を、バイト 0 から 3 の位置に出す。
- そうでなく、CR を含めば G0103 を、最初の CR の UTF-8 のバイト位置に出す。修正案は `readSource` と同じである。
- 結果は高々一つの診断である。
- `readSource` は、復号の後でこの関数を使うように書き換え、二つの検査の定義を一箇所にする。

golem-project の `loadSources` で overlay のテキストを使うときと、golem-lsp の `loose` は、`checkText` が診断を返したら、そのファイルの構文の診断の前に加える。
ディスクのファイルと違い、プロジェクトの読み込みは止めない。
エディタの上で BOM や CR を見せながら、ほかの機能（補完や定義へのジャンプ）を使い続けられるようにするためである。
ただし `golem build` と `golem check` は overlay を使わないので、ビルドの振る舞いは変わらない。

#### G0120 の二重

4 の問題を直す。
golem-lsp の `loose` は、構文の診断にエラーがあるとき、評価の診断を捨て、構文の診断だけを返す。
評価の結果（`erDocument` など）は、補完やホバーのために今までどおり保つ。
これは golem-driver の「構文エラーのあるファイルの評価の診断は出さない」と同じ規則であり、G0120 に限らず、構文エラーに引きずられた評価の診断をすべて止める。

golem-eval の G0120 は残す。
番号も変えない。
`EError` を評価したときに値を作らずに失敗させるには、どこかで診断が要る。
構文エラーのあるファイルの評価の診断は利用者に見せないので、この G0120 が表示されることはない。

#### exprOf の位置

5 の問題を直す。
`Golem.Parser.Lower.exprOf` は、式のノードが一つもないとき、呼び出し側から受け取った位置の幅 0 の `EError` を作る。
呼び出し側は、式を期待した節のスパンの始まり（`[=` の `NExpr` の節、`@set` のブロック、展開する引数の節）を渡す。
`FileId 0` を決め打ちにする箇所はなくす。

#### G0111 のメッセージ

6 の問題を直す。
メッセージを次に変える。

`インデントが不正です（タブ、またはブロックの深さより多い空白）`

条件は変えない。

#### G0117 のメッセージ

7 の問題を直す。
メッセージを次に変える。

`ここに閉じ括弧 ] が必要です`

閉じ括弧がない場合（位置は段落の終わり）と、式やコマンドの後に余計なものがある場合（位置はその余計なものの始まり）の両方で、「この位置に `]` が来るべきだった」と読める。
二つの場合を別のコードに分けることはしない。
文法の上では同じラベルの同じ失敗であり、分けるには `close` を二つのラベルに分け、回復の規則も分ける必要がある。

#### 必ず失敗する規則の位置

8 の問題を直す。
`Golem.peg` の次の 4 つの規則で、誤りの文字を消費せずに先読みで確かめ、その前でラベルを送出する。

```
BadIndent <- Ind(ind) &[ \t] (&{ False })^indent { () }
OrphanDef <- Ind(ind) &'=:' (&{ False })^def_orphan { () }
TooDeep <- &'#' (&{ False })^heading_level { () }
BadBracket <- &LBr (&{ False })^bracket { () }
```

診断の位置は、次のように変わる。

| コード | 変更の前 | 変更の後 |
|---|---|---|
| G0111 | 余分な空白かタブの次から | 余分な空白かタブから |
| G0112 | 4 つ目の `#` の次から | 4 つ目の `#` から |
| G0113 | `=:` の次から | `=:` から |
| G0121 | `[` の次から | `[` から |

回復の規則は、ラベルを送出した位置から読み飛ばすので、読み飛ばす範囲が誤りの文字の分だけ前に広がる。
CST はロスレスのままであり、受理する言語は変わらない（必ず失敗する式のラベルなので、送出の位置だけが変わる）。

#### 文書の更新

- [docs/diagnostics.md](../../diagnostics.md) の G0101 から G0103、G0110 から G0122、G0129 の「ADR」の項目を、この ADR へのリンクに変える。G0111 と G0117 のメッセージを新しい文言に、G0101 から G0103 の意味に `style.toml` と `manifest.toml` を加える。G0120 の項目に、golem-eval の G0120 が表示されないことを書く。

新しい診断コードは割り当てない。

## トレードオフ

**G0115 と G0116 の位置**：G0115 はセルの数を数え終えた行の終わりを、G0116 はファイルの終わりを指す。
利用者が直すのは行の頭や開きのフェンスなので、その位置を指すほうが親切である。
しかし、位置は peg-hs の `SyntaxError` の範囲から作ると [ADR 0002](0002-parser-on-peg-hs.md) で決めており、ラベルごとに位置を作り変える仕組みは golem-parser にない。
G0115 は行の終わりなので、エディタでは同じ行に出る。
G0116 は、閉じていないことが分かるのがファイルの終わりである。
開きの位置を関連位置として載せる変更は、ほかのコード（G0117 の開きの `[`）と合わせて別の ADR で扱う。

**同じ位置の G0117 と G0120**：`本文 [=` で終わるファイルには、式がないことと `]` がないことの二つの誤りがある。
片方を止めると、一つ直した後に、もう一つの誤りが初めて出ることになる。
二つの誤りを一度に見せるほうがよい。
`[f *[x y]]` の二つの G0117 も、閉じていない `[` が二つあり、位置も異なるので、同じ理由で残す。

**G0117 を分けないこと**：「閉じ括弧がない」と「余計なものがある」を別のコードにすれば、利用者は原因をより早く知れる。
しかし、文法の上では `close` の同じ失敗であり、分けるには `close` を `]` の前の検査と段落の終わりの検査の二つのラベルに分ける必要がある。
どちらのラベルも安全性の確認（[ADR 0007](0007-grammar-label-safety.md)）をやり直すことになる。
メッセージを「ここに閉じ括弧 ] が必要です」にすれば、位置と合わせて両方の場合を説明できるので、コードは一つのままにする。

**golem-eval の G0120 を残すこと**：golem-eval が `EError` を黙って失敗させる道を作れば、G0120 を golem-parser だけのコードにできる。
そのためには `Eval` の型（`Either Diagnostic`）に、診断のない失敗を足す必要がある。
構文エラーのあるファイルの評価の診断を表示しないと決めれば、golem-eval の G0120 は表示されないので、型を変える利点は小さい。

**LSP のバッファで読み込みを止めないこと**：ディスクのファイルでは BOM や CR で読み込みが止まるのに、LSP のバッファでは止まらない。
二つの振る舞いは違うが、エディタの上で読み込みを止めると、BOM の一文字のためにすべての機能が使えなくなる。
コードと位置は同じにして、止めるかどうかだけを変える。

**必ず失敗する規則の位置を変えること**：回復の読み飛ばしが 1 文字前に広がる。
CST の誤りのノードの範囲も変わるので、golem-fmt と golem-lsp が誤りのノードの範囲に頼っていれば影響を受ける。
golem-fmt は構文エラーのあるファイルを書き換えないので影響しない。
golem-lsp の golden（`protocol.txt`）は G0117 の位置だけを固定しており、この変更の対象外である。
