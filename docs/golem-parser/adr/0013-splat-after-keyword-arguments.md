# ADR 0013: `**[式]` をキーワード引数と同じ位置に書けるようにする

ステータス: 採択

## 文脈

仕様書の「既知の不具合」は、`[f k=v **[h]]` が G01019 になると書いている。
ロードマップの v0.1.0-rc3 の「既知の不具合の修正」は、文法の引数の並びを改め、`**[式]` をキーワード引数と同じ位置に書けるようにし、同じキーが二度出たときは後に書いたほうを採る、という直し方を案として挙げている。
この ADR は前半を採り、同じキーについてはメンテナーの決定（下の「メンテナーが決めたこと」）に従って誤りとする。

### 再現

main（0231d98）と golem-parser、golem-cli が同じ `golem` で、次の原稿を `golem inspect --as ast` にかけた。

| 原稿 | 診断 | AST の引数 |
| --- | --- | --- |
| `[f k=v **[h]]` | G01019（バイト 8 から 14） | `k=v` だけ |
| `[f **[h] k=v]` | なし | `**[h]`、`k=v` |
| `[f x **[h] *[g]]` | なし | `x`、`**[h]`、`*[g]` |
| `[f k=v *[g]]` | G01019（バイト 8 から 13） | `k=v` だけ |

`**[式]` は、キーワード引数の前にしか書けない。
キーワード引数の後に書くと、位置引数の誤りとして G01019 になり、回復が `**[h]` を読み飛ばすので、AST から消える。
逆に、`**[h]` の後に位置引数 `*[g]` を書いても誤りにならない。

### 原因

`modules/golem-parser/grammar/Golem.hpeg` の引数の規則は次のとおりである。

```
Arguments <- (Sp PosArg)* (Sp KeywordArgument)* (!(Sp PosArg))^arg_order
PosArg <- !(Word Eq) SplatArgument
        / !(Word Eq) !Splat Argument
Splat <- '**[' / '*['
```

`SplatArgument` は `*[` と `**[` の両方を読み、`PosArg` の選択肢に入っている。
文法の上では、`**[式]` も位置引数の一つとして扱われる。
このため、位置引数の並びの中ならどこにでも書け、キーワード引数の後には書けない。
AST に下ろす段階（`Golem.Parser.Lower` の `arguments`）は `**[` を見て `SplatKeyword` にするので、AST の型は二つを区別している。
区別していないのは文法だけである。

docs/markup.md は、「位置引数をすべて書いてから、キーワード引数を書く」と、「`*[式]` は配列を位置引数に、`**[式]` は連想配列をキーワード引数に展開する」を並べて書いている。
`**[式]` がどちらの並びに属するかは書いていない。
[golem-parser ADR 0004](0004-inline-grammar.md) も、引数の種類に「展開：`*[式]` と `**[式]`」を挙げ、順序を文法で強制するとだけ定めている。

### 評価の側

評価は、今のところ `*[式]` も `**[式]` も展開しない。
組み込みのコマンドの引数を読む golem-eval の `keywords` は `Keyword` だけを拾い、展開の引数を黙って捨てる。
プラグインのコマンドには、展開の引数を `nil` として渡す。
展開そのものは、ロードマップの v0.1.0-rc4 の「`*[式]` の展開とプラグインへの引数」で扱う。

同じキーの扱いも揃っていない。

- 組み込みのコマンドは、`keywords` が返した一覧を `lookup` で引くので、`[f k=1 k=2]` では先に書いた `k=1` が効く。
- `@manifest` と `@style-def` は、同じキーを二度書くと G02052 にする（golem-eval の `Golem.Eval.Settings` の `keywordArgs`）。この二つは展開の引数も G02052 にする。

### メンテナーが決めたこと

起草の後、メンテナーが次のように決めた。

- **`[f **[h] x]` は誤りとする**：両方の並びに `**[式]` を書けるようにすると、利用者は必ず書き誤る。`**[式]` はキーワード引数の並びにだけ書ける。
- **G01019 のメッセージ**：新しい、分かりやすいメッセージにする。`**[h] x` で「キーワード引数の後に位置引数があります」と出ても、`**[h]` がキーワード引数の側だとは読み取れないからである。
- **同じキーを二度書いたら誤りとする**：字面で二度書いても、`**[式]` の展開で重なっても、エラーとする。後に書いたほうを採る規則より、厳しく検査するほうが長い目で見てよい。

## 実装すること

### 規則

- 位置引数と `*[式]` を、位置引数の並びとする。
- キーワード引数と `**[式]` を、キーワード引数の並びとする。
- 位置引数の並びをすべて書いてから、キーワード引数の並びを書く。二つの並びの中では、どの順に書いてもよい。
- キーワード引数の並びの後に、位置引数の並びの要素が来たら G01019 とする。
- キーワード引数の並びの中で、同じキーが二度以上出たら、二度めから後のそれぞれを G02077 とする（「同じキー」の節）。

| 原稿 | この ADR の後 |
| --- | --- |
| `[f k=v **[h]]` | 通る |
| `[f **[h] k=v]` | 通る（今と同じ） |
| `[f k=1 **[h] j=2 **[i]]` | 通る |
| `[f k=1 k=2]` | G02077（今は通り、`k=1` が効く） |
| `[f x *[g] **[h] k=v]` | 通る（今と同じ） |
| `[f **[h] x]` | G01019（今は通る） |
| `[f **[h] *[g]]` | G01019（今は通る） |
| `[f k=v *[g]]` | G01019（今と同じ） |

規則は `Arguments` を使うところすべてに及ぶ。
インラインのコマンド、ブロックコマンドの行（`@name ...`）、コードブロックの開始の行（```` ``` 言語 ... ````）である。

### 文法（golem-parser）

```
Arguments <- (Sp PosArg)* (Sp KwArg)* (!(Sp PosArg))^arg_order
PosArg <- !(Word Eq) !'**[' SplatArgument
        / !(Word Eq) !Splat Argument
KwArg <- KeywordArgument
       / &'**[' SplatArgument
```

`KwArg` は `PosArg` と同じく `%inline` にする。
CST の節の種類（`NArgument`、`NKeywordArgument`、`NSplatArgument`）は変わらないので、`Golem.Parser.Lower` と AST の型は変えない。
回復の `SkippedArgs <- (Sp PosArg)+` も変えない。
`**[h]` の後の `x` は、今の `k=v` の後の `x` と同じく読み飛ばされ、G01019 の範囲になる。

### G01019 のメッセージ

G01019 のメッセージを次のように改める。

| | メッセージ |
| --- | --- |
| 今 | `キーワード引数の後に位置引数があります` |
| この ADR の後 | `位置引数と *[...] は、key=value と **[...] より前に書きます` |

新しいメッセージは、誤りの箇所を述べる代わりに、守るべき並びを述べる。
`**[h] x` と `k=v x` のどちらで出ても、利用者は `**[...]` がどちらの並びに属するかを、メッセージだけから読み取れる。
コードは G01019 のまま変えない。
条件は「引数の並びの順序の誤り」で同じであり、`*[式]` と `**[式]` を並びに数える分だけ広がるが、利用者の直し方（並べ替える）は変わらないからである。
重大度と位置の決め方（読み飛ばした引数の範囲）も変えない。
メッセージの文言は、golem-parser の `Golem.Parser` の `arg_order` の枝に書く。

`scripts/gen-parser.sh` で `Generated.hs` と `test/StrippedGrammar.hs` を生成し直し、生成物をコミットする。

### ラベルの安全性

[golem-parser ADR 0007](0007-grammar-label-safety.md) の検査は、上の文法で警告を出さない。
起草のときに、手元で文法を上の形に変え、`CABAL=cabal-3.16.1.0 sh scripts/gen-parser.sh`（`--Werror`）が通ること、golem-parser のテスト（`LabelSafetySpec` を含む 136 件）がすべて通ることを確かめた。
`%safe` を新たに足す必要はない。

`arg_order` が安全である理由は、[golem-parser ADR 0007](0007-grammar-label-safety.md) の表のとおり変わらない。
`Arguments` が失敗すると、命令文脈、ブロックコマンドの行、コードブロックの開始の行が失敗し、`[`、`@`、```` ``` ```` で始まる入力はほかの規則が読めない。
`close` の `%safe` の注釈は「`(Sp KeywordArgument)*`」を挙げているので、「`(Sp KwArg)*`」に書き換える。
注釈はコメントであり、受理する言語は変わらない。

### 同じキー（golem-eval）

キーワード引数の並びの中で同じキーが二度以上出たら、エラーとする。
キーワード引数の並びは、字面のキーワード引数と、`**[式]` を展開したキーワード引数を、原稿に書いた順に並べたものである。

診断は次のとおりとする。

| コード | 条件 | メッセージ | 位置 |
| --- | --- | --- | --- |
| G02077 | 字面のキーワード引数のキーが、それより前のキーワード引数のキーと同じ | `同じキーを二度書いています: <キー>` | 二度めのキーワード引数の全体（`k=2`） |
| G02077 | `**[式]` を展開したキーが、ほかのキーワード引数のキーと同じ（v0.1.0-rc4 から） | `**[...] を展開したキーが、ほかのキーワード引数と重なります: <キー>` | 重なりの後のほうの引数の全体（`**[h]` か `k=2`） |

- 重大度はエラーとする。段階は評価（golem-eval）である。
- 二度めから後の引数は、どれも捨てる。最初に書いたものだけを使い、評価を続ける。誤りの後の診断を、なるべく原稿に近い形で出すためである。
- 検査は、golem-eval がコマンドの引数を読むところすべてに当てる。インラインのコマンド（組み込みとプラグイン）、ブロックコマンド（`@toc` など）、コードブロックの開始の行と `@listing` である。一つの関数 `duplicateKeys :: [Located Argument] -> [Diagnostic]` にまとめ、引数を読む前に呼ぶ。
- `@manifest` と `@style-def` は、今と同じく同じキーを G02052 にする。この二つはコマンドではなく設定であり、引数の読み方を別に持つ（golem-eval の `Golem.Eval.Settings`）。G02077 を重ねて出さない。
- `**[式]` の展開は、v0.1.0-rc4 の「`*[式]` の展開とプラグインへの引数」で実装する。展開の実装は、展開した組を `**[式]` の位置に差し込んでから `duplicateKeys` と同じ規則で検査する。この ADR の時点では、`**[式]` は展開されないので、表の二行めの診断は出ない。

G02077 は、草稿の ADR が使う 02 の区分の番号（G02070 から G02076）の次である。
並行する草稿が同じ番号を取っていれば、実装の順にずらす。

## 実装しないこと

- `*[式]` と `**[式]` の評価での展開と、プラグインに渡すキーワード引数の形。v0.1.0-rc4 の「`*[式]` の展開とプラグインへの引数」で扱う。この ADR の後も、組み込みのコマンドは `**[式]` を黙って捨てる。
- 同じキーで後に書いたほうを採ること。ロードマップの案だったが、誤りとする（「メンテナーが決めたこと」）。
- `@manifest` と `@style-def` の同じキーの扱いの変更。今と同じく G02052 とする。
- G01019 のコード、重大度、位置の決め方の変更。メッセージだけを改める。
- 同じキーの検査を構文の段階（`Golem.Parser.Lower`）で行うこと。展開の重なりは評価でしか分からないので、検査を一か所にまとめる。
- golem-fmt、golem-lint、golem-lsp の変更。どれも CST か AST を読むだけで、引数の並びの規則を持たない。`[f k=v **[h]]` を `golem fmt` が整形するようになるのは、G01019 がなくなった結果である。

## テスト設計

次のテストを先に書き、今の文法と `keywords` で失敗することを確かめてから実装する。

`modules/golem-parser/test/ParserSpec.hs`（診断の位置は原稿のバイトの位置）：

| 原稿 | 期待 |
| --- | --- |
| `"[f k=v **[h]]\n"` | 診断なし |
| `"[f k=1 **[h] j=2 **[i]]\n"` | 診断なし |
| `"[f k=1 k=2]\n"` | 診断なし（同じキーは評価の段階で検査する） |
| `"[f **[h] x]\n"` | G01019 がちょうど一つで、位置が 8 から 10、メッセージが `位置引数と *[...] は、key=value と **[...] より前に書きます` |
| `"[f **[h] *[g]]\n"` | G01019 がちょうど一つで、位置が 8 から 13 |
| `"@b k=v **[h]\n"` | 診断なし |
| `"``` text k=v **[h]\ncode\n```\n"` | 診断なし |

今ある `"[f k=v *[g]]"` 相当の G01019 のテストは、新しいメッセージに書き直して通ること。
`"[number-text 10 style=tcy] [f *[xs] **[kw]: 本文 | 二つ目]\n"` の受理のテストは、そのまま通ること。

`modules/golem-parser/test/SplatEscapeSpec.hs`：

- `[f k=v **[h]]` の引数の種類が `keyword`、`keyword splat` の順であること。
- `[f k=1 **[h] j=2 **[i]]` の引数の種類が `keyword`、`keyword splat`、`keyword`、`keyword splat` の順であること。
- 今ある「splats keep their places among the other arguments」（`[f a *[xs] **[h] k=v]`）がそのまま通ること。

`modules/golem-parser/test/LabelSafetySpec.hs`：

- 断片の一覧（`pieces`）に `"k=v"`、`"**[h]"`、`"*[g]"` を加え、二つの文法が三つまでの断片の連結で一致することを確かめる。

golem-eval のテスト：

- `[number-text 10 style=kanji style=tcy]` が、二つめの `style=tcy` の位置に G02077（`同じキーを二度書いています: style`）を一つ出し、`style=kanji` の `Number` を作ること。今は診断が出ない。
- `@toc depth=1 depth=3` が G02077 を一つ出し、目次の深さが 1 であること。
- ```` ``` text numbers=true numbers=false ```` が G02077 を一つ出すこと。
- プラグインのコマンド `[broken k=1 k=2]` が G02077 を一つ出すこと。
- `[f k=1 k=2 k=3]` が G02077 を二つ（`k=2` と `k=3`）出すこと。
- `[f k=1 j=1]` と `[f k=1 **[h]]` が G02077 を出さないこと（`**[h]` はこの ADR では展開しない）。
- `@style-def character x weight=bold weight=normal` が今と同じく G02052 だけを出し、G02077 を出さないこと。

`modules/golem-fmt/test`：

- `"[f k=v **[h]]\n"` が整形できる（`Formatted`）こと。今は G01019 で `Unformattable` になる。

## トレードオフ

`**[式]` を両方の並びに書けるようにする案もある。
`PosArg` の `**[` を残したまま `KwArg` にも加えれば、今通る原稿はすべて通り続ける。
採らなかったのは、`**[式]` が展開されるとキーワード引数になるからである。
`[f **[h] x]` を許すと、展開した後の引数の並びは `k=v x` の形になり、字面で書けば G01019 になる並びを、展開を通せば書けることになる。
規則を「`*[式]` は位置引数、`**[式]` はキーワード引数と同じ位置に書く」の一文で言えるほうを選んだ。
両方の並びに書けると、利用者は `**[式]` がどちらの並びに属するかを覚えずに済む代わりに、`**[h] x` が通り `k=v x` が通らない理由を説明できなくなり、書き誤りを生む。
Python の関数の呼び出しも、`f(**kw, x)` を構文の誤りにする（記憶による）。

同じキーを誤りにしたので、既定の値をまとめた連想配列を `**[式]` で渡し、その後に一部を字面で上書きする書き方はできない。
上書きしたいときは、`**[式]` に渡す連想配列の側を式で作り直す。
後に書いたほうを採る規則なら、この書き方ができ、ロードマップの案もそれだった。
採らなかったのは、同じキーの重なりが書き誤りであるときに、黙って片方を捨てることになるからである。
厳しく検査しておけば、後から規則を緩めても今の原稿は通り続ける。
逆に、緩い規則を後から厳しくすると、通っていた原稿が誤りになる。

同じキーの検査を評価の段階に置いたので、字面の重なりも構文の誤りではなく評価の誤りになる。
構文の段階で字面の重なりを、評価の段階で展開の重なりを検査すると、同じ規則が二か所に分かれる。
コマンドの引数を読むところは golem-eval に集まっているので、一つの関数で両方を扱う。

組み込みのコマンドの `[f k=1 k=2]` は、今は `k=1` で通るが、この ADR の後は G02077 になる。
リポジトリの原稿、fixture、マニュアルに同じキーを二度書いた箇所はないことを、実装のときに `git grep` で確かめる。

## データ構造

AST と CST の型は変えない。
golem-eval に `duplicateKeys :: [Located Argument] -> [Diagnostic]` を加える。
`Golem.Parser.AST` の `Argument` は、すでに `SplatPositional` と `SplatKeyword` を区別している。
