# ADR 0008: G0904 を、文字の大きさを決めた定義と色の組ごとに、原稿の文字の位置で報告する

ステータス: 採択

## 文脈

[ADR 0006](0006-preflight.md) は、golem preflight の G0904（小さすぎる文字、`type-size`）を次のように定めた。

> - **位置**：その文字を含む原稿の `Text` の位置。
> - **まとめ**：段落スタイルか文字スタイルと色の組ごとに一つ。

実装と docs/diagnostics.md は、どちらとも違う。

- `Golem.Driver.Pdf` は、プリフライトのビューの字（`GlyphView`）の `gvStyle` に、和文のフォントの役割（`lkFace`）と文字の大きさをつないだ文字列を入れる（3457 行）。`gvSpan` には、その字を描いた行の記録（`LineRec`）の `lrSpan`、つまり行を含むブロックの位置を入れる。
- `Golem.Preflight` の `typeSize`（168 行）は、`gvStyle` とスウォッチの名前の組でまとめ、組ごとに、ビューの字の並び（ページの順）で最初の字の位置に G0904 を一つ出す。
- docs/diagnostics.md は、この実装を写して「文字の役割と大きさと色の組ごとに一つにまとめる」「位置は、その文字を含む原稿のブロックの位置である」と書く。

レビュー（`.claude/reviews/2026-10-20-adr-spec-review.md` の A-12）が、この食い違いを挙げた。

### diagnostic の原則

メンテナーは、この食い違いを、今の実装を追認して片づけるのではなく、diagnostic の原則に照らして直すと決めた。
原則は次の二つである。

- 違う原因に、一つの diagnostic のコードを使わない。一つの diagnostic が、別々に直す必要のある二つ以上の原因を代表してもいけない。
- diagnostic は安定していて、予測できる。同じ原因は、原稿のほかの箇所を直しても、同じ形（同じまとまり、同じ位置）で報告される。

### 今の G0904 が原則に反する点

#### 役割と大きさでまとめると、別々の原因が一つにまとまる
段落スタイル `a` と `b` がどちらも同じ役割で 4pt を指定すると、二つの段落スタイルの `size` は別々に直す必要があるのに、G0904 は一つしか出ない。
一つめを直して検査し直すと、同じコードの G0904 がもう一つの箇所に移って現れる。
逆に、一つの原因（たとえばルビの大きさ）が、親文字の役割の違いで二つ以上に分かれることもある。
役割と大きさの組は、書き手が直す単位（`style.toml` のどの `size` を変えるか）と対応しない。

#### 報告する位置が、ページの並びで変わる
組の代表は、ビューの字の並びで最初の字であり、その並びはページの順である。
ページの順は原稿の順と一致しない。
脚注、傍注、回した図版、送った図版はページの上で原稿と違う位置に置かれ、柱とノンブルはどのページにも描かれる。
そのため、組の中のどの字が代表になるかは、改ページの位置で決まる。
離れた箇所の段落を一行増やしただけで脚注が隣のページに移り、G0904 の位置が別のブロックに移ることがある。
これは「予測できる」に反する。

#### 位置がブロックであり、原因の文字を指さない
行の記録はブロックの位置しか持たないので、長い段落や表では、どの文字が小さいかを位置から決められない。
[ADR 0006](0006-preflight.md) が `Text` の位置としたのは、エディターと LSP で原因の文字へ移れるようにするためである。

### 書き手が直す単位と、字を描く段階に残っている情報

[ADR 0006](0006-preflight.md) の「段落スタイルか文字スタイルと色の組」は、書き手が直す単位でまとめるという意図である。
G0904 を直す手段は、文字を大きくするか、色を一つの版にするかであり（docs/diagnostics.md の「直し方」）、大きさを直す場所は、その文字の大きさを決めた `style.toml` の `size` の定義である。

字を描く段階には、この情報が残っていない。

- 見た目（`Golem.Layout.Look` の `Look`）は、解決した役割、大きさ、色などを持つが、どの定義から来たかを持たない。
- 段落スタイルは `paraStyle` が `based-on` をたどって一つに平らにし、文字スタイルは `restyle`（`Golem.Driver.Pdf` 463 行）が外側の見た目に重ねる。どちらも、`size` を書いた定義の名前を捨てる。
- 行分割の箱（`Golem.Layout.KnuthPlass` の `BoxContent`）は `bcLook` を持つが、原稿の位置を持たない。

したがって、[ADR 0006](0006-preflight.md) の意図どおりにまとめるには、大きさを決めた定義と原稿の位置を、見た目を解決する段階から字を描く段階まで運ぶ必要がある。

## 実装すること

### まとめの単位

G0904 は、次の三つの組ごとに一つ出す。

1. **大きさの出どころ**：その字の大きさを決めた定義。次のどれかである。
   - `[paragraph-styles.<名前>]` の `size`（組み込みの `body`、`caption`、`sidenote`、`code` を含む）
   - `[character-styles.<名前>]` の `size`（正規表現で当てた文字スタイルを含む）
   - `[headings.<階層>]` の `size`
   - `[notes]` の `mark-size`
   - `[page.grid]` の `font-size`（どの定義も `size` を書かず、版面の文字の大きさで組んだ字。柱とノンブルを含む）
   - `[hidden-folio]` の `size`
   ここでの「定義」は、`size` のキーを書いた定義である。段落スタイル `b` が `based-on = "a"` で `a` の `size` を引き継ぐなら、出どころは `a` とする。`a` の `size` を変えれば、`b` の文字も直るからである。
2. **字の種類**：親文字（本文の字）、ルビ、圏点のどれか。ルビと圏点は親文字の大きさから決まる大きさで組むので、同じ出どころでも親文字とは別に小さくなる。直し方（ルビだけが小さいのか、親文字も小さいのか）が違うので、別の組とする。
3. **色**：スウォッチの名前。スウォッチを持たない字（既定の黒）は一つの組とする。

違う出どころは、大きさと役割が同じでも、別の G0904 になる。
コードは G0904 の一つのままとする。
検査の条件（`min-size` 未満の文字）は一つであり、出どころと字の種類は、その条件に当たった原因を一つずつに分ける単位だからである。

### 位置と順

- 位置は、組の中で原稿の順に最初の字を含む、原稿の `Text` の位置とする。ページの順ではなく、原稿の `Text` の位置の順で比べる。
- 原稿の `Text` を持たない字（見出しの番号、図番号、目次の項目、リーダー、柱、ノンブル、隠しノンブル）は、その字を生んだ要素の位置とする。見出しの番号は見出しのブロック、目次の項目はその見出し、柱とノンブルと隠しノンブルは `style.toml` の先頭である。
- G0904 の並びは、各組の位置の原稿の順とする。
- メッセージの `<ページ>` には、その組の字が出たすべてのページを挙げる（[ADR 0006](0006-preflight.md) の `pagesPhrase` のとおり）。

こうすると、まとまりと位置は原稿と `style.toml` だけで決まり、改ページの位置に依らない。
改ページで変わるのは、メッセージのページの列だけである。

### メッセージと事実

メッセージに大きさの出どころと字の種類を加える。

`文字が小さすぎます: <大きさ>（<min-size> 未満、<出どころ>、色 <スウォッチの名前>、<ページ>）`

`<出どころ>` は、`段落スタイル a の size`、`文字スタイル b の size のルビ`、`[notes] の mark-size`、`[page.grid] の font-size` のように書く。
diagnostic の事実（`diagFacts`）に、出どころ（`source`）と字の種類（`part`）を加える。

### データ構造の変更

- golem-layout の `Golem.Layout.Look` に、大きさの出どころを表す和の型 `SizeSource` を加える。構成子は上の六つの出どころに一つずつ対応させ、出どころの名前（段落スタイル、文字スタイルの名前、見出しの階層）を持たせる。新しい出どころが増えたときに、網羅の検査で取り残しに気づけるよう、文字列ではなく和の型とする。
- `SizeSource` と原稿の位置は、`Look` には入れない。`Look` は字形の選択、行分割、箱の比較に使われており、見た目が同じで出どころだけが違う字が別の見た目になると、出力の PDF が変わりうるからである。代わりに、行分割の箱 `BoxContent` に、アルゴリズムが読まない欄 `bcSource :: !(SizeSource, SrcSpan)` を加える。`bcLook` と同じく、行分割は読まない。ルビの箱では、読みの字の出どころを親文字の出どころとし、字の種類で区別する。
- `Golem.Driver.Pdf`：段落スタイルの大きさを決める `paraFace` と、文字スタイルを重ねる `restyle` が、大きさと一緒に出どころを返すようにする。`based-on` をたどって `size` を書いた定義を返す関数を golem-project の `Golem.Project.Style` に加える（`paraStyle` と同じたどり方で、平らにする前の定義の名前を返す）。
- `GlyphUse` に出どころ、字の種類、原稿の位置を加え、プリフライトのビューの `GlyphView` の `gvStyle` を、出どころと字の種類の二つの欄（`gvSizeSource`、`gvPart`）に置き換える。`gvSpan` は行の記録のブロックの位置ではなく、字の原稿の位置とする。
- `Golem.Preflight` の `typeSize` は、`(gvSizeSource, gvPart, 色)` でまとめ、組の代表を `gvSpan` の最小の字とする。

### 守ること

- PDF のバイト列を変えない。出どころと位置は、行分割、字形の選択、描画に使わない。
- 同じ入力から同じ G0904 の列を出す（決定性は diagnostic にも及ぶ）。

### 文書

- docs/diagnostics.md の G0904 の「意味」を、この ADR のまとめの単位、位置、並びに改め、メッセージの形を新しいものにし、ADR の行にこの ADR を加える。
- 仕様書の golem preflight の節の、プリフライトのビューを説明する箇所に、字が大きさの出どころと原稿の位置を持つことを書く。検査の表（2787 行）は、どの検査のまとめの単位も書いていないので変えない。
- 使い手のマニュアル（`manual/appendices/e-errors.gm` の G0904 の項）に、メッセージがどの `size` の定義から来た文字かを示すことと、示された定義の `size` を大きくするか色を変えれば直ることを書く。
- `GlyphView` の欄の変更は、仕様書のプリフライトのビューの説明に書く（golem-preflight のモジュールの仕様書はない）。

### ステータスの行

- [ADR 0006](0006-preflight.md)：「採択→G0905 の廃止と、図版の検査の PDF の図版への拡張は [golem-pdf ADR 0008](../../golem-pdf/adr/0008-pdf-figures.md)、（G0904 のまとめの単位と位置）は ADR 0008」とする。

## 実装しないこと

- 色の出どころ（どのスタイルがスウォッチを決めたか）でまとめること。色は、スウォッチの名前が同じなら直し方も同じ（そのスウォッチを一つの版にするか、使う箇所で別のスウォッチに替える）なので、名前でまとめる。
- ほかのプリフライトの検査（G0912 など）の位置を、同じ仕組みで字の原稿の位置に改めること。この ADR が加える `bcSource` を使えば後で改められるが、それぞれの検査のまとめの単位を決める ADR で扱う。
- 字の原稿の位置を、LSP の範囲の表示などほかの用途に使うこと。
- G0904 の条件（`min-size`、`multi-ink-only`）と重大度。

## テスト設計

### 先に書いて失敗させるテスト

golem-preflight の `test/Main.hs` に次を加える。
テストは `GlyphView` の新しい欄で書く。

- 出どころが違い（段落スタイル `a` と `b`）、大きさ、役割、色が同じ二つの字は、二つの G0904 になる。今の実装は一つにまとめるので失敗する。
- 同じ出どころで、親文字とルビの二つの字は、二つの G0904 になる。
- 同じ出どころ、字の種類、色の字が、1 ページ目（原稿の位置が後）と 2 ページ目（原稿の位置が先）にあると、G0904 は一つで、位置は 2 ページ目の字の位置、ページの列は 1 と 2 である。今の実装はページの順の最初の字を位置にするので失敗する。
- 二つの組の G0904 の並びが、ページの順ではなく位置の原稿の順である。

golem-driver のテストに次を加える。

- 段落スタイル `a` と `b` を同じフォントの役割、4pt、二版以上のスウォッチで定義し、それぞれの段落を組んで golem preflight を走らせると、G0904 が二つ出る。それぞれの位置は各段落の `Text` の位置で、メッセージに `段落スタイル a の size` と `段落スタイル b の size` が入る。
- 段落スタイル `c` が `based-on = "a"` で `size` を書かないとき、`c` の段落の小さな文字は `段落スタイル a の size` の組に入る。
- 段落スタイルは大きく、文字スタイル `s` が 4pt を指定した文字は、`文字スタイル s の size` の組に入り、位置はその文字スタイルの中の `Text` である。
- 長い段落の途中の一語だけが小さいとき、G0904 の位置がその語の `Text` の位置であり、段落のブロックの位置ではない。
- 本文の前のほうの段落に付けた脚注が後のページに送られる原稿で、脚注の前に一行足しても、G0904 の位置と並びが変わらない。

### 出力を変えないことの確かめ

- golem-driver の PDF の golden のテストと、CI の `determinism` ジョブが、変更の前後で同じバイト列を出す。新しい欄を描画に使っていないことを、この二つで確かめる。

## トレードオフ

- 出どころと原稿の位置を字まで運ぶので、`BoxContent`、`GlyphUse`、`GlyphView` の三つの型が太り、組版の途中のすべての箱に欄が一つ増える。代わりに、描いた後の字から出どころを推す方法（大きさの値から逆にたどる）は、同じ大きさを書いた定義が二つあると決められず、原則を満たせない。
- `size` を書いた定義を出どころとするので、`based-on` で引き継ぐ段落スタイルが多い本では、一つの G0904 が多くのスタイルの文字を代表する。どれも同じ一箇所（引き継ぎ元の `size`）を直せば直るので、原因は一つである。引き継ぐ側で `size` を書き足して直したい書き手は、メッセージのページの列から箇所を探すことになる。
- 位置を原稿の順で最初の字とするので、ページの上で最初に目に付く箇所と、報告の位置が違うことがある。改ページで位置が動かないことを優先した。

## 検討の記録

- **大きさの出どころの粒度**：「その字に当てた段落スタイルか文字スタイル（当てた名前）」を出どころにする案もあった。[ADR 0006](0006-preflight.md) の字面に近く、書き手が原稿で見ている名前で報告できるが、引き継ぎ元の一つの `size` が原因でも、当てたスタイルの数だけ G0904 が出て、一つの原因が複数の diagnostic に分かれる。メンテナーは、この ADR の案（`size` を書いた定義）を採った。
- **位置を `style.toml` に置く案**：直す場所は `style.toml` の `size` の定義なので、G0904 の位置を `style.toml` の定義の位置にする案もあった。原稿の位置は「どの文字か」を、`style.toml` の位置は「どこを直すか」を指す。メンテナーは、[ADR 0006](0006-preflight.md) のとおり原稿の位置を採り、直す場所はメッセージの出どころで示すこの ADR の案を採った。`style.toml` の定義の位置を diagnostic の関連する位置として足すかは、diagnostic が二つめの位置を持てるようになったときに決める。
