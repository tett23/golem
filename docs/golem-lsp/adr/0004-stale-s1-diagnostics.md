# ADR 0004: 編集のたびに S1 を組み直し、古い S1 の診断を残さない

ステータス: 採択

## 文脈

仕様書の「既知の不具合」は、LSP で、見出しやラベルを変えずに存在しないラベルへの参照を足しても G04003 が出ず、前の S1 の診断が残る、と書いている。
[golem-lsp ADR 0001](0001-language-server.md) の再評価の規則どおりの振る舞いだが、利用者には誤りが見えない。
ロードマップの v0.1.0-rc3 の「既知の不具合の修正」は、ラベルを参照する箇所の集合が変わったときにも S1 を評価し直すという案を挙げ、[golem-lsp ADR 0001](0001-language-server.md) の再評価の規則を改める ADR が要るとしている。

### 再現

main（0231d98）の golem-lsp を `cabal repl` で読み、`modules/golem-lsp/test/fixtures/proj` を `openWorkspace` で開いて、`b.gm` を `updateFile` で書き換えた。
`b.gm` の元の中身は、`@label second`、`# 次の章`、`[ref-title intro]と[ref-page intro]を見る。` の三つのブロックである。
表の「全体の評価」は `wsFullEvaluations`（プロジェクトの全体を評価した回数）、「診断」は `diagnosticsFor` の G03023 以外のコードとバイトの位置である。

| `b.gm` の中身 | 全体の評価 | 診断 |
| --- | --- | --- |
| 開いたとき | 1 | なし |
| `[ref-page intro]` を `[ref-page nolabel]` にする | 1 | なし（G04003 が出るべき） |
| さらに `@toc` を二つ足す | 1 | なし（G04002 も出るべき） |
| `nolabel` と `@toc` を消す | 1 | なし |

続けて、`nolabel` への参照と二つの `@toc` を含む `b.gm` をディスクに置き、開いてから書き換えた。

| `b.gm` の中身 | 全体の評価 | 診断 |
| --- | --- | --- |
| 開いたとき | 1 | G04003（47）、G04002（85） |
| 参照の前に段落を一つ足す | 1 | G04003（47）、G04002（85）。位置が動かない |
| 参照と `@toc` をすべて消す | 1 | G04003（47）、G04002（85）。消えない |

S1 の診断は、出るべきときに出ず、消えるべきときに消えない。
残った診断は、編集の前の位置を指したままになる。

### 原因

golem-lsp の `Golem.Lsp.Workspace` の `updateFile` は、編集されたファイルを構文解析し、そのファイルだけを S0 で評価し直す（`evReevaluate`）。
その後、`summaryOf` で編集の前と後の要約を比べ、同じなら `replaceFile` で結果を差し替え、違えば `fullEvaluate` でプロジェクトの全体を評価し直す。

要約は、`@import` のパス、エクスポートする変数、見出しと属性（`@label`、`@number` など）の三つである。
ラベルへの参照（`[ref-number]`、`[ref-title]`、`[ref-page]`）は段落の中にあるので、要約に入らない。
本体のないブロックコマンド（`@toc`、`@page-break`）も、`summaryOf` の `BlockCommand` の枝が本体だけをたどるので、要約に入らない。

`replaceFile` は、そのファイルの古い S0 と構文の診断を除いて新しいものに替えるが、S1 の診断（`evDiagnostics` のうち `assemble` が出したもの）と、S1 の結果（`evBook`）はそのまま残す。
S1 の診断は文書の全体から決まるので、どのファイルの S0 の結果が変わっても、変わりうる。
今の規則は、S1 が要約の三つにだけ依存するとみなしている。

### S1 が見るもの

S1（golem-doc の `assemble`）が出す診断は次のとおりである。

| コード | 内容 | 決める入力 | 今の要約 |
| --- | --- | --- | --- |
| G04001 | ラベルの重複 | ラベル | 入る |
| G04002 | `@toc` が二つ以上 | `@toc` | 入らない |
| G04003 | 存在しないラベルへの参照 | ラベルと参照 | 参照が入らない |
| G04004 | 章の外の図版とコードの章番号 | 見出しと図版の位置 | 図版が入らない |
| G04005、G04006 | 番号や題を持たない要素への参照 | 参照と参照先 | 参照が入らない |
| G04007 | `@number` が自動の番号と同じ | 見出しと `@number` | 入る |
| G04008 | 本の最後の改ページ | `@page-break` の位置 | 入らない |

ロードマップの案のとおり参照の集合を要約に足しても、G04002、G04004、G04008 は直らない。
それに、要約が変わらない編集でも、編集したファイルの S1 の診断の位置はずれる（上の「参照の前に段落を一つ足す」）。
S1 の診断の位置を正しく保つには、要約の比較によらず、編集のたびに S1 を組み直す必要がある。

### 費用

S1 の `assemble` は、各ファイルの S0 の結果（`erDocument`）を受け取る純粋な関数である。
ほかのファイルの構文解析と S0 の評価をやり直さなくても、手元の結果から組み直せる。

起草のときに、main（0231d98）の golem-driver を `cabal repl` で読み（golem-driver は解釈実行、依存するモジュールはコンパイル済み）、二冊のマニュアルで時間を測った。
`assemble` の欄は、組み直した `Book` の文書、目次、索引、見出しと診断をすべて `show` で文字列にするまでの時間で、`show` の分を含む上限である。

| プロジェクト | ファイル | 全体の評価 | `assemble` 一回 | 全ファイルの S0 |
| --- | --- | --- | --- | --- |
| manual | 24 | 0.22 秒 | 21 ミリ秒以下 | 20 ミリ秒 |
| manual-dev | 22 | 0.11 秒 | 13 ミリ秒以下 | 12 ミリ秒 |

全体の評価の時間の大半は、ファイルの読み込み、構文解析、体裁、プラグイン、図版と参考文献の読み込みである。
編集のたびに S1 を組み直すと、一回の編集の費用に数十ミリ秒以下が加わる。
LSP は最後の変更から一定の時間を待ってから評価する（[golem-lsp ADR 0001](0001-language-server.md)）ので、打鍵のたびに走ることはない。

### メンテナーが決めたこと

起草の後、メンテナーが次のように決めた。

- 編集のたびに S1 を組み直す、というこの ADR の直し方を採る。
- 組み直しの費用が問題になったら、そのときに最適化をまとめて扱う。見出しとラベルの変更でプロジェクトの全体を評価し直す条件（要約）を `@import` とエクスポートだけに縮めることも、その最適化に含めて考える。

S1 を毎回組み直せば、見出しとラベルの変更で全体を評価し直す必要は、おそらくない。
見出しとラベルは S1 にだけ効き、ほかのファイルの S0 には効かないはずだからである。
それでもこの ADR では、安全のため、要約と全体の評価の条件を変えずに残す。

## 実装すること

### 再評価の規則

[golem-lsp ADR 0001](0001-language-server.md) の「再評価」の二つめの規則を、次の二つで置き換える。

- S0 の結果のうち、見出し、ラベル、import される変数が変わった場合は、今と同じく、S1 と影響を受けるほかのファイルを評価し直す。
- それ以外の編集では、編集したファイルの S0 の結果を差し替えた後、すべてのファイルの S0 の結果から S1 を組み直す。古い S1 の診断はすべて捨て、組み直した S1 の診断に替える。S1 の結果（ホバーが使う章の番号など）も替える。

全体を評価し直す条件のうち、構文の誤りに関わるもの（編集の前か後のファイルに構文の誤りがある）は、今と同じとする。
`golem build` と同じく、プロジェクトの段階の診断（G03007、プラグイン、参考文献の誤り）と、すべてのファイルの S0 の診断のどれかにエラーがあれば、S1 を行わず、S1 の診断を空にし、S1 の結果をなしとする。
今は S1 の結果がないとき（`evBook` が `Nothing`）に全体を評価し直しているが、この条件はやめ、S1 を組み直す側で扱う。
S0 のエラーを直す編集で、全体を評価し直さずに S1 の診断が出るようになる。

マニフェストから到達しないファイル（`wsLoose`）の扱いは変えない。

### golem-driver

`Evaluated` に、S1 を組み直す関数と、診断の内訳を持たせる。
`evReevaluate` と同じく、前回の評価の文脈（体裁、章の並び、マニフェスト）を閉じ込めた純粋な関数とする。

```haskell
data Evaluated = Evaluated
  { ...
    -- | プロジェクトの段階の診断（G03007、G03023、プラグイン、参考文献）
    evProjectDiagnostics :: ![Diagnostic],
    -- | S1 の診断
    evS1Diagnostics :: ![Diagnostic],
    -- | 各ファイルの S0 の結果から S1 を組み直す。
    -- エラーの診断があれば S1 を行わず、(Nothing, []) を返す
    evReassemble :: Map FileId EvalResult -> (Maybe Book, [Diagnostic])
  }
```

`evaluateProjectWith` は、今 `pre` と `s1Diags` として作っているものを、それぞれ `evProjectDiagnostics` と S0 の診断、`evS1Diagnostics` に分けて入れる。
`evDiagnostics` は、今と同じく全体を並べたものとして残す。
`evReassemble` は、`evaluateProjectWith` が `AssembleConfig` を作る式（`erNumberSites` を結果から集める部分を含む）と `assemble` を、結果の表を引数にした関数にくくり出したものである。
全体の評価も、この関数を通して S1 を行う。
同じ結果の表を渡せば、全体の評価と同じ `Book` と診断になる。

### golem-lsp

`replaceFile` を次のようにする。

1. 編集したファイルの S0 の結果を、結果の表に差し替える。
2. `evReassemble` に結果の表を渡し、新しい `Book` と S1 の診断を得る。
3. `evDiagnostics` から、そのファイルの古い S0 と構文の診断と、古い S1 の診断（`evS1Diagnostics`）をすべて除き、新しい S0、構文、S1 の診断を加える。
4. `evBook` と `evS1Diagnostics` を替える。

## 実装しないこと

- 要約を `@import` とエクスポートだけに縮めること。組み直しの費用が問題になったときの最適化とまとめて扱う（「メンテナーが決めたこと」）。
- S1 の差分の計算（変わった部分だけを組み直すこと）。測った費用では要らない。
- レイアウト（S2）の再実行。[golem-lsp ADR 0001](0001-language-server.md) のとおり、LSP は S2 を行わない。
- 待つ時間（デバウンス）の長さの変更。
- `golem build` と `golem check` の変更。全体の評価が通る経路は `evReassemble` にくくり出すだけで、結果は変わらない。

## テスト設計

`modules/golem-lsp/test/Main.hs` に次のテストを加え、今の golem-lsp で失敗することを確かめてから実装する。
どれも、表の操作の後で `wsFullEvaluations` が開いたときと同じであることも確かめる。

| 始めの `b.gm` | 書き換えた `b.gm` | 期待 |
| --- | --- | --- |
| fixture のまま | `[ref-page intro]` を `[ref-page nolabel]` に | `b.gm` に G04003 が一つ、位置は `nolabel` の参照 |
| fixture のまま | `@toc` を二つ足す | G04002 |
| `nolabel` への参照を含む（ディスク） | 参照を消す | G04003 がない |
| `nolabel` への参照を含む（ディスク） | 参照の前に段落を足す | G04003 の位置が、足した段落のバイト数だけ後ろに動く |
| fixture のまま | 未知のコマンド（G02022）と `nolabel` への参照を足す | G02022 があり、G04003 がない（S0 のエラーで S1 を行わない） |
| 前の行の書き換えの後 | 未知のコマンドだけを消す | G04003 が出る |

さらに、次の性質を確かめる。

- 上の各行で、書き換えた後の `diagnosticsFor` が、同じ中身をディスクに置いた一時ディレクトリを `openWorkspace` で開いたときの `diagnosticsFor` と一致すること。編集の経路と全体の評価の経路が、同じ診断を出すことの検査である。
- 今ある「only changes to headings, labels or exports re-evaluate the project」と「editing the file settings evaluates that file alone」が、そのまま通ること。

golem-driver のテスト：

- fixture のプロジェクトで、`evReassemble (evResults e)` の診断が `evS1Diagnostics e` と一致し、`Book` の文書が `evBook e` の文書と一致すること。

## トレードオフ

ロードマップの案（参照の集合が変わったときに S1 を評価し直す）は、参照を足す編集と消す編集を直すが、上の表の G04002、G04004、G04008 と、位置のずれを直さない。
直すには、S1 の入力をすべて要約に写すことになり、要約が S1 の実装の写しになる。
S1 を毎回組み直すほうが、規則が一つで済み、S1 に診断を足しても LSP の側に手を入れずに済む。

代わりに、一回の編集の費用が、編集したファイルの S0 だけから、S0 と S1 の組み直しに増える。
測った値では二冊のマニュアルで数十ミリ秒以下であり、全体の評価の数分の一である。
章が数百あるような大きな本では組み直しの時間が目に見えて伸びるかもしれない。
そのときは、S1 の差分の計算と要約の縮小を、測った値を添えて別の ADR でまとめて扱う。

`Evaluated` に関数を持たせるのは `evReevaluate` と同じ形であり、前回の評価の文脈を LSP の側に漏らさずに済む。

## データ構造

golem-driver の `Evaluated` に `evProjectDiagnostics`、`evS1Diagnostics`、`evReassemble` を加える（「golem-driver」の節）。
golem-lsp の `Workspace` は変えない。
