# 互換性

この文書は、Golem が 1.0.0 から互換を守る範囲と、互換を壊してよい条件、バージョンの付け方、廃止の手順を書く（[ADR 0174](adr/0174-compatibility-promises-for-1-0.md)）。
1.0.0 より前は、互換を壊してよい。
1.0.0 より前のバージョンの付け方は、仕様書の [「バージョン」の節](specifications.md#バージョン) にある。

## 1.x で守ること

1.0.0 から 1.x の最後までのあいだ、次の表のものを守る。
「守る」とは、1.a で使えたものが、b が a より大きい 1.b でも、同じ意味で使えることをいう。
古いバージョンで新しいバージョンの書き方を読めること（前方の互換）は約束しない。

| 対象 | 守ること | 守らないこと |
| --- | --- | --- |
| 原稿の記法（`.gm`） | 1.a でエラーなく組めた原稿は、1.b でもエラーなく組め、同じ意味になる。記法を足すときは、それまでエラーだった形にだけ足す | 警告、notice、info を足すこと。Emet を使う書き方（下の Emet の行） |
| `manifest.toml`、`style.toml`、`preflight.toml`、`plugins.lock` | 受け付けたキーと値は、同じ意味で受け付ける。組み込みのプリフライトの設定 `print` の値を、検査が厳しくなる向きに変えない | キーを足すこと。値の既定を変えること（出力を変えるので、出力の規則に従う）。Emet を指すキー（下の Emet の行） |
| CLI | コマンド、オプション、オプションの値、終了コード（0、1、2）の意味、`golem --version` の一行の形 | コマンドとオプションを足すこと。人が読む形の diagnostics、ヘルプ、使い方の表示の文言。`golem inspect` の `--as cst`、`--as ast`、`--as ir` の表示。`golem new` の雛形の中身。`golem lsp` |
| 出力（PDF、HTML、EPUB、プレーンテキスト） | 同じバージョンと同じ入力からは、同じバイト列を得る。patch のバージョンは、Golem のバージョンから作る値（PDF の Producer とインスタンス ID）のほかに、出力を変えない | minor のバージョンで、組版の結果を変えること |
| 意味論 IR | なし | minor のバージョンで変えること。IR はプラグインの ABI なので、変えるときは ABI の手順に従う |
| プラグインの ABI と CBOR | ABI を変えるのは、予告した後の minor のバージョンに限る。予告では、どこがどう変わるかを開発者に示す。patch のバージョンは ABI を変えない。`golem inspect --as cbor` のバイト列も ABI の CBOR である | 予告した後の minor のバージョンで、ABI のバージョンを上げること。そのとき、古い ABI のプラグインは読み込めなくなる |
| JSON の diagnostics（`--format json`） | キーと値の型。重大度の値は `error`、`warning`、`notice`、`info` の四つに限る | キーを足すこと（読む側は知らないキーを読み飛ばす）。`message` の文言 |
| diagnostic のコード（`G` で始まるもの） | 使用中のコードの意味。1.x のあいだ、コードを廃止せず、分けず、重大度をエラーの側へ上げない | コードを足すこと。重大度を下げること。[docs/diagnostics.md](diagnostics.md) と `golem explain` の文言 |
| 関数の言語 Emet | なし。1.x のあいだ、実験的な機能とする | すべて（範囲は「約束しないもの」の節） |
| LSP | なし | すべて |
| エディタ向けの構文の定義 | なし | すべて |
| Haskell のパッケージの API | なし | すべて。golem のパッケージは Hackage に出さず、`golem` の実行ファイルだけを配る |

JSON の diagnostics の `message` の文言は、誤字を直したり、原因を詳しく書く補足を足したりするために変えることがある。
`message` を文字列で照合する CI は、minor のバージョンで落ちることがある。
原因はコードと位置で引く。

## 互換を壊してよい条件

1.0.0 の後に互換を壊してよいのは、次の三つの場合に限る。
上の表の「守らないこと」と、予告した ABI の変更は、互換を壊すことに当たらない。

- **major のバージョン**：`X` を上げるリリースでは、上の表のどれを変えてもよい。変えたものは、ADR とリリースノートの「互換を壊す変更」の項に書く。
- **セキュリティの修正**：どのバージョンでもよい。互換を壊した理由を ADR に書き、リリースノートの「互換を壊す修正」の項に挙げる。
- **仕様に反する振る舞いの修正**：仕様書か ADR がエラーとする入力を受け付けていた、仕様と違う出力を作っていた、という不具合は、minor のバージョンで直す。出力を変える修正は patch では行わない。リリースノートの「互換を壊す修正」の項に挙げる。仕様が振る舞いを定めていなかった箇所は、この条件に当たらない。

仕様に反する振る舞いを minor で直すと、それまで組めていた原稿が、エラーで組めなくなることがある。
Golem は、壊れた出力を黙って作るより止めるほうを選ぶ（仕様書の [「設計原則」](specifications.md#設計原則)）。

## バージョンの付け方

1.0.0 の後は、バージョン `X.Y.Z` を次のように上げる。

- 互換を壊す変更（セキュリティの修正を除く）で `X` を上げる。
- 足すだけの変更、出力を変える変更（仕様に反する振る舞いの修正を含む）、意味論 IR と ABI の変更、廃止の予告で `Y` を上げる。
- 出力を変えない修正で `Z` を上げる。

この文書で、`X` を上げるリリースを major のバージョン、`Y` を上げるリリースを minor のバージョン、`Z` を上げるリリースを patch のバージョンと呼ぶ。

## 廃止の手順

記法と設定のキーを廃止するときは、次の順に進める。

1. 廃止を決める ADR で、廃止予定の notice のコードを決める。メッセージと [docs/diagnostics.md](diagnostics.md) の書き方は、docs/diagnostics.md の「廃止予定の手順」のとおりとする。
2. 1.0.0 の後は、その notice を minor のバージョンで出し始めることで、廃止を予告する。予告した書き方は、1.x のあいだ受け付け続け、出力も変えない。リリースノートの「変更」の項と、この文書の「廃止予定の書き方」の一覧に挙げる。
3. 次の major のバージョンで、ADR を作ってその書き方をエラーにする。エラーには新しいコードを割り当て、notice のコードは状態を「廃止」にする。`silence-notices` にそのコードを書いたプロジェクトは G03024 になるので、リリースノートに、その行を消すよう書く。
4. 1.0.0 より前は、手順の 2 の「minor のバージョン」を「プレリリースを含むリリース」と読み替える。notice を少なくとも一つのリリースで出した後なら、次のリリースでエラーにしてよい。

1.0.0 より前に minor のリリースはない（v0.1.0-rc4 の次が 1.0.0 である）ので、手順の 4 がなければ、1.0.0 より前に廃止を予告できない。
1.0.0 より前は互換を壊してよいので、予告を minor に限る決まりは 1.0.0 の後にだけ当てる。

### 廃止予定の書き方

番号と柱の旧書式、注の `mark-size` は [ADR 0344](adr/0344-revise-retire-legacy-style-formats.md) により G03250〜G03253 のエラーになった。
旧 notice の G03114〜G03117 を `silence-notices` に書いていた場合は、その指定を消す。
残すと G03024 になる。

今、廃止を予告している書き方は次の三つである。
1.0.0 には廃止予定の書き方を残さないので、どれも 1.0.0 の前か 1.0.0 でエラーにする。
エラーにするのは、それぞれの ADR で行う。

| コード | 書き方 | 代わりの書き方 | エラーにする時期 |
| --- | --- | --- | --- |
| [G02065](diagnostics.md#g02065) | `@listing` の `src=` | パスを最初の引数に書く（`@listing src/Main.hs`） | v0.1.0-rc2 と v0.1.0-rc3 で notice を出したので、v0.1.0-rc4 からエラーにしてよい |
| [G02108](diagnostics.md#g02108) | `@listing` の `lines` とコードブロックの `highlight` の、`10-20` のような `-` で区切った範囲（[ADR 0113](adr/0113-closed-range-literal.md)） | `...` で区切った範囲（`10...20`） | v0.1.0-rc4 で初めて notice を出すので、v0.1.0-rc4 の後、1.0.0 までにエラーにする。1.0.0 でエラーにしてもよい |
| [G02129](diagnostics.md#g02129) | `@table` の `src=`（[ADR 0184](adr/0184-table-positional-path.md)） | パスを最初の引数に書く（`@table data/sizes.csv`） | v0.1.0-rc4 で初めて notice を出すので、v0.1.0-rc4 の後、1.0.0 までにエラーにする。1.0.0 でエラーにしてもよい |

## 予告している ABI の変更

プラグインの ABI は、予告した後でだけ変える。

1. ABI を変える ADR で、変更の中身を決める。
2. その ADR の後の最初の minor のリリースで、変更を予告する。予告は、この節と、リリースノートの「予告」の項に書く。このリリースでは ABI をまだ変えない。
3. 予告を載せたリリースより後の minor のリリースで、ABI を変え、ABI のバージョンを一つ上げる。

予告は、新しい ABI のバージョンの番号を見出しにし（`### ABI のバージョン 9` の形）、次のことを書く。

- 変わる CDDL の規則と、変更の前と後の CDDL の差分。
- 変わる要求と応答（コマンド、フィルタ、チャネル、データのどれか）と、プラグインの側で直すこと。
- 予告の元になった ADR へのリンク。

ABI を変えたリリースの後、その予告はこの節から消し、リリースノートに残す。
1.0.0 より前の ABI のバージョンの規則は、仕様書の [「プラグイン」の節](specifications.md#プラグイン) にある。

今、予告している ABI の変更はない。

## 約束しないもの

次のものは、1.x の約束に含めない。

- **関数の言語 Emet**：1.x のあいだ、実験的な機能とする。Emet のためだけにあるものすべてを約束の外とする。`.emet` の言語、マニフェストの `[functions.requires]` と `[[filters]]` の `function`、`.gm` の `.emet` を取り込む `@import` とその名前空間を通した呼び出し、`E` で始まるコード、`golem fmt` と `golem lint` の `.emet` への振る舞いを含む。`.gm` のほかの書き方と、プラグインの `[[filters]]` は約束に含める。Emet を約束に含めるのは、早くても次の major のバージョンとする。
- **LSP**：`golem lsp` の機能と振る舞い。LSP のクライアントは、初期化のときにサーバーが知らせた機能だけを使う。
- **エディタ向けの構文の定義**：`tools/editors/` の TextMate と tree-sitter の文法（配布物の `share/golem/editors/`）。エディタの色の割り当てが minor で変わることがある。
- **Haskell のパッケージの API**：golem のパッケージは Hackage に出さない。

LSP とエディタ向けの構文の定義は、エディタで書く人にとって重要な機能である。
ただし、同じ入力から同じ出力を得るという決定性には関わらないので、約束の対象にしない。

次のことも約束しない。

- 長く保守するバージョン（LTS）を設けることと、古い minor のバージョンにセキュリティの修正を戻すこと。
- ホストが二つ以上の ABI のバージョンのプラグインを読み込むこと。
- minor のバージョンで組版の結果を変えないこと。

## 約束を検査する仕組み

約束のうち、スクリプトで確かめられるものを CI で確かめる。
どれも、`v1.0.0` 以降のタグがないあいだは、何も確かめずに成功するか、1.0.0 より前の規則だけを確かめる。
直前のリリースは、HEAD から辿れる最も新しい `v` で始まるタグである。
1.0.0 のプレリリース（`v1.0.0-rc1` など）は `v1.0.0` より前に数える。

- **ABI のバージョン**：CI の `changes` ジョブの `scripts/ci/abi-version.sh` は、直前のリリースが `v1.0.0` 以降のとき、次のことを確かめる。HEAD の `VERSION` が patch（下の「patch の判定」）なら、ABI のバージョンが直前のリリースと同じであり、HEAD から辿れる patch の基準のリリースがあること。patch でなく、`VERSION` の `X` が直前のリリースと同じなら、ABI のバージョンが直前のリリースと違うとき、直前のリリースのこの文書に、HEAD の ABI のバージョンの見出し（`### ABI のバージョン 9` の形）があること。どの場合も、1.0.0 より前の規則（ABI を変えたら一つ上げる）も確かめる（[ADR 0212](adr/0212-patch-release-check-on-the-inputs-of-the-previous-release.md)）。
- **diagnostic のコード**：CI の `changes` ジョブの `scripts/ci/diagnostic-codes.sh` は、直前のリリースが `v1.0.0` 以降で、HEAD の `VERSION` の `X` が同じとき、直前のリリースの [docs/diagnostics.md](diagnostics.md) と今のものを比べる。直前のリリースで使用中の `G` のコードが、今も使用中であり、重大度がエラーの側へ上がっていないことを確かめる。`E` のコード（Emet）は比べない。重大度は docs/diagnostics.md の重大度の欄の値で比べ、上がる向きは「情報」（info）、「お知らせ」（notice）、「警告」、「dev では警告、prod ではエラー」、「エラー」の順とする。プリフライトの設定によるコードは、組み込みの `print` の既定の値で比べ、off を info より下に置く。
- **patch の判定**：バージョン `X.Y.Z` は、`X` が 1 以上で `Z` が 1 以上のとき、そのときに限り patch である。プレリリースの部分は見ないので、`v1.0.1-rc1` も patch である。patch の基準のリリースは、作るタグ（`abi-version.sh` では HEAD）から辿れる `v` で始まるタグのうち、プレリリースでなく、`X.Y` が同じで、作るタグとは別のものの最も新しいものである。patch なのに基準のリリースがない（`v1.0.1` の前に `v1.0.0` のタグがない）ときは、タグの誤りとして検査は失敗する。`scripts/release/check-patch.sh` と `scripts/ci/abi-version.sh` は、この同じ規則を書く（[ADR 0212](adr/0212-patch-release-check-on-the-inputs-of-the-previous-release.md)）。
- **patch のリリース**：リリースのワークフローの `version` ジョブの `scripts/release/check-patch.sh` は、作るタグが patch かを決め、patch なら基準のリリースのタグを `patch` ジョブに渡す。`patch` ジョブの `scripts/release/check-patch-output.sh` は、基準のリリースの木を取り出し、その木の `scripts/visual/build.sh` と `scripts/visual/check.sh` を作るタグの `golem` で走らせて、基準のリリースの見た目の回帰テストの参照 `scripts/visual/pages/` と比べる。基準のリリースに決定性の検査の出力のハッシュの一覧 `scripts/determinism/hashes.txt`（[ADR 0173](adr/0173-rc4-refactoring.md)）があれば、その木の `scripts/determinism.sh` も作るタグの `golem` で走らせ、PDF のファイルの行を除いて一覧と同じであることを確かめる。入力は基準のリリースのものなので、patch の前にマニュアルや fixture の原稿を直しても、検査の結果は変わらない。patch でなければ、何も比べない（[ADR 0212](adr/0212-patch-release-check-on-the-inputs-of-the-previous-release.md)）。

廃止の手順は、廃止予定の書き方をエラーにする ADR のレビューで確かめる。
