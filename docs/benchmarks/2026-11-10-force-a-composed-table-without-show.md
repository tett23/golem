# 組んだ表を文字列にせずに評価した前と後（2026-11-10）

[ADR 0299](../adr/0299-force-a-composed-table-without-turning-it-into-a-string.md) の実装のプルリクエストで、組んだ表を `show` で文字列にして評価する前と、`forceTable` で行まで評価する後とを、同じ入力で測った記録である。
コミットした後は変更しない。

## 結論

- 表の割り当ては、どの大きさでも 52.3% から 53.2% 減った（表 1）。ADR の条件の 40% 以上を満たす。
- CPU 時間の比の中央値は 0.79 から 0.90、壁時計の比の中央値は 0.72 から 0.84 で、どちらも減った。
- 出力は変わらない。どの入力でも、前と後のすべての回のハッシュは一つだった。
- 最大常駐は、10,000 セルと 100,000 セルで減り、20,000 から 80,000 セルで増えた（37.0 MB から 80.6 MB など）。ADR のテスト設計の「最大常駐が増えないこと」は、この三つの入力で満たさない。下の「最大常駐について」に、標本の取り方による見かけの増えである見込みと、確かめきれていないことを書いた。
- 利用者向けマニュアルと十冊の割り当てと壁時計は悪くならなかった（表 2）。マニュアルは割り当てが 5.9% 減った。

## 環境

- 計算機：[2026-11-10 の表の費用の記録](2026-11-10-cost-of-tables-within-the-cell-limit.md) と同じ計算機（Apple M1 Max、メモリ 64GB）、macOS 27.0。
- 前：`main` の `2ca838ce` に [ADR 0299](../adr/0299-force-a-composed-table-without-turning-it-into-a-string.md) から 0301 の採択を足したコミット（`66ac244b`）。
- 後：それに [ADR 0299](../adr/0299-force-a-composed-table-without-turning-it-into-a-string.md) の実装を足した作業ツリー。
- どちらも GHC 9.10.3、cabal の既定の最適化（`-O1`）で、作業ツリーの `cabal.project.local` に `package golem-cli` の `ghc-options: -rtsopts` を足してリンクした（以下 `golem-before` と `golem-after`）。`-with-rtsopts` は製品と同じ `-N -A64m` である。
- 負荷：同じ計算機でほかのエージェントの作業が動いていた。表の 120 回の load average（1 分）は 10.7 から 29.8、中央値は 17.2 である。マニュアルと十冊の 110 回は 23.8 から 39.4、中央値は 27.7 である。

## 方法

表の入力は、記録の [`make-tables.sh`](2026-11-10-cost-of-tables-within-the-cell-limit/make-tables.sh) で作った六つ（c10-r1000 から c10-r10000 と c8-r10000）である。

一回ごとに `build/` を消し、`golem-before` か `golem-after` で `build --target pdf +RTS -s<ファイル> -RTS` を実行した（[`measure.sh`](2026-11-10-force-a-composed-table-without-show/measure.sh)）。
記録の `measure.sh` と同じ値を一行に書く。
記録の「監査の設定」（`-A4m`）は測っていない。
一周で六つの入力を順に、それぞれ前と後を一回ずつ走らせ、前と後の順は周ごとに入れ替えた。
これを 10 周した。
時間は、同じ周の後と前の比を取り、その中央値で読む（[docs/benchmarks/2026-11-09-link-golem-with-a-64-mb-allocation-area.md](2026-11-09-link-golem-with-a-64-mb-allocation-area.md) と同じ方法）。

利用者向けマニュアルと十冊は、[速さの調査](2026-11-09-typesetting-speed-survey.md) と同じ入力で、同じ方法を 5 周走らせた（[`measure-books.sh`](2026-11-10-force-a-composed-table-without-show/measure-books.sh)）。
マニュアルは `manual/` を写して `scripts/manual/fetch-fonts.sh` のフォントを置き、`common/build-info.gm` を `scripts/manual/build-info.sh` で作った。
十冊には `scripts/fixtures/copy-fonts.sh` と同じフォントを置いた。

値は [`summary.sh`](2026-11-10-force-a-composed-table-without-show/summary.sh) でまとめた。
各回の値は [`results-tables.txt`](2026-11-10-force-a-composed-table-without-show/results-tables.txt) と [`results-books.txt`](2026-11-10-force-a-composed-table-without-show/results-books.txt) に、まとめは [`summary-tables.txt`](2026-11-10-force-a-composed-table-without-show/summary-tables.txt) と [`summary-books.txt`](2026-11-10-force-a-composed-table-without-show/summary-books.txt) にある。
すべての回が終了コード 0 で終わった。

## 最大常駐について

表の 20,000 から 80,000 セルの最大常駐の増えは、10 回とも同じ向きで、揺れではない。
ただし `+RTS -s` の最大常駐は、主の GC（世代 1）のときにだけ測られる。
割り当てが半分になると主の GC の起きる時点が変わり、生きているデータの多い時点に当たれば値は大きくなる。
同じ二つの実行ファイルを `+RTS -A4m` で走らせると、GC が多く起き、値は次のようになった（1 回ずつ）。

| 入力 | 前 | 後 |
| --- | --- | --- |
| c10-r2000 | 83.8 | 94.2 |
| c10-r4000 | 169.5 | 160.2 |
| c10-r8000 | 292.6 | 319.5 |

`-A64m` で 37.0 MB だった c10-r2000 の前の値は、`-A4m` では 83.8 MB になる。
`-A64m` の値は、生きているデータの山を測りそこねている。
細かく測ると、前と後の差は -5% から +12% で、向きも入力によって違う。

行の項目のリスト（`lineItems`）まで評価する版も作って測ったが、`-A64m` の最大常駐は後とほとんど同じだった（c10-r4000 で 185.2 MB と 188.2 MB）。
評価の浅さが常駐を増やしているのではないと見る。
生きているデータの山を正しく比べるには、ヒープのプロファイルが要る。
この記録では取っていない。
