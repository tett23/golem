# root [ADR 0479](../adr/0479-treat-tate-chu-yoko-as-a-japanese-character.md) の受けいれ条件の検証

2026-11-27 に、[root ADR 0479](../adr/0479-treat-tate-chu-yoko-as-a-japanese-character.md) A1 から A3 を検証した。
実装のコードは `d07f335a3247d07f90349e2eb5d68eead7c821e0`、組版と各出力に使った通常 CLI の SHA256 は `6bb2e6907331619947900ba3dd7554e180dffacab2972d632b1c82c12c7b4781` である。
後続の PDF の期待値と文書の更新は、CLI の実装を変えていない。
環境は macOS 27.0（26A428）、GHC 9.10.3 である。

## 通常の CLI と IR（A1）

縦組みと横組みの二つのプロジェクトで、通常の `golem check` と `golem build` を実行した。
PDF、HTML、EPUB、テキストのすべてを生成し、両プロジェクトの両コマンドが終了コード 0 になった。
原稿には、次の対照と三つの記法を含めた。

```golem
あ漢い
あ[tcy: 1]い
あ[number-text 1 style=tcy]い
あ##1:tcy##い
```

さらに、`ab`、`!?`、`001`、三つ連続した縦中横、外側の欧文と括弧、小数 `0.10` と `0.1`、正負のトラッキング、明示した四分アキ、文字サイズ、リンク、ルビ、注の本文、三桁の文字列と数値を含めた。
`golem inspect a.gm --as ir` でも、文字列が `TcyLiteral`、明示した数値と糖衣構文が `TcyNumber` になったことを確認した。
横組みで文字列の縦中横と数値の表示が異なる既存の規則は、回帰テストでも比較した。

## PDF の表示と座標（A2）

両プロジェクトの PDF の先頭ページを `pdftoppm -r 150` で画像にし、実際に表示して比較した。
縦組みの最初の三つの縦中横では、前後の和文との余分な空きが消えた。
`pdftotext -bbox` で得た座標も、root [ADR 0478](../adr/0478-accept-rational-values-in-number-text.md) の CLI による同じ原稿の結果と比較した。
文字の大きさは 10 pt である。

| 記法 | 修正前の「い」の上端 | 修正後の「い」の上端 |
| --- | --- | --- |
| `[tcy: 1]` | 66.0236 pt | 61.0236 pt |
| `[number-text 1 style=tcy]` | 66.0236 pt | 61.0236 pt |
| `##1:tcy##` | 66.0236 pt | 61.0236 pt |

いずれも「あ」の上端は 41.0236 pt、下端は 51.0236 pt のままである。
縦中横の箱は一字分を保ち、前後の四分アキが合計 5 pt 消えた。
三つの記法の全体の長さは、対照の「あ漢い」と同じ 30 pt になった。
単体の組版テストでは、sp 単位の箱、禁則、明示したアキ、トラッキングの行末での除去も比較している。

既存の 24 件の PDF も、`scripts/visual/build.sh` と `scripts/visual/check.sh` で生成して比較した。
変化した 8 冊の 83 ページすべてを、修正前後の画像の組で確認した。
新しい重なり、文字の欠け、図や罫線との衝突は見つからなかった。
縦中横の空きによる改行の変化と、両マニュアルの説明追加による再配置を確認して、該当する 8 ファイルの参照ハッシュを更新した。
ページ数は、利用者マニュアル 488、開発者マニュアル 239 のままである。
開発者マニュアルの物理ページ 88 から 89 では、図 6-4 が次ページへ移り、その説明文が図より前に来る。

## HTML と EPUB の表示（A3）

生成した HTML を、macOS の Quick Look の `qlmanage -t -s 1600` で描画して、実画像を確認した。
和文の対照と三つの記法、文字列の縦中横が表示され、前後の和文に対照より余分な空きは見えなかった。
生成した CSS は、既存の `text-combine-upright: all` と `-epub-text-combine: horizontal` を保つ。
明示した正負の字間も、既存の `letter-spacing` のままである。

EPUB は Kindle Previewer 4.0.3 の CLI で KPF へ変換した。
変換ログは Success、Enhanced Typesetting は Supported、Error Count と Quality Issue Count はともに 0 だった。
その KPF を Kindle Previewer のネイティブアプリで開き、検証本のウィンドウだけを `screencapture -x -l` で撮影して実画像を確認した。
設定は Tablet、縦向き、Mincho、Size 4 である。
右の閲覧画面で、和文の対照、文字列、数値、糖衣構文の三つの記法、および `ab`、`!?`、`001` の縦中横を確認した。
和文の対照に比べた余分な外側の空きは見えなかった。

EPUB に入った XHTML と CSS も展開し、Quick Look で描画して確認した。
Kindle Previewer の次ページの注などは、サムネイルでの確認にとどまり、拡大表示の確認はしていない。
この結果は、ここに記した閲覧環境での確認であり、ほかの閲覧ソフトで同じ字間になることまでは保証しない。

## 自動テスト

共通 IR、CBOR、SDK の旧形式拒否と往復、および外側の空きについて、実装前に回帰テストが失敗することを確認した。
実装後は、組版の 1799 件、文書の 144 件、評価の 1098 件、Emet の 236 件、プラグインの 161 件、Rust ワークスペースの 114 件を含む関連スイートが成功した。
組版の境界の 15 件は、文字列と数値、ルビ、ページ参照、注の呼出印、正負のトラッキング、明示したアキ、横組みの幅を含む。
実際の Wasm と Emet の入出力も試験し、Wasm 8 個の再生成と一致検査を通した。
PDF の期待値の変更は、画像で確認した sample、complex-vertical と、sp 単位で比較した縦中横の配置の 3 件に限定した。
決定性の参照ハッシュは、同じ間隔修正で変わった sample の入稿用と画面用、complex-vertical の PDF の 3 行だけを更新した。
ローカルの `scripts/determinism.sh --no-manuals` の結果は、CI の x86 と ARM の両方の成果物と一致した。
sample の入稿用と画面用の全ページの描画は、視覚確認済みの sample の描画とも一致した。
