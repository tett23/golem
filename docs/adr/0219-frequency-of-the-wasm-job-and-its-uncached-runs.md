# ADR 0219: CI の wasm のジョブを走らせる頻度と、キャッシュのない実行の扱い

ステータス: 採択（未実装）

## 文脈

[ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md) の「メンテナーが決めること」の 6 は、`ci.yml` のジョブ `wasm` を、プルリクエストごとに、Haskell のソースか cabal のファイルか wasm のスクリプトが変わったときに走らせると決めた。
同じ項は、ビルドの時間が長すぎるときは頻度を新しい ADR で決め直す、とも書く。
CONTRIBUTING は、CI の実行時間を 5 分以内に保ち、プルリクエストの CI が 5 分を超えたらほかの作業を止めて CI を直すと定める（[`CONTRIBUTING.md`](https://github.com/tett23/golem/blob/4c808d072df6918bf20ab57fd97eb7e75005f38c/CONTRIBUTING.md#L372-L376)）。

### 測った時間

[docs/ci-timings/2026-11-08-wasm-job.md](../ci-timings/2026-11-08-wasm-job.md) は、キャッシュのない実行でジョブ全体が 973 秒、三つのキャッシュがすべて当たった実行で 101 秒だったと記録する。
キャッシュのない実行の 591 秒は `golem.wasm` のビルドで、そのほとんどは Hackage のパッケージである。
Fable の ADR のレビュー（2026-11-08）は、973 秒を 5 分の方針からの逸脱に挙げ、0199 が頻度を決め直すとした ADR がないことを指摘した。

その後の `ci.yml` の 20 回の実行（2026-11-07 から 2026-11-08、`gh run view --json jobs` で数えた）では、`wasm` は 107 秒から 152 秒で終わった。
同じ実行の `build (ubuntu-24.04, outputs)` は 121 秒から 210 秒で、`wasm` は `outputs` のネイティブの一覧を待つ（[`ci.yml`](https://github.com/tett23/golem/blob/4c808d072df6918bf20ab57fd97eb7e75005f38c/.github/workflows/ci.yml#L686-L691)）。
キャッシュが当たるあいだ、`wasm` はプルリクエストの CI の長さを決めるジョブではない。

### キャッシュが外れるとき

`wasm` は三つのキャッシュを持つ（[`ci.yml`](https://github.com/tett23/golem/blob/4c808d072df6918bf20ab57fd97eb7e75005f38c/.github/workflows/ci.yml#L532-L544)）。

- ネイティブの `alex` と `happy`：GHC の版とランナーのイメージで決まる。
- ツールチェーンと wasm の cabal の store（`ghc-wasm-…`）：キーは `scripts/fetch-ghc-wasm.sh` のハッシュと、`cabal.project.wasm`、`cabal.project.wasm.freeze`、`scripts/fetch-wasm-packages.sh`、`scripts/wasm/patches/*` のハッシュである。`restore-keys` は前の部分だけなので、プロジェクトかその freeze を変えても、同じツールチェーンの古い store から組み直す（[`ci.yml`](https://github.com/tett23/golem/blob/4c808d072df6918bf20ab57fd97eb7e75005f38c/.github/workflows/ci.yml#L600-L606)）。
- `dist-wasm`：キーはコミットごとで、組み直したときに保存する（[`ci.yml`](https://github.com/tett23/golem/blob/4c808d072df6918bf20ab57fd97eb7e75005f38c/.github/workflows/ci.yml#L668-L672)）。

すべてが外れるのは、ツールチェーンを替えたとき（`fetch-ghc-wasm.sh` を変えたとき）と、キャッシュが消されたときである。
`fetch-ghc-wasm.sh` も `cabal.project.wasm.freeze` も、origin/main に入ってから一度しか変わっていない（`git log` で数えた）。
ネイティブの `cabal.project.freeze` は、2026-10-12 から一度も変わっていない。

キャッシュが消される見込みは小さくない。
2026-11-08 のリポジトリのキャッシュは、34 個で 10,611,978,648 バイトあり（`gh api repos/tett23/golem/actions/cache/usage`）、GitHub の上限の 10 GB を超えている。
上限を超えると、GitHub は最も長く使われていないキャッシュから消す。
`ghc-wasm-…` は 1.1 GB で、`wasm` が走るたびに読まれるが、文書だけのプルリクエストが続くあいだは読まれない。
そのあいだにも、プルリクエストごとに `dist-…`（ARM64 で 519 MB、x86-64 で 325 MB）と `dist-wasm-…`（111 MB）が保存される。

## 実装すること

### 頻度

[ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md) の 6 の頻度（プルリクエストごとに、ビルドに関わる変更があったとき）を変えない（「メンテナーが決めること」の 1）。

### キャッシュのない実行

- `wasm` の最後の `Times` のステップで、ツールチェーンのキャッシュ（`steps.ghcwasm.outputs.cache-hit`）が外れたかどうかと、外れた理由を一行で書く。理由は、`fetch-ghc-wasm.sh` が main と違う（ツールチェーンを替えた）、プロジェクトか freeze が main と違う、どれも同じなのに外れた（キャッシュが消された）の三つである。
- 三つめのときは、`::warning::` の注釈を出す（「メンテナーが決めること」の 2）。ジョブは失敗させない。
- CONTRIBUTING の CI の時間の段落に、例外を一文足す。ツールチェーンか wasm の freeze を替えるプルリクエストでは、`wasm` の最初の実行が 5 分を超えてよい。そのプルリクエストは、キャッシュのない実行とキャッシュのある実行の時間を `docs/ci-timings/` に記録する。
- キャッシュが消されて 5 分を超えた実行は、例外に当たらない。CONTRIBUTING の方針どおり、CI を直す（キャッシュの量を減らす）作業を先にする。

### キャッシュの量

- `wasm` の `dist-wasm` の保存を、main への push のときだけにする（「メンテナーが決めること」の 3）。プルリクエストは main の `dist-wasm` を `restore-keys` で戻し、変わったパッケージだけを組み直す。今と同じく、保存しない実行も組み直したパッケージの分だけ時間がかかる。
- ツールチェーンのキャッシュの保存は、今のまま、キーが外れたときだけとする。

### 文書

- README の CI のジョブの表の `wasm` の行に、頻度と、キャッシュのない実行の扱いを書く。
- [ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md) のステータスの行に、頻度とキャッシュのない実行の扱いはこの ADR が決めたと書く。

## 実装しないこと

- **ほかのジョブのキャッシュ**：`build` の `dist-…` をプルリクエストごとに保存することが、上限を超える量のほとんどを占める。これを減らすのは `wasm` の頻度とは別の決定なので、ロードマップの「v0.1.0-rc4」に「CI のキャッシュの量を 10 GB の上限の下に保つ」の項目を足し、別の ADR で扱う。
- **wasm のビルドを速くすること**：`executable-stripping`、最適化の段階、パッケージの数を変えることは扱わない。キャッシュのない実行はまれで、キャッシュのある実行は 5 分の中にある。
- **リリースのワークフローの `wasm` ジョブ**：リリースはプルリクエストの CI ではないので、5 分の方針の外にある。

## 不変条件

この ADR は Golem の振る舞いを変えず、CI のジョブの頻度とキャッシュの扱いだけを決める。
入力と出力の関係として書ける性質がないので、不変条件は置かない。
代わりに、次の確かめ方をとる。

| 場合 | 確かめること |
| --- | --- |
| Haskell のソースを変えたプルリクエスト | `wasm` が走り、`ghc-wasm-…` が当たり、`dist-wasm` を main から戻し、`dist-wasm` を保存しない |
| 文書だけのプルリクエスト | `wasm` が走らない（今と同じ） |
| main への push | `dist-wasm` を保存する |
| `fetch-ghc-wasm.sh` を変えたプルリクエスト | `Times` に「ツールチェーンを替えた」と書き、注釈を出さない |
| キーが同じなのにツールチェーンのキャッシュがない | `Times` に「キャッシュが消された」と書き、`::warning::` の注釈を出す |

## テスト設計

ワークフローの変更なので、自動のテストは書けない。
外れた理由を決める処理は、`scripts/ci/` のシェルスクリプトに分け、`scripts/ci/test.sh` に先にテストを書いて失敗させる。
スクリプトは、キャッシュが当たったか、`fetch-ghc-wasm.sh` とプロジェクトと freeze のハッシュが main と同じかを引数で受け取り、三つの理由のどれかを一行で書く。
三つの理由と、キャッシュが当たった場合の四つの入力を調べる。

実装のプルリクエストでは、次を実際に動かして確かめ、結果をプルリクエストの説明に書く。

- 表の一行めから三行めは、実装のプルリクエストとそのマージの push で見る。
- 五行めは、`gh cache delete` でツールチェーンのキャッシュを一つ消した後のプルリクエストの実行で見る。消すとそのあとの一回が 973 秒前後かかるので、メンテナーの了承を得てから行う。

## トレードオフ

頻度を変えないので、ネイティブと wasm の出力のずれは、今のとおりマージの前に見つかる。
その代わり、ツールチェーンを替えるプルリクエストは、一度だけ 15 分前後の CI を待つ。
ツールチェーンは SHA-256 で固定していて、origin/main に入ってから一度も替えていない。

`dist-wasm` をプルリクエストで保存しないと、同じプルリクエストの二度めの push でも、main からの差分を組み直す。
Haskell のソースを変えたプルリクエストの `wasm` は少し延びるが、`outputs` のネイティブのビルドを待つ時間に収まる見込みが高い。
収まらなければ、実装のプルリクエストで測った時間をもとに、この決定を改める ADR を書く。

キャッシュが消されたときに失敗させず注釈にとどめるのは、プルリクエストの変更と関係のない原因で、マージを止めないためである。
注釈は CI の画面に残るので、黙って時間が延びることにはならない。

## メンテナーが決めること

1. **頻度**：推奨は、[ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md) の 6 のとおり、ビルドに関わる変更のあるプルリクエストごとに走らせることである。キャッシュのある実行は 107 秒から 152 秒で、プルリクエストの CI の長さを決めていない。
   - 退けた案の一つは、毎晩だけ走らせることである。ネイティブと wasm のずれが main に入ってから見つかる（0199 が退けた理由と同じ）。
   - 二つめは、main への push だけで走らせることである。ずれを見つけたときには、原因のプルリクエストがもうマージされている。
   - 三つめは、wasm のスクリプトか cabal のファイルが変わったときだけ走らせることである。ずれの原因は Haskell のソースの変更にもありうるので、それを見逃す。
2. **キャッシュのない実行**：推奨は、ツールチェーンか freeze を替えるプルリクエストに限り 5 分を超えてよいとし、キャッシュが消されたときは注釈を出してジョブは通すことである。替えるプルリクエストでは組み直しは避けられず、消されたときは CI の側の不具合である。
   - 退けた案の一つは、ツールチェーンのキャッシュが外れたら `wasm` を飛ばすことである。そのプルリクエストでは、wasm の検査が黙って行われない。
   - 二つめは、キャッシュが消されたらジョブを失敗させることである。プルリクエストの変更と関係のない原因でマージが止まり、キャッシュを作り直すには結局ビルドが要る。
   - 三つめは、ジョブの時間の上限を 5 分にすることである。ツールチェーンを替えるたびに失敗し、キャッシュを作れない。
3. **`dist-wasm` の保存**：推奨は、main への push のときだけ保存することである。プルリクエストごとの 111 MB の保存がなくなり、上限を超えたキャッシュがツールチェーンを追い出す見込みが下がる。
   - 退けた案は、今のまま、組み直したコミットごとに保存することである。プルリクエストの二度めの push は速くなるが、上限の 10 GB をすでに超えていて、消されるのは使われていない順なので、文書だけのプルリクエストが続くとツールチェーンのキャッシュが消されうる。
