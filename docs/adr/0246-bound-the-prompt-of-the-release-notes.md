# ADR 0246: リリースノートのプロンプトの大きさを抑え、状態の変わった ADR を渡す

ステータス: 採択

## 文脈

### v0.1.0-rc4 のノートを AI が書かなかった

v0.1.0-rc4 のリリースのワークフロー（[実行 42529741450](https://github.com/tett23/golem/actions/runs/42529741450)）で、ジョブ `notes` の Release notes のステップは約 3 秒で終わった。
上がった `notes.md` は 4962 バイトで、`notes.sh` の一覧のままだった。
ノートは人が手で書いた。

原因は二つあった。

一つ目は、`notes.sh` がプルリクエストを一つも拾わなかったことである。
`notes.sh` は `Merge pull request #N: 題名` の形のマージのコミットだけを拾っていた（[ADR 0004](0004-binary-distribution-and-release.md) の「リリースノート」の規則のとおり）。
GitHub がマージしたコミットの題名は `Merge pull request #N from <所有者>/<ブランチ>` で、プルリクエストの題名は本文の 1 行目にある。
v0.1.0-rc2 からは、マージのコミットがすべて GitHub の形だった（rc2 で 38、rc3 で 253、rc4 で 339）。
これは [#753](https://github.com/tett23/golem/pull/753) で、両方の形を拾うように直した。
v0.1.0-rc3 のノートは AI が書いたが、プルリクエストへのリンクがなかった。
`check-notes.sh` は `notes.sh` が挙げたプルリクエストの番号がすべて現れることを確かめるが、挙げた番号が一つもなかったので通った。

二つ目は、プロンプトの大きさである。
`write-notes.sh` は、範囲で追加された ADR の本文をすべてプロンプトに入れる（[write-notes.sh の 64 行から 70 行](https://github.com/tett23/golem/blob/e313e3b05e5c0cdb240760974a6bb6f118c72961/scripts/release/write-notes.sh#L64-L70)）。
v0.1.0-rc3 から v0.1.0-rc4 までに追加された ADR は 186 で、本文の合計は 3705302 バイトだった。
一つ目を直すと、339 のプルリクエストの題名と本文（合計 725734 バイト、最大 9042 バイト）も加わる。
v0.1.0-rc3 では、追加された ADR の本文は 1667309 バイトで、プルリクエストの本文は入らず、AI はノートを書けた。
rc4 の失敗の文言は、ジョブの要約にしか書かれず、要約は API で読めないので、確かめられていない。
3 秒で終わったことと大きさから、プロンプトがモデルのコンテキストウィンドウを超えたと推定する。
手元で確かめると、`claude -p` は API のエラーを標準エラーではなく標準出力に書いた。
`write-notes.sh` は標準エラーの先頭だけを理由にしていたので、要約にも理由が残らなかった可能性が高い。
理由をジョブのログにも書き、標準出力も含める修正も、[#753](https://github.com/tett23/golem/pull/753) で行った。

### 状態の変わった ADR が渡らない

`notes.sh` の `## ADRs` と、プロンプトの ADR は、範囲で追加された ADR（`git diff --diff-filter=A`）だけである。
rc4 の変更の多くは、rc3 までに採択された ADR の実装で、その ADR のステータスの行が `採択（未実装）` から `採択` に変わった。
ステータスの行だけが変わった ADR は追加ではなく変更なので、一覧にもプロンプトにも現れない。
v0.1.0-rc3 から v0.1.0-rc4 までに変更された ADR は 46 あった。
AI は、プルリクエストがどの ADR を実装したかを、プルリクエストの本文からしか知れない。

## 実装すること

### 1. `notes.sh` の ADR の一覧

- `## ADRs` には、今までどおり範囲で追加された ADR を並べる。
- その後に `## ADRs whose status changed` を置き、範囲で変更された ADR（`--diff-filter=M`）のうち、ステータスの行（行頭が `ステータス:` の行）が前のタグとタグで違うものを並べる。
- 各行は `- [<パス>](https://github.com/tett23/golem/blob/<タグ>/<パス>): <前のステータス> → <タグのステータス>` とする。ステータスは `ステータス:` の後の文字列で、前後の空白を除く。
- 並びは `LC_ALL=C sort` のパスの順とする。
- 前のタグがない最初のリリースでは、変更された ADR はないので、見出しだけを書く。

### 2. プロンプトの ADR は題名とステータスだけにする

- `write-notes.sh` は、ADR の本文を入れない。
- 追加された ADR と、ステータスの変わった ADR のそれぞれについて、パス、タグの版への絶対 URL、題名（最初の `# ` の行）、ステータスの行だけを入れる。
- 見出しは `# The ADRs added in this release` と `# The ADRs whose status changed in this release` とする。

### 3. プルリクエストの本文の上限

- 各プルリクエストの本文は、先頭の 4000 バイトまでを入れる。切ったときは、その後に `(cut at 4000 bytes)` の行を足す。
- バイトで切るので、UTF-8 の文字の途中で切れることがある。切った後の不完全な末尾のバイト列は、`iconv -c` で落とす（`iconv` は macOS と Ubuntu の両方にある）。

### 4. プロンプト全体の上限

- プロンプトが 1000000 バイトを超えたら、`claude -p` を動かさず、`notes.sh` の一覧をノートにする。理由は `the prompt is N bytes, over 1000000` とし、ジョブの要約とジョブのログに書く。
- 上限は `write-notes.sh` の先頭に変数として書く。環境変数では変えられない。

### 5. ドキュメント

- [仕様書](../specifications.md) の「リリースの手順」の、リリースノートの段落に、プロンプトの中身と二つの上限、`## ADRs whose status changed` を書く。
- [ADR 0004](0004-binary-distribution-and-release.md) のステータスの行に、プロンプトの ADR の中身と `## ADRs whose status changed` はこの ADR であることを書く。

## 実装しないこと

- ADR の本文の要約を AI に別に書かせること。`claude -p` の呼び出しが ADR の数だけ増え、費用と時間がかかる。
- プロンプトを分けて、何回かに分けてノートを書かせること。分類の基準が呼び出しごとにずれる。
- 上限をモデルのコンテキストウィンドウに合わせて計算すること。コンテキストウィンドウの大きさは Claude Code の版とモデルで変わり、`write-notes.sh` から確かめる手段がない。
- 改名された ADR（`--diff-filter=R`）を拾うこと。コミット済みの ADR はパスも変えない運用である。
- ステータス以外の行が変わった ADR を拾うこと。リンクの修正（`adr-guard links --fix`）だけの変更が多く、ノートの材料にならない。

## 不変条件

| 番号 | 不変条件 |
| --- | --- |
| I1 | プロンプトのバイト数は、上限（1000000）を超えない。超えるときは `claude -p` が動かず、ノートは `notes.sh` の出力とバイト単位で同じである。 |
| I2 | プロンプトに入るプルリクエストの本文は、どれも 4000 バイト以下に `(cut at 4000 bytes)` の行を足した大きさを超えない。 |
| I3 | プロンプトには、ADR の本文のうち題名の行とステータスの行のほかの行が入らない。 |
| I4 | `## ADRs whose status changed` に並ぶ ADR は、どれも範囲で変更され、前のタグとタグでステータスの行が違う。逆に、そういう ADR はすべて並ぶ。 |
| I5 | `## ADRs` と `## ADRs whose status changed` に、同じパスは現れない。 |
| I6 | `notes.sh` の出力は、同じリポジトリと同じ二つのタグに対して、何度実行しても同じである。 |
| I7 | `claude -p` を動かさなかったときと、動かして失敗したときは、ジョブのログ（標準エラー）に理由が書かれる。 |

境界の入力は次のとおりとする。

| 入力 | 期待 |
| --- | --- |
| プロンプトがちょうど 1000000 バイト | `claude -p` が動く |
| プロンプトが 1000001 バイト | `claude -p` が動かず、一覧がノートになる（I1） |
| 本文がちょうど 4000 バイト | 切らず、`(cut at …)` の行もない |
| 本文が 4001 バイト | 4000 バイトで切り、`(cut at 4000 bytes)` の行を足す（I2） |
| 本文の 4000 バイトめが多バイト文字の途中 | 不完全な文字を落とし、結果は正しい UTF-8 である |
| 本文が空 | 題名だけが入る |
| ステータスの行だけが変わった ADR | `## ADRs whose status changed` に並ぶ（I4） |
| ステータス以外の行だけが変わった ADR | どちらにも並ばない（I4） |
| 範囲で追加され、同じ範囲でステータスも変わった ADR | `## ADRs` にだけ並ぶ（I5） |
| 前のタグがない | `## ADRs whose status changed` は見出しだけ |

## テスト設計

`scripts/release/test.sh` に足す。
テストの名前に不変条件の番号を入れる。

- I1：偽の `gh` が大きな本文を返し、プロンプトが上限を 1 バイト超える入力で、偽の `claude` が呼ばれず（引数の記録がない）、ノートが `notes.sh` の出力と `cmp` で同じこと。ちょうど上限の入力で、偽の `claude` が呼ばれること。上限の境界を作るため、テストは `write-notes.sh` の上限の変数を読んで本文の大きさを決める。
- I2：4000 バイト、4001 バイト、4000 バイトめが「あ」の途中になる本文を偽の `gh` に返させ、偽の `claude` が受け取ったプロンプトの本文の大きさと `(cut at 4000 bytes)` の有無、`iconv -f UTF-8 -t UTF-8` が通ることを確かめる。
- I3：ADR の本文に目印の行を入れ、プロンプトにその行がなく、題名とステータスの行があること。
- I4、I5：ステータスの行だけを変えた ADR、ほかの行だけを変えた ADR、追加と同じ範囲でステータスを変えた ADR を作り、`notes.sh` の golden のファイルと比べる。
- I6：`notes.sh` を二度動かし、出力が同じこと。
- I7：上限を超えたとき、偽の `claude` が失敗したときに、`write-notes.sh` の標準エラーに理由があること。

自動テストにしないもの：次のリリースの `notes` ジョブのログで、プロンプトのバイト数と、AI のノートが `check-notes.sh` を通ったことを見る。
タグの前に `workflow_dispatch` で `release.yml` を動かして確かめてもよい。

## トレードオフ

- AI は ADR の本文を読めなくなる。分類はプルリクエストの題名と本文、ADR の題名とステータスに頼る。プルリクエストの本文が短いと、分類が粗くなる。
- 本文を 4000 バイトで切ると、rc4 では 40 のプルリクエストの本文の後ろが落ちる。後ろにある「実装しないこと」などが読めない。
- 上限の 1000000 バイトは、rc3 で AI が書けた大きさ（約 1.7MB）より小さく、余裕を見た値である。根拠はモデルのコンテキストウィンドウの実測ではない。超えたときは一覧に戻るので、ノートは必ず出るが、人の手間は増える。
- 339 のプルリクエストをすべてノートに載せるには、出力も長くなる。`claude -p` の出力の上限で切れると、`check-notes.sh` が番号の抜けで落とし、一覧に戻る。この ADR はそれを直さない。
- `## ADRs whose status changed` は一覧の中身を増やし、AI が失敗したときに公開する一覧も長くなる。
