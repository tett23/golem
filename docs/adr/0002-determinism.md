# ADR 0002: 決定性の規則

ステータス: 採択

## 文脈

Golem の存在理由は、同じ入力からバイト単位で同じ出力を得ることにある。
この性質があるとき、そしてそのときに限り、出力の差分は変更の影響と一致し、ビジュアルリグレッションテストが意味を持つ。
決定性は一箇所の注意では保てない。
時計、乱数、環境変数、ファイルの列挙順、ハッシュ表の走査順、並列処理の完了順、浮動小数点数、ネイティブライブラリの版のどれか一つが入力の外から入り込めば、出力は揺れる。
そこで、全モジュールが従う規則をこの ADR で定め、各モジュールの ADR はこの規則を前提にする。

## 実装すること

### 入力の定義

ビルドの入力は次のものに限る。

- `manifest.toml`、`style.toml`、`plugins.lock`
- マニフェストから到達できるソースファイル（`.gm`）、import されるファイル、図版、CSV、書誌データ、取り込むコードのファイル
- `style.toml` が指すフォントと ICC プロファイル
- プラグインの配布物（`plugins.lock` のハッシュで固定されたもの）
- Golem 自身の版と、Golem に同梱して版を固定したネイティブライブラリ

インスタンス ID の計算に使う「入力全体」は、この一覧と一致させる。

### 入力の外から値を持ち込まない

- 時計を読まない。成果物の日時はマニフェストの `metadata.date` だけから作る。`SOURCE_DATE_EPOCH` も読まない。
- 乱数を使わない。唯一の例外は `golem new` での `id` の生成である。
- 環境変数、ロケール、タイムゾーンを出力に影響させない。
- システムにインストールされたフォントを探さない。
- ビルド中にネットワークへ接続しない。プラグインはキャッシュから読み、キャッシュになければ `golem plugin fetch` を求めるエラーとする。
- ディレクトリの内容を列挙して入力を決めない。読むファイルは、マニフェストと各ファイルの記述から明示的に決まる。

### 処理の順序を固定する

- 走査の順序が出力に影響しうる集合には、順序の定まったデータ構造（`Data.Map` など）を使い、走査順が実装依存のハッシュ表は使わない。
- 並列に処理した結果は、完了の順ではなく、マニフェストの章の順と章の中の位置で並べ直してから統合する。
- 診断の出力順も、ファイルの順と位置の順に固定する。

### 数値

- レイアウトの寸法は整数の sp（1pt = 65536sp）で表し、浮動小数点数を使わない。
- 式の言語の浮動小数点数は、言語仕様の「数の規則」に従う。超越関数は v1 では持たない。
- 処理系は積和演算の融合（FMA）による最適化を使わない。

### ネイティブライブラリ

HarfBuzz と FreeType は版を固定して Golem に同梱し、版を README に記載する。
版を上げるときは ADR を作成する。

### 検査

[ADR 0001](0001-haskell-workspace-and-ci.md) の `determinism` ジョブで、二つのアーキテクチャの出力のバイト列が一致することを検査する。
加えて、同じ環境で二回ビルドした出力が一致することも検査する。

### 範囲

v1 で決定性を保証するのは PDF、HTML、プレーンテキストである。
EPUB の決定性は v2 で扱う。

## 実装しないこと

- EPUB（zip）の決定性。zip のエントリの時刻と順序の固定は v2 で扱う。
- 異なる版の Golem の間での出力の一致。Golem の版は入力の一部であり、版が変われば出力が変わってよい。
- 決定性に反する処理を静的に検出する仕組み。規則はレビューとテストで守る。

## テスト設計

- 同じ入力を二回ビルドし、出力のバイト列が一致することを検査するテストを、出力を持つ各バックエンドに置く。
- 環境変数（`TZ`、`LANG`、`SOURCE_DATE_EPOCH`）を変えてビルドしても出力が変わらないことを検査する。
- 章を並列に処理する場合と逐次に処理する場合で、出力が一致することを検査する。
- 浮動小数点数の計算の結果を、x86-64 と aarch64 で比較する。

## トレードオフ

時計を読まないので、成果物の日時は著者がマニフェストを書き換えるまで変わらない。
CI で何度ビルドしても同じ日時が書かれるが、これは決定性の帰結として受け入れる。

ネイティブライブラリを同梱して版を固定すると、利用者のシステムにある新しい版の改善（不具合の修正を含む）は自動では取り込まれない。
取り込むには ADR を書いて版を上げる必要があり、その手間を受け入れる。
