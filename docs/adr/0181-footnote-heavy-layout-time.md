# ADR 0181: 脚注の多い本の組版の時間を測り直し、項目を閉じる

ステータス: 採択

## 文脈

ロードマップの v0.1.0-rc4 の「脚注の多い本の組版の時間」は、脚注を 14 件持つ『Nightmare Abbey』の fixture だけ PDF の組版に 17 秒から 20 秒かかり、ほかの九冊は 1 秒から 6 秒だとしている。
この項目は 2026-10-16 のコミット `00132322` で書かれた。
原因が脚注にあるという見立ては、項目の名前が示すだけで、測って確かめた記録はない。

この ADR は、今の `main` で同じことが起きるかを測り、時間がどこで変わったかを調べた結果を記録する。

### 測り方

- 計算機：Apple M1 Max（10 コア）、メモリ 64GB、macOS 27.0（26A428）。
- `golem`：各コミットを `git archive` で新しい作業用のディレクトリに取り出し、`cabal build exe:golem --disable-tests` でビルドした（GHC 9.10.3、最適化は cabal の既定、ほかのフラグもリポジトリのまま）。wasmtime はリポジトリの `scripts/fetch-wasmtime.sh` が取得したもの（49.0.5）を使った。
- 入力：`modules/golem-driver/test/fixtures/pd/` の十冊を作業用のディレクトリに写し、`scripts/fixtures/copy-fonts.sh` と同じフォントを置いた。
- 一冊ごとに `build/` を消してから `golem build --target pdf +RTS -s -RTS` を 5 回実行し、`/usr/bin/time -p` の壁時計の時間の中央値を取った。割り当ての量は 5 回めの `+RTS -s` の「bytes allocated」である。
- 測るあいだ、ほかの重い処理は動かしていない（2026-11-06）。

### 結果

`458fc5a4` は項目を書いた翌日（2026-10-17）のコミット、`c505a214` はその次のコミット、`50b9fca8` は今の `main` である。

| 本 | 原稿 | `458fc5a4` | `c505a214` | `50b9fca8` | `50b9fca8` の割り当て |
| --- | --- | --- | --- | --- | --- |
| elements-of-style | 88KB | 2.69 秒 | 2.70 秒 | 1.09 秒 | 4.7GB |
| frogs | 96KB | 1.50 秒 | 1.57 秒 | 1.18 秒 | 4.4GB |
| haru-to-shura | 158KB | 1.77 秒 | 1.98 秒 | 1.54 秒 | 6.7GB |
| ichiaku-no-suna | 82KB | 0.90 秒 | 0.96 秒 | 0.77 秒 | 2.8GB |
| koya-hijiri | 163KB | 1.56 秒 | 1.59 秒 | 1.29 秒 | 5.4GB |
| merry-wives | 165KB | 6.45 秒 | 6.26 秒 | 1.97 秒 | 7.8GB |
| nightmare-abbey | 159KB | 20.15 秒 | 19.72 秒 | 2.07 秒 | 9.0GB |
| snark | 36KB | 0.51 秒 | 0.50 秒 | 0.44 秒 | 1.5GB |
| taira-no-masakado | 146KB | 2.71 秒 | 2.87 秒 | 1.57 秒 | 8.3GB |
| ushiyama-hotel | 114KB | 1.15 秒 | 1.22 秒 | 0.91 秒 | 4.4GB |

`c505a214` の『Nightmare Abbey』の割り当ては 54.3GB で、今の六倍ある。
今の `main` では、『Nightmare Abbey』は原稿の大きさが近いほかの本（`merry-wives`、`haru-to-shura`、`koya-hijiri`）と同じ程度の時間で組める。
ロードマップの項目が書いた現象は、今の `main` では起きない。

### 脚注は原因ではなかった

原稿から 14 件の `[note: ...]` を取り除いた『Nightmare Abbey』も、同じ方法で 5 回ずつ組んだ。

| コミット | 脚注あり（中央値） | 脚注なし（5 回） |
| --- | --- | --- |
| `c505a214` | 19.72 秒 | 19.22、19.02、18.91、17.98、17.82 秒 |
| `458fc5a4` | 20.15 秒 | 18.07、17.82、18.28、18.97、18.68 秒 |
| `50b9fca8` | 2.07 秒 | 2.43、2.17、2.19、2.20、2.21 秒 |

古いコミットでも、脚注を除いて 1 秒から 2 秒しか縮まない。
時間の大部分は、脚注ではなく本文の組版にかかっていた。

### 時間が縮んだコミット

`c505a214` から `50b9fca8` までの `main` の first-parent の 406 のコミットを、二分探索で調べた（一回ずつのビルドと計測で、8 秒を境にした）。

| コミット | 『Nightmare Abbey』の時間（1 回） |
| --- | --- |
| `468bf6b2` | 20.79 秒 |
| `d87445f6` | 13.84 秒 |
| `fede8f43` | 11.33 秒 |
| `da4dedd0` | 3.84 秒 |
| `62ffea4a` | 2.46 秒 |
| `8daf06f1` | 3.85 秒 |
| `56cf37d4` | 3.54 秒 |

大きく縮んだのは、`fede8f43` と `da4dedd0` のあいだである。
`da4dedd0` は PR #231（行分割の最後の段で収まらない箱を追い出す、`32f8ea5e`）のマージである。
`468bf6b2` から `d87445f6` のあいだでも 7 秒ほど縮んでいるが、その範囲は調べていない。

`32f8ea5e` の前は、最後の段（段階 4）が不良度 10000 までのすべての行を許容し、はみ出さない限りどの分割の候補も活性のノードとして残した（[`KnuthPlass.hs`](https://github.com/tett23/golem/blob/fede8f43ac1437610e32da4a7661f05999c1876f/modules/golem-layout/src/Golem/Layout/KnuthPlass.hs#L207-L285)）。
`32f8ea5e` は、許容を不良度 9999 までにし、収まらなくなった箇所では追い出して分割をやり直す（[`KnuthPlass.hs`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/modules/golem-layout/src/Golem/Layout/KnuthPlass.hs#L214-L327)）。
段階 4 に進む段落で活性のノードが増えにくくなったことが、時間が縮んだ理由だと推測している。
活性のノードの数は数えていないので、推測にとどまる。
`32f8ea5e` は、コミットの説明のとおり、間延びした行を選ばないように行の分け方を変える変更で、速くするための変更ではなかった。

### 測る途中で分かったこと

一つの作業用のディレクトリで、`dist-newstyle` を残したまま別のコミットを `git archive` で上書きしてビルドすると、`golem` が段落を組む前に落ちた（終了コード 139）。
`git archive` が書くファイルの更新日時はコミットの日時なので、C のソース（`cbits`）の変更が、新しい日時のオブジェクトに隠れて再コンパイルされなかったと推測している。
この ADR の数字は、コミットごとに新しいディレクトリでビルドしたものか、取り出した後にすべてのファイルの更新日時を新しくしてからビルドしたもの（二分探索）である。

## 実装すること

コードは変えない。
出力も変わらない。

- ロードマップの v0.1.0-rc4 から「脚注の多い本の組版の時間」を消す。
- 上の計測を `docs/benchmarks/2026-11-06-pd-fixtures-layout-time.md` に記録として置く（「メンテナーが決めること」の 1）。記録の形は `docs/benchmarks/2026-10-14-regex-styles.md` に合わせ、計算機、コミット、方法、結果を書く。コミットした後は変更しない。

## 実装しないこと

- 組版をさらに速くすること。今の『Nightmare Abbey』は、ほかの本と同じ程度の時間で組める。
- `468bf6b2` から `d87445f6` のあいだで縮んだ理由を調べること。
- 組版の時間や割り当ての量を CI で検査すること（「メンテナーが決めること」の 2）。
- プロファイルを取るビルド。依存するパッケージをすべてプロファイル付きでビルドし直す必要があり、今の `main` では時間の偏りがないので、取る理由がない。

## テスト設計

コードを変えないので、自動のテストは足さない。
記録のファイルは、実装のプルリクエストで、上と同じ方法で今の `main` を測り直した数字で書く。
測り直した『Nightmare Abbey』の時間が、原稿の大きさが近いほかの本の二倍を超える場合は、項目を閉じずにこの ADR を見直す。

## トレードオフ

速くした変更を探さずに項目を閉じる選択肢もあるが、原因を記録しないと、同じ遅さが戻ったときに手がかりがない。
この ADR は、速くなったコミットと、脚注が原因でなかったことを記録する。

CI で時間を検査しないので、組版が遅くなる変更が入っても気付くのは人である。
壁時計の時間は CI の計算機の混み具合で揺れ、決まった上限で落とす検査は不安定になる。
割り当ての量は時間より揺れにくいが、GHC や依存の版を上げるだけでも変わる。

## 決めたことの記録

- **脚注の多い本の組版の時間を調べること**（ロードマップ、v0.1.0-rc4 の「脚注の多い本の組版の時間」）：脚注を 14 件持つ『Nightmare Abbey』の fixture だけ、PDF の組版に 17 秒から 20 秒かかる。ほかの九冊は 1 秒から 6 秒である。
- **計測の記録**（2026-11-07、メンテナー）：「計測の記録を benchmarks に置く」。実装のときに測り直した数字を `docs/benchmarks/` に記録として置く。
- **CI での検査**（2026-11-07、メンテナー）：「CI では検査不要」。組版の時間は揺れが大きすぎ、信頼できるデータにならないからである。

## メンテナーが決めること

すべて決めた（「決めたことの記録」）。

1. **計測の記録を置くか**：決めた。推奨のとおり、`docs/benchmarks/` に記録を置く（「決めたことの記録」）。ADR の数字はこの ADR を書いた時点のもので、実装のときに測り直した数字を、変更しない記録として残せる。退けた案は、ADR に書いた数字だけで済ませる案である。測り直した結果の置き場所がなくなる。
2. **組版の時間を CI で検査するか**：決めた。推奨のとおり、検査しない。時間の揺れが大きすぎ、信頼できるデータにならないからである（「決めたことの記録」）。ロードマップの「テストのスイートの時間の上限」が、時間の上限の決め方を別に扱っている。退けた案の一つは、fixture ごとに壁時計の時間の上限を設ける案で、CI の計算機の混み具合で揺れて不安定な検査になる。もう一つは、`+RTS -s` の割り当ての量に上限を設ける案で、揺れは小さいが、GHC と依存の版を上げるたびに上限を直す必要がある。
