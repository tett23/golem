# ADR 0149: .gmx の関数の要求と driver のハンドラ

ステータス: 破棄

## 文脈

[ADR 0148](0148-gmx-function-language-core.md) は、`.gmx` の関数を純粋なものとした。
しかし、社内の使い手が書きたい関数の多くは、手元の表や辞書を読む。
ルビの読みの一覧、用語の表、社内の表記の規則などである。
プラグインは同じ必要を、`manifest.toml` で渡すデータ（[docs/adr/0105](0105-plugin-data.md)）と、プラグインが宣言して受け取る本の文脈（[docs/adr/0121](0121-host-context-in-plugin-requests.md)）で満たしている。

メンテナーの案は、関数が処理系に求めるもの（**要求**）を、関数のシグネチャに書くことである。

```
pub inline/block docStyles :: Evaluated -> FileId -> Style => file
```

案の要点は次のとおりである。

- 代数的エフェクトを部分的に実装する。エフェクトを処理するハンドラは driver に集め、利用者はハンドラを書けない。型の上では、ハンドラを足す余地を残す。
- シグネチャを読めば、関数が driver に何を求めるかが分かる。wasm のモジュールが import でホストに求めるものを宣言するのと同じ形である。
- 未知の要求はエラーとする。
- コードを読み込めば、`manifest.toml` に足りない要求を見つけられる。ファイルがない場合はエラーとする。

例の型（`Evaluated`、`FileId`、`Style`）は Golem の内部の型であり（[`docStyles`](https://github.com/tett23/golem/blob/4f86b945b6e60913fc63e22c0bf4ec14e5114bed/modules/golem-driver/src/Golem/Driver.hs#L169-L170)）、`.gmx` からは見えない。
この ADR は、例を `=> 要求` の位置と形を示すものとして読む。

プラグインのホストは、wasm の import を一切渡さない（[golem-plugin ADR 0001](../golem-plugin/adr/0001-wasm-host-and-abi.md)）。
プラグインが外のものを受け取る経路は、`golem_describe` で宣言した名前に限られ、宣言できる名前は閉じた一覧である。
一覧にない名前を宣言したプラグインは、読み込みの時点で G06105 になる（[docs/adr/0121](0121-host-context-in-plugin-requests.md)）。
案の「未知の要求はエラー」は、この規則を `.gmx` の型に移したものと読める。

## 実装すること

### シグネチャの要求

シグネチャの型の後ろに `=>` を置き、要求の名前をカンマで区切って並べる。

```haskell
pub inline reading :: String -> Inlines => file;
lookupReading :: String -> Maybe String => file;
total :: List Nat -> Nat;
```

- `=>` のない関数は、要求を持たない純粋な関数である。
- 要求の順は意味を持たず、fmt が名前の順に並べ替える。同じ名前を二度書くと G10502 とする。
- 要求の名前は、下の一覧の名前に限る。一覧にない名前は G10500 とし、プラグインの G06105 と同じく、知らない名前をすべて一つの diagnostic に並べ、メッセージに使える名前の一覧を添える。

### 要求の一覧

v1 の一覧は `file` だけとする。

| 名前 | 使える操作 | ハンドラ |
| --- | --- | --- |
| `file` | `File.read :: String -> String => file` | driver。`manifest.toml` の `[functions.data]` の名前のファイルを読む |

`File.read name` は、`[functions.data]` の `name` のファイルの中身を文字列で返す。

- 中身は UTF-8 として読む。不正なバイト列は G10504 とする。先頭の BOM は読み飛ばし、CRLF は受け付ける。`@table` の表のファイルと同じ扱いである（[golem-eval ADR 0004](../golem-eval/adr/0004-tsv-tables.md)）。
- `[functions.data]` にない名前を読むと G10503 とする。名前は実行の中で決まりうるので、この誤りは評価のときに見つかる。
- 同じ名前のファイルを何度読んでも、driver は一度だけ読み、同じ値を返す。

本の文脈（書字方向、数の表記）、`meta` の値、文書構造（S1）の値を読む要求は、v1 では入れない。
入れるときは、この ADR の修正の ADR で一覧に足す。
一覧はプラグインの文脈の一覧（[docs/adr/0121](0121-host-context-in-plugin-requests.md)）と別に管理する。

### 要求の伝わり方

要求は関数の型の一部であり、型の検査で確かめる。

- 関数の中で `File.read` を呼ぶか、`file` を要求する関数を呼ぶなら、その関数のシグネチャは `file` を持たなければならない。持たなければ G10501 とし、位置は呼び出しを、メッセージは足りない要求の名前を指す。
- 使わない要求をシグネチャに書いても誤りにしない。将来使う予定の要求を先に書くことを妨げないためである。
- `where` の中の局所の関数は、外の関数の要求を受け継ぐ。
- 関数を値として引数に渡す場合、その関数は要求を持ってはならない。要求を持つ関数を渡すと G10501 とする。高階の関数の型に要求の変数（エフェクトの多相）を入れると、型の推論とメッセージが複雑になるからである。

この形は、型の上では要求の集合を関数の型に付ける代数的エフェクトの型である（参考文献の Leijen）。
v1 は、要求の集合を一覧の名前の具体的な集合に限り、変数を持たせない。
ハンドラは driver が持つものだけであり、`.gmx` の中で要求を処理して消すことはできない。
型の内部の表現は、要求の変数と利用者のハンドラを後から足せるよう、要求の集合を型の項として持つ。

### `manifest.toml` での許可

関数のファイルと、関数に許す要求と、読ませるデータは、`manifest.toml` の `[functions]` に書く。

```toml
[functions]
files = ["functions/book.gmx"]
requires = ["file"]

[functions.data]
words = "data/words.tsv"
```

- `files` は、`.gm` から呼べる関数を持つ `.gmx` の一覧である（[ADR 0150](0150-calling-gmx-functions-from-gm.md)）。そこから `import` で読む `.gmx` は、一覧に書かなくてよい。
- `requires` は、関数に許す要求の一覧である。省けば空の一覧である。
- `[functions.data]` は、`File.read` の名前から、プロジェクトのルートを基準にしたパスへの表である。名前の形は、プラグインのデータの名前と同じ（英小文字で始まり、英小文字、数字、`-` だけ）である（[docs/adr/0105](0105-plugin-data.md)）。

読み込みの時点で、次のことを検査する。

- `files` から `import` でたどれるすべての `.gmx` の、すべての関数のシグネチャの要求を集め、`requires` にない要求があれば G10505 とする。位置は、その要求を書いたシグネチャである。メッセージには `manifest.toml` の `requires` に足す名前を書く。
- `requires` に一覧にない名前があれば G03101 とする。
- `[functions.data]` のパスは、プラグインのデータと同じく `resolveInRoot` で検査する（[`resolveInRoot`](https://github.com/tett23/golem/blob/4f86b945b6e60913fc63e22c0bf4ec14e5114bed/modules/golem-project/src/Golem/Project/Paths.hs#L47-L48)）。ルートの外を指すパスは G03003 とする。原因がプラグインのデータと同じなので、コードを分けない。
- `files` と `[functions.data]` のファイルがなければ G03102 とする。関数を一つも呼ばない本でも検査する。誤りが見えるかどうかを、原稿に呼び出しを書いたかどうかで変えないためである（[docs/adr/0120](0120-plugin-data-check-at-load.md) と同じ理由）。
- `[functions.data]` の大きさの合計は、プラグインのデータと同じく 64 MiB までとし、超えれば G03103 とする。
- `[functions.data]` があるのに `requires` に `file` がなければ、G03104 とする。読む手段のないデータを渡す書き方は、`requires` の書き忘れであることが多いからである。

`requires` を `manifest.toml` に書かせるのは、関数が何を読むかを、`.gmx` を開かずにプロジェクトの設定だけで確かめられるようにするためである。
本を作る側の責任者は、`manifest.toml` の差分で、関数が新しくファイルを読むようになったことに気付ける。

### driver のハンドラ

- ハンドラは golem-driver に置く。golem-gmx の評価器は、要求の操作に出会うと、評価を止めずに driver から渡されたハンドラの関数を呼ぶ。
- `file` のハンドラは、読み込みの時点で `[functions.data]` のファイルをすべて読み、評価のあいだはその値だけを返す。評価の途中でファイルシステムに触れない。プラグインのデータと同じく、評価を純粋に保ち、ファイルを並列に評価できるようにするためである。
- LSP は `[functions.data]` のファイルと `.gmx` のファイルを、表のファイルと同じ仕組みで監視し、変われば評価し直す（[仕様書の「LSP」](../specifications.md#lsp)）。

### 誤りのコード

| コード | 重大度 | 原因 |
| --- | --- | --- |
| G10500 | エラー | シグネチャに一覧にない要求の名前がある |
| G10501 | エラー | シグネチャにない要求を使っている（要求を持つ関数を値として渡した場合を含む） |
| G10502 | エラー | シグネチャに同じ要求を二度書いた |
| G10503 | エラー | `File.read` に `[functions.data]` にない名前を渡した |
| G10504 | エラー | `File.read` で読んだファイルが UTF-8 として読めない |
| G10505 | エラー | シグネチャの要求が `manifest.toml` の `requires` にない |
| G03101 | エラー | `[functions]` の `requires` に一覧にない名前がある |
| G03102 | エラー | `[functions]` の `files` か `[functions.data]` のファイルがない |
| G03103 | エラー | `[functions.data]` の大きさの合計が上限を超えた |
| G03104 | エラー | `[functions.data]` があるのに `requires` に `file` がない |

G10500 と G03101 は、どちらも一覧にない名前だが、書いた場所と直す人が違う。
G10500 は関数の作者が `.gmx` を、G03101 は本の設定の担当が `manifest.toml` を直す。
一つのコードに一つの原因の原則に従い、分ける。

`files` のファイルがないことと `[functions.data]` のファイルがないことは、どちらも宣言したファイルがないという同じ原因なので、G03102 にまとめ、メッセージで欄を示す。

## 実装しないこと

- 利用者がハンドラを書くこと。
- 要求の変数（エフェクトの多相）。
- `file` のほかの要求（本の文脈、`meta`、S1 と S2 の値、時刻、乱数、ネットワーク、環境変数）。時刻、乱数、ネットワーク、環境変数は、決定性を壊すので今後も入れない。
- `.gmx` の中でパスを書いてファイルを読むこと。読むファイルは `manifest.toml` の名前で選ぶ。
- データを表として解釈すること。`File.read` は文字列を返し、分けるのは関数である。
- 関数ごとに読めるデータを分けること。`requires` と `[functions.data]` はプロジェクトの全体で一つである。

## テスト設計

テストを先に書き、`File.read` と `[functions]` の読み込みがないためにコンパイルできないことを確かめてから実装する。

golem-gmx のテストでは、次のことを確かめる。

- `=> file` のある関数が `File.read` を呼べ、`=>` のない関数から呼ぶと G10501 になること。`file` を要求する関数を呼ぶ関数も、シグネチャに `file` がなければ G10501 になること。
- `=> net` が G10500 になり、メッセージに `file` が出ること。`=> file, file` が G10502 になること。
- 要求を持つ関数を `List.map` に渡すと G10501 になること。
- 使わない `=> file` が誤りにならないこと。

golem-driver のテストでは、次のことを確かめる。

- `requires` のない `manifest.toml` で `=> file` の関数を持つと、関数を呼ばない本でも G10505 になること。
- `requires = ["net"]` が G03101 になること。
- `[functions.data]` のファイルがないと、関数を呼ばない本でも G03102 になること。`files` のファイルがない場合も G03102 になること。
- ルートの外のパスが G03003、合計の上限を超えたデータが G03103、`requires` に `file` のない `[functions.data]` が G03104 になること。
- `File.read "missing"` が G10503、不正な UTF-8 のファイルが G10504 になること。BOM と CRLF のファイルを読めること。
- 同じデータを二つの呼び出しで読み、評価のあいだにファイルを書き換えても、二つが同じ値になること。

golem-lsp のテストでは、`[functions.data]` のファイルを書き換えると、diagnostics が公開し直されることを確かめる。

## トレードオフ

読むファイルを名前で選ばせるので、`.gmx` の中でパスを組み立てて読むことはできない。
章ごとに辞書のファイルを分けるような書き方では、`manifest.toml` に名前を並べることになる。
その代わり、本が読むファイルの一覧が `manifest.toml` だけで決まり、読み込みの時点でファイルの有無を確かめられ、LSP が監視するファイルも決まる。

`requires` を `manifest.toml` と `.gmx` の両方に書くので、一つの要求を足すのに二か所を変える。
二重に書かせるのは、`.gmx` を書く人と本の設定に責任を持つ人が分かれている場合に、後者が気付けるようにするためである。
社内の小さな本では同じ人が両方を書くので、手間だけが増える。

v1 の一覧が `file` だけなので、縦組みかどうかで漢数字にするような関数は書けない。
プラグインでは文脈として読めるので、使い手の要望が出た時点で、この ADR の修正で一覧に足す。

## メンテナーが決めること

1. **「ファイルがない場合はエラー」の読み方**：推奨は、`manifest.toml` に書いたファイル（`files` と `[functions.data]`）がないことを、読み込みの時点のエラー（G03102）にすることである。採らなかった案は、`File.read` が実行のときにパスを受け取り、ファイルがなければ実行のエラーにすることである。読み込みの時点で見つからず、LSP が監視するファイルも決まらない。
2. **`manifest.toml` に要求を許可させるか**：推奨は `requires` を書かせることである（「manifest に足りていない要求を検出できる」を、manifest に許可の一覧があると読んだ）。採らなかった案は、`.gmx` の要求をそのまま信じ、manifest には `files` と `[functions.data]` だけを書かせることである。こちらは二か所に書く手間がないが、関数が新しくファイルを読むようになっても `manifest.toml` の差分に現れない。
3. **v1 の要求の一覧**：推奨は `file` だけである。採らなかった案は、プラグインの文脈と同じ `writing-mode` と `vertical-numbers` を最初から入れることである。入れる場合は、要求の名前を `writing-mode` のように一つずつにするか、`context` 一つにするかも決める。
4. **使わない要求を許すか**：推奨は許すことである。採らなかった案は、使わない要求を G10501 と別のコードのエラーにすることである。緩い規則より厳しい規則の原則に寄せるなら、こちらになる。ただし、許可を広く取りすぎる書き方は誤った出力を生まないので、推奨では許した。
5. **シグネチャの `=>` の位置**：推奨は案のとおり型の後ろである。Haskell では `=>` は型の前に置く制約の記号なので、Haskell を知る人には逆に見える。採らなかった案は、`!` などの別の記号（Koka の `-> e` に近い形）にすることである。
6. **`[functions]` の名前**：推奨は `[functions]` である。採らなかった案は `[gmx]` である。拡張子より、何を書くかを表す名前を選んだ。
