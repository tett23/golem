# ADR 0399: プロジェクトをまたぐ移動の章登録と参照編集を計画する

Status: accepted

## 文脈

[Aleph ADR 0100](https://github.com/tett23/aleph/blob/2cf61128368cd7105a47892c16fbe482bef05b6f/docs/adr/0100-move-tree-files-and-folders.md) は、同じワークスペース内で、フォルダとその子孫を別のプロジェクトへ移す操作を定めた。
登録済みの章は移動先へ登録を引き継ぎ、原稿と Wiki リンクの参照先を保つ。
Golem の構文と解決規則を Aleph に複製せず、この操作の前に必要な編集を Golem から取得したい。

[root ADR 0338](0338-update-references-on-file-and-folder-renames.md) の改名契約は、複数プロジェクトにまたがる移動を対象外にしている。
本 ADR はその対象外の範囲を置き換え、章登録の移管とプロジェクト内外の移動を扱う要求を追加する。
既存の単一プロジェクト向けの標準 LSP 要求は互換性を保つ。

## 調査した事項

基準版は `05c4a20de1b532a4346fc9e22f997dbed4e1aa96` である。
LSP の改名処理は、旧 URI と新 URI を同じプロジェクトルートで検査する。
manifest の編集計画はパスの置換を扱うが、章の削除と別 manifest への追加は扱わない。
章の内部表現にはファイルとグループがあるが、平坦なファイル一覧では入れ子と章の追加属性を移管できない。
これらの根拠は末尾に固定した版のリンクを示す。

Wiki リンクの設定は、ワークスペースとシート集合をクライアントから受け取る。
現行処理では読めない文書を省くため、編集がない応答だけでは対象をすべて読んだことを確認できない。
移動には、検査を完了して編集がなかった場合と、検査を完了できなかった場合を区別する応答が要る。

## 実装すること

### 移動前の要求

Golem LSP に `golem/planFileMove` 要求を追加する。
対応するサーバーは `initialize` の `capabilities.experimental.golem.planFileMove` に契約の版 `1` を返す。
この要求はディスクを書かず、ファイルシステムの移動前の状態を読み、移動後のパスと所属を仮定して編集を返す。

初期化設定は `initializationOptions.golem.fileMove = { version: 1, workspaceUri: "file:///..." }` とする。
クライアントは、一つの登録済みワークスペースを対象に、次の入力を送る。
URI は `file` スキームとする。

| 入力 | 意味 |
| --- | --- |
| `workspaceUri` | 登録済みワークスペースのルート |
| `oldUri`, `newUri` | 一つのファイルまたはフォルダの移動元と移動先 |
| `projects` | 操作前の全プロジェクトのルート URI と、参照更新を有効にしたプロットの URI。プロットを扱わない場合は `null` |
| `wikiSheets` | 操作前の可視シートの URI とタイトル。タイトルなしは `null` |
| `inventoryComplete` | プロジェクトとシートの列挙を完了した場合だけ `true` |
| `documents` | 対象範囲で開いている文書の URI、本文、版の一覧 |

要求を受けるサーバーの初期化時に、クライアントは対象の `workspaceUri` とこの拡張の利用を明示する。
サーバーは要求のワークスペースがその登録と一致することを確認する。
プロジェクトがないワークスペースでも、この登録による要求を受けられるようにする。
複数のプロジェクトを扱うために、既存の単一プロジェクトのルート検査を単に外してはいけない。

クライアントは保存を終えてから一覧と文書を取得し、要求から適用完了まで同じ対象への別の移動を開始しない。
サーバーは manifest の所在と入れ子を調べ、申告されたプロジェクト集合と照合する。
必要なディレクトリや文書を読めない場合、列挙が未完了の場合、申告と実際の所属が異なる場合は失敗する。
Wiki の可視性とタイトルの規則は Aleph が決めるため、シート集合の完全性はクライアントの責任とする。
サーバーは申告された各シートの読み取り失敗を省略しない。

### 章登録と参照の計画

サーバーは旧パスと新パスの対応を一度作り、子孫にも同じ対応を適用する。
操作前の所属と仮定した操作後の所属を、それぞれプロジェクトのルートから求める。
プロジェクトを丸ごと移した場合は所属を保ち、プロジェクトの入れ子になる移動は拒む。
シンボリックリンクを経由する場所、ワークスペース外、自分自身の子孫、既存の移動先も拒む。

登録済みの章を別プロジェクトへ移す場合は、移動元の chapters から対象だけを除き、移動先の chapters の末尾へ加える。
対象だけを残した元の配列構造を引き継ぎ、元の順序、入れ子、表形式の章の追加属性を保つ。
パスだけを移動先プロジェクトからの相対パスに変える。
移動元に残る章と移動先の既存の章の順序は変えず、空になった入れ子を除く。
元の章がすべて移った場合は `chapters = []` を残す。
重複した章の出現は元の出現数と順序を保って移管する。

プロジェクト外へ出す章は登録を外す。
未登録の原稿をプロジェクトへ入れても登録しない。
同じプロジェクト内の移動では章のパスだけを変える。
章登録の移管だけを理由に manifest の章以外の値を変えない。
ただし、後述の参照更新に必要なパスの編集は行う。
章以外のコメントと、残る章に付いているコメントを失わない。
移管する章に付いているコメントは元の章とともに移す。

参照の種類と解決規則は root [ADR 0338](0338-update-references-on-file-and-folder-renames.md) を引き継ぐ。
参照元と参照先の両方に移動の対応を適用し、操作後も同じ対象を指す綴りを求める。
移動した原稿から動かない画像などを指す場合も検査する。
プロットは入力で明示された URI だけを扱い、同名の CSV を自動検出しない。
指定したプロットがそのプロジェクトの外にある場合は失敗する。
Golem のプロジェクト境界の制限は緩めず、新しい所属から許されない参照は、参照元、位置、参照先、理由を示して失敗する。
プロジェクト外の Golem 原稿も構文上の参照を調べ、操作後の所属の規則で検査する。
プロジェクトがない状態で解決できない参照は、解決済みとして扱わない。

Wiki リンクはワークスペースの可視シート集合全体で検査する。
移動対象を指すリンクと、移動するシートから外側を指す相対リンクを扱い、見出しとラベルを保つ。
タイトルまたは名前の曖昧さによって移動対象との関係を確定できない場合は、該当する参照を示して移動計画を失敗させる。
URL、通常の本文、明示的に対象外とした形式をパスとして置換しない。

### 応答と適用

成功応答は `complete: true`、参照と章登録の編集、検査に使った文書のスナップショット、章登録変更の要約を返す。
編集は操作前の URI と位置を使った `TextDocumentEdit` とし、開いた文書には入力の版、閉じた文書には `null` を付ける。
位置の単位は LSP で交渉したエンコーディングに従う。
ファイルの移動操作は応答に含めない。

編集は操作前の所属でグループ化する。
一つの応答から移動元と移動先の両プロジェクトの計画を取得でき、所属のない文書のグループは `projectUri: null` とする。
同じ文書は一つのグループだけに属し、同じ範囲の同じ編集は一度だけ返す。
異なる編集が重なる場合は全体を失敗させる。
検査を完了して編集が不要なときは、空の編集一覧を返す。

スナップショットは、検査した文書の操作前の本文と URI、開いた文書の版、プロジェクトとシートの一覧を含む。
参照元の探索で列挙したディレクトリと直下の項目の URI と種別も含み、可視シート以外の参照元の追加と削除も照合する。
クライアントは適用直前に本文、版、一覧を照合し、変化があれば編集を適用せず再要求する。
読み取り失敗、不正な入力、解決不能、権限外の参照、矛盾する編集は JSON-RPC のエラーとして返し、エラーの `data` に該当 URI、位置があれば位置、理由を含める。
部分的な成功や編集一覧を返さない。

クライアントは章登録、参照、メタデータ、ファイルシステムの移動を一つの計画として適用する。
失敗時の巻き戻しと競合保護は [Aleph ADR 0100](https://github.com/tett23/aleph/blob/2cf61128368cd7105a47892c16fbe482bef05b6f/docs/adr/0100-move-tree-files-and-folders.md) に従う。
成功後は移動前後の各プロジェクトの LSP 接続を新しい所属で再構築し、旧 URI を閉じ、新 URI と最新の本文を同期する。
事後通知を受けたサーバーは同じ編集を再適用しない。

### 契約版1のデータ構造

要求と成功応答は次の構造に固定する。
全フィールドを必須とし、要素がない一覧は空配列、所属と版とタイトルがない場合は `null` とする。
`TextDocumentEdit` は LSP の同名の型を指す。
`chapters` は移管する各出現を元の配列の添字で識別し、表示用の一覧であって編集を生成する入力には使わない。

```typescript
type Project = { uri: string; plotCsv: string | null };
type Sheet = { uri: string; title: string | null };
type Document = { uri: string; text: string; version: number | null };
type Request = {
  workspaceUri: string;
  oldUri: string;
  newUri: string;
  projects: Project[];
  wikiSheets: Sheet[];
  inventoryComplete: boolean;
  documents: Document[];
};
type Response = {
  complete: true;
  groups: { projectUri: string | null; edits: TextDocumentEdit[] }[];
  snapshot: {
    documents: Document[];
    projects: Project[];
    wikiSheets: Sheet[];
    directories: {
      uri: string;
      entries: { uri: string; kind: "file" | "directory" | "symlink" }[];
    }[];
  };
  chapters: {
    oldUri: string;
    newUri: string;
    sourceProjectUri: string;
    destinationProjectUri: string | null;
    sourceIndices: number[];
  }[];
};
```

要求の `documents` は開いた文書だけなので、`version` に整数を要求し、重複した URI を拒む。
応答のスナップショットでは閉じた文書の `version` を `null` にする。
`chapters` はプロジェクト境界を越える登録変更を元の章順で並べ、登録変更がなければ空配列とする。
`sourceIndices` は chapters の最上位から数えた 0 始まりの添字の列である。
エラーの `data` は `{ issues: [{ uri: string, range: Range | null, targetUri: string | null, reason: string }] }` とし、位置と参照先がない場合を `null` にする。
`Range` は LSP の同名の型とする。

## 実装しないこと

複数項目の一括移動、ワークスペース間の移動、Golem のプロジェクト境界の緩和、Golem LSP によるディスクへの書き込みは含めない。
パスを計算する式を評価して書き換える処理は追加しない。

## 不変条件

- I1: 成功した計画を適用すると、対象とした参照は、操作前の参照先を一度移動した先に解決する。
- I2: 章の移管は対象の登録だけを移し、出現数、順序、入れ子、追加属性と対象外の章登録を保つ。
- I3: 要求の成功と失敗のいずれでも、サーバーはファイルシステムとクライアントの本文を変更しない。
- I4: 成功応答の編集は操作前の文書を指し、同じ範囲を重ねて編集しない。
- I5: 検査対象を読み取れない場合と解決できない対象参照がある場合には、空の編集による成功を返さない。
- I6: ワークスペース外とシンボリックリンクを経由する対象への編集を返さず、操作後の Golem の参照制限を保つ。

| 入力 | 期待 | 不変条件 |
| --- | --- | --- |
| 参照も章登録もないファイル一つ | 完全な検査結果と空の編集 | I3, I5 |
| 章が一つ、複数、すべて移る | 対象だけを移管し、全移動後の元の chapters は空 | I2 |
| 文字列、表、入れ子、同じ章の複数出現 | 構造と属性と出現数を保つ | I2 |
| フォルダ内から外側の画像を指す | 同じ対象を保持できれば編集し、境界違反なら失敗 | I1, I6 |
| プロジェクト外への移動、外からの移動 | 登録を削除、自動登録はしない | I2 |
| 未完了の索引、読み取り失敗、古い本文 | 不完全な成功を返さず、古い応答は適用しない | I4, I5 |
| 同名の別シート、曖昧なリンク | 推測して置換しない | I1, I5 |
| 親と似た名前の隣接フォルダ | 移動対象の子孫だけに対応を適用 | I1 |
| 登録外ルート、シンボリックリンク、プロジェクトの入れ子 | 失敗し、変更なし | I3, I6 |

## 受けいれ条件

- A1: 実際の Golem LSP に二つのプロジェクトを渡し、章フォルダの移動に必要な両 manifest と参照の計画を一度の応答から取得できる。
- A2: Aleph の試験用ワークスペースで計画を適用すると、章の構造と Wiki リンクの解決先を保ってフォルダを移動できる。
- A3: 移動先から許されない参照と読み取り失敗は、対象と理由を表示してファイル操作前に中止できる。

## テスト設計

I1〜I6 は表の境界を純粋な計画処理と一時ディレクトリで検査する。
章のテストは両 manifest を読み直し、型に変換する前の TOML の値も比較して追加属性の欠落を検出する。
参照更新で編集するパスを除いた章と無関係な値、コメント、空の chapters を確認する。
参照のテストは移動前後の解決結果を比較し、編集文字列の一致だけで判定しない。

実 LSP の試験では UTF-8 と UTF-16、空白と非 ASCII の URI、未保存文書、移動後の禁止参照、未完了の索引、読めない文書を扱う。
未指定の CSV を編集しないことと、別プロジェクトで指定されたプロットを更新することを検査する。
スナップショット取得後に本文を変え、可視シートと Emet の参照元を追加または削除し、クライアントが適用を拒むことを確認する。
A1〜A3 は公開する実行ファイルと Aleph の統合試験で確かめる。
テスト名には `root ADR 0399` と、不変条件と受けいれ条件のうち対応する番号を付ける。

## トレードオフ

ワークスペース全体の参照を調べるため、一つのプロジェクトの改名より読み取りと応答が増える。
本文のスナップショットを返すと応答も大きくなるが、クライアントはハッシュ形式や版のない文書の扱いを推測せずに適用前の照合ができる。
章登録と参照を一度に計画すると、複数の LSP 応答を別々の時点で組み合わせる問題を避けられる。
