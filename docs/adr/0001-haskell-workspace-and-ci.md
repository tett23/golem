# ADR 0001: Haskell のワークスペースと CI

ステータス: 採択→docs だけの変更で CI のジョブを省くことと、`format` ジョブの hlint の入れ方は [ADR 0009](0009-ci-speed.md)、`adr` ジョブの置き場所と CI の判定のジョブは [ADR 0021](0021-docs-workflow-and-ci-gate.md)

## 文脈

Golem は Haskell で実装し、`modules/` の下に複数のモジュールを置く。
モジュール間のインターフェースを先に ADR で定め、各モジュールを並行して実装する方針なので、コードを一行も書く前に、モジュールの置き方、ビルドの方法、テストの道具、CI の構成を揃えておく必要がある。
揃えないまま並行して実装を始めると、モジュールごとにビルドの設定とテストの書き方がばらつき、後から統一する作業が全モジュールに波及する。

決定性は Golem の最優先の制約であり、ビルドの道具立てにも及ぶ。
依存するライブラリの版が環境ごとに異なれば、同じ原稿から同じ出力は得られない。

## 実装すること

### 構成

- ビルドには cabal を使う。リポジトリのルートに `cabal.project` を置き、`modules/` の下の各ディレクトリを一つの cabal パッケージとする。パッケージ名はモジュール名と同じ（`golem-syntax` など）にする。
- GHC の版は、実装を始める時点の最新の安定版に固定し、`cabal.project` と mise の設定に記録する。版を上げるときは ADR を作成する。
- 依存ライブラリの版は `cabal.project.freeze` で固定し、リポジトリにコミットする。
- 実行ファイルは `golem-cli` だけが持ち、ほかのモジュールはライブラリとする。

### 依存の方針

ライセンスに問題がなく、必要な機能が限られていて再実装が容易なものは、依存に加えず再実装する。
再実装する場合は、元のライブラリのテストを参考にして、十分に厚いテストを書く。
C のライブラリ（HarfBuzz、FreeType、wasmtime）は、それぞれを担当するモジュールの ADR で扱い、ほかのモジュールからは直接呼ばない。

### テスト

- 単体テストとプロパティテストには tasty と hedgehog を使う。
- 出力を固定値と比べるテストには tasty-golden を使う。
- 各パッケージの `cabal test` が単独で通ることを保つ。

### コードの整形と検査

- Haskell のコードは fourmolu で整形し、CI で整形済みであることを検査する。
- hlint の警告を CI でエラーとして扱う。

### CI

GitHub Actions の `.github/workflows/ci.yml` に、既存の `adr` ジョブと並べて次のジョブを置く。

- `build`：x86-64 と aarch64 の Linux の両方で、全パッケージのビルドとテストを実行する。
- `determinism`：同じ入力からの出力を二つのアーキテクチャで生成し、バイト列が一致することを検査する。出力を生成できるモジュールが揃うまでは、式の評価の結果を比べる。
- `format`：fourmolu と hlint の検査を実行する。

Actions は Node 24 以降で動く最新のメジャー版を使う。

## 実装しないこと

- macOS と Windows での CI。開発者の手元では macOS を使うが、CI での検査は Linux の二つのアーキテクチャで行う。
- stack によるビルド。cabal と freeze ファイルで十分に版を固定できる。
- バイナリの配布とリリースの自動化。最初に配布できる機能が揃った段階で、別の ADR で扱う。

## テスト設計

- 空のライブラリを一つ（`golem-syntax`）作り、`cabal build all` と `cabal test all` が両方のアーキテクチャの CI で通ることを確かめる。
- 整形されていない Haskell のファイルを含む変更で、`format` ジョブが失敗することを確かめる。
- `cabal.project.freeze` を消してビルドすると依存の版が変わりうることを、手順書（README の開発の節）に記載する。

## トレードオフ

依存の版を freeze ファイルで固定すると、ライブラリの更新は手作業になる。
決定性を優先するので、更新の手間は受け入れる。

aarch64 の CI ランナーは x86-64 より選択肢が少なく、実行時間も長くなりうる。
それでも、浮動小数点数の計算とネイティブライブラリの結果が二つのアーキテクチャで一致することは、決定性の主張の根拠そのものなので、省略できない。
