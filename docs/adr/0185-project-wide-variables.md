# ADR 0185: プロジェクト全体の変数を `manifest.toml` の `[vars]` に書く

ステータス: 採択（未実装）

## 文脈

`@set` の変数はファイル単位である。
ほかのファイルからは、`@import パス as 名前空間` で取り込み、名前空間を通してだけ参照できる（[仕様書の「マニフェスト」の定義の取り込み](../specifications.md)）。
名前空間を付けずに定義を展開する取り込みは認めない。
`.emet` の関数の取り込みも、同じ `@import` の形で、名前空間を必ず付ける（[ADR 0162](0162-calling-emet-functions-from-gm.md)）。

このため、本の全体で使う値（扱うソフトウェアの名前と版、柱に出す著者の短い名前など）も、使う章ごとに `@import` を書くことになる。
柱の書式の `{set.<名前>}` は、そのページのファイルの変数しか読まないので、本の全体で同じ値を柱に出すには、すべての章のファイルで同じ `@import` を書く（[仕様書の柱の差し込み](../specifications.md)）。
ロードマップの v0.1.0-rc4 の「プロジェクト全体の変数」は、`@import` なしで読める変数を宣言する手段を求めている。

### 今ある読み取り専用の名前空間

`meta` は、マニフェストの `[metadata]` の値を、どのファイルからも `@import` なしで読ませる名前空間である（[仕様書の「本文からの参照」](../specifications.md#本文からの参照)）。
評価の前に値が決まっているので、ファイル内評価（S0）の値であり、見出しの中でも使える。
実装では、ファイルを評価するときの名前空間の表に、最初から `meta` を入れている（[`evalFile`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/modules/golem-eval/src/Golem/Eval/File.hs#L217-L228)）。
`doc` と `meta` は予約語であり、`@set` の名前にも `@import` の名前空間にも使えない（G02023）。
v0.1.0-rc3 の `golem check` で、`@import values.gm as meta` と `@set doc = 1` が G02023 になることを確かめた（2026-11-06）。

`meta` は書名などの決まったキーだけを持ち、マニフェストの `[metadata]` は未知のキーを G03001 とする。
書き手が自由な名前の値を置く場所はない。
v0.1.0-rc3 の `golem check` で、`manifest.toml` の `[variables]` の表が G03001（`知らないキーです: variables`）になることを確かめた。

### Emet との関係

Emet の関数は `.gm` の `@set` の変数を直接読めず、引数として受け取る（[ADR 0162](0162-calling-emet-functions-from-gm.md) の「メンテナーが決めること」の 3）。
ロードマップの未決事項の「Emet の関数から `@set` の変数を読むこと」は、読めるようにすると関数の結果が呼び出しの位置の変数の状態に依存することを挙げ、この項目と合わせて決めるかを残している。

### プロファイル

dev と prod のプロファイルが変えるのは、今は diagnostics の重大度、校正用のコメント（`%%=`）を出力に出すかどうか、PDF のインスタンス ID である（[仕様書](../specifications.md)、[docs/markup.md](../markup.md) のコメントの節）。
組んだ本文の値をプロファイルで変える仕組みはない。

## 実装すること

### 宣言の置き場所

プロジェクト全体の変数は、`manifest.toml` の `[vars]` の表に書く（「メンテナーが決めること」の 1）。

```toml
[vars]
product = "Golem"
version = "0.1.0"
edition-count = 3

[vars.author]
short = "tett23"
```

- 値は評価の前に決まる。`meta` と同じく S0 の値であり、見出しの中でも使える。
- `[vars]` がなければ、`vars` は空の名前空間である。

### 参照の書き方と名前空間

式文脈から、予約した名前空間 `vars` を通して読む（「メンテナーが決めること」の 2）。

```
[= vars.product] [= vars.version] の使い方
[= vars.author.short]
```

- `vars` を `doc` と `meta` に並べて予約語にする。`@set vars = ...` と `@import ... as vars` は G02023 になる。今 `vars` を名前空間や変数の名前に使っている原稿は、名前を変えることになる。
- `vars` は名前空間なので、`@set` の変数とも `meta` とも名前が重ならない。`@set product = "x"` と `[vars] product = "y"` があれば、`[= product]` は `x`、`[= vars.product]` は `y` である。重なりを誤りにする規則は要らない。
- 名前空間を付けずに定義を展開する取り込みを認めない今の規則は、そのまま保つ。プロジェクト全体の変数も、`vars.` を付けなければ読めない。どの名前がどこから来たかは、名前の形だけで分かる。
- 未定義のキーを引くと、`meta` と同じく G02002 になる。

### 値に書ける型

値は TOML の値で書き、式は書けない（「メンテナーが決めること」の 3）。
TOML の型を、式の値に次のように写す。

| TOML | 式の値 |
| --- | --- |
| 文字列 | 文字列 |
| 整数 | 整数（0 以上なら自然数） |
| 真偽値 | 真偽値 |
| ローカルの日付（`2026-11-06`） | `2026-11-06` の形の文字列（`meta.date` と同じ） |
| 配列 | 配列（要素も同じ規則で写す） |
| 表 | 連想配列（`vars.author.short` で引く） |

- 浮動小数点数（`1.5`）は、新しいエラー（G03109）とする。golem-project が使う toml-parser 2.0.2.0 は、浮動小数点数を `Double` で持つ（`Toml.Semantics.Types`）ので、Golem の数（正確な有理数）に写すと書いた値と違う数になりうる。整数でない数は、文字列で書いて使う側で読むか、`@set` の式で作る。
- 時刻と日時（ローカルの時刻、ローカルの日時、時差つきの日時）も G03109 とする。`meta` に当たる値がなく、文字列の形を決める理由がない。
- キーは、式の識別子の形（`[a-zA-Z_][a-zA-Z0-9_]*`）でなければ、新しいエラー（G03110）とする。`edition-count` のような `-` を含むキーも G03110 である。`meta` はマニフェストのキーの `-` を `_` に直すが、`[vars]` のキーは書き手が決めるので、直さずに書いたとおりの名前で引けるようにする。
- 二つのコードの位置は、`manifest.toml` の誤った値かキーとする。G03001 と同じく、manifest の位置を持つ。

上の例の `edition-count` は G03110 になるので、`edition_count` と書く。

新しいコードの番号は、ほかの草案と重ならないよう、採択の前に確かめて振り直す。

### 柱の書式

柱の書式に `{vars.<名前>}` の差し込みを足す（「メンテナーが決めること」の 4）。

- 値は `{set.<名前>}` と同じく、文字列はそのまま、数は式文脈で本文に埋め込んだときと同じ文字列にする。
- 表の中の値は `{vars.author.short}` と書く。
- キーが `[vars]` にない場合は新しいエラー（G03111）、値が文字列でも数でもない場合は新しいエラー（G03112）とする。`{set.<名前>}` の G02067 と G02068 とは原因が違う（変数の出どころが章のファイルでなく `manifest.toml` であり、検査の段階も違う）ので、コードを分ける。
- `manifest.toml` と `style.toml` の両方を読んだところで検査する。章のファイルを評価しなくても決まるので、`{set.<名前>}` と違い、`golem check` と PDF のビルドのどちらでも、章ごとでなく一度だけ出す。位置は `style.toml` の書式の値とする。
- `?` を付けた `{vars.<名前>?}` は、ほかの差し込みと同じく、値がないときに空の文字列にする。このとき G03111 は出さない。

### プロファイル

値をプロファイルで変える仕組みは作らない（「メンテナーが決めること」の 5）。
`[vars]` の値は、dev と prod のどちらでも同じである。

### Emet

Emet の関数から `vars` を直接読む手段は、この ADR では作らない（「メンテナーが決めること」の 6）。
関数には、今のとおり引数として渡す（`[= book.total(vars.prices)]`）。
`vars` の値は本の全体で一つに決まり、呼び出しの位置によらないので、ロードマップの未決事項が挙げた「呼び出しの位置の変数の状態に依存する」問題は `vars` にはない。
この点をロードマップの未決事項の「Emet の関数から `@set` の変数を読むこと」に書き足し、`vars` を読む要求の種類を足すかを、要求の種類の未決事項とあわせて残す。

### LSP

- 式の中の `vars.` の後ろで、`[vars]` のキーを補う。`meta.` の補完と同じ形で、表の中は `vars.author.` の後ろで補う。
- ホバーで `[= vars.product]` の評価の結果を表示するのは、今の式のホバーのままでよい。
- `manifest.toml` の変更で評価し直す。今の LSP は、`@table` の表のファイルを監視して評価し直すが、`manifest.toml` を監視する箇所は見つからなかった（[`syncWatches`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/modules/golem-lsp/src/Golem/Lsp/Server.hs#L333-L354) を読んだ。エディタでは確かめていない）。`manifest.toml` を表のファイルと同じく監視し、ディスクの内容が変われば、プロジェクトを読み直して評価し直す。エディタの未保存の内容は使わない（文脈を宣言したプラグインがあるときの `style.toml` の監視と同じ）。
- `[vars]` のキーの名前の変更（`manifest.toml` のキーと原稿の `vars.<名前>` を一度に書き換えること）は作らない。

### ドキュメント

- 仕様書の「マニフェスト」の節に `[vars]` の表を、「本文からの参照」の節に `vars` の名前空間を、柱の差し込みの表に `{vars.<名前>}` を足す。「名前のスコープ」の段落に、`vars` が名前空間を通してどこからでも見えることを書く。
- 仕様書の柱の節の「本の全体で同じ値を出したい場合は、変数を一つのファイルに置き、各章のファイルで `@import` する」を、`[vars]` に置く書き方に改める。
- [docs/markup.md](../markup.md) の予約された名前空間の一覧に `vars` を足す。
- [docs/diagnostics.md](../diagnostics.md) に G03109 から G03112 を足し、G02023 の予約語の一覧に `vars` を足す。
- 使い手のマニュアルの `@set` と `@import` の説明の近くに、本の全体で使う値は `[vars]` に置けることを書く。

## 実装しないこと

- 式で値を書くこと（`[vars] total = "[= 1 + 2]"` を評価すること）と、プロジェクトの変数を書く `.gm` を決めること。
- プロファイルごとに値を変えること。
- Emet の関数から `vars` を直接読むこと。
- 名前空間を付けずに `vars` のキーを読むこと（`[= product]` で `vars.product` を読むこと）。
- `[vars]` のキーの名前の変更を LSP で行うこと。
- `style.toml` のほかの欄（`[fonts]` のパスなど）から `vars` を読むこと。
- `meta` に自由なキーを足すこと。

## テスト設計

テストを先に書き、今の実装で失敗することを確かめてから実装する。

golem-project のテストでは、次のことを確かめる。

- `[vars]` の文字列、整数、真偽値、日付、配列、表が、上の表の値になること。今は G03001 になるので失敗する。
- 浮動小数点数、時刻、日時の値が G03109 になり、位置がその値であること。配列の要素と表の中の値でも同じであること。
- `edition-count`、`2nd`、`"日本語"` のキーが G03110 になること。
- `[vars]` がなければ、空の名前空間になること。

golem-eval のテストでは、次のことを確かめる。

- 二つの章のファイルが、どちらも `@import` なしで `[= vars.product]` を同じ値に評価すること。
- 見出しの中の `[= vars.product]` が評価されること（S0 の値）。
- `@set product = "x"` があるファイルで、`[= product]` と `[= vars.product]` が別の値になること。
- `@set vars = 1` と `@import a.gm as vars` が G02023 になること。
- `[= vars.missing]` が G02002 になること。
- `[= vars.author.short]` が表の中の値を引くこと。

golem-driver のテストでは、次のことを確かめる。

- 柱の `{vars.product}` が値を出し、`{vars.missing}` が G03111、`{vars.list}`（配列）が G03112 になること。`{vars.missing?}` は空になり、diagnostics を出さないこと。
- 二つの章を持つ本で、G03111 が章の数にかかわらず一度だけ出ること。
- `--profile prod` と dev で、`[vars]` の値が同じ出力になること。
- 決定性の検査（同じ入力から同じ出力のバイト列）が通ること。

golem-lsp のテストでは、次のことを確かめる。

- 式の中の `vars.` の後ろで `[vars]` のキーを補い、`vars.author.` の後ろで表の中のキーを補うこと。
- ディスクの `manifest.toml` の `[vars]` を変えたとき、`[= vars.product]` を使う原稿の diagnostics とホバーが新しい値になること。

## トレードオフ

値に式を書けないので、ほかの値から計算した値（`[vars]` の価格の合計など）は、使う章で `@set` の式にするか、Emet の関数に渡すことになる。
その代わり、値は TOML を読むだけで決まり、評価の順も循環も考えなくてよい。
LSP の補完も柱の検査も、原稿を評価せずに `manifest.toml` から作れる。

予約語に `vars` を足すので、今 `vars` を変数か名前空間の名前に使っている原稿は、G02023 で止まる。
v1.0.0 の前なので、互換を壊してよい期間に入れる。

浮動小数点数を拒むので、TOML で `ratio = 1.5` と書く書き手は、文字列か整数で書き直すことになる。
書いた数と組まれる数が違うことを、黙って許さないためである。

プロファイルで値を変えられないので、校正刷りにだけ「校正用」と入れるような使い方は、`[vars]` ではできない。
プロファイルが本文の値を変えるようになると、dev で確かめた本と prod で組んだ本の本文が違ってしまう。

## 決めたことの記録

- **プロジェクト全体の変数**（ロードマップ）：プロジェクトのどのファイルからも、`@import` なしで読める変数を宣言できるようにする。宣言の置き場所、参照の書き方と名前空間（`@set` の名前や `meta` と重なったときの扱いを含む）、名前空間を付けずに定義を展開する取り込みを認めない今の規則との関係、値に書ける型と式、`style.toml` の柱の差し込みから読めるか、プロファイルで値を変えられるか、LSP の補完と変更の扱いを ADR で決める。
- **Emet の関数から `@set` の変数を読むこと**（ロードマップの未決事項）：読む手段を要求の種類として足すか、「プロジェクト全体の変数」と合わせて決めるかが決まっていない。
- **すべての項目**（2026-11-07、メンテナー）：「推奨で問題ない」。「メンテナーが決めること」の 1 から 6 を、すべて推奨のとおりとした。

## メンテナーが決めること

すべて決めた（「決めたことの記録」）。

1. **宣言の置き場所**：決めた。推奨のとおり、`manifest.toml` の `[vars]` の表に書く（「決めたことの記録」）。値が評価の前に決まり、`meta` と同じ経路で読める。LSP の補完と柱の検査も、原稿を評価せずにできる。退けた案の一つは、プロジェクトの変数を書く `.gm` を `manifest.toml` で指し、その `@set` をすべてのファイルに見せることである。式は書けるが、そのファイルを先に評価する段階が増え、そのファイルの `@import` と `meta` の参照の順を決めることになる。もう一つは、`.emet` の定数を見せることである。関数の言語で値を宣言することになり、`.gm` の書き手に Emet を求める。
2. **名前空間の名前**：決めた。推奨のとおり、`vars` とし、表の名前と同じにする（「決めたことの記録」）。退けた案は、`meta` に入れること（`meta` は `[metadata]` の決まったキーの名前空間であり、キーが重なりうる。将来 `[metadata]` にキーを足すと書き手の値とぶつかる）、`project`（`manifest.toml` の設定そのものを指すと読める）、`global`（どこからでも見えるのは `meta` と `doc` も同じで、区別にならない）。名前を付けずに展開する案は、今の規則に反するので退ける。
3. **値に書ける型**：決めた。推奨のとおり、TOML の文字列、整数、真偽値、ローカルの日付、配列、表とし、浮動小数点数と時刻と日時を G03109 にする（「決めたことの記録」）。式は書かない。退けた案は、浮動小数点数を受け付けること（`Double` を経るので書いた値と違う有理数になりうる）と、文字列の値を式として評価すること（`"1 + 2"` が文字列か式かを書き手が区別できない）。
4. **柱から読めるか**：決めた。推奨のとおり、`{vars.<名前>}` の差し込みを足す（「決めたことの記録」）。本の全体で同じ値を柱に出すのが、この項目の動機の一つである。退けた案は、柱からは読まず `{set.<名前>}` だけにすること（すべての章のファイルに `@import` と `@set` が要るまま残る）。
5. **プロファイルで値を変えるか**：決めた。推奨のとおり、変えない（「決めたことの記録」）。退けた案は、`[vars.dev]` と `[vars.prod]` で上書きすること（プロファイルが本文の値を変え、dev で確かめた本と prod の本の本文が違う。今のプロファイルは、校正用のコメントのほかに原稿の本文を変えない）。
6. **Emet から読むか**：決めた。推奨のとおり、この ADR では読ませず、今のとおり引数で渡す（「決めたことの記録」）。`vars` は呼び出しの位置によらないので、読ませても結果は引数で決まる関数と同じく決定的だが、要求の種類を足すかは要求の種類の未決事項とあわせて決める。退けた案は、Emet の組み込みの値として `vars` を見せること（Emet の関数が `manifest.toml` に依存し、同じ `.emet` を別のプロジェクトで使うと結果が変わる）。
