# ADR 0040: PDF の図版の取り込みの資源の上限

ステータス: 採択→`Contents` の繰り返しの名指しの扱いと上限、テストの C3 は [ADR 0051](0051-reuse-repeated-pdf-content-streams.md)

## 文脈

golem-pdf は、`@figure` の PDF の図版を自分で読み、1 ページを Form XObject として写す（[golem-pdf ADR 0008](../golem-pdf/adr/0008-pdf-figures.md)）。
[docs/adr/0035](0035-security-hardening.md) は、ストリームの展開の上限を 256 MiB とした。
2026-10-18 のセキュリティ監査（[docs/audits/2026-10-18-security-audit.md](../audits/2026-10-18-security-audit.md)）で、この上限をすり抜ける入力と、上限のない処理が見つかった。

- C1：ページの木を DAG にすると、葉の訪問が深さの指数で増える。訪れた参照の集合を経路ごとに持つためである。
- C3：一つのストリームを `Contents` の配列で何度も名指しすると、展開の上限がその回数だけ倍になる。ICC のプロファイルのストリームも同じである。
- C4：Flate の TIFF の予測子の `Colors` を 65536 まで受け付け、行の処理が `Colors` に比例して遅い。
- C5：フィルタの列で Flate の後に ASCII85 を置くと、ASCII85 の展開に上限がない。
- C6：複数の改訂が `XRefStm` で同じ相互参照ストリームを指すと、そのたびに展開して `Map` を作る。
- C7：内容のストリームの小さなトークンの列で、トークンの列を全部持つために、入力の百倍を超えるメモリを使う。

いずれも、原稿のリポジトリに置いた小さな PDF で、`golem build` と `golem preflight` を止めるか、数 GB のメモリを使わせる。
C2（リテラル文字列の 8 進エスケープの二乗の時間）も同じ監査で見つかったが、仕様を変えずに直せるので、この ADR には含めない。

上限の決め方は、Golem の開発の方針に従う。
緩い規則より厳しい規則を選ぶ。
壊れた出力を生む緩い規則や、壊れうる設計は、入力を拒むことより悪いためである。
たとえば、同じ `Page` を二つの `Kids` から指す木は、PDF の仕様に反する。
これを読める PDF の道具は多いが、Golem は読まずにエラーにする。

## 実装すること

上限はすべて、ファイル一つの取り込み（`importPage`）の中で数える。
上限を超えた取り込みは、既存のエラー G08010 とし、理由を括弧の中に書く。
新しい diagnostic のコードは作らない。

### 展開の合計の上限

- 一つの図版の PDF の取り込みで展開したバイト数の合計を数え、256 MiB（2^28 バイト）を超えれば `展開した大きさが上限を超えました` の理由で止める。
- 数えるのは、フィルタの各段の出力である。Flate の出力、その後の予測子の出力、ASCIIHex と ASCII85 の出力を、それぞれ足す。
- 同じオブジェクトのストリームは、一度だけ展開して結果を使い回す。`Contents` の配列、ICC のプロファイル、Form XObject、相互参照ストリームのどれでも同じである。使い回した展開は合計に足さない。
- 一つのストリームの上限 256 MiB（`maxStreamBytes`）はそのまま残す。合計の上限と同じ値なので、どちらで止まっても理由は同じ文言にする。
- ASCII85 と ASCIIHex は、出力が上限に達した時点で止める。入力の全体を読んでから測らない。

### ページの木

- 訪れた参照の集合を、木の全体で一つ持つ。一度訪れたノードをもう一度指す参照は `ページの木` の理由で止める。
- 理由は、PDF の仕様がページの木のノードに `Parent` を一つだけ許すことによる。同じノードを二つの `Kids` から指す木は、正しい PDF ではない。
- 深さの上限 64 は変えない。
- 葉の数は、`page` のページに届いた時点で歩くのをやめる。それより後ろのページは数えない。

### 相互参照

- `XRefStm` が指す位置も、改訂の開始位置と同じ集合（`seen'`）に入れる。すでに見た位置を指す `XRefStm` と `Prev` は、読み直さずに空として扱う。
- 相互参照の項目の数の合計（表とストリームのすべての改訂を合わせたもの）が 8,388,607（PDF の仕様が定めるオブジェクト番号の最大）を超えれば、`相互参照` の理由で止める。
- 相互参照ストリームの `Size` の上限 1 億は、8,388,608 に下げる。

### 予測子

- `Colors` は 1 以上 32 以下、`BitsPerComponent` は 1、2、4、8、16 のどれか、`Columns` は 1 以上とする。外れれば `予測子` の理由で止める。
- 32 は、DeviceN の色空間の成分の数の上限である。
- TIFF の予測子の行の処理を、行の長さに比例する時間にする。これは仕様を変えないが、`Colors` の上限とあわせて同じ変更で直す。

### 内容のストリーム

- 内容のストリームの書き換えは、トークンの列を全部持たずに、入力を一度歩きながら出力を書く。
- 内容のストリームの大きさは、展開の合計の上限が限る。別の上限は設けない。

### ドキュメント

- `docs/diagnostics.md` の G08010 の節に、新しい理由（展開の合計、ページの木の重なり、相互参照の項目の数、予測子の値）を足す。
- 仕様書の図版の節に、取り込みの上限を書く。
- golem-pdf の仕様書に、上限の値と数え方を書く。
- 利用者向けマニュアルの図版の章に、PDF の図版の大きさの上限を書く。

## 実装しないこと

- 新しい diagnostic のコードを作ること。G08010 の理由で足りる。
- PDF のファイルの大きさの上限。ファイルの大きさは展開の合計で間接的に限られ、ファイルそのものは一度しか読まない。
- 展開の合計の上限を `manifest.toml` で変えられるようにすること。必要になれば別の ADR で足す。
- 画像のストリーム（DCTDecode など）の中身の検査。写すだけで展開しないので、合計には足さない。
- C2 の修正。仕様を変えないので、ADR なしで直す。

## テスト設計

ブランチ `security-audit-rc3-tests` の golem-pdf の SecuritySpec にあるテストが、修正の前に失敗し、修正の後に通ることを確かめる。

- C1：深さ 24 の DAG のページの木が、5 秒以内に G08010 の `ページの木` の理由で止まる。
- C3：8 MiB のストリームを 40 回名指しした `Contents` が、300 MiB 未満の割り当てで読める（展開は一度）。同じストリームを 40 回名指ししても合計は 8 MiB である。
- C4：`Colors` 65536 の予測子が `予測子` の理由で止まる。`Colors` 4 の 1 MiB のデータが 10 秒以内に読める。
- C5：Flate の後の ASCII85 で 320 MiB になる入力が、`展開した大きさが上限を超えました` の理由で止まり、割り当てが 300 MiB 未満である。
- C6：4 百万行の相互参照ストリームを四つの改訂が指す PDF が、256 MiB 未満の割り当てで読めるか止まる。
- C7：16 MiB の小さなトークンの内容が、入力の 16 倍未満の割り当てで書き換えられ、長さが変わらない。

これに加えて、次を足す。

- 展開の合計が 256 MiB をちょうど超える二つのストリームの `Contents` が止まり、超えない二つが読める。
- 同じオブジェクトを二度訪れるページの木（二つの `Kids` から同じ `Page` を指す）が止まる。
- 既存の fixture の PDF の図版の出力が、この変更の前とバイト列で同じである。

## トレードオフ

- 一つの PDF の図版が展開して 256 MiB を超えると使えなくなる。ベクターの図版でこの大きさになることはまずない。大きなラスタの画像を持つ PDF の図版は、画像のストリームを写すだけで展開しないので、合計に入らない。
- `Colors` を 32 に限ることで、仕様上は許される 33 成分以上の DeviceN の予測子つきの PDF は読めなくなる。実際にそのような PDF を作る道具は見当たらない。
- 同じ `Page` を二つの `Kids` から指す PDF は、今は読めるが、この変更でエラーになる。仕様に反する PDF であり、主要な PDF の道具もこれを修復の対象とする。`Count` を信じて一度だけ数える緩い読み方もできるが、開発の方針（緩い規則より厳しい規則）に従い、拒む。
- 内容のストリームの書き換えを一度の走査にすると、コードの構造が変わる。既存の fixture のバイト列の一致で確かめる。
