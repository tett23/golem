# ADR 0321: プリフライトの設定を読めない原因をコードで区別する

ステータス: 採択（未実装）

## 文脈

`golem preflight --rules rules.toml` は、ファイルがないときも未知のキーを書いたときも G09001 を返す。
前者を直すにはコマンドに渡すパスを変える。
後者を直すにはファイルの中のキーを変える。
現行の CLI で六つの入力を試すと、ファイル不在、不正な UTF-8、TOML の構文違反、キーの二重定義、未知のキー、値の誤りがすべて G09001 になった。

[diagnostics の一覧](../diagnostics.md) の全 409 節と生成済みの説明文を除く Haskell の実装を照合した。
試作の `experiments/diagnostics/catalog.tsv` は使用中の 402 件と廃止した 7 件について、説明の位置とコードの文字列が現れる行を記録する。
出現箇所の数だけで違う原因とは決められない。
たとえば G01001 は読むファイルの種類が違っても、直す対象は不正な UTF-8 のバイト列である。

一方、G02085 の空の表と列数の不一致、G06010 の存在しないプラグインと提供されないフィルタ、G08013 のリンクと通常のファイルには異なる対処がある。
G08010 は画像の読み込みと図版の PDF の取り込みの両方を含む。
これらはそれぞれ別の提案で実際の入力を比べる（[Golem ADR 0328](0328-table-file-shape-diagnostics.md)、[Golem ADR 0329](0329-output-path-file-diagnostic.md)、[Golem ADR 0330](0330-undeclared-plugin-and-missing-filter.md)、[Golem ADR 0331](0331-encrypted-figure-and-missing-page.md)）。

DTP オペレーターが残りの修正時間を見積もるには、独立した誤りを一度の実行で知る必要がある。
最初の一件を直すたびに次の一件が初めて表示されると、作業量を見積もれない。

## 実装すること

次の表に従い、読み込みで見つけた原因ごとに報告する。
スキーマとは、設定に書けるキーと、その値の型や範囲を定めたものである。
TOML を読み終えた場合は未知のキーと、知っているキーの不正な値をそれぞれの位置で報告する。

| 条件 | コード | 書き手が直す箇所 |
| --- | --- | --- |
| 明示したファイルがない | G09100 | `--rules` のパス |
| UTF-8 で読めない | G09101 | ファイルの符号化 |
| TOML の文法に合わない | G09001 | 括弧や引用符などの記法 |
| TOML の定義が衝突する | G09104 | キーやテーブルの再定義 |
| 未知のキー | G09103 | キー名 |
| 知っているキーの値がスキーマに合わない | G09102 | 指されたキーの値 |

自然数に負の値を渡したときは既存の G02103 を優先する。
暗黙の `preflight.toml` がない場合は従来どおり組み込みの設定を使う。
1.0.0 の前に新旧コードの対応を仕様書と `golem explain` に載せ、G09001 を条件にしている CI に移行方法を示す。
設定の読み込みで出る六つのエラーは、プリフライトの検査の重大度を選ぶ対象に加えない。

### 文法エラーから回復して後続の項目を読む

ファイルを開け、文字列として読めたら、TOML の文法エラーがあっても、終わりを識別できる項目を読み飛ばして次の項目から構文解析を続ける。
行番号や元のバイト位置は保持する。
読めたテーブルの既知の値と未知のキーは、それぞれスキーマで確かめる。
スキップしたキーの値を仮定して相関エラーを増やさない。
未知のキー、誤った値、文法エラーが同じファイルにあれば、拾えたものを一度に報告して終了コード 1 を返す。

複数行文字列に閉じる引用符がない場合、次の行頭の `[` だけでは新しいテーブルか文字列の一部かを判別できない。
信頼できる境界までの範囲を未検査とし、表示時には検出済みの件数と未検査範囲を分ける。
未検査部分をエラー 0 件として数えない。
構文に誤りがある設定をビルドに適用したり、その設定に依存する検査を成功扱いしたりしない。

この設定の TOML は `toml-parser` が読むため、今回の回復には peg-hs の変更は要らない。
一方、原稿の `.gm` には peg-hs を使う。
不正な見出しを二つ置いた原稿では、現行の `check` は両方の位置を返した。
原稿側で安全な再開位置を文法に指定しても一件で打ち切られる入力が見つかった場合は、その小さな文法、入力、期待する二か所を peg-hs で再現してから変更範囲を決める。

## 実装しないこと

G09001 を包括的な第二の diagnostic として併記しない。
ほかのコードの分割には、入力、直し方、現行コードと移行先を組にした検証が要る。
台帳の候補を一括で採択しない。

## 不変条件

1. D1〜D6：表の六つの条件を一つずつ作ったファイルからは、対応するコードだけを一度得る。
2. D7：スキーマまで読めた一つのファイルに未知のキーと不正な値があれば、双方の位置を保つ。

3. D8：境界が確定した不正な項目の後に独立な誤りがあれば、元の位置で両方を報告する。
4. D9：境界が確定できない範囲内の文字列から、次のテーブルのエラーを作らない。

| 境界の入力 | 結果 |
| --- | --- |
| ファイルなし、引数なし | 組み込みの設定 |
| ファイルなし、引数あり | G09100 |
| 1 バイトの `ff` | G09101 |
| `[` だけ | G09001 |
| 同じキーを二度定義 | G09104 |
| 一行で終わる値の文法違反二つとスキーマ違反二つ | 独立した四件 |
| 閉じない複数行文字列の中のテーブルらしい行 | 文法エラーと未検査範囲 |
| 有効なキーに未知の値、同じ表に未知のキー | G09102 と G09103 |

## テスト設計

未コミットの試作の `experiments/diagnostics/baseline.mjs` が入力と CLI の JSON 出力を作る。
`node experiments/diagnostics/expected.mjs experiments/diagnostics/baseline.json` の D1〜D6 は、現行の構文エラーだけが通る。
試作の D7 は未知のキーを一行目、不正な値を三行目に書き、コードと位置の組を確かめた。
本実装では G02103 の優先順位と、すべての新しいコードについて説明の登録を検査する。

D8 の [試作](../../experiments/diagnostics-review/probe.mjs) は、単独の行に閉じる不正な値を同じバイト数の空白に置いて読み直した。
一行目と四行目の G09001、二行目の G09103、六行目の G09102 をまとめて得た。
D9 は閉じていない複数行文字列を一件として打ち切った。
この試作が回復するのは境界の分かる単純な代入である。
本実装ではトークンの範囲を使い、一つの項目を二度読み飛ばさず、入力の長さに比例する走査にする。

## トレードオフ

G09001 を照合する CI は従来の六通りのうち五通りを拾わなくなる。
全設定エラーを止めたい CI は終了コードを使える。
原因ごとの案内を出す CI は対応表のコードを選べる。
