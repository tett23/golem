# ADR 0156: wasmtime を 49.0.5 に上げる

ステータス: 採択（未実装）

## 文脈

[2026-11-05 のセキュリティ監査](../audits/2026-11-05-security-audit.md) の V-01 は、Golem が固定する wasmtime 49.0.2 が、aarch64 でサンドボックスを逸脱しうる既知の脆弱性の対象であると報告した。
[CONTRIBUTING.md](../../CONTRIBUTING.md) は、固定したネイティブライブラリの版を上げるときに ADR を書くと定めている。
この ADR は、上げる版と、版を上げるときにそろえて変えるもの（取得の SHA-256、ライセンスの文書、キャッシュ、配布物、リンクした版の確かめ方）を決める。

### アドバイザリの確認

2026-11-05 に、GitHub の API（`gh api /repos/bytecodealliance/wasmtime/security-advisories/GHSA-mghf-wjfp-p5xm`）で公式のアドバイザリを読んだ。
監査の記述と食い違う点はなかった。

| 項目 | 値 |
| --- | --- |
| ID | GHSA-mghf-wjfp-p5xm、CVE-2026-115893 |
| 重大度 | critical（CVSS 3.1 9.9、`AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H`） |
| 公開 | 2026-10-19 |
| 影響する版（パッケージ `wasmtime`） | `<36.0.19, >=37.0.0, <48.0.7, >=49.0.0, <49.0.4` |
| 修正した版 | 36.0.19、48.0.7、49.0.4 |

アドバイザリは次のように述べる。
aarch64 で Cranelift を使うと、一つの `br_table` に約 256k を超える分岐先を持つモジュールを、条件分岐の飛び先を誤ってコンパイルする。
飛び先の位置はモジュールが決められるので、サンドボックスを逸脱しうる。
既定の設定の engine が対象である。

Golem の C のホストは、コンパイラーを指定せず（既定の Cranelift）、`wasmtime_module_new` でプラグインをコンパイルする（[golem_plugin.c#L41-L56](https://github.com/tett23/golem/blob/709b499ae29a0eb78515d67320f0924f996e4071/modules/golem-plugin/cbits/golem_plugin.c#L41-L56)）。
`loadPluginWith` は、コンパイルの後に import を検査し、`golem_abi_version` と `golem_describe` を実行する（[Plugin.hs#L277-L301](https://github.com/tett23/golem/blob/709b499ae29a0eb78515d67320f0924f996e4071/modules/golem-plugin/src/Golem/Plugin.hs#L277-L301)）。
誤ってコンパイルされた機械語は、import の禁止、fuel、メモリの上限の外で動く。
配布物のうち aarch64 のもの（macOS と Linux の musl）が該当する。
x86-64 は、このアドバイザリの対象ではない。

修正の差分（`v49.0.3...v49.0.4`）は、`br_table` の分岐先の数に 65520 の上限を設け、超えるモジュールをコンパイルの誤りとする（`crates/cranelift/src/translate/code_translator.rs`、`MAX_BR_TABLE_TARGETS`）。
上限の検査は機械語を作る前の翻訳で行うので、アーキテクチャーによらない。
上流の回帰テスト（`tests/all/br_table.rs`）は、分岐先が 65520 のモジュールが正しく動き、65521 のモジュールが `exceeds the implementation limit of 65520` で拒まれることを確かめる。

### 49.0.2 に当たるほかのアドバイザリ

同じ API で、2026-09-20 より後に公開されたアドバイザリの影響範囲をすべて見た。
49.0.2 は、GHSA-mghf-wjfp-p5xm のほかにも、49.0.3、49.0.4、49.0.5 で直ったアドバイザリの範囲に入る。
多くは WASI、wasi-http、component model のもので、Golem のホストはこれらを使わない。
ただし、コアの wasm に関わるもの（GHSA-wjc8-633q-pwxr「再帰する型の長い連鎖を捨てるときのスタックあふれ」、GHSA-p79w-pv2r-29qp「例外のタグ」、GHSA-3982-jqvv-277m「`i31` と `nullref` の引数」）が Golem のホストから届くかは確かめていない。
監査は公開情報の照合を三つのアドバイザリに限っており、これらを扱っていない。
49.0.5 は、49 系のアドバイザリをすべて直した版であり、2026-11-05 の時点で 49.0.5 を範囲に含むアドバイザリはない。

### 選べる版

| 版 | 公開 | サポートの終わり（上流の規則から計算） | Golem への影響 |
| --- | --- | --- | --- |
| 49.0.4 | 2026-10-19 | 2026-11-20 ごろ | 49.0.5 で直ったアドバイザリが残る |
| 49.0.5 | 2026-10-29 | 2026-11-20 ごろ | パッチ版の上げのみ。rustc は 1.98.0 のまま |
| 50.0.1 | 2026-10-29 | 2026-12-20 ごろ | メジャー版の上げ。C API のヘッダーに差分があり、rustc は 1.99.0 |
| 48.0.8（LTS） | 2026-10-29 | 2028-08-20 ごろ | 版を下げる。fuel の値（[ADR 0124](0124-filter-fuel-by-document-size.md)）を 49 で決めた |

上流の規則（`docs/stability-release.md`）は、12 の倍数の版を LTS として 24 か月、ほかの版を 2 か月サポートし、毎月 20 日ごろに新しいメジャー版を出すと定めている。
49.0.0 は 2026-09-21 に出たので、49 系は 51.0.0 が出る 2026-11-20 ごろにサポートを終える見込みである。
表の終わりの日付は、この規則から計算したもので、上流が日付を公表したものではない。

### 配布物の SHA-256

`scripts/fetch-wasmtime.sh` が取得する五つの配布物について、GitHub の release の API が返す `digest` を記録した。
49.0.2 の五つの `digest` は、今のスクリプトの SHA-256 と一致した。
49.0.5 の五つは、手元に取得して `shasum -a 256` で計算した値とも一致した。
取得した配布物は、どれも `include/wasmtime.h` の `WASMTIME_VERSION` が `"49.0.5"` で、`libwasmtime.a` の `rustc version` が 1.98.0 だった。

| 配布物 | SHA-256 |
| --- | --- |
| `wasmtime-v49.0.5-aarch64-macos-c-api.tar.xz` | `16bf4584b586bf18c708bf7b98cb94c415c0201575d5ad24860dcbdf83c213e5` |
| `wasmtime-v49.0.5-x86_64-linux-c-api.tar.xz` | `9dd9a5b4d29bfe172656e9c060ab494ce8db2c15e659351bd86ae891bb3bd330` |
| `wasmtime-v49.0.5-aarch64-linux-c-api.tar.xz` | `e9286bc2ec8e216aa63c7b4004fa1a7a786bd9e0b7541e70247210ec83f452ed` |
| `wasmtime-v49.0.5-x86_64-musl-c-api.tar.xz` | `a56728962f434ad6eed02c6b9313069b0044e2ac3143574bc9fa2c0f5cb2cebc` |
| `wasmtime-v49.0.5-aarch64-musl-c-api.tar.xz` | `2e2a6cb8cabf22f88f2dc52018ac0b048bfc9ba45b09455bb5b17af6588239b1` |

タグ `v49.0.5` のコミットは `805a0f15320e8836cf2b9f001b53d884bf866c89` である（`git ls-remote`、2026-11-05）。

aarch64-macos の `libwasmtime.a` のパニックの位置から取り出したクレートを 49.0.2 と比べると、`http` 1.3.1 が 1.5.0 に、`rustls` 0.23.37 が 0.23.46 に、`rustls-webpki` 0.103.13 が 0.103.15 に変わった。
ほかの二つの配布物と、シンボルから取り出すクレートは比べていない。

### リンクした版の確かめ方

`dist-newstyle` のキャッシュのキーは `cabal.project` と `cabal.project.freeze` の内容だけから作る（[ci.yml#L264-L268](https://github.com/tett23/golem/blob/709b499ae29a0eb78515d67320f0924f996e4071/.github/workflows/ci.yml#L264-L268)）。
cabal は `extra-lib-dirs` の下の `libwasmtime.a` の変化を見ないので、復元した `dist-newstyle` の `golem` が古い `libwasmtime.a` とリンクしたまま使われる可能性がある。
これを CI で確かめたことはない。

`libwasmtime.a` は `version: <wasmtime の版>` という行の文字列を持つ。
手元で、49.0.2 と 49.0.5 の五つの `libwasmtime.a`、49.0.2 とリンクした `golem`、それを `strip` したものを `strings -a` で見た。
どれも `^version: [0-9]+\.[0-9]+\.[0-9]+$` に当たる行をちょうど一つ持ち、値はその版だった。
リリースの `golem` は `strip` するが、この文字列は残る。

## 実装すること

### 版

wasmtime を 49.0.5 に上げる。
`scripts/fetch-wasmtime.sh` の `VERSION` を `49.0.5` にし、五つの SHA-256 を上の表の値にする。
SHA-256 は、実装者が配布物を取得して自分で計算し、上の表と一致することを確かめてから書く。

### 版を書いた箇所

次の箇所の 49.0.2 を 49.0.5 にする。

- `scripts/fetch-wasmtime.sh` の先頭の注釈
- `modules/golem-plugin/src/Golem/Plugin.hs` のモジュールの説明と、`modules/golem-plugin/golem-plugin.cabal` の注釈
- `README.md` の固定したライブラリの表
- 開発者向けマニュアルの `manual-dev/part1/05-plugins.gm`、`manual-dev/part2/07-modules.gm`、`manual-dev/part2/08-build-test.gm`

`golem-plugin.cabal` の注釈を変えると、cabal は `.cabal` の内容の違いから golem-plugin を設定し直す（[ADR 0147](0147-touch-setup-config-after-restoring-dist.md)）。
ただし、これで実行ファイルがリンクし直されるとは限らないので、下の「キャッシュ」の節の変更と、「リンクした版の検査」の節の検査を加える。

`scripts/release/test.sh` の 49.0.2 は、`licenses.sh` のテストのための偽の入力であり、固定した版とは関係しないので変えない。

### ライセンスの文書

[ADR 0007](0007-third-party-licenses.md) の手順に従う。

- `scripts/wasmtime-licenses.sh` の `VERSION` を `49.0.5` に、`COMMIT` を `805a0f15320e8836cf2b9f001b53d884bf866c89` にする。注釈の日付は実行した日にする。
- `RUSTC_VERSION`（1.98.0）と `COMPILER_RT_LICENSE_SHA256` は変えない。三つの配布物の rustc は 1.98.0 だった。スクリプトが rustc の違いで止まったら、この ADR の前提が崩れたので実装を止める。
- スクリプトを実行し、`licenses/wasmtime-v49.0.5/` を生成してコミットする。`c-objects.tsv` の構成要素の列は、49.0.2 の行を引き継ぎ、新しい行を手で埋める。
- `licenses/wasmtime-v49.0.2/` を消す。`licenses.sh` は `third_party/wasmtime/VERSION` の版のディレクトリだけを読むので、残しても使われない。

### キャッシュ

- `release.yml` の musl の wasmtime のキャッシュのキーは `hashFiles('scripts/fetch-wasmtime.sh')` を含むので、変えない。
- `ci.yml`（`build` のジョブの復元と、二つの保存）と `race.yml` の `dist-newstyle` のキーと `restore-keys` に、`hashFiles('cabal.project', 'cabal.project.freeze')` の後ろで `hashFiles('scripts/fetch-wasmtime.sh')` を加える。wasmtime の版を変えたプルリクエストは、古い wasmtime とリンクした `dist-newstyle` を復元しない。
- 手元の `third_party/wasmtime` は、`VERSION` の行が変わるので、`fetch-wasmtime.sh` が取得し直す（[ADR 0044](0044-release-workflow-hardening.md)）。

### リンクした版の検査

`scripts/check-wasmtime-linked.sh BINARY` を足す。

- `scripts/fetch-wasmtime.sh --expected` の出力の名前（`wasmtime-v<版>-<プラットフォーム>-c-api`）から版を取り出す。
- `strings -a BINARY` の行のうち `^version: [0-9]+\.[0-9]+\.[0-9]+$` に当たるものを集める。
- 集めた行がちょうど一つで、値が取り出した版と一致すれば終了コード 0 で終える。行がない、二つ以上ある、値が違う、のどれかなら、見つけた行と期待した版を標準エラー出力に書き、終了コード 1 で終える。

`ci.yml` の `build` のジョブ（x86-64 と aarch64）で、`cabal build` の後に `cabal list-bin golem` の実行ファイルに対して実行する。
`release.yml` の `smoke` のジョブで、展開した配布物の `golem` に対して実行する。

### 配布物と過去のリリース

- この ADR の実装を `main` に入れた後に作るリリースは、49.0.5 とリンクする。リリースの前に、[ADR 0035](0035-security-hardening.md) のとおりセキュリティ監査する。
- 公開済みの v0.1.0-rc1、rc2、rc3 は、どれも 49.0.2 とリンクしている。配布物は差し替えない。差し替えると、ビルドの来歴の証明とタグの中身が配布物と合わなくなる。
- 三つのリリースのノートの先頭に、次の内容の注意を英語で足す。aarch64 の配布物は GHSA-mghf-wjfp-p5xm（CVE-2026-115893）の対象であること、信頼できないプラグインを読み込まないこと、修正した版のリリースへのリンク。リンクは、修正した版のリリースを出したときに足す。

### ドキュメント

- 仕様書は wasmtime の版を書いていないので変えない。
- `docs/roadmap.md` は変えない。

## 実装しないこと

- 50.0.1 に上げること。C API のヘッダーに差分があり（aarch64-macos で 67 行）、rustc が 1.99.0 に変わるので、ライセンスの文書の手順の rustc と compiler-rt の固定も変わる。今回は緊急の修正であり、変える量を最小にする。
- 48.0.8（LTS）に下げること。版を下げると、49 で調べた fuel の値（[ADR 0124](0124-filter-fuel-by-document-size.md)）と C API の動きを確かめ直すことになる。
- wasmtime の版を追う方針（49 系のサポートが終わった後に、最新の版を追うか、LTS を追うか）。49 系は 2026-11-20 ごろにサポートを終える見込みで、その後のセキュリティの修正は 49 系に出ない。方針は別の ADR で決める。
- 既知の脆弱な版の固定を拒む検査。[ADR 0157](0157-check-wasmtime-pin-against-advisories.md) で決める。
- `br_table` の分岐先の数を Golem の側で制限すること。49.0.4 から wasmtime 自身が 65520 で拒む。
- 公開済みのリリースの配布物を作り直して差し替えること。理由は「配布物と過去のリリース」の節にある。
- Cranelift の代わりに Winch などのコンパイラーを選ぶこと。

## テスト設計

- golem-plugin のテストに、分岐先が 65521 の `br_table` を持つモジュールを足す。上流の `br_table_module` と同じ形の WAT を、テストの中で文字列として作り、`watToWasm` で wasm にする。`loadPlugin` が `CompileFailed` を返し、メッセージに `exceeds the implementation limit of 65520` を含むことを確かめる。49.0.2 ではコンパイルが通り、ABI の関数がないことで別の誤りになるので、このテストは版を上げる前に失敗する。機械語は実行しないので、49.0.2 の aarch64 でもテストは安全に失敗する。
- 同じ形で分岐先が 65520 のモジュールは、`CompileFailed` にならないことを確かめる（ABI の関数がない誤りになる）。上限の境界が wasmtime の側にあることを確かめるテストであり、Golem が上限を持つわけではない。
- `scripts/check-wasmtime-linked.sh` のテストを、[ADR 0078](0078-tests-for-release-and-hand-run-scripts.md) のスクリプトのテストに足す。`version: 49.0.5` の行を一つ持つファイルで成功し、行がないファイル、`version: 49.0.2` だけのファイル、`version: 49.0.5` と `version: 1.2.3` の二行を持つファイルで失敗する。
- `check-wasmtime-linked.sh` を、版を上げる前の `golem` に対して実行し、49.0.2 との不一致で失敗することを手で確かめる。
- 版を上げた後に、全モジュールのテスト（`scripts/test.sh`）を x86-64 と aarch64 の CI で通す。とくに golem-plugin の ABI、import の拒否、fuel（`FuelSpec`）、メモリとテーブルの上限、並行性（`ConcurrencySpec`）と、golem-driver のプラグインのテスト、サンプルのプラグインのテストを見る。fuel の消費は wasmtime の版で変わりうる。[ADR 0124](0124-filter-fuel-by-document-size.md) の fuel の値で落ちるテストがあれば、実装を止めて報告する。
- `scripts/release/test.sh` の `licenses.sh` のテストを通す。
- リリースのワークフローを手で一度動かし（`workflow_dispatch`）、三つの配布物の `licenses.sh` が `licenses/wasmtime-v49.0.5/` との照合を通ることと、`smoke` の `check-wasmtime-linked.sh` が通ることを確かめる。

## トレードオフ

- 49.0.5 は約 2 週間でサポートを終える見込みである。それでも選ぶのは、パッチ版の上げで C API と rustc が変わらず、今日から aarch64 の利用者を守れるためである。サポートの終わりの後に見つかる 49 系の脆弱性には修正が出ないので、版を追う方針の ADR を急ぐ必要がある。
- 49.0.4 ではなく 49.0.5 を選ぶ。49.0.5 で直ったアドバイザリが Golem に届くかは確かめていないが、パッチ版の差分はセキュリティの修正だけで、上げない理由がない。
- `dist-newstyle` のキーに `fetch-wasmtime.sh` の内容を加えるので、このスクリプトを変えるたびに `dist-newstyle` のキャッシュが当たらなくなり、全体をビルドし直す。スクリプトを変えるのは wasmtime の版を変えるときにほぼ限られる。
- `check-wasmtime-linked.sh` は、wasmtime が `version: <版>` の文字列を持つことに依存する。上流がこの文字列を変えると検査が失敗するが、そのときは黙って通るのではなく止まる。
- 過去のリリースの配布物は脆弱なまま残る。差し替えないので、ノートの注意を読まない利用者には届かない。

## 決めたことの記録

- **採択**：メンテナーが採択した（2026-11-05）。この ADR が決めてほしい点として挙げた項目は、どれも ADR の推奨のとおりとする。
