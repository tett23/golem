# ADR 0111: 数のリテラルの形をした引数の語を数として読む

ステータス: 採択（未実装）

## 文脈

コマンドの引数は、語（`3`、`kanji`）、文字列（`"a b"`）、式（`[= 1 + 2]`）、入れ子のコマンドのいずれかで書く。
評価器は、語を次の規則で値にしている（[`argValueRaw`](https://github.com/tett23/golem/blob/fa55dc76be6fef7189cb80883fd0bb0b0630911f/modules/golem-eval/src/Golem/Eval/File.hs#L1903-L1909)）。

- ASCII の数字だけの語は自然数。
- ほかの語は文字列。

この規則で値になった語を受け取るのは、`[number-text ...]` の数と、プラグインのコマンドの引数である。
自然数を求める箇所（`@blank-line` など）は、語を別の関数 [`numberWord`](https://github.com/tett23/golem/blob/fa55dc76be6fef7189cb80883fd0bb0b0630911f/modules/golem-parser/src/Golem/Parser/Lower.hs#L358-L369) で数のリテラルとして読み、先頭の `-` も許す（[ADR 0102](0102-natural-number-type.md)）。

二つの規則が食い違うので、同じ字の語が、書く場所によって違う値になる。

- `[number-text -3]` は、語が文字列の `"-3"` になり、G02019（`number-text に渡せるのは整数だけです`）になる。`[number-text [= -3]]` は -3 である。[docs/markup.md](../markup.md) は `[number-text ...]` の負の数に意味があるとするが、語では書けなかった。
- プラグインのコマンドの `[x 3.14]` は、プラグインに文字列の `"3.14"` が届く。`[x [= 3.14]]` は有理数の 157/50 が届く。見本のプラグイン `kansuji`（[docs/adr/0125](0125-kansuji-plugin-overrides-number-text.md)）を書いて、これが分かった。
- `@blank-line -1` は G02103 になり、語を数として読む。

`numberWord` 自体も、式の文法より緩い。
式の数のリテラルは `[0-9]+ ('.' [0-9]+)? ('e' [+\-]? [0-9]+)?` であり（[Golem.hpeg の 456 行め](https://github.com/tett23/golem/blob/fa55dc76be6fef7189cb80883fd0bb0b0630911f/modules/golem-parser/grammar/Golem.hpeg#L456)）、`.5` と `5.` は数ではない。
ところが `numberWord` が使う [`number`](https://github.com/tett23/golem/blob/fa55dc76be6fef7189cb80883fd0bb0b0630911f/modules/golem-parser/src/Golem/Parser/Lower.hs#L375-L400) は、文法を通った字を値にするための関数なので、形を確かめない。
`@blank-line .5` は 1/2 と読まれて G02104 になり、`@blank-line [= .5]` は構文の誤りになる。

### 範囲との関係

[ADR 0113](0113-closed-range-literal.md) は、閉じた範囲を `a...b` と書き、範囲を式の言語の値にすると決めた（この草稿を書いた時点では採択、未実装。今は実装済み）。
同じ ADR は、`lines` と `highlight` の語と文字列を、範囲を読む規則（カンマ、`...`、廃止予定の `-`）で読むと決めている。
`3...5` は引数の語の文法ではそのまま一つの語であり、語の文法は変えなくてよいとも確かめている。
この ADR の規則は、範囲を受け取る箇所の語の読み方を変えない。

## 実装すること

### 語を数として読む規則

引数の語が数のリテラルの形なら、同じ字を式に書いたときの数とする。

- 数のリテラルの形は、式の文法の数のリテラルに、先頭の `-` を一つだけ許したものである。`3`、`-3`、`3.14`、`-0.5`、`1e3`、`15e-1`、`007`、`-0` は数のリテラルである。
- 値と型は、同じ字を式に書いたときと同じにする（[ADR 0101](0101-rational-numbers-in-expressions.md)）。数字だけは自然数、`-` と数字は整数（自然数に単項の `-` を当てた式と同じ）、小数と指数は有理数である。`1e3` は値が整数でも有理数である。
- 数のリテラルの形でない語は、今までどおり文字列である。`+3`、`--3`、`.5`、`5.`、`3.1.4`、`1e`、`1-2`、`a3` は文字列である。

この規則を、`argValueRaw` で語を値にするすべての箇所に当てる。
今の箇所は `[number-text ...]` の数とプラグインのコマンドの引数であり、組み込みのコマンドが語を値として読む箇所を後で足すときも同じ規則になる。
名前を受け取る引数（`[style 名前: ...]` など）と、キーワード引数の値を字として読む箇所（`shape=`、コードブロックのキー）は、語を値にせずに字のまま読むので、変わらない。

### `numberWord` を文法に合わせる

`numberWord` は、語が上の数のリテラルの形のときだけ数を返す。
自然数を求める箇所の `.5` と `5.` は、数として読めない語として、各箇所の今のコード（`@blank-line` なら G02092）になる。
語を数として読む規則が二つあると同じ食い違いがまた起きるので、どちらも同じ形の検査を通す。

### diagnostic

新しいコードは作らない。
語と式で、同じ原因には同じコードを出す。

| 原稿 | 語の今のコード | 語のこの ADR のコード | 式のコード |
| --- | --- | --- | --- |
| `[number-text -3]` | G02019 | なし（-3） | なし（-3） |
| `[number-text 3.14]` | G02019 | G02019 | G02019 |
| `[number-text 1e3]` | G02019 | なし（1000） | なし（1000） |
| `[number-text 1e1301]` | G02019 | G02086 | G02086 |
| `[number-text abc]` | G02019 | G02019 | （式には書かない） |
| `@blank-line .5` | G02104 | G02092 | （`.5` は式の構文の誤り） |

- 評価の上限を超える数のリテラルは、今の数字だけの語と同じく G02086 とする（2026-10-28 の監査の F-01 の修正と同じ）。
- `int64` を超える数は、今と同じく、`[number-text ...]` では G02091、プラグインのコマンドでは呼ぶ前に G02091 である。

### 範囲の語

[ADR 0113](0113-closed-range-literal.md) の実装の後も、`lines` と `highlight` の語は、[ADR 0113](0113-closed-range-literal.md) の規則で読む。
語を値として読み、範囲を受け取らない箇所（`[number-text ...]` の数と、自然数を求める箇所）の語は、次のとおりにする。

- `<数のリテラル>...<数のリテラル>` の形の語（`3...5`、`-1...1.5`）は、範囲の値でも文字列でもなく、新しいエラー G02113 とする。メッセージは `範囲を受け取らない引数に範囲を書いています: <語>`、位置は引数である。
- 同じ箇所に式で範囲を書いた場合（`[number-text [= 1...3]]`、`@blank-line [= 1...3]`）も、この ADR の実装で G02113 とする。原因が「範囲を受け取らない引数に範囲を書いた」で同じだからである。[ADR 0113](0113-closed-range-literal.md) の実装（#467）は、この場合を各コマンドの型の誤りのまま残した。
- それ以外の `...` を含む語（`1...`、`a...3`、`1...2...3`）は、今までどおりである。`[number-text ...]` とプラグインのコマンドでは文字列、自然数を求める箇所では数として読めない語になる。
- `..` を含む語も今までどおりである。G01100 は、[ADR 0113](0113-closed-range-literal.md) のとおり範囲を受け取る箇所と式に限る。

[ADR 0113](0113-closed-range-literal.md) は、範囲を受け取らない引数に範囲の値を渡したときのコードを決めていない。
範囲を値として受け取る関数や演算子には G02007 と G02001 を当てているが、引数については書いていない。
そこでこの草稿は、語と式で共通の G02113 を提案する。
この ADR の実装は、範囲の値が範囲を受け取らない組み込みのコマンドの引数に届いたとき、各コマンドの型の誤り（`[number-text ...]` の G02019 など）ではなく G02113 を出すようにする。

プラグインのコマンドの引数は、[ADR 0113](0113-closed-range-literal.md) のとおり範囲の値を受け取れる（CDDL の `value` に `range` がある）。
したがってプラグインのコマンドは「範囲を受け取る箇所」であり、`<数>...<数>` の語は、同じ字の式（`[= 3...5]`）と同じ範囲の値としてプラグインに渡す。
試しの実装は、範囲の値が main に入る前だったので、プラグインのコマンドの語を G02113 にしていた。
この ADR の実装で、範囲の値に改める。

名前やキーワードの字として語を読む箇所（`[style 名前: ...]`、`shape=`、コードブロックのキー）は、語を値として読まないので、この規則の外である。

### ドキュメント

- docs/markup.md の「数の規則」の後に、数を受け取るほかの引数の語の段落を足す（試しの実装で足した）。
- docs/markup.md の「数の表記」の `[number-text ...]` の説明に、`[number-text -3]` と書けることを足す。
- 使い手のマニュアルの数の表記の節に、`[number-text -3]` の例を足す。

## 実装しないこと

- 先頭の `+` を許すこと。式の言語に単項の `+` がないので、語でも許さない。
- `--3` を 3 と読むこと。式では `--3` は二重の否定だが、語の数のリテラルは符号を一つしか持たない。
- 全角の数字や桁区切り（`1,000`）を数として読むこと。
- 語を文字列として受け取りたい引数のために、数として読むことを止める書き方。文字列が要るときは `"3.14"` と書く。

## テスト設計

試しの実装（ブランチ `arg-words-as-numbers`、origin/main の `fa55dc76` から分岐、コミット `cea31931`）で、次のテストを先に書き、失敗することを確かめてから実装した。

golem-eval の `FileSpec` の `argWordTests` では、次のことを確かめる。

- 引数の値を表示するプラグインのコマンドに、`12`、`-3`、`3.14`、`-0.5`、`1e3`、`15e-1`、`-0`、`007` を語と式（`[= ...]`）で渡すと、同じ値と型になる。`-3`、`3.14`、`1e3` は `VInt (-3)`、`VRat (157 % 50)`、`VRat (1000 % 1)` である。
- `+3`、`--3`、`3.1.4`、`1e`、`.5`、`5.`、`1-2`、`a3`、`1...`、`a...3`、`1...2...3` は文字列のままである。修正の前は、`.5` と `5.` が有理数になって失敗した。
- `[number-text -3]` が `[number-text [= -3]]` と同じ数のノードになり、`[number-text 1e3 style=kanji]` が 1000 の数のノードになる。
- `[number-text 3.14]` が G02019 で、メッセージも `[number-text [= 3.14]]` と同じである。
- `[number-text 1e1301]` が G02086 で、メッセージも `[number-text [= 1e1301]]` と同じである。`-1e1301` も G02086 である。
- `[number-text 1...3]`、`[number-text -1...1.5]`、`@blank-line 1...3` が G02113 になる（コミット `99afd4a0`）。修正の前は G02019 などになった。`1...`、`a...3`、`1...2...3` は今までどおり文字列である。
- `[number-text [= 1...3]]` と `@blank-line [= 1...3]` も G02113 になる。この二つは試しの実装の後に足すテストで、今の main では G02019 と G02092 になることを確かめてから実装する。
- 引数の値を表示するプラグインのコマンドに渡した `1...3` と `-1...1.5` の語が、`[= 1...3]` と `[= -1...1.5]` と同じ範囲の値になる。試しの実装の G02113 の期待は、このテストに改める。

golem-eval の `NaturalSpec` では、`@blank-line .5` と `@blank-line 5.` が、`@blank-line x` と同じ G02092 になることを確かめる。

既存の golem-parser、golem-eval、golem-driver、golem-lsp のテストは、変えずに通った。

## トレードオフ

数のリテラルの形の語を、プラグインは文字列として受け取れなくなる。
`[x 3.14]` で文字列の `"3.14"` を受け取っていたプラグインは、有理数を受け取る。
文字列が要るときは `"3.14"` と書けばよく、式と同じ値になる利点のほうが大きい。
ABI の形は変わらない（値の型が変わるだけである）。

`numberWord` を厳しくしたので、自然数を求める箇所の `.5` は、G02104（整数でない）から、数として読めない語のコードに変わる。
`.5` は式の文法では数ではないので、語でも数でないとするほうが、二つの書き方の規則が揃う。

範囲を受け取らない箇所で、範囲の形でない `...` の語を今までどおりに扱うので、`[number-text 1...]` は G02110 ではなく G02019 になる。
範囲を受け取る箇所では同じ語が G02110 になる。
コードが違うのは、前者の原因が「数でない値を渡した」、後者が「範囲の端がない」で、原因が違うからである。

プラグインのコマンドの `<数>...<数>` の語は、範囲の値になる。
今の main では文字列として渡るので、`[x 3...5]` で文字列の `"3...5"` を受け取っていたプラグインは、範囲を受け取るようになる。
数のリテラルの形の語と同じく、文字列が要るときは `"3...5"` と書けばよい。

## 決めたことの記録

- **語を数として読むか**：メンテナーが、`-3` と `3.14` の語を数として読む ADR を書くと決め、[ADR 0101](0101-rational-numbers-in-expressions.md) と [ADR 0102](0102-natural-number-type.md) の数のリテラル、[ADR 0113](0113-closed-range-literal.md) の範囲と整合させ、語と式の経路で一つの原因に一つのコードを保つよう求めた（2026-10-29）。
- **試しの実装の場所**：メンテナーが、評価器の中心の変更なので、origin/main から分けたブランチ `arg-words-as-numbers` で試すと決めた。
- **`numberWord` を文法に合わせるか**：メンテナーが、合わせると決めた（2026-10-29）。`.5` と `5.` は数でなくなり、`@blank-line .5` は G02092 になる。
- **範囲を受け取らない箇所の `<数>...<数>` の語**：メンテナーが、範囲の値でも文字列でもなく、ビルドのエラーにすると決めた（2026-10-29）。コードは、同じ箇所に式で範囲（`[= 1...3]`）を書いた場合と同じにする。[ADR 0113](0113-closed-range-literal.md) にそのコードがないので、この草稿で G02113 を提案した。試しの実装は、[ADR 0113](0113-closed-range-literal.md) の範囲の値を要らないので、語の部分を `arg-words-as-numbers` に入れた。式の部分は [ADR 0113](0113-closed-range-literal.md) の実装に残す。
- **プラグインのコマンドの `<数>...<数>` の語**：この草稿は、プラグインのコマンドの引数を [ADR 0113](0113-closed-range-literal.md) のとおり範囲を受け取る箇所と解し、[ADR 0113](0113-closed-range-literal.md) の実装の後は範囲の値にする案にした。メンテナーが、範囲の値とすると決めた（2026-11-04）。
