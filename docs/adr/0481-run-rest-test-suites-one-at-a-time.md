# ADR 0481: CI の rest の各脚でスイートを一つずつ実行する

Status: accepted

## 文脈

CI の tests-rest-a と tests-rest-b では、機能の試験がすべて成功しても、スイートの実行時間が既存の上限を超えて失敗している。
[root ADR 0457](0457-split-the-tests-rest-runner-in-two.md) が許す割り当ての変更だけでは、この失敗を解消できなかった。
そのため、同じ脚でスイートを同時に実行することをやめ、既存の上限を変えずに測り直す。

この ADR は root [ADR 0457](0457-split-the-tests-rest-runner-in-two.md) のスイートの実行方法を補足する。
[root ADR 0037](0037-ci-build-job-speedup.md) で対象外とした `cabal test` の並列度の変更を、rest の二つの脚に限って行う。
機能の試験、スイートごとの上限、CI 全体の 300 秒の予算は保つ。

## 調査した事項

実装 PR #1234 の head `85e65b113c3e73c39376cd1fbd6abc596f0e93b6` と、CI の実行 `46020165025` を調べた。
この head は、rest-a に Emet、geometry、typeset を置き、parser を含む残りを rest-b に置く。
両アーキテクチャの全 35 スイートの名前と試験数は、比較元の #1230 と一致した。
34 の Tasty スイートは合計 8717 件で、color は 18 checks と 1210 parity だった。

x86-64 の geometry は 59 件すべて成功したが、Tasty の表示で 11.40 秒かかった。
ラッパーの計測は 11 秒で、上限の 10 秒を超えた。
layout も 1784 件すべて成功したが、ラッパーの計測が 144 秒で、上限の 142 秒を超えた。
ARM64 の rest の両脚は成功した。
同じ変更で、typeset の x86-64 の 461 件は 8.53 秒で成功した。

現行の `.github/workflows/ci.yml` は、`test-suites.sh` の一覧を一度の `cabal test` に渡している。
各スイートは `suite-timeout.sh` を通り、実行中の経過秒数を上限と比べる。
待機時間を引く実装や、CPU 時間に置き換える実装はない。

これらの結果だけでは、同時実行が時間超過の唯一の原因とは断定できない。
直列化すれば各スイートが上限に収まるか、CI 全体が速くなるかは、実装後の測定事項である。

## 実装すること

rest-a と rest-b のテストの手順は、それぞれのスイートを一つずつ実行する。
`scripts/ci/run-rest-suites.sh` を追加し、引数として `rest-a` または `rest-b` を一つ受け取る。
このスクリプトは `test-suites.sh` を一度呼び、終了コードと出力を受け取ってから実行を始める。
一覧を取得できなければ、どのスイートも実行せず失敗する。

ジョブのキャンセルや手順全体の時間切れは、GitHub Actions の既存の停止に従う。
以下の全対象の実行と終了コードの規則は、そのような外部からの中断がない場合に適用する。

取得した一覧の順に、各対象について `cabal test --jobs=1 TARGET` を呼び、終了を待ってから次へ進む。
開始順序を変える別の一覧は持たない。
一覧が空なら、何も実行せず成功する。
スイートが失敗しても、後のスイートを実行する。
一つでも失敗したらスクリプトは終了コード 1、すべて成功したら 0 で終わる。
未知の引数や引数の過不足は、実行前に終了コード 2 で拒む。

`ci.yml` は rest の二つの脚でだけ、このスクリプトを呼ぶ。
driver の二つの脚は、従来の一覧を一度の `cabal test` に渡す。
ビルドの手順とその並列度は変えない。
Tasty と RTS の引数や環境変数も変えず、一つのスイートの内部の実行方法は保つ。

ラッパーは、今と同じく `cabal.project.local` の `test-wrapper` から使う。
個別の上限と停止条件、手順の 20 分の上限、外部ツール必須、公開書籍の試験、golden の新規作成禁止を保つ。
失敗した実行を自動で再試行する仕組みは追加しない。
README、仕様書、開発者向けマニュアルの CI の説明も同時に更新する。

## 実装しないこと

スイートの分割、試験の省略、試験の名前の変更、上限の引き上げは行わない。
matrix の 12 の脚、スイートの割り当て、生成物を照合する脚も、この ADR では変えない。
#1234 の割り当て変更は、root [ADR 0457](0457-split-the-tests-rest-runner-in-two.md) の範囲で別に検証する。
キャッシュ、runner の種類、GHC、cabal-install のバージョンは変えない。

## 不変条件

- I1: 各 rest の脚では、一覧に含まれる各対象を、一覧の順にちょうど一度呼ぶ。
- I2: 同じ脚では、前の `cabal test` が終了してから次の `cabal test` を開始する。
- I3: 一つ以上の対象が失敗しても、残りの対象を呼び、最終的に終了コード 1 を返す。
- I4: 一覧の取得が失敗した場合と、不正な引数の場合は、`cabal test` を一度も呼ばない。
- I5: 各呼び出しは `--jobs=1` と対象だけを指定し、既存のラッパーと試験用の環境変数を保つ。
- I6: driver の脚は従来の呼び出しを保ち、rest の両脚でだけ直列実行のスクリプトを使う。

| 入力 | 期待 | 不変条件 |
| --- | --- | --- |
| 空の一覧 | 呼び出しなし、終了コード 0 | I1 |
| 対象一つ、成功 | 一度実行し、終了コード 0 | I1, I5 |
| 対象二つ、両方成功 | 前の終了後に次を実行、終了コード 0 | I1, I2 |
| 三つのうち中央が失敗 | 三つとも実行、終了コード 1 | I1, I3 |
| 最初または最後が失敗 | 全対象を実行、終了コード 1 | I3 |
| 一覧の取得が部分出力後に失敗 | スイートを実行せず失敗 | I4 |
| 引数なし、未知の脚、余分な引数 | 実行せず終了コード 2 | I4 |
| driver の脚 | 従来の一覧を一度に渡す | I6 |

## 受けいれ条件

A1: 実装 PR の CI で、両アーキテクチャの rest の全スイートが、既存の上限を保ったまま成功する。
スイート名と試験数を #1234 のログと照合し、欠落と重複がないことを示す。
試験の追加による差がある場合は、その変更と件数を個別に示す。

A2: 各脚のテストの手順と個別スイートの時間を記録し、並列実行時と比較する。
成功後も root [ADR 0457](0457-split-the-tests-rest-runner-in-two.md) の 20 回の測定と 300 秒の予算の条件は残す。
直列化だけで予算に収まったとは扱わない。
既存の上限を超えるスイートが残った場合は、マージせず原因を調べ、必要な次の変更を別の ADR で決める。

A3: `--jobs=1` と対象ごとの呼び出しで、パッケージの設定が変わらないことを確認する。
CI のビルド済みの計画とテスト時のログを照合し、テストの手順で設定変更に起因する再ビルドがないことを示す。

## テスト設計

`scripts/ci/test.sh` で、対象の一覧を出すコマンドと `cabal` を一時ディレクトリのスタブに置き換える。
各スタブが開始と終了をログに書き、前の終了が次の開始より先にあることを確かめる。
I1 から I6 の名前を付けた試験を実装より先に書き、失敗を確認する。
空、一つ、複数、途中の失敗、部分出力後の一覧取得失敗、不正な引数を含める。
CI の分岐、既存のラッパー設定、試験用の環境変数が残ることも検査する。
CI の対象を静的に読む `ci-checks.sh` の検査も、新しい呼び出しから同じ全対象をたどれるように更新する。
A1 と A2 は、実際の GitHub Actions のログを `gh` で取得して確かめる。

## トレードオフ

スイート間の CPU とメモリの競合を減らせる可能性がある。
一方で、各スイートの起動と cabal の処理を繰り返すため、脚全体の時間が長くなる可能性もある。
この変更は、既存の時間上限を保つための測定可能な試行とし、速度改善を事前の保証にはしない。
