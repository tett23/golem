# ADR 0135: 範囲を受け取らない引数の範囲の語を、同じ字の式と同じに読む

ステータス: 採択

## 文脈

[docs/adr/0111](0111-argument-words-as-number-literals.md) は、引数の語が数のリテラルの形なら、同じ字を式に書いたときの数とし、語と式で同じ原因には同じコードを出すと決めた。
同じ ADR は、範囲を受け取らない引数（`[number-text ...]` の数と、自然数を求める箇所）に書いた `<数のリテラル>...<数のリテラル>` の語を G02113 にすると決め、テスト設計に `[number-text -1...1.5]` を G02113 の例として挙げた。

ところが、同じ字を式に書くと、G02113 にならない。
式は範囲の値を作るときに端と向きを調べ、作れなければその時点でエラーにする（[docs/adr/0113](0113-closed-range-literal.md)）。
範囲を受け取らないことを調べるのは、値ができた後である。
2026-11-04 に、`golem new` で作ったプロジェクトで確かめた結果は次のとおりである（コードは [97be81e8](https://github.com/tett23/golem/tree/97be81e8de344a22a15079b2e56bf0e5ce20ea62) と同じ 5db37cb9 から組んだ `golem`）。

| 原稿 | 語 | 式（`[= ...]`） |
| --- | --- | --- |
| `[number-text -1...1.5]` | G02113 | G02104 |
| `[number-text 1.5...3]` | G02113 | G02104 |
| `[number-text 7...3]` | G02113 | G02106 |
| `[number-text 1e1301...2]` | G02113 | G02086 |
| `@blank-line 1...1.5` | G02113 | G02104 |
| `@blank-line 7...3` | G02113 | G02106 |
| コードブロックの `numbers=7...3` | G02113 | G02106 |

語は、形だけを見て先に G02113 にする（[`plainArgValue`](https://github.com/tett23/golem/blob/97be81e8de344a22a15079b2e56bf0e5ce20ea62/modules/golem-eval/src/Golem/Eval/File.hs#L2135-L2145)、[`naturalArg`](https://github.com/tett23/golem/blob/97be81e8de344a22a15079b2e56bf0e5ce20ea62/modules/golem-eval/src/Golem/Eval/File.hs#L2176-L2187)）。
式は、値を作る段で G02104 か G02106 になる。
同じ字の語と式が別のコードになり、[docs/adr/0111](0111-argument-words-as-number-literals.md) の「語と式で、同じ原因には同じコードを出す」に反する。
[docs/adr/0111](0111-argument-words-as-number-literals.md) の例 `-1...1.5` は範囲として成り立たない値であり、ADR の二つの規則が両立しないことに、ADR を書いた時点で気づいていなかった。
実装はテスト設計の例に従った（[FileSpec.hs の 718 行め](https://github.com/tett23/golem/blob/97be81e8de344a22a15079b2e56bf0e5ce20ea62/modules/golem-eval/test/FileSpec.hs#L718)）。

ほかの箇所では、語と式はすでに揃っている。

- 範囲を受け取る箇所（`@listing` の `lines`、コードブロックの `highlight`）では、`7...3` の語は G02106、`1...1.5` の語は G02104 で、式と同じである（[docs/adr/0113](0113-closed-range-literal.md)）。
- プラグインのコマンドでは、語の `-1...1.5` を式の `[= -1...1.5]` と同じに読む（[`argValue`](https://github.com/tett23/golem/blob/97be81e8de344a22a15079b2e56bf0e5ce20ea62/modules/golem-eval/src/Golem/Eval/File.hs#L2116-L2133)、[FileSpec.hs の 729 行め](https://github.com/tett23/golem/blob/97be81e8de344a22a15079b2e56bf0e5ce20ea62/modules/golem-eval/test/FileSpec.hs#L729)）。

範囲を受け取らない箇所だけが、語を形で先に判定している。

2026-11-04 の監査（[docs/audits/2026-11-04-rc4-plugin-adr-conformance.md](../audits/2026-11-04-rc4-plugin-adr-conformance.md) の F-15）は、これを整理する ADR が要るとした。

## 実装すること

### 規則

範囲を受け取らない引数の `<数のリテラル>...<数のリテラル>` の語は、同じ字の式（`[= <語>]`）と同じく、まず範囲の値として作る。

1. 範囲の値を作れなければ、作るときのコードとする。端が整数でなければ G02104、始めが終わりより大きければ G02106、端が評価の上限を超えれば G02086 である。どれも、同じ字の式と同じメッセージである。
2. 範囲の値を作れれば、G02113 とする。メッセージの `<値>` は、今と同じく書いた語の字である。

| 原稿 | 今の語 | この ADR の語 | 式 |
| --- | --- | --- | --- |
| `[number-text 1...3]` | G02113 | G02113 | G02113 |
| `[number-text -1...1.5]` | G02113 | G02104 | G02104 |
| `[number-text 7...3]` | G02113 | G02106 | G02106 |
| `[number-text 1e1301...2]` | G02113 | G02086 | G02086 |
| `@blank-line 1...1.5` | G02113 | G02104 | G02104 |
| `@blank-line 7...3` | G02113 | G02106 | G02106 |
| `numbers=7...3` | G02113 | G02106 | G02106 |

これで、範囲の形の語は、範囲を受け取るかどうかによらず、どの箇所でも同じ字の式と同じ範囲の値として読まれる。
範囲を受け取らないことは、範囲の値ができた後に一か所で調べる。

範囲の形でない `...` を含む語（`1...`、`a...3`、`1...2...3`）は、[docs/adr/0111](0111-argument-words-as-number-literals.md) のとおり今までどおりとする。

### 実装の形

`plainArgValue` と `naturalArg` の語の枝は、`rangeWord` の形の判定で G02113 を返す代わりに、`argValue` と同じ経路で範囲の値を作る。
作れなければその diagnostic を返し、作れれば G02113 を語の字で返す。
語の範囲を作る処理は `argValue` にすでにあるので、新しい規則は足さない。

### 文書

- docs/diagnostics.md の G02113 の「意味」の「語では、`<数のリテラル>...<数のリテラル>` の形（`3...5`、`-1...1.5`）がこのコードになる」を、範囲として成り立つ語に限る文に改め、例から `-1...1.5` を除く。成り立たない語は G02104、G02106、G02086 になることを書く。
- docs/diagnostics.md の G02104 と G02106 の節に、範囲を受け取らない引数の語でもこのコードになることを足す。
- docs/markup.md の「範囲を受け取らない引数の範囲」の段落（今の 1104 行め）の例 `-1...1.5` を除き、同じ規則を書く。
- [docs/adr/0111](0111-argument-words-as-number-literals.md) のステータスの行に、「範囲として成り立たない範囲の語のコードは [ADR 0135](0135-range-words-read-as-range-expressions.md)」を足す。

## 実装しないこと

- 式の側を語に合わせること（値が範囲になる式を、値を作る前に構文で見分けて G02113 にする）。下の「検討した案」を参照。
- 範囲を受け取る箇所とプラグインのコマンドの振る舞い。すでに語と式が揃っている。
- G02113 の位置。`[number-text ...]` と自然数を求めるブロックコマンドではコマンドの位置になる件（監査の F-16）は、既存の慣行によるもので、この ADR では扱わない。

## テスト設計

golem-eval の `FileSpec` の `argWordTests` に、次のテストを先に書き、今の main で失敗することを確かめてから実装する。

- 上の表の G02113 でない六つの語が、同じ行の式と同じコードとメッセージになる。今の main では、語がどれも G02113 になって失敗する。
- `[number-text 1...3]`、`@blank-line 1...3`、`numbers=5...5` が、今と同じ G02113 で、メッセージの値が書いた語の字（`1...3`）である。
- `1...`、`a...3`、`1...2...3` の語が、今までどおりである。

[FileSpec.hs の 718 行め](https://github.com/tett23/golem/blob/97be81e8de344a22a15079b2e56bf0e5ce20ea62/modules/golem-eval/test/FileSpec.hs#L718) の `[number-text -1...1.5]` を G02113 とする期待は、G02104 に改める。

## トレードオフ

範囲を受け取らない箇所に成り立たない範囲を書いた書き手は、まず範囲の端か向きのエラー（G02104、G02106）を見る。
直して `1...3` にすると、次に G02113 を見る。
書き手の誤りの根は「範囲を書いたこと」であり、二度の修正を求めることになる。
それでも、同じ字の語と式が同じ結果になる規則を選ぶ。
式ではこの順を避けられず、語だけを先に G02113 にすると、語と式で別のコードになるからである。
規則も「範囲の形の語は、同じ字の式と同じ値」の一つで済み、箇所ごとの例外を持たない。

### 検討した案

- **今のまま（語は形で先に G02113）**：書き手に根の誤りを先に示せる。しかし語と式のコードが分かれ、[docs/adr/0111](0111-argument-words-as-number-literals.md) の原則に反する。範囲を受け取る箇所とプラグインのコマンドの語は式と同じに読むので、範囲を受け取らない箇所だけが例外になる。採らない。
- **式も先に G02113 にする**：引数の式の最上位が範囲の式（`[= 7...3]`）なら、評価の前に G02113 とする案である。`@set r = 7...3` の変数を `[= r]` で渡す場合は、`@set` の段で G02106 になるので揃わない。最上位が範囲かどうかで評価の順を変える特例が要り、[docs/adr/0102](0102-natural-number-type.md) の「解析してから評価する」経路に分岐が増える。採らない。
