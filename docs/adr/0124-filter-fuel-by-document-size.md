# ADR 0124: フィルタの命令の数の上限を文書の大きさに比例させる

ステータス: 採択

## 文脈

プラグインの一回の呼び出しには、実行できる命令の数に上限がある（[golem-plugin ADR 0001](../golem-plugin/adr/0001-wasm-host-and-abi.md)）。
今の上限は、コマンドにもフィルタにも同じ 10 億である（[`defaultFuel`](https://github.com/tett23/golem/blob/668ed3acc8df131ed53fdafe49200b4a8ed05d2d/modules/golem-plugin/src/Golem/Plugin.hs#L77-L78)）。

コマンドは原稿の一箇所の引数を受け取るので、仕事の量は呼び出しの数で決まる。
フィルタはファイル一つ分の文書を受け取るので、仕事の量はファイルの大きさとともに増える。
同じ上限では、短いファイルには余り、長いファイルには足りない。

総ルビのプラグイン（[docs/adr/0130](0130-sou-ruby-plugin.md)）を試すと、この差が実際に問題になった。
形態素解析で読みを振るフィルタは、高野聖の一章（原稿 162696 バイト）では上限に収まった。
しかし、それを二つつないだ章（325392 バイト）と四つつないだ章（650784 バイト）では上限を超え、G06009 になった。
上限がファイルの大きさによらないので、利用者は、組版の都合ではなくプラグインの都合で章をファイルに分けることになる。

### 使った命令の数を測る

ホストは、使った命令の数をどこにも出していなかった。
係数を決めるには数を測る必要があるので、ABI（wasm の取り決め）を変えずに読む経路を足した。

- C の `golem_plugin_call` が、呼び出しの後に wasmtime の残りの fuel を読み、使った数を返す（上限を超えたときは上限の全部）。wasm のモジュールから見える取り決めは変わらない。
- `Golem.Plugin.applyFilterFuel` が、フィルタの結果と使った数を返す。テストはこれで数を確かめる。
- 環境変数 `GOLEM_DEBUG_PLUGIN_FUEL` があれば、ホストは呼び出しごとに一行を標準エラーに書く（`golem-debug-fuel: mode=2 request=<要求のバイト数> fuel=<上限> used=<使った数> status=<結果>`）。出力のファイルと diagnostic は変わらない。手で測るための経路である。

### 測った値

パブリックドメインの fixture の十冊（一冊一章）と、高野聖を二つと四つつないだ章を、二つのルビのプラグインで組んで測った。

- 総ルビ（`sou-ruby`）：Lindera 6.2.0 と IPADIC。辞書（47.5 MB）をデータで渡し、利用者の TSV は渡さない。
- 初出ルビ（`first-ruby`）：fixture の原稿のルビから作った 3456 語の TSV を渡す。

表の「文書」は、フィルタに渡す文書の CBOR のバイト数（データを含まない）である。

| 章 | 原稿 | 文書 | sou-ruby | first-ruby |

| elements-of-style | 88123 | 112722 | 253646831 | 103992286 |
| frogs | 95741 | 153429 | 285668705 | 135474703 |
| haru-to-shura | 158006 | 246937 | 801185585 | 193809430 |
| ichiaku-no-suna | 82237 | 143281 | 456907837 | 155621173 |
| koya-hijiri | 162696 | 266021 | 756693758 | 228698159 |

| nightmare-abbey | 159265 | 185549 | 259734906 | 124729845 |

読み取れることは三つある。

- **データを読む分**：`sou-ruby` は、最も短い snark でも約 2.3 億を使った。要求の 47.5 MB の辞書を読み、Lindera の構造を作る分であり、文書の大きさによらない。
- **文書の 1 バイトあたり**：データを読む分（2.3 億）を除くと、`sou-ruby` は文書の 1 バイトあたり最大で約 3400（taira-no-masakado）、`first-ruby` は最大で約 1500（snark、TSV を読む分を含む）だった。和文の章が重く、英文の章は軽い。
- **プラグインの作りの影響**：測る前の `first-ruby` は、照合で語の長さごとに文字列を作っていたので、英文の nightmare-abbey で 22.7 億を使い、今の上限でも止まった。最初の文字で候補を絞る作りに直して、1.2 億になった。上限を決める値には、直した後の数を使った。

## 実装すること

フィルタの一回の呼び出しの上限を、次の式にする。

```
上限 = 10 億 + 10000 × 文書のバイト数
```

- **文書のバイト数**は、フィルタの要求に入れる文書の CBOR のバイト数である。データ（[docs/adr/0105](0105-plugin-data.md)）は数えない。
- **10 億**は、コマンドの上限（`defaultFuel`）と同じ値で、どのフィルタにも最低限これだけを与える。データを読む分（47.5 MB で約 2.3 億、64 MiB のデータでは比例させて約 3.2 億と見込む）もここに収まる。
- **10000**は、測った最大の約 3400 の約 3 倍である。
- コマンドの上限は変えない。
- 上限は文書のバイト列だけで決まり、文書は原稿とデータから決定的に決まるので、決定性は保たれる。同じ入力からは、同じ位置で同じ G06009 になる。

この式で、測った十二の章はどれも上限に収まった。
余裕（上限を使った数で割った値）が最も小さいのは `sou-ruby` の taira-no-masakado で 3.4 倍、止まっていた二つの章は 5.0 倍だった。
`first-ruby` の余裕は、どの章でも 15 倍以上だった。

### 止まらないフィルタが止まるまで

上限を大きくすると、止まらないフィルタが G06009 になるまでの時間が延びる。
無限ループのフィルタ（golem-plugin のテストの `loop-filter.wat` のメモリを広げたもの）に、高野聖を四つつないだ章と同じ大きさの文書（1107025 バイト）を渡すと、上限は約 121 億になり、1.63 秒で G06009 になった（macOS arm64 の手元、一回）。
ループの命令は軽いので、メモリを読み書きする命令の多いフィルタでは、同じ数の命令にもっと時間がかかる。
`sou-ruby` は高野聖を四つつないだ章で 24 億の命令を使い、ビルドの全体が 2.55 秒だったので、上限まで回り続けても十数秒で止まる見込みである（上限まで回る `sou-ruby` は作れないので、測っていない）。

### 名前と場所

- `Golem.Plugin` に、係数 `fuelPerDocumentByte`（10000）と、上限を求める `filterFuel` を置く。`applyFilter` は `filterFuel` の上限で呼ぶ。
- 使った数を読む経路（`applyFilterFuel`、`GOLEM_DEBUG_PLUGIN_FUEL`）は、上の「使った命令の数を測る」のとおりに置く。
- golem-* の build-depends は変えない。

## 実装しないこと

- 利用者が `manifest.toml` で上限を変えること。本ごとの設定にすると、同じプラグインが本によって動いたり止まったりする。
- プラグインが `golem_describe` で上限を求めること。プラグインが自分で上限を外せることになる。
- データの大きさに比例させること。データを読む分は、64 MiB の上限まで 10 億の内に収まる。
- メモリの上限（256 MiB）を変えること。測った章では、メモリの上限には届かなかった。
- 使った命令の数を、`golem build` の出力や JSON の diagnostics に出すこと。測るための経路は、標準エラーの一行だけにとどめる。

## テスト設計

テストを先に書き、`filterFuel` と `applyFilterFuel` がないためにコンパイルできないことを確かめてから実装した。
加える式を `max` から和に変えたときも、テストを先に直して失敗させた。

golem-plugin のテスト（`modules/golem-plugin/test/FuelSpec.hs`）では、次のことを確かめる。

- `fuelPerDocumentByte` が 10000 であり、`filterFuel` が下限と係数の和になること。
- 下限がコマンドの上限（`defaultFuel`）と同じであること。
- 無限ループのフィルタが、小さな文書でも大きな文書でも上限をちょうど使い切って G06009 になり、大きな文書のほうが多く使うこと。同じ文書で二度呼んで同じ数になること。
- 終わるフィルタが、上限より少ない、0 より多い数を返すこと。

既存の「無限ループが毎回同じ位置で止まる」テストは、そのまま通る。

手で確かめたこと：上の表の十二の章を、上の式で組み、すべて G06009 なしで終わることを確かめた（`GOLEM_DEBUG_PLUGIN_FUEL` の行の `status=0`）。

## トレードオフ

上限が延びるので、止まらないフィルタが止まるまでの時間は、長いファイルで延びる。
係数を測った最大の約 3 倍に置いたので、止まるまでの時間は、正常に終わるときの数倍にとどまる。

係数は、二つのルビのプラグインと十二の章だけから決めた。
形態素解析より重い処理をするフィルタは、この係数でも足りないおそれがある。
足りないと分かれば、別の ADR で係数を上げる。

上限を、原稿のバイト数ではなく文書の CBOR のバイト数に比例させた。
CBOR のバイト数は `golem-plugin` の中で求められ、driver に原稿の大きさを渡す変更が要らない。
その代わり、コマンドが返した断片や `@import` の値も上限に数えられ、原稿の大きさだけでは上限が決まらない。
どちらも原稿とデータから決定的に決まるので、決定性は損なわれない。

`GOLEM_DEBUG_PLUGIN_FUEL` は、環境変数で振る舞いを足す。
足すのは標準エラーへの一行だけで、出力と diagnostic は変えない。

## 決めたことの記録

- 2026-10-29、メンテナー：上限を文書の大きさに比例させる方針は、上限が十分に大きければよい。使った数を読む経路を ABI を変えずに足し、二つのルビのプラグインで fixture と止まっていた章を測り、余裕を持った係数と下限を選ぶこと。止まらないフィルタが有限の時間で止まることも確かめること。この ADR の値は、その指示で測って決めた。
