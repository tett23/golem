# ADR 0174: 1.0.0 から互換を守る範囲と、廃止の手順

ステータス: 採択（未実装）

## 文脈

ロードマップは、v0.1.0-rc4 の後に v1.0.0 を出すと予定している（[docs/roadmap.md](../roadmap.md) の「リリースの予定」）。
1.0.0 までは互換を壊してよいが、1.0.0 から何を守るかは決まっていない。
v0.1.0-rc4 の「1.0 で約束すること」は、守る対象（原稿の記法、CLI、`style.toml`、出力のバイト列、プラグインの ABI と CBOR、JSON の diagnostics、diagnostic のコード、LSP）と、壊してよい条件、廃止の手順を ADR で決める、とする。
[2026-10-20 のロードマップのレビュー](../audits/2026-10-20-roadmap-review.md) も、この ADR がないことを致命的な点の一つに挙げた。

### 今の規則

バージョンの規則は、1.0.0 より前のことしか書いていない。
仕様書の「バージョン」の節は、「1.0.0 までは、原稿の記法、CLI、出力の互換性を壊す変更で `Y` を、それ以外の変更で `Z` を上げる」とする（[仕様書の「バージョン」](../specifications.md#バージョン)）。
1.0.0 の後に、どの変更でどの桁を上げるかは書いていない。

廃止の手順は、仕様書と [docs/diagnostics.md](../diagnostics.md) の「廃止予定の手順」にある（[golem-syntax ADR 0002](../golem-syntax/adr/0002-notice-severity.md)）。

1. 廃止を決める ADR で、廃止予定の notice のコードを決める。
2. その notice を出すバージョンを、少なくとも一つの minor のバージョンとしてリリースする。プレリリースは数えない。
3. 次の ADR で、その書き方をエラーにする。

この手順は、0.1.0 の次が 1.0.0 だと成り立たない。
これまでのリリースは `v0.1.0-rc1` から `v0.1.0-rc3` の三つで、どれもプレリリースである（`git tag` で確かめた）。
rc4 の次が 1.0.0 なら、1.0.0 より前に、手順の 2 を満たすリリースはない。
1.0.0 の後は、書き方をエラーにすると互換を壊すので、手順の 3 を minor で行えない。
今の規則のままだと、廃止予定の書き方は 1.x のあいだずっと残る。

廃止予定の書き方は、今は二つある。

- `@listing` の `src=`（G02065）。v0.1.0-rc2 から notice を出している（rc2 のコードは 4 桁の G0265）。
- `lines=10-20` のような `-` で区切った範囲（G02108、[ADR 0113](0113-closed-range-literal.md)）。rc3 の後に main に入り、まだどのリリースにもない。

fixture の `sample` を写して `@listing src=front.gm` と `@listing front.gm lines=1-2` を加え、`~/.local/bin/golem check`（`golem --version` は `golem 0.1.0-rc3`）で、二つの notice が出ることを確かめた（2026-11-06）。
ロードマップの未決事項「`-` で区切った範囲をエラーにする時期」は、この ADR を待っている。

### 互換に関わる今の振る舞い

守る対象を決めるために、それぞれが今どうなっているかを調べた。

- **出力のバイト列**：同じ入力と同じバージョンからは、同じバイト列を得る（[ADR 0002](0002-determinism.md)）。PDF の Producer とインスタンス ID は Golem のバージョンを含むので、バージョンを変えると PDF のバイト列はかならず変わる（[仕様書の「メタデータ」の節](../specifications.md#メタデータ)、[`Fonts.hs`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/modules/golem-driver/src/Golem/Driver/Pdf/Fonts.hs#L176-L182)）。Golem のバージョンを出力に書くのはここだけである（`golemVersion` を使う箇所を `rg` で探した）。見た目の回帰テストの参照は、`VERSION` だけを変えても変わらない（[ADR 0094](0094-visual-regression-page-hashes-at-72-dpi.md)）。
- **意味論 IR とプラグインの ABI**：プラグインとホストは、意味論 IR を CBOR にして受け渡す。IR の正本は CDDL であり（[golem-doc ADR 0001](../golem-doc/adr/0001-semantic-ir-in-cddl.md)）、IR を変えれば ABI も変わる。ABI のバージョンは、リリースごとに、変えたときだけ一つ上げる（[ADR 0052](0052-plugin-abi-version-bump-rule.md)）。ホストは、プラグインの返すバージョンが自分のものと違えば読み込まない。ABI のバージョンは、rc1 で 3、rc2 で 6、rc3 で 7、今の main で 8 である（各タグの `Golem.Doc.IR` の `abiVersion` で確かめた）。今まで、プレリリースのたびに、すべてのプラグインが読み込めなくなった。
- **diagnostic のコード**：一度使った番号は、ほかの意味に使い回さない。使わなくなったコードは、節を消さずに状態を「廃止」にする（[docs/diagnostics.md](../diagnostics.md) の「番号の区分」）。マニフェストの `silence-notices` に notice でないコードを書くと G03024 のエラーになる。上の fixture の写しに `silence-notices = ["G02065", "G01001"]` を書き、`G01001` に G03024 が出ることを確かめた。notice のコードを廃止にすると、それを `silence-notices` に書いたプロジェクトは組めなくなる。
- **JSON の diagnostics**：一つの diagnostic は、`code`、`severity`、`span`、`message`、`related`、`fixes` を持ち、事実を持つものだけが `facts` を持つ（[仕様書の「構文木と diagnostics」](../specifications.md#構文木と-diagnostics)）。`facts` と重大度 `info` は後から足した（[golem-cli ADR 0006](../golem-cli/adr/0006-preflight.md)、[ADR 0104](0104-info-severity.md)）。
- **Emet とエディタ向けの構文の定義**：関数の言語 Emet（[ADR 0160](0160-emet-function-language-core.md)）と、`tools/editors/` の構文の定義（[ADR 0170](0170-emet-editor-support.md)）は、rc3 の後に入った。`v0.1.0-rc3` のツリーには `modules/golem-emet` も `tools/editors` もない（`git ls-tree` で確かめた）。どちらも、利用者が手にする最初のリリースは rc4 になる。Emet を使うのは、`.emet` のファイルのほかに、マニフェストの `[functions.requires]` と `[[filters]]` の `function`、`.gm` の `.emet` を取り込む `@import` とその名前空間を通した呼び出しである（[仕様書の「関数の言語 Emet」](../specifications.md#関数の言語-emet)）。Emet のコードは `E` で始まる（[docs/diagnostics.md](../diagnostics.md) の「番号の区分」）。
- **LSP**：LSP は、初期化のときにサーバーとクライアントが、使える機能を互いに知らせる（LSP 3.17 の `initialize`）。機能を足しても減らしても、クライアントは知らされた機能だけを使う。

### 仕様書の長さ

仕様書は 4,054 行ある（`wc -l` で数えた）。
約束を仕様書の一節に書くと、利用者とプラグインの開発者が、互換の範囲を確かめるために仕様書の全体を探すことになる。
メンテナーは、互換性を扱う専用の文書を `docs/` に作ると決めた（「決めたことの記録」）。

## 実装すること

### 互換性の文書

`docs/compatibility.md` を作り、この ADR の約束を書く（「メンテナーが決めること」の 9）。
仕様書は、「バージョン」の節からこの文書にリンクするだけにし、約束の中身を写さない。

文書には、次の節を置く。

- 1.x で守ること（下の表）
- 互換を壊してよい条件
- バージョンの付け方
- 廃止の手順と、廃止予定の書き方の一覧
- 予告している ABI の変更
- 約束しないもの（Emet、LSP、エディタ向けの構文の定義、Haskell のパッケージの API）

### 1.x で守ること

1.0.0 から 1.x の最後までのあいだ、次のものを守る。
「守る」とは、1.a で使えたものが、b が a より大きい 1.b でも、同じ意味で使えることをいう。
古いバージョンで新しいバージョンの書き方を読めること（前方の互換）は約束しない。

| 対象 | 守ること | 守らないこと |
| --- | --- | --- |
| 原稿の記法（`.gm`） | 1.a でエラーなく組めた原稿は、1.b でもエラーなく組め、同じ意味になる。記法を足すときは、それまでエラーだった形にだけ足す | 警告、notice、info を足すこと。Emet を使う書き方（下の Emet の行） |
| `manifest.toml`、`style.toml`、`preflight.toml`、`plugins.lock` | 受け付けたキーと値は、同じ意味で受け付ける。組み込みのプリフライトの設定 `print` の値を、検査が厳しくなる向きに変えない | キーを足すこと。値の既定を変えること（出力を変えるので、出力の規則に従う）。Emet を指すキー（下の Emet の行） |
| CLI | コマンド、オプション、オプションの値、終了コード（0、1、2）の意味、`golem --version` の一行の形 | コマンドとオプションを足すこと。人が読む形の diagnostics、ヘルプ、使い方の表示の文言。`golem inspect` の `--as cst`、`--as ast`、`--as ir` の表示。`golem new` の雛形の中身。`golem lsp` |
| 出力（PDF、HTML、EPUB、プレーンテキスト） | 同じバージョンと同じ入力からは、同じバイト列を得る。patch のバージョンは、Golem のバージョンから作る値（PDF の Producer とインスタンス ID）のほかに、出力を変えない（「メンテナーが決めること」の 1） | minor のバージョンで、組版の結果を変えること |
| 意味論 IR | なし | minor のバージョンで変えること（「メンテナーが決めること」の 2）。IR はプラグインの ABI なので、変えるときは ABI の手順に従う |
| プラグインの ABI と CBOR | ABI を変えるのは、予告した後の minor のバージョンに限る。予告では、どこがどう変わるかを開発者に示す。patch のバージョンは ABI を変えない。`golem inspect --as cbor` のバイト列も ABI の CBOR である | 予告した後の minor のバージョンで、ABI のバージョンを上げること。そのとき、古い ABI のプラグインは読み込めなくなる |
| JSON の diagnostics（`--format json`） | キーと値の型。重大度の値は `error`、`warning`、`notice`、`info` の四つに限る | キーを足すこと（読む側は知らないキーを読み飛ばす）。`message` の文言（「メンテナーが決めること」の 5） |
| diagnostic のコード（`G` で始まるもの） | 使用中のコードの意味。1.x のあいだ、コードを廃止せず、分けず、重大度をエラーの側へ上げない（「メンテナーが決めること」の 5） | コードを足すこと。重大度を下げること。docs/diagnostics.md と `golem explain` の文言 |
| 関数の言語 Emet | なし。1.x のあいだ、実験的な機能とする（「メンテナーが決めること」の 7） | すべて（範囲は「メンテナーが決めること」の 12） |
| LSP | なし（「メンテナーが決めること」の 8） | すべて |
| エディタ向けの構文の定義 | なし（「メンテナーが決めること」の 8） | すべて |
| Haskell のパッケージの API | なし | すべて。golem のパッケージは Hackage に出さず、`golem` の実行ファイルだけを配る |

### 互換を壊してよい条件

1.0.0 の後に互換を壊してよいのは、次の三つの場合に限る。
上の表の「守らないこと」と、予告した ABI の変更は、互換を壊すことに当たらない。

- **major のバージョン**：`X` を上げるリリースでは、上の表のどれを変えてもよい。変えたものは、ADR とリリースノートの「互換を壊す変更」の項に書く。
- **セキュリティの修正**：どのバージョンでもよい。互換を壊した理由を ADR に書き、リリースノートの「互換を壊す修正」の項に挙げる。
- **仕様に反する振る舞いの修正**：仕様書か ADR がエラーとする入力を受け付けていた、仕様と違う出力を作っていた、という不具合は、minor のバージョンで直す（「メンテナーが決めること」の 6）。出力を変える修正は patch では行わない。リリースノートの「互換を壊す修正」の項に挙げる。仕様が振る舞いを定めていなかった箇所は、この条件に当たらない。

### バージョンの付け方

1.0.0 の後の規則を、互換性の文書に書く。

- 互換を壊す変更（セキュリティの修正を除く）で `X` を上げる。
- 足すだけの変更、出力を変える変更（仕様に反する振る舞いの修正を含む）、意味論 IR と ABI の変更、廃止の予告で `Y` を上げる。
- 出力を変えない修正で `Z` を上げる。

1.0.0 より前の規則（互換を壊す変更で `Y` を上げる）は、仕様書の「バージョン」の節に残す。

### ABI の変更の予告

ABI は、予告した後でだけ変える（「メンテナーが決めること」の 2 と 10）。

1. ABI を変える ADR で、変更の中身を決める。
2. その ADR の後の最初の minor のリリースで、変更を予告する。予告は、互換性の文書の「予告している ABI の変更」の節と、リリースノートの「予告」の項に書く。このリリースでは ABI をまだ変えない。
3. 予告を載せたリリースより後の minor のリリースで、ABI を変え、ABI のバージョンを一つ上げる。

予告には、次のことを書く。

- 新しい ABI のバージョンの番号。互換性の文書では、`### ABI のバージョン 9` のように、番号を見出しにする。
- 変わる CDDL の規則と、変更の前と後の CDDL の差分。
- 変わる要求と応答（コマンド、フィルタ、チャネル、データのどれか）と、プラグインの側で直すこと。
- 予告の元になった ADR へのリンク。

ABI を変えたリリースの後、その予告は互換性の文書から消し、リリースノートに残す。

### 廃止の手順

仕様書と docs/diagnostics.md の「廃止予定の手順」を、次のように書き直す（「メンテナーが決めること」の 3 と 11）。

1. 廃止を決める ADR で、廃止予定の notice のコードを決める。メッセージと docs/diagnostics.md の書き方は今のとおりとする。
2. 1.0.0 の後は、その notice を minor のバージョンで出し始めることで、廃止を予告する。予告した書き方は、1.x のあいだ受け付け続け、出力も変えない。リリースノートの「変更」の項と、互換性の文書の廃止予定の一覧に挙げる。
3. 次の major のバージョンで、ADR を作ってその書き方をエラーにする。エラーには新しいコードを割り当て、notice のコードは状態を「廃止」にする。`silence-notices` にそのコードを書いたプロジェクトは G03024 になるので、リリースノートに、その行を消すよう書く。
4. 1.0.0 より前は、手順の 2 の「minor のバージョン」を「プレリリースを含むリリース」と読み替える。notice を少なくとも一つのリリースで出した後なら、次のリリースでエラーにしてよい。

1.0.0 より前に minor のリリースはない（rc4 の次が 1.0.0 である）ので、手順の 4 がなければ、1.0.0 より前に廃止を予告できない。
1.0.0 より前は互換を壊してよいので、予告を minor に限る決まりは 1.0.0 の後にだけ当てる。

### 1.0.0 の時点の廃止予定

1.0.0 には、廃止予定の書き方を残さない（「メンテナーが決めること」の 4）。

- G02065（`@listing` の `src=`）は、rc2 と rc3 で notice を出したので、rc4 でエラーにしてよい。
- G02108（`-` で区切った範囲）は、rc4 で初めて notice を出すので、rc4 の後、1.0.0 までにエラーにする。1.0.0 でエラーにしてもよい。

どちらも、手順の 4 に沿う。
エラーにする ADR は別に作り、この ADR は時期だけを決める。
ロードマップの未決事項「`-` で区切った範囲をエラーにする時期」を、この決定に合わせて書き直す。

### 約束を検査する仕組み

約束のうち、スクリプトで確かめられるものを CI で確かめる。
どれも、`v1.0.0` 以降のタグがないあいだは今のとおりに振る舞う。

- **ABI のバージョン**：`scripts/ci/abi-version.sh` は、直前のリリースが `v1.0.0` 以降で、HEAD の `VERSION` の `X` が同じとき、次のことを確かめる。ABI のバージョンが直前のリリースと違うなら、直前のリリースの `docs/compatibility.md` に、HEAD の ABI のバージョンの見出しがあること。HEAD の `VERSION` が直前のリリースの patch（`X` と `Y` が同じ）なら、ABI のバージョンが同じであること。
- **diagnostic のコード**：新しい検査のスクリプトが、直前のリリース（`v1.0.0` 以降、`X` が同じもの）の docs/diagnostics.md と今のものを比べる。直前のリリースで使用中の `G` のコードが、今も使用中であり、重大度が error の側へ上がっていないことを確かめる。`E` のコード（Emet）は比べない。重大度は docs/diagnostics.md の重大度の欄の値で比べ、上がる向きは info、notice、warning、「dev では警告、prod ではエラー」、error の順とする。プリフライトの設定によるコードは、組み込みの `print` の既定の値で比べる。
- **patch のリリース**：リリースのワークフローは、作るタグが直前のリリースの patch なら、`scripts/visual/pages/` の参照が直前のリリースと同じであることを確かめる。[ADR 0173](0173-rc4-refactoring.md) の出力のハッシュの一覧があれば、PDF の行を除いて同じであることも確かめる。

### 文書

- `docs/compatibility.md` を作る。
- 仕様書の「バージョン」の節に、1.0.0 の後の規則は互換性の文書にあると書き、リンクする。diagnostics の節の廃止の手順の一文も、互換性の文書へのリンクにする。
- docs/diagnostics.md の「廃止予定の手順」を書き直し、互換性の文書にリンクする。
- README に、1.0.0 から互換を守ることと、互換性の文書へのリンクを書く。
- 使い手のマニュアルと開発者のマニュアルに、それぞれの読み手に関わる約束（使い手には原稿、設定、出力、廃止予定の notice の扱いと、Emet が実験的な機能であること、開発者には CLI、JSON の diagnostics、ABI と予告）を書く。置く章は、docs/manual-policy.md に従って実装のときに決める。
- 互換性の文書はビルドが読まないので、`scripts/ci/needs-build.sh` の一覧には加えない。
- ロードマップの v0.1.0-rc4 から「1.0 で約束すること」を消す。

## 実装しないこと

- **G02065 と G02108 をエラーにすること**：時期だけを決め、エラーにするのは別の ADR で行う。
- **マニフェストに、組むのに要る Golem のバージョンを書く欄**：前方の互換を約束しないので、新しい書き方を古い Golem で組むと、知らないキーや記法のエラーになる。バージョンの欄で先に止めるかは、必要になったら別の ADR で決める。
- **ホストが二つ以上の ABI のバージョンのプラグインを読み込むこと**：ABI は予告した後に変え、プラグインは予告に従って作り直す。古い ABI の IR への変換は作らない。
- **数式のための `$` などの予約**：レビューが挙げた、v2 の数式の記法のために今から文字を予約するかは、この ADR では決めない。予約しないまま 1.0.0 を出すと、`$` に意味を与えるのは major のバージョンになる。
- **LTS（長く保守するバージョン）を設けること**と、古い minor のバージョンにセキュリティの修正を戻すこと。
- **出力の約束を、patch より広げること**：minor のバージョンで組版の結果を変えないとは約束しない。
- **Emet の約束を 1.x の途中で始めること**：Emet を約束に含めるのは、早くても次の major とし、そのときに ADR で決める。

## テスト設計

約束そのものは文書なので、自動のテストを書けるのは検査の仕組みだけである。
検査のスクリプトは、テストを先に書き、今のスクリプトで失敗することを確かめてから実装する。
今の `abi-version.sh` のテストと同じく、一時的な Git のリポジトリにタグを打って確かめる。

`abi-version.sh` について、次のことを確かめる。

- `v1.0.0` 以降のタグがなければ、今のとおり（リリースごとに一つ上げる規則）に振る舞うこと。
- 直前のリリースが `v1.0.0` で、HEAD の `VERSION` が `1.1.0` のとき、CDDL を変えて ABI のバージョンを上げると、`v1.0.0` の `docs/compatibility.md` にその番号の見出しがなければ失敗し、あれば成功すること。何も変えなければ成功すること。
- HEAD の `VERSION` が `1.0.1` のとき、ABI のバージョンを上げると、予告があっても失敗すること。
- HEAD の `VERSION` が `2.0.0` なら、予告がなくても ABI のバージョンを一つ上げてよいこと。

diagnostic のコードの検査について、次のことを確かめる。

- 直前のリリースで使用中の `G` のコードを「廃止」にすると失敗すること。
- 重大度を notice から warning、warning から error、warning から「dev では警告、prod ではエラー」に上げると失敗し、error から warning に下げると成功すること。
- `E` のコードを「廃止」にしても、重大度を上げても成功すること。
- コードを足すと成功すること。
- `X` を上げたときと、`v1.0.0` 以降のタグがないときは、何も確かめずに成功すること。

patch のリリースの検査について、見た目の回帰テストの参照の一つのページのハッシュを変えると失敗し、変えなければ成功することを確かめる。

廃止の手順は、G02065 と G02108 をエラーにする ADR が、手順の 4 に沿っていることを、その ADR のレビューで確かめる。
互換性の文書は、`adr-guard links` と textlint で確かめる。

## トレードオフ

patch で出力を変えないと約束すると、組版の不具合の修正は、どんなに小さくても minor を待つ。
その代わり、入稿の前の本を組んでいる利用者は、patch に上げても改行と改ページが変わらないと分かり、セキュリティの修正だけを受け取れる。

意味論 IR を minor で変えてよいので、意味論 IR に新しいノードや欄を足す機能（複数段落の注、索引の参照など）を、1.x のうちに入れられる。
IR を major でしか変えられないと、v1.0.0 の項目が 1.0.0 に間に合わなかったときに 2.0 まで入れられず、開発の計画が崩れる。
その代わり、ABI を変える minor のたびに、すべてのプラグインは作り直すまで読み込めなくなる。
予告は、作り直す期間を開発者に与えるが、作り直しそのものはなくならない。
予告から変更まで、少なくとも一つの minor のリリースを挟むので、ABI を変える機能は、ADR から二つの minor を待つ。

JSON の `message` の文言を約束しないので、`message` を文字列で照合する CI は、minor で落ちることがある。
利用者が原因を知るにはコードと位置で足り、文言に補足を足しても困らない。
文言を約束すると、誤字の修正や、原因をより詳しく書く補足ができなくなる。

diagnostic のコードを 1.x で分けないと、「一つのコードに一つの原因」に反するコードが 1.0.0 の後に見つかっても、2.0 まで直せない。
ロードマップの v1.0.0 の「一つのコードに一つの原因の監査」を、1.0.0 の前に済ませる理由がここにある。

廃止予定の書き方を 1.x のあいだ受け付けるので、二つの書き方を保守する期間が長い。
`@listing` の `src=` のような書き方が 1.x で見つかると、2.0 まで残る。

仕様に反する振る舞いを minor で直すと、それまで組めていた原稿が、エラーで組めなくなることがある。
Golem は「緩い規則より厳しい規則」を設計原則に置き、壊れた出力を黙って作るより止めるほうを選ぶ（[仕様書の「設計原則」](../specifications.md#設計原則)）。
この条件はその原則に従うが、利用者から見ると、minor に上げただけで CI が落ちることがある。

Emet を実験的な機能とするので、`.emet` の関数を使う本は、minor に上げると組めなくなることがある。
`.gm` から `.emet` を呼ぶ原稿も同じである。
Emet は rc4 で初めてリリースに入り、1.0.0 までに使われて直す機会が一度しかないので、言語の形を 1.x のあいだ変えられるようにした。

LSP とエディタの構文の定義を約束しないので、エディタの設定（色の割り当てなど）や、LSP のクライアントの動きが minor で変わることがある。
どちらも、エディタで書く人にとって重要な機能である。
ただし、同じ入力から同じ出力を得るという Golem の決定性には関わらないので、約束の対象にしない。

- **互換性の文書**（2026-11-07、メンテナー）：仕様書は長すぎるので、互換性を扱う専用の文書を `docs/` に作る。
- **意味論 IR**（2026-11-07、メンテナー）：意味論 IR を major でしか変えられないと開発の計画が壊れるので、minor で変えてよい。
- **出力**（2026-11-07、メンテナー）：patch では出力を変えないことを約束する。
- **プラグインの ABI**（2026-11-07、メンテナー）：ABI は、変更を予告してから変える。予告では、どこがどう変わるかを開発者に示す。

- **JSON の diagnostics**（2026-11-07、メンテナー）：JSON の約束は、メッセージの文言までは保証しない。利用者は原因が分かればよく、補足を足しても困らない。

## メンテナーが決めること

すべて決めた（「決めたことの記録」）。

1. **出力の約束**：決めた。同じバージョンの中の決定性に加えて、patch のバージョンは、Golem のバージョンから作る値のほかに出力を変えない。
2. **意味論 IR とプラグインの ABI**：決めた。意味論 IR は minor で変えてよい。ABI は、変更を予告してから変え、予告ではどこがどう変わるかを開発者に示す。予告の場所と期間は 10 で決める。
3. **廃止の予告**：決めた。1.0.0 の後は、廃止を minor で予告する。予告した書き方をエラーにする時期は 11 で決める。
4. **1.0.0 の時点の廃止予定**：決めた。G02065 と G02108 を 1.0.0 の前にエラーにし、1.0.0 に廃止予定を残さない。1.0.0 より前に minor のリリースはないので、廃止の手順の 4（プレリリースを含むリリースで予告すれば足りる）に沿う。
   - 退けた案は、二つを 1.x のあいだ notice のまま残し、2.0 でエラーにすることである。1.0.0 から二つの書き方を保守し続けることになり、1.0.0 より前は互換を壊してよいという今の規則を使わないことになる。
5. **diagnostic のコードと JSON の約束**：決めた。メッセージの文言は約束せず、補足を足してよい。使用中の `G` のコードの意味を守り、1.x でコードを廃止せず、分けず、重大度をエラーの側へ上げない。JSON はキーを足すことだけを許し、重大度の値を四つに限る。
   - 退けた案は、コードを約束せず、メッセージだけを人が読むものとすることである。書き手と CI はコードで誤りを引くので、コードが変わると CI の扱いが変わる（仕様書の「設計原則」の「diagnostics の決定性」、[仕様書](../specifications.md#設計原則)）。
6. **仕様に反する振る舞いを直すとき**：決めた。minor のバージョンで直し、リリースノートの「互換を壊す修正」に挙げる。
7. **Emet を約束に含めるか**：決めた。Emet は v1.x のあいだ実験的な機能とし、約束に含めない。
8. **LSP とエディタ向けの構文の定義**：決めた。どちらも約束しない。重要な機能だが、Golem の決定性とは関係がない。
9. **互換性の文書の名前**：決めた。`docs/compatibility.md` とする。
   - 退けた案は、`docs/versioning.md` のように、バージョンの規則の文書として名付けることである。約束の中身は、バージョンの付け方より、何を守り何を守らないかの表が主であり、名前と中身がずれる。
10. **ABI の変更の予告の場所と期間**：決めた。予告を互換性の文書とリリースノートの「予告」の項に書き、予告を載せた minor のリリースより後の minor のリリースで変える。予告には、新しい ABI のバージョン、CDDL の差分、変わる要求と応答、プラグインの側で直すこと、元の ADR を書く。
    - 退けた案の一つは、予告をリリースノートだけに書くことである。リリースノートはリリースごとに分かれるので、開発者は、今どの変更が予告されているかを、いくつものリリースノートから探すことになる。`abi-version.sh` が予告を確かめる先にもならない。
    - もう一つは、ADR が main に入ったことを予告とし、次のリリースで変えることである。リリースを追う開発者は、main の ADR を読まないと予告に気付かない。
    - もう一つは、予告から変更まで期間（日数）を決めることである。リリースの間隔は決まっていないので、日数はリリースと結び付かず、CI で確かめられない。
11. **予告した廃止をエラーにする時期**：決めた。1.x のあいだは notice のまま受け付け、次の major でエラーにする。
    - 退けた案は、予告した次の minor でエラーにすることである。原稿の記法の約束（1.a で組めた原稿は 1.b でも組める）を破る。
12. **実験的な Emet の範囲**：決めた。Emet のためだけにあるものすべてを、約束の外とする。`.emet` の言語、マニフェストの `[functions.requires]` と `[[filters]]` の `function`、`.gm` の `.emet` を取り込む `@import` とその名前空間を通した呼び出し、`E` のコード、`golem fmt` と `golem lint` の `.emet` への振る舞いを含む。`.gm` のほかの書き方と、プラグインの `[[filters]]` は約束に含める。
    - 退けた案は、`.emet` の言語だけを実験的とし、`.gm` から呼ぶ書き方とマニフェストのキーは約束に含めることである。言語を変えると、呼ぶ側の書き方も変わることがあり、約束を守れない。
