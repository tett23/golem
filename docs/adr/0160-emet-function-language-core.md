# ADR 0160: 関数を書く言語 Emet の核

ステータス: 採択

## 文脈

v0.1.0-rc4 のロードマップは、書き手が関数を宣言できるようにする項目を持つ（[docs/roadmap.md](../roadmap.md) の「`.gmx` の関数の宣言」）。
関数は、社内の使い手や組版のオペレーターが手元の不便を解消するためのものであり、技術者が作って配るプラグインとは立ち位置を分ける。

メンテナーの案は、この言語を `.gmx`（Golem Expression のつもりだった）と呼んでいたが、メンテナーは名前を Emet（拡張子 `.emet`）に変えた（「決めたことの記録」）。
この ADR と [ADR 0161](0161-emet-requirements-and-driver-handlers.md)、[ADR 0162](0162-calling-emet-functions-from-gm.md) は、新しい名前で書く。
ロードマップの項目の名前と、戻した実装のファイルの名前は、元のまま `gmx` で引く。

### 破棄した草案からの引き継ぎ

この ADR は、破棄した [docs/adr/0148](0148-gmx-function-language-core.md) を引き継ぐ。
0148 は、メンテナーの案を ADR の草案にしたものだった。
草案は、メンテナーがまだ決めていない点を「メンテナーが決めること」として挙げていたが、[PR #526](https://github.com/tett23/golem/pull/526) でほかの草案とともに誤って採択され、挙げた点はどれも「推奨のとおり」と記録された。
その記録のまま [PR #531](https://github.com/tett23/golem/pull/531) で実装されたが、メンテナーは 2026-11-05 に設計の検討を続けるために三つの ADR を取り下げ、実装を戻した（[PR #538](https://github.com/tett23/golem/pull/538)。[仕様書の「破棄した ADR」](../specifications.md#破棄した-adr)）。

この ADR では、メンテナーが決めた点だけを「決めたことの記録」に書き、それ以外は、草案が足した設計を含めてすべて「メンテナーが決めること」に挙げる。
本文の「実装すること」は、決めた点と、各項目の推奨の案で書いてある。
推奨と違う案を採れば、該当する箇所を書き換える。

戻した実装は、設計を確かめる材料として使う。
実装から分かったことは、下の「実装から分かったこと」にまとめ、コードは戻す前の最後のコミット（[ba6635ad](https://github.com/tett23/golem/commit/ba6635adfc787a92a1c003a37650a5919a26e3eb)）の URL で引く。

### メンテナーの案

メンテナーは、この関数を `.gm` の中ではなく、別のファイル（案では `.gmx`、この ADR では `.emet`）に書く案を出した。
`.emet` は Haskell の方言であり、`.gm` の `[...]` と `@` の記法を使わない。
案の要点は次のとおりである。

- 言語は正格評価とし、`lazy` を付けたものだけを遅延評価する。
- 最上位の宣言のうち `pub` を付けたものを公開する。
- オフサイドルール（字下げで構造を決める規則）を採らない。`golem fmt` との相性が悪いからである。
- `if` と `for` を持たない。分岐は引数の位置のパターンマッチで、繰り返しは再帰で書く。再帰は末尾呼び出しの最適化で実装する。三項演算子はパターンマッチの糖衣構文とし、一つ目の条件を一つ目のパターン、二つ目を `_` として実装する。
- パターンマッチは網羅していなければならない。
- 関数が処理系に求めるもの（要求）をシグネチャに書く。代数的エフェクトを部分的に実装したものであり、要求を処理するハンドラは driver に集める。

案の例は、Golem 自身の Haskell のコード（[`cidSystemInfo`](https://github.com/tett23/golem/blob/4f86b945b6e60913fc63e22c0bf4ec14e5114bed/modules/golem-font/src/Golem/Font.hs#L194-L199)）をそのまま写したものである。

```haskell
cidSystemInfo :: String -> String -> Int -> Maybe CidSystemInfo
cidSystemInfo registry ordering supplement
  | all printable registry && all printable ordering && supplement >= 0 = Just (CidSystemInfo (T.pack registry) (T.pack ordering) supplement)
  | otherwise = Nothing
  where
    printable c = c >= ' ' && c <= '~'
```

`T.pack` は Haskell の `Data.Text` を前提にしており、`String` と `Text` の二つの文字列の型があるように見える。
メンテナーは、文字列の型を一つにすると決めた（下の「決めたことの記録」）。
例の `where` は字下げで閉じているが、オフサイドルールを採らないので、どこで閉じるかを字下げのほかの方法で示す必要がある。
メンテナーは、`where` を関数の末尾に置いて `{ }` で囲み、中の束縛を改行で区切ると決めた。

### 三つの ADR

この話題は一つの ADR に収まらないので、三つに分ける。

- **この ADR**：言語の核。ファイル、構文、型、評価、パターンマッチ、再帰と停止、fmt、新しいパッケージ。
- **[ADR 0161](0161-emet-requirements-and-driver-handlers.md)**：要求。Koka にならったシグネチャの書き方、要求の合成と多相、要求の一覧、driver のハンドラ、`manifest.toml` での許可。破棄した [docs/adr/0149](0149-gmx-requirements-and-driver-handlers.md) を引き継ぐ。
- **[ADR 0162](0162-calling-emet-functions-from-gm.md)**：`.gm` からの使い方。`@import` での取り込み、インラインのコマンド、ブロックコマンド、式文脈からの呼び出し、フィルタ、意味論 IR を表すデータ型、補完と lint。[golem-eval ADR 0001](../golem-eval/adr/0001-expression-language-and-numerics.md) の立場を改める。破棄した [docs/adr/0150](0150-calling-gmx-functions-from-gm.md) を引き継ぐ。

三つは同時に採択し、同じ順に実装する。
この ADR だけを実装しても、`.gm` から関数を呼べないので、使い手には何も変わらない。

### 実装から分かったこと

戻した実装（PR #531、#533、#534、#536）から、この ADR に関わることとして次が分かった。

- **区切りの記号を決めれば、文法と fmt を書けた**。戻した実装は `{ ; }` で区切った。peg-hs の文法（[`Emet.hpeg`](https://github.com/tett23/golem/blob/ba6635adfc787a92a1c003a37650a5919a26e3eb/modules/golem-gmx/grammar/Gmx.hpeg)）は、AST とロスレスな構文木の二つの入口を持ち、fmt はロスレスな構文木の字句の上で整形してコメントを残せた。この ADR は `;` をやめて改行で区切るので、文法の空白の規則を書き直す（下の「改行による区切り」）。
- **`:` を持たないと、`List.uncons` の戻り値の型が要る**。草案は `:` を持たない代わりに `List.uncons` で先頭と残りを分けるとしたが、組の型がないので、戻り値を表す型がなかった。実装は組み込みのデータ型 `List.Cons a` を足した（[`Builtins.hs`](https://github.com/tett23/golem/blob/ba6635adfc787a92a1c003a37650a5919a26e3eb/modules/golem-gmx/src/Golem/Gmx/Builtins.hs#L75-L81)）。メンテナーが `(x : xs)` を残すと決めたので、この型は要らなくなる。
- **手数の上限は 100,000,000 で測れた**。見本のプラグイン `kansuji` と同じ仕事が 423 手、`first-ruby` と同じ仕事（1000 語の列の 50 語の初出に印を付ける）が 30,290 手、テストが求める 1000 万回の末尾再帰が 30,000,002 手だった。実装は末尾再帰の約 3 倍の 100,000,000 を上限にした（[`Eval.hs`](https://github.com/tett23/golem/blob/ba6635adfc787a92a1c003a37650a5919a26e3eb/modules/golem-gmx/src/Golem/Gmx/Eval.hs#L55-L65)）。
- **等式の引数の数がシグネチャと合わない誤り**が要った（E02106）。
- **E02104 に七つの原因が集まった**。名前空間、型、コンストラクタ、シグネチャ、レコードの欄、パターンの中の変数の二度の定義のほか、同じ関数の等式が離れていることも E02104 にした（[`Check.hs`](https://github.com/tett23/golem/blob/ba6635adfc787a92a1c003a37650a5919a26e3eb/modules/golem-gmx/src/Golem/Gmx/Check.hs#L305-L308)）。二度の定義は一つの原因と見てよいが、等式が離れていることは別の原因なので、この ADR では E02107 に分ける。
- **型クラスがないと、演算子の左右が型変数のままの式に決め方が要る**。実装は、型変数に「数」「比べられる型」「つなげる型」の制約を付け、算術の演算子の左右がどちらも型変数なら `Rat` に決めた。この ADR は、この三つの制約を、後から型クラスに開ける形で持つ（下の「型クラスの余地」）。
- **`where` の束縛の評価の時期**を決める必要があった。実装は、関数が呼ばれるたびに束縛を作り、`lazy` のない束縛を等式を選ぶ前に上から順に評価し、束縛が自分自身の値を求めたら手数の上限の誤りにした。メンテナーは `where` の束縛を遅延評価にすると決めた（「決めたことの記録」）。
- **文法の誤りは最初の一つだけ**を報告した。文法に回復の規則を持たせなかったからである。
- このほか、`import` のパスはプロジェクトのルートからの相対パスとし、ないファイルは `.gm` の `@import` と同じ G03002、ルートの外は G03003 にした。`\u{...}` の値が Unicode のスカラー値でなければ E01100、パターンには負の数のリテラルも書け、レコードは位置でも欄の名前でも作れ、`where` の中の束縛にもシグネチャを書けるようにした。これらは実装の細部として、採択の後に仕様書に書く。

## 実装すること

### ファイル

- 拡張子は `.emet` とし、文字コードは UTF-8 とする。
- BOM と CR の扱いは `.gm` と同じである。BOM は G01002、CR は G01003 とし、`golem fmt` で直せる。原因が `.gm` と同じなので、コードを分けない。
- 一つのファイルが一つのモジュールである。`module` の宣言は書かない。モジュールに名前を付けない（「取り込み」）。

### 字句

- 識別子は Haskell と同じく、値と関数は英小文字か `_` で始まり、型とコンストラクタは英大文字で始まる。識別子に `-` は使えない。
- 予約語は `pub`、`inline`、`block`、`filter`、`fn`、`data`、`type`、`import`、`as`、`where`、`case`、`of`、`otherwise` とする。`otherwise` はガードにだけ書ける語であり、`Bool` の値ではない。
- `if`、`then`、`else`、`for`、`while`、`let`、`in`、`lazy` も予約し、使うと E01102（使えない予約語）とする。書き手が慣れた言語の癖で書いたときに、名前の誤りではなく、使えない構文であることを伝えるためである。`lazy` は、`where` の束縛がすべて遅延評価になったので、付ける場所がなくなった（下の「評価」）。
- `class`、`instance`、`deriving`、`default` も予約し、使うと E01102 とする。型クラスを後から足すときに、利用者の名前と重ならないようにするためである（下の「型クラスの余地」）。
- コメントは `--` から行末までとする。`{- -}` は持たない。
- 文字列のリテラルは `"..."`、文字のリテラルは `'a'` とし、エスケープは `\"`、`\'`、`\\`、`\n`、`\t`、`\u{XXXX}` に限る（文字の型は「メンテナーが決めること」の 5）。
- 数のリテラルは、`.gm` の式文脈と同じ規則（自然数、小数、指数）で読む（[docs/adr/0101](0101-rational-numbers-in-expressions.md)）。

### 改行による区切り

字下げに意味を持たせないので、宣言と束縛の終わりは改行で示す。
Go や Kotlin と同じく、改行を区切りとして読み、続きの行であることが字句で分かる場合だけ改行を空白として読む。
`;` は区切りの記号として持たない（「決めたことの記録」）。

- 最上位の宣言、`where { }` の中の束縛、`case ... of { }` の中の選択肢は、改行で区切る。シグネチャも等式も一つの宣言である。
- 空行は区切りが続くだけであり、意味を持たない。
- 次のどれかに当たる改行は、区切りではなく空白として読む。
  - `(` と `)` のあいだ、`[` と `]` のあいだ、レコードの `{ }`（コンストラクタの後ろの `{ }`）のあいだにある改行。
  - 行の最後の字句が、二項演算子、`=`、`->`、`::`、`,`、`?`、`:` である行の終わりの改行。
  - 次の空でない行の最初の字句が、`|`（ガード）、`-` を除く二項演算子、`?`、`:`、`where`、`->` である場合の改行。
- 行頭の `-` は、続きの行ではなく新しい項目の始まりとして読む。`case` の選択肢のパターンに負の数を書けるようにするためである。引き算を次の行に続けるときは、行の最後に `-` を置く。
- 字下げは空白と同じであり、構文に影響しない。字下げは `golem fmt` が決める。

これは字下げの規則ではないので、オフサイドルールとは違う。
どの改行が区切りかは、改行の前後の字句と括弧の入れ子だけで決まり、行頭の桁に依らない。
fmt が字下げを変えても、区切りは変わらない。

`where` は関数の末尾に置き、中の束縛を `{ }` で囲み、束縛を改行で区切る（「決めたことの記録」）。

- `where` は一つの関数に多くても一つであり、その関数の最後の等式（ガードがあれば最後のガードの右辺）の後ろに置く。
- 最後でない等式の後ろの `where` と、二つめの `where` は、E01103（関数の末尾にない `where`）とする。`case` の選択肢とガードの後ろには、`where` を書けない。
- `where` の束縛は、その関数のすべての等式から見える。等式ごとの引数のパターンの変数は、`where` の中からは見えない（「メンテナーが決めること」の 10）。引数の値を使う局所の関数は、その値を引数として受け取る形で書く。
- 束縛にはシグネチャ（`name :: 型`）を書ける。
- `where` の中の束縛は、その中で `where` を持てない。入れ子にした局所の定義は、同じ `where` の中に並べる。
- 束縛は遅延評価する（下の「評価」）。
- どの等式からも、ほかの束縛からも使われない束縛は、notice の E02109 とする（「決めたことの記録」）。位置はその束縛の名前、メッセージは束縛の名前である。遅延評価なので評価されず、出力には影響しないが、書き手の思い違いを示すことが多い。notice なので `manifest.toml` の `silence-notices` で抑制できる（[golem-syntax ADR 0002](../golem-syntax/adr/0002-notice-severity.md)）。

案の例は、次のように書く。

```haskell
cidSystemInfo :: String -> String -> Nat -> Maybe CidSystemInfo
cidSystemInfo registry ordering supplement
  | String.all printable registry && String.all printable ordering = Just (CidSystemInfo registry ordering supplement)
  | otherwise = Nothing
  where {
    printable c = c >= ' ' && c <= '~'
  }
```

`supplement >= 0` は、型を `Int` から `Nat` に変えれば要らなくなるので消した。
`T.pack` は、文字列の型が一つなので要らない。
`all` は、文字列がリストではないので `String.all` と書く。
`printable` は引数のパターンの変数を使わないので、関数の末尾の `where` に置ける。
二つのガードの行は `|` で始まるので、前の行の続きとして読む。

等式が二つ以上ある関数では、`where` は最後の等式の後ろに一つだけ置き、すべての等式から使う。

```haskell
label :: Maybe Nat -> String
label Nothing = bracket "なし"
label (Just n) = bracket (String.fromNat n)
  where {
    bracket s = "［" ++ s ++ "］"
  }
```

### 宣言

- **関数**：シグネチャと、一つ以上の等式からなる。最上位の関数はシグネチャを必ず持つ。同じ関数の等式は続けて書き、あいだにほかの宣言を挟まない（挟めば E02107）。すべての等式は同じ数の引数を持ち、その数はシグネチャの矢印の数を超えてはならない（E02106）。矢印の数より少なければ、残りの矢印は関数が返す関数の型である（[ADR 0161](0161-emet-requirements-and-driver-handlers.md) の「列を書く矢印」）。
- **データ型**：`data Shape = Circle Rat | Rect Rat Rat` の形の代数的データ型と、`data Book = Book { title :: String, year :: Nat }` の形のレコードを宣言できる。型の引数（`data Pair a b = ...`）を持てる。レコードの値は、位置（`Book "題" 2020`）でも欄の名前（`Book { title = "題", year = 2020 }`）でも作れ、欄はパターンで取り出す。
- **型の別名**：`type Name = String` を書ける。
- **公開**：`pub` を付けた関数とデータ型を、ほかのモジュールに公開する。データ型を公開すると、コンストラクタも公開する。中身を隠した型は v1 では作れない。
- **取り込み**：`import "lib/text.emet"` で、ほかの `.emet` の公開された名前（関数、データ型、コンストラクタ、型の別名）を、名前空間を付けずに取り込む（「決めたことの記録」）。取り込んだ名前は、そのファイルの中で定義した名前と同じく `name` の形で参照する。取り込んだ名前が、ほかの取り込みの名前か、そのファイルで定義した名前と重なれば E02108 とし、メッセージに両方の出どころを書く。重なりは、名前を参照したかどうかによらず、取り込んだ時点で誤りにする。どの名前がどこから来たかを、参照の有無で変えないためである。パスはプロジェクトのルートからの相対パスに限り、ないファイルは G03002、外を指せば G03003 とする。循環は E02103 とする。取り込みは推移しない。`a.emet` が取り込んだ `b.emet` の名前は、`a.emet` を取り込んだファイルからは見えない。

### 型

型は静的に検査する。
最上位の関数はシグネチャを持つので、型の推論は `where` の中の局所の宣言と式の中にとどまる。
推論は Hindley-Milner の型推論で行う。
v1 は型クラスを持たないが、後から足せる形にしておく（下の「型クラスの余地」）。

組み込みの型は次のとおりである。

| 型 | 中身 |
| --- | --- |
| `Nat`、`Int`、`Rat` | `.gm` の式文脈の三つの数の型と同じ。自然数から整数へ、整数から有理数へは暗に広げる（[docs/adr/0101](0101-rational-numbers-in-expressions.md)、[docs/adr/0102](0102-natural-number-type.md)） |
| `Bool` | `True` と `False` |
| `Char` | Unicode のスカラー値一つ。リテラルは `'a'` |
| `String` | Unicode のスカラー値の列。文字列の型はこれ一つであり、`List Char` とは別の型である |
| `List a` | リスト。`[]` と `[a, b, c]` で書き、`x : xs` で先頭と残りをつなぐ |
| `(a, b)` | 組。`(x, y)` で書く。三つ以上の組も書ける（「メンテナーが決めること」の 6） |
| `Maybe a` | `Just a` と `Nothing` |
| `Inline`、`Block` | 意味論 IR のインラインとブロックを表すデータ型。`Inlines` は `List Inline`、`Blocks` は `List Block` の別名である（[ADR 0162](0162-calling-emet-functions-from-gm.md)） |

浮動小数点数の型は持たない。
`.gm` の式と同じく、計算の結果が実行の環境によって変わらないようにするためである。

- `==`、`/=`、`<`、`<=`、`>`、`>=` は、数、`Bool`、`Char`、`String` にだけ使える組み込みの演算子である。ほかの型の値は、パターンマッチで比べる。v1 では、利用者のデータ型に比較を足す手段はない。
- `+`、`-`、`*`、`/`、`div`、`%`、`**` は、式文脈の数の規則（結果の型、0 での割り算、累乗の上限）にそのまま従う。誤りのコードも式文脈と同じ（G02001 など）であり、位置は `.emet` の中を指す。原因が同じなので、コードを分けない。
- `++` は `String` どうしと `List a` どうしをつなぐ。
- `:` は右に結合する演算子で、`a -> List a -> List a` の型を持つ。
- `Char` どうしと `String` どうしの大小は、Unicode のコードポイントの順で比べる（`.gm` の式文脈と同じ）。
- 字の単位の操作は、モジュール `String` の関数で行う。`String.chars :: String -> List Char` は字のリストを、`String.fromChars :: List Char -> String` はその逆を返す。`String.all`、`String.any`、`String.map` は、`Char` を受け取る関数を各字に当てる。`String.length` は Unicode のスカラー値の数を返す。
- `T.pack` のような文字列の型の変換は、型が一つなので持たない。
- 文字列とリストの操作は、組み込みのモジュール `String` と `List` の関数として持つ（`String.all`、`String.length`、`List.map`、`List.foldl` など）。一覧は仕様書に書く。組み込みのモジュールは `import` なしで使い、つねに `String.all` のようにモジュールの名前を付けて参照する。利用者の型やコンストラクタの名前が組み込みのモジュールの名前と重なれば E02104 とする。

### 型クラスの余地

v1 は型クラスを持たない。
ただし、メンテナーは型クラスを将来足す可能性があるとし、後で苦労しないよう、なるべく余地を残すと決めた（「決めたことの記録」）。
足すときに、言語の記法、型の検査、評価器、利用者の書いたコードのどれも作り直さずに済むよう、次のようにしておく。

- **組み込みの制約**：比較、算術、`++` の演算子の型は、型の検査の中で、閉じた三つの述語（「数」「比べられる型」「つなげる型」）を型変数に付けて表す。述語が満たされる型は組み込みの型に限る。型クラスを足すときは、この三つを組み込みの型クラス（`Num`、`Ord`、`Concat` に当たるもの）として開き、利用者のデータ型にインスタンスを足せるようにする。
- **既定の型**：算術の演算子の左右がどちらも型変数のまま残れば `Rat` に決める。Haskell の `default` 宣言と同じ働きであり、型クラスを足しても規則を変えない。
- **記法**：シグネチャに制約を書く記法は v1 では持たない。Haskell が制約に使う `=>` は、要求の記法（[ADR 0161](0161-emet-requirements-and-driver-handlers.md)）では使わないので、型クラスを足すときに Haskell と同じ位置（型の前）で使える。
- **予約語**：`class`、`instance`、`deriving`、`default` を予約しておく（上の「字句」）。
- **型の検査の形**：型の検査は、制約を集める段と解く段を分けて実装する。v1 の制約は、型の等しさ、要求の列（[ADR 0161](0161-emet-requirements-and-driver-handlers.md)）、上の三つの述語である。型クラスを足すときは、述語の制約を解く規則にインスタンスを足すだけで済む。単一化の中で述語をその場で決める形にすると、型クラスを足すときに型の検査を書き直すことになる。
- **評価器の形**：比較、算術、`++` の演算子は、評価器の中で、述語ごとの実装の表を型から引いて呼ぶ。型クラスの辞書渡しと同じ形である。型クラスを足すときは、利用者のインスタンスを表に足すだけで済む。
- **組み込みの関数の型**：組み込みのモジュールの関数のうち、型クラスを足せば多相になるもの（`List.sort`、`List.elem`、`String.fromNat` に当たる表示の関数など）は、v1 では組み込みの型に限った型を持つ。名前は Haskell の型クラスのメソッドと重ならない形にし、型クラスを足したときに、同じ名前のまま型を広げられるようにする。
- **データ型の比較**：利用者のデータ型は v1 では比べられない。`deriving` を足したときに、比較の順（コンストラクタの宣言の順、次に欄の順）を Haskell と同じにできるよう、コンストラクタの宣言の順を AST に残す。

### 評価

- 評価は正格であり、関数を呼ぶ前に引数を左から順に評価する。
- `where` の束縛は遅延評価する（「決めたことの記録」）。関数が呼ばれるたびに束縛を作り、束縛は最初に使ったときに一度だけ評価する。使わなかった束縛は評価しない（`table = parse (File.read "data/words.tsv")` は、`table` を使った呼び出しでだけファイルを解析する）。
- 束縛を評価している途中で、同じ束縛の値を求めれば、決して終わらないので E04102 とし、メッセージに束縛の名前と、値を求めた束縛の並びを書く。手数の上限（E04100）を待たずに、循環を見つけた時点で止める。
- 関数の引数は、つねに呼ぶ前に評価する。
- `&&` と `||` は、右辺を必要なときだけ評価する。
- 関数は純粋であり、要求（[ADR 0161](0161-emet-requirements-and-driver-handlers.md)）を通さずに外の値を読めない。

`where` の束縛で誤りが起きるかどうかは、どの束縛を使ったかで決まる。
どの値を使うかは入力だけで決まるので、同じ入力からは同じ diagnostic になる（diagnostics の決定性。[仕様書の「設計原則」](../specifications.md#設計原則)）。

### パターンマッチ

- 等式の引数の位置にパターンを書ける。パターンは、変数、`_`、リテラル（負の数を含む）、コンストラクタ、リスト（`[]`、`[a, b]`）、先頭と残り（`(x : xs)`）、組（`(a, b)`）、レコード（`Book { title = t }`）である。
- `case e of { ... }` で、式の中でも分岐できる。選択肢は `p -> e` の形で、改行で区切る。
- ガード（`| 条件 = 式`）は、等式と `case` の選択肢に書ける。条件は `Bool` の式である（「メンテナーが決めること」の 3）。
- `if` の式は持たない。条件で分ける場合はガードか `case` で書く。

```haskell
total :: List Nat -> Nat
total [] = 0
total (x : xs) = x + total xs
```

三項演算子 `c ? a : b` は、`case c of { True -> a; _ -> b }` と同じ意味の糖衣構文である（メンテナーの案。この式の `;` は説明のための書き方であり、`.emet` では改行で区切る）。
一つ目の選択肢が `True` の場合、二つ目が `_` の場合になる。

三項演算子の `:` とリストの `:` は同じ記号なので、次の規則で読む（「メンテナーが決めること」の 6）。

- `?` の後ろ、`:` の前の式（真の枝）の最上位には、括弧のない `:` と `?` を書けない。真の枝でリストをつなぐときは括弧で囲む（`c ? (x : xs) : ys`）。
- `:` の後ろの式（偽の枝）は、どの式でもよい。`?` と `:` は右に結合し、`a ? b : c ? d : e` は `a ? b : (c ? d : e)` と読む。偽の枝の `x : xs` は、リストをつなぐ式として読む（`c ? [] : x : xs` は `c ? [] : (x : xs)`）。
- `?` の前の式（条件）の最上位には、括弧のない `?` を書けない。
- `?` と `:` は、`||` より弱く結合する。

この規則は、PEG の順序付きの選択で、真の枝を `:` と `?` を含まない式の規則で読むことで書ける。
真の枝に括弧のない `:` を書くと、三項演算子の `:` として読まれ、続く字句が余るので E01100 になる。

### 網羅性の検査

パターンマッチは、すべての値を網羅しなければならない。
網羅していない等式の並びと `case` は、型の検査の段階で E03100 とし、メッセージに網羅していない値の形の例を一つ添える。
検査は Maranget の方法（参考文献）で行う。
`(x : xs)` と `[]` は、リストの二つのコンストラクタとして数える。
`[a, b]` のようなリストのリテラルのパターンは、`(a : (b : []))` と同じものとして数える。

ガードの条件は意味で解析せず、構文の規則で検査する（「決めたことの記録」）。
条件の意味を解析して網羅を判定すると、どの条件の組を網羅と見なすかが解析の強さで決まり、その範囲を仕様の言葉で書きにくいからである。

- **ガードの規則**：ガードを持つ等式と `case` の選択肢は、ガードの並びの最後を `otherwise` にしなければならない。最後のガードが `otherwise` でなければ E03102 とする。ほかの条件（`True`、`n >= 0 || n < 0` など）は、つねに真になる式でも `otherwise` と見なさない。
- **例外**：ガードの並びの最後が `otherwise` でなくても、関数の最後の等式（`case` なら最後の選択肢）がガードを持たず、パターンがすべて変数か `_` であれば、E03102 にしない。値は必ずその等式に落ちるからである。
- **`otherwise` の後ろ**：`otherwise` の後ろのガードは、決して選ばれないので E03101 とする。
- **選ばれない選択肢**：前の選択肢がすべて覆っていて、決して選ばれない選択肢も E03101 とする。書き手の思い違いを示すことが多いからである（「メンテナーが決めること」の 7）。
- **パターンとの組み合わせ**：`otherwise` で終わるガードの並びを持つ等式は、ガードのない等式としてパターンの網羅に数える。終わらない等式は、上の例外に当たる場合にだけ許され、網羅に数えない。

| メッセージ | 位置 |
| --- | --- |
| `ガードの並びの最後が otherwise ではありません: <関数の名前>` | 並びの最後のガード（縦線から右辺の終わりまで） |

### 再帰と停止

`for` と `while` は持たず、繰り返しは再帰で書く。

- **末尾呼び出し**：等式の右辺、`case` の選択肢の右辺、三項演算子の二つの枝、ガードの右辺の位置にある関数の呼び出しを、末尾呼び出しとする。`&&` と `||` の右辺も末尾の位置である。末尾呼び出しは、相手の関数によらず（相互再帰を含め）呼び出しの深さを増やさない。これを最適化ではなく言語の約束とし、仕様書に書く。
- **深さの上限**：末尾でない呼び出しは深さを一つ増やす。深さが 10000 を超えたら E04101 とする。
- **手数の上限**：`.gm` からの一つの呼び出し（コマンド、式、フィルタ。[ADR 0162](0162-calling-emet-functions-from-gm.md)）が始めた評価の手数（簡約の数）に、上限を設ける。上限を超えたら E04100 とする。手数は言語の意味で数えるので、上限を超えるかどうかと止まる位置は、マシンと実行の環境によらない。手数は、関数の呼び出し、組み込みの関数の呼び出し、コンストラクタの適用、演算子、等式と選択肢の選択、`where` の束縛の評価を一つずつ数える。
- **大きさの手数**：`++` と、文字列とリストを作る組み込みの関数は、作った値の長さを手数に足す。`s ++ s` を繰り返して手数の小さいまま巨大な値を作ることを防ぐためである。
- **数の大きさ**：累乗と数のリテラルは、式文脈と同じ上限に従う（[golem-eval ADR 0006](../golem-eval/adr/0006-exact-power-limit-before-range.md)）。

二つの上限は、原因が違うので別のコードにする（「メンテナーが決めること」の 8 と 9）。
E04101 は、末尾でない再帰が深すぎることを表し、関数を末尾再帰に書き直せば直ることが多い。
E04100 は、仕事の量が多すぎるか、止まらないことを表し、書き直しで深さを減らしても直らない。
上限を超えた呼び出しは、出力を何も返さない。
途中までの結果を組むと、書き手の入力と違う出力を黙って作ることになるからである。

| コード | 重大度 | メッセージ | 位置 |
| --- | --- | --- | --- |
| E04100 | エラー | `関数の評価の手数が上限（<上限> 手）を超えました: <関数の名前>（<.emet のパス>:<行>）` | 評価を始めた `.gm` の呼び出し |
| E04101 | エラー | `末尾でない呼び出しの深さが上限（10000）を超えました: <関数の名前>（<.emet のパス>:<行>）` | 評価を始めた `.gm` の呼び出し |

`<関数の名前>` と `<.emet のパス>:<行>` は、上限を超えた時点で評価していた関数とその宣言である。
評価を始めた `.gm` の呼び出しは、コマンドと式ではその呼び出しの位置、フィルタではフィルタを当てたファイルの先頭である（[ADR 0162](0162-calling-emet-functions-from-gm.md)）。
位置を `.gm` の側にするのは、同じ関数でも、止まるかどうかが呼び出しの引数で決まるからである。
どちらの値も評価の意味だけで決まるので、同じ入力からは同じメッセージになる。
`.emet` の中を指す位置を持たせると、一つの誤りが二つのファイルに載り、LSP の表示が呼び出しの数だけ増える。

手数の上限は 100,000,000 とする。
戻した実装で測った値（「実装から分かったこと」）にもとづき、[docs/adr/0124](0124-filter-fuel-by-document-size.md) にならって、正常に終わる最大の仕事（1000 万回の末尾再帰、30,000,002 手）の約 3 倍とした。
利用者が `manifest.toml` で上限を変える手段は設けない。
本ごとに上限が変わると、同じ関数が本によって動いたり止まったりするからである（[docs/adr/0124](0124-filter-fuel-by-document-size.md) と同じ理由）。
フィルタの上限を文書の大きさで変えるかは、[ADR 0162](0162-calling-emet-functions-from-gm.md) で決める。

評価器は、継続を明示したスタックを持つ抽象的な計算機として実装する。
GHC のスタックに深さを任せると、深さの上限がランタイムの設定で変わるからである。

### 型と評価の誤りのコード

Emet の誤りには、新しい接頭辞 `E` のコードを作る（「決めたことの記録」）。
`.gm` の `G` のコードと同じく、接頭辞の後ろに 5 桁の数を置き、上 2 桁を段階、下 3 桁を段階の中の番号とする。
段階は次のとおりで、番号は 100 から使う。

| 段階 | 中身 | ADR |
| --- | --- | --- |
| E01 | 構文 | この ADR |
| E02 | 名前と型 | この ADR |
| E03 | パターンマッチの網羅性 | この ADR |
| E04 | 評価の上限と循環 | この ADR |
| E05 | 要求 | [ADR 0161](0161-emet-requirements-and-driver-handlers.md) |
| E06 | `.gm` から使う関数の宣言と出力 | [ADR 0162](0162-calling-emet-functions-from-gm.md) |
| E07 | lint | [ADR 0162](0162-calling-emet-functions-from-gm.md) |

`.gm` の原稿の側で起きる誤り（引数の数と型、`manifest.toml` の誤りなど）は、原因が `.gm` の側にあるので、今の `G` のコードを使う。
`E` のコードは、`.gm` の `G` のコードと同じ形で JSON の diagnostics と [docs/diagnostics.md](../diagnostics.md) に載せる。
コードの体系は、v1 で廃止したコードを整理するときに見直してよい（「決めたことの記録」）。
この ADR が使うコードは次のとおりである。

| コード | 重大度 | 原因 |
| --- | --- | --- |
| E01100 | エラー | `.emet` の構文の誤り（期待した字句を添える。`\u{...}` が Unicode のスカラー値でない場合、三項演算子の真の枝の括弧のない `:` を含む） |
| E01101 | エラー | 閉じていない `{`、`(`、`[`、文字列 |
| E01102 | エラー | 使えない予約語（`if`、`for`、`lazy`、`class` など） |
| E01103 | エラー | 関数の末尾にない `where`（最後でない等式の後ろ、二つめ、`case` とガードの後ろ、`where` の中） |
| E02100 | エラー | 未定義の名前 |
| E02101 | エラー | 型の不一致 |
| E02102 | エラー | シグネチャのない最上位の関数 |
| E02103 | エラー | `import` の循環 |
| E02104 | エラー | 同じ名前の二度の定義（名前空間、型、コンストラクタ、関数のシグネチャ、レコードの欄、一つのパターンの中の変数。組み込みのモジュールとの重なりを含む） |
| E02105 | エラー | 公開されていない名前の参照 |
| E02106 | エラー | 等式どうしで引数の数が違うか、シグネチャの矢印の数より多い |
| E02107 | エラー | 同じ関数の等式が離れている |
| E02108 | エラー | 取り込んだ名前が、ほかの取り込みの名前か、ファイルで定義した名前と重なる |
| E02109 | notice | 使われていない `where` の束縛 |
| E03100 | エラー | 網羅していないパターンマッチ |
| E03101 | エラー | 選ばれない選択肢（`otherwise` の後ろのガードを含む） |
| E03102 | エラー | ガードの並びの最後が `otherwise` ではない |
| E04100 | エラー | 手数の上限を超えた |
| E04101 | エラー | 末尾でない呼び出しの深さの上限を超えた |
| E04102 | エラー | `where` の束縛が、評価の途中で自分自身の値を求めた |

E01100 と E01101 は、golem-parser の構文の誤りと同じく、peg-hs のラベル付きの失敗で分ける（[golem-parser ADR 0009](../golem-parser/adr/0009-syntax-diagnostic-codes.md)）。
文法に回復の規則を持たせないので、一つのファイルの構文の誤りは最初の一つだけを報告する。
実装の中で原因がさらに分かれれば、E01104 から番号を足す。

戻した実装は、同じ誤りに上 2 桁 `10` の `G` のコード（G10100 など）を使っていた。
新しい接頭辞にしたので、`G10` の番号はどれも使わず、ほかの意味にも使い回さない。

### fmt

`golem fmt` は `.emet` も整形する。

- 字下げは空白二つとし、`where` と `case` の `{` の後と `}` の前で改行して、中を一段下げる。束縛と選択肢は一行に一つずつ置く。ガードは等式の名前の行の次の行から一段下げる。
- 宣言のあいだの空行は一つにまとめる。
- 行の長さで折り返さない。`.gm` と同じく、改行の位置は書き手が決める。続きの行の改行は、書き手が置いた位置に残す。
- コメントは元の位置に残す。
- 整形の前後で AST が一致すること、二度整形しても結果が変わらないことを、プロパティテストで検査する（[仕様書の「fmt」](../specifications.md#fmt) と同じ）。

改行は区切りなので、fmt は区切りの改行を足しも消しもしない。
字下げは意味を持たないので、fmt は字下げを自由に直せる。
オフサイドルールの言語では、字下げを変えると束縛の範囲が変わりうるので、fmt は字下げを自由に直せない。
この性質が、オフサイドルールを採らない理由である。
字下げの細部は実装で決め、仕様書に書く。

### パッケージ

新しいパッケージ `golem-emet` を `modules/golem-emet` に作る（名前は「メンテナーが決めること」の 14 と 16）。

- 文法は `modules/golem-emet/grammar/Emet.hpeg` に置き、peg-hs で生成する。生成物はコミットし、CI で生成し直して一致を検査する（[golem-parser ADR 0002](../golem-parser/adr/0002-parser-on-peg-hs.md)、[golem-parser ADR 0008](../golem-parser/adr/0008-hpeg-extension.md)）。
- 改行が区切りになる位置と空白になる位置で、空白の規則を分ける。括弧の中の式と外の式で空白の規則が違うので、式の規則を二通り持つ。
- CST、AST、型の検査、網羅性の検査、評価器、整形を、このパッケージに置く。
- build-depends は、golem-syntax（位置と diagnostic）、golem-doc（意味論 IR）、golem-eval（`Value` と数の演算）と、peg-runtime だけにする。golem-eval の数の演算を使うのは、式文脈と `.emet` で数の規則を二つ持たないためである。golem-eval は、そのために二項演算子と `div` を値の上の関数として公開する。
- golem-emet に依存するのは golem-driver と golem-lsp だけとする（[ADR 0162](0162-calling-emet-functions-from-gm.md)）。golem-fmt は golem-emet に依存せず、`golem fmt` は golem-driver を通して `.emet` の整形を呼ぶ。

## 実装しないこと

- 型クラス（後から足せる形にしておく。上の「型クラスの余地」）、高階の種、GADT、存在型、ランクの高い型。
- 中身を隠した型（コンストラクタを公開しない `pub data`）。
- 浮動小数点数と超越関数。
- オフサイドルール。字下げは意味を持たない。
- `;` の区切り。`;` は字句として持たず、書けば E01100 とする。
- `if`、`for`、`while`、`let ... in`。
- 利用者が演算子を定義すること。
- 利用者がハンドラを書くこと（[ADR 0161](0161-emet-requirements-and-driver-handlers.md)）。
- REPL と、`.emet` だけを実行するコマンド。
- 構文の誤りからの回復（二つめ以降の構文の誤りの報告）。

## テスト設計

テストを先に書き、golem-emet のモジュールがないためにコンパイルできないことを確かめてから実装する。

golem-emet のテストでは、次のことを確かめる。

- **区切り**：上の `cidSystemInfo` と `label` を読めること。字下げを変えた同じ宣言が同じ AST になること。括弧の中の改行、行末の演算子の後ろの改行、行頭の `|` と演算子の前の改行が、区切りにならないこと。行頭の `-` が新しい選択肢の負の数のパターンになること。二つの束縛を一行に書くと E01100、`;` を書くと E01100、閉じていない `{` が E01101、`if` と `class` が E01102 になること。
- **`where`**：最初の等式の後ろの `where`、二つめの `where`、`case` の選択肢の後ろの `where`、`where` の中の `where` が、それぞれ E01103 になること。`where` の中から引数のパターンの変数を参照すると E02100 になること。等式の引数の数がシグネチャと違えば E02106、等式のあいだに別の宣言を挟めば E02107 になること。
- **`:` と三項演算子**：`total` が `[1, 2, 3]` に 6 を返すこと。`c ? (x : xs) : ys`、`c ? [] : x : xs`、`a ? b : c ? d : e` が上の規則のとおりに読めること。`c ? x : xs : ys` が E01100 になること。
- **型**：未定義の名前が E02100、`Nat` を求める位置の `String` が E02101、シグネチャのない最上位の関数が E02102、`import` の循環（長さ 1 を含む）が E02103、二度の定義が E02104、公開されていない名前が E02105 になること。`Nat` から `Rat` へ暗に広がること。`'a' == "a"` が E02101 になること。`String.chars "漢字"` が二つの `Char` になること。利用者のデータ型を `==` で比べると E02101 になること。
- **網羅性**：`Maybe` の `Nothing` を欠いた等式が E03100 になり、メッセージに `Nothing` が出ること。`(x : xs)` だけの等式が E03100 になり、メッセージに `[]` が出ること。`otherwise` のないガードの並びが E03102 になり、最後に変数だけのガードのない等式があれば誤りにならないこと。最後のガードが `True` でも E03102 になること。`otherwise` の後ろのガードと二つ目の `_` が E03101 になること。三項演算子は常に網羅すること。
- **評価**：`where` の束縛の 0 での割り算が、その束縛を使わなければ誤りにならず、使えば G02 の割り算のコードになること。束縛を二度使っても一度だけ評価し、手数が一度分だけ増えること。どこからも使われない束縛が E02109 の notice になり、`silence-notices` に書けば出ないこと。自分自身を参照する束縛と、二つの束縛が互いを参照する場合が E04102 になり、メッセージに束縛の並びが出ること。`lazy` が E01102 になること。
- **取り込み**：`import "lib/a.emet"` の公開された関数を名前空間なしで呼べ、公開されていない名前が E02105 になること。二つの取り込みが同じ名前を公開すれば、参照しなくても E02108 になること。取り込んだ名前とファイルの中の定義が重なれば E02108 になること。`a.emet` が取り込んだ `b.emet` の名前が、`a.emet` を取り込んだファイルから E02100 になること。
- **末尾呼び出し**：1000 万回の末尾再帰と、二つの関数の相互の末尾再帰が、E04101 にならずに終わること。末尾でない再帰が深さ 10000 を超えて E04101 になり、メッセージと位置が上の表のとおりであること。
- **手数**：止まらない末尾再帰が E04100 になり、二度実行して同じメッセージと位置になること。上限を超えた呼び出しが出力を返さないこと。`s ++ s` を繰り返す関数が、メモリを使い果たす前に E04100 になること。「実装から分かったこと」の三つの仕事の手数が、上限の 3 分の 1 以下であること。
- **決定性**：同じ関数を並列に評価した結果と diagnostic が、逐次に評価したものと一致すること。
- **fmt**：任意の AST から作った原稿について、整形の前後で AST が一致し、二度の整形で変わらないことをプロパティテストする。続きの行の改行の位置が変わらないこと。コメントが整形の後も残ること。

## トレードオフ

改行で区切るので、一つの式を複数の行に分けるときは、続きの行であることを字句で示す必要がある。
行の最後に演算子を置くか、次の行を `|` や演算子で始めるか、括弧で囲む。
行頭の `-` だけは新しい項目の始まりになるので、引き算を次の行に続ける書き方は、行末に `-` を置く形に限られる。
その代わり、`;` を書かずに済み、Haskell の字下げで書いたコードに近い見た目になる。
字下げに意味を持たせないので、字下げの誤りで意味が変わることはない。

文法は、改行を字句として扱い、括弧の中と外で空白の規則を分けるので、戻した実装の `{ ; }` の文法より規則が増える。

型クラスを持たないので、v1 では利用者のデータ型を `==` で比べられず、`show` のような汎用の関数も書けない。
型クラスは、型の検査と誤りのメッセージを複雑にする。
v1 は組み込みの三つの述語にとどめ、足すときに開ける形にしておく。

`:` をリストの演算子にしたので、三項演算子の真の枝でリストをつなぐときは括弧が要る。
括弧を忘れると構文の誤りになり、別の意味に読まれて黙って通ることはない。

手数の上限で止めるので、正しいが重い関数は止まる。
止まったときに、上限を上げる手段を使い手は持たない。
重い仕事はプラグインの役割とする（[ADR 0162](0162-calling-emet-functions-from-gm.md)）。

メンテナーの案の拡張子 `.gmx` は、GameMaker Studio 1 のプロジェクトのファイルも使っていた。
`.emet` は、実装の前に、エディタと GitHub の言語の判定でほかの形式と重ならないかを確かめる。

新しいパッケージを一つ足し、golem-driver と golem-lsp の build-depends を変える。
golem-emet は golem-eval に依存するので、golem-eval の数の演算の変更が `.emet` にも及ぶ。
二つの言語の数の規則が同じであることを保つための、意図した依存である。

## 決めたことの記録

メンテナーが決めたことだけを書く。
ここにないことは、草案と戻した実装が選んだものであり、「メンテナーが決めること」に挙げる。

- **関数の立ち位置**（ロードマップ、メンテナー）：関数は社内の使い手と組版のオペレーターのものであり、プロジェクトの中だけで使う。配布の仕組みは作らない。[golem-eval ADR 0001](../golem-eval/adr/0001-expression-language-and-numerics.md) の「ユーザー定義の関数はプラグインの役割」の立場を改める（[ADR 0162](0162-calling-emet-functions-from-gm.md)）。
- **`where` の位置**（2026-11-04、メンテナー）：「where は関数の末尾に `{}` 内で宣言させる」。この草稿はこれを、一つの関数に一つの `where` を、最後の等式の後ろに `{ }` で置くことと読んだ。Haskell の `where` は等式ごとに置け、その等式の引数を参照できるが、関数ごとに一つにすると、`where` が等式の引数を参照できなくなる。`where` の中から等式の引数が見えるかは、「メンテナーが決めること」の 10 に残す。
- **ガードの網羅性**（2026-11-04、メンテナー）：ガードのある関数の網羅性は、条件の意味を解析せず、構文の規則で検査する。規則の中身（`otherwise` で終わること、例外、E03102）は草案が書いたものであり、「網羅性の検査」の節のとおりとする。
- **止まらない評価のコード**（2026-11-04、メンテナー）：「コードを決めましょう」。上限を超えたときの diagnostic のコードは、実装に任せずこの ADR で決める。深さと手数を分けること、番号、重大度、位置、上限の値は草案と実装が選んだものであり、「メンテナーが決めること」の 8 と 9 に挙げる。
- **文字列の型**（2026-11-04、メンテナー）：「型をひとつにする」。`String` と `Text` のような二つの文字列の型を持たず、`T.pack` のような変換も持たない。`Char` の型を持つかは別の問題であり、「メンテナーが決めること」の 5 に挙げる。
- **`lazy` の対象**（2026-11-04、メンテナー）：「lazy の範囲」に「束縛」と答えた。`lazy` は束縛に付ける。関数と引数には付けない。
- **名前を変えること**（2026-11-05、メンテナー）：「gmx は名前を変える。Golem Expression のつもりだった」。この草稿が出した候補から、「名前は emet で」と決めた。言語の名前を Emet、拡張子を `.emet`、パッケージを golem-emet とする。
- **型クラス**（2026-11-05、メンテナー）：型クラスは将来拡張する可能性があるとした。v1 は型クラスを持たないが、後から足せる形にする。どう余地を残すか（「型クラスの余地」の節）は、この草稿の案であり、「メンテナーが決めること」の 12 に挙げる。
- **`where` の中の区切り**（2026-11-05、メンテナー）：「where 内の `;` の区切りは採用しない。改行で区切る」。同じ規則を最上位の宣言と `case` の選択肢に広げるこの草稿の読み方を、メンテナーは「問題なし」とした。
- **リストの `:`**（2026-11-05、メンテナー）：「リストの `(x : xs)` は維持する。おそらく PEG で書けるはず」。`:` をリストの先頭と残りをつなぐ演算子とし、パターンにも書ける。三項演算子の `:` との読み分け（「パターンマッチ」の節の規則）は、この草稿の案であり、「メンテナーが決めること」の 6 に挙げる。
- **リストのリテラル**（2026-11-05、メンテナー）：「リストリテラルの `[]` は許容する」。`[]` と `[a, b, c]` をリストのリテラルとして書ける。
- **`let` を持たないこと**（2026-11-06、メンテナー）：「let は where があるからおそらく不要」。
- **`Char` の型**（2026-11-06、メンテナー）：「Char はいちおう残す。リストとの整合性がとれないので」。`String.chars` が字のリストを返すために、一字を表す型を持つ。
- **三項演算子**（2026-11-06、メンテナー）：「三項演算子は何とかして残して。枝の最上位にはたぶん書けなくても大丈夫」。真の枝の最上位に括弧のない `:` を書けなくする読み分けを採る。
- **二つの上限**（2026-11-06、メンテナー）：「8、9 はおそらく問題ない。問題が発生したら緩和する」。
- **`where` から引数を見ないこと**（2026-11-06、メンテナー）：「where のなかから引数は見えない」。
- **型クラスの余地**（2026-11-06、メンテナー）：「なるべく余地を残して。あとで苦労することになるから」。
- **パッケージ**（2026-11-06、メンテナー）：「eval には混ぜない」。
- **ガード**（2026-11-06、メンテナー）：「`|` でよい。if が排除できるほうが嬉しい」。
- **組の型**（2026-11-06、メンテナー）：「推奨で」。
- **選ばれない選択肢**（2026-11-06、メンテナー）：「原則に従いエラーで」。
- **`where` の評価**（2026-11-06、メンテナー）：「where 内は遅延評価とする」。2026-11-04 の「`lazy` は束縛に付ける」は、`where` の束縛を遅延評価にすることで満たし、`lazy` の語は使わない。
- **取り込みの名前空間**（2026-11-06、メンテナー）：「変数も名前空間をつけない。衝突したらエラー」。
- **使われていない束縛**（2026-11-06、メンテナー）：「使わなかった束縛は notice にして」。[ADR 0162](0162-calling-emet-functions-from-gm.md) の lint の規則から外し、型の検査の notice（E02109）にする。
- **コードの接頭辞**（2026-11-06、メンテナー）：「新たなエラーコードのプレフィックスを作って。どうせ v1 で廃止したエラーとかを消すので、この段階では自由にいじってよい」。

## メンテナーが決めること

採択の前に、次のことを決めてほしい。
それぞれに、この草稿の推奨と、採らなかった案を書く。
本文は推奨の案で書いてあり、違う案を採れば書き換える。
決めた項目は、番号を変えないように残し、決めたことを書く。

1. **改行の区切りを最上位と `case` にも広げるか**：決めた。最上位の宣言と `case` の選択肢も改行で区切り、`;` を字句として持たない（「決めたことの記録」）。
2. **`[]` を使わないことの範囲**：決めた。リストのリテラル `[]` と `[a, b, c]` を許す（「決めたことの記録」）。
3. **`if` の扱い**：決めた。条件はガード `|` としてだけ書き、`if` を言語から除く（「決めたことの記録」）。
4. **`let ... in` を持たないこと**：決めた。`let ... in` を持たず、局所の束縛は `where` だけで書く（「決めたことの記録」）。
5. **文字の型**：決めた。`Char` の型と文字のリテラル `'a'` を持ち、`String` は `List Char` とは別の一つの型とする（「決めたことの記録」）。
6. **三項演算子と `:` の読み分けと、組の型**：決めた。三項演算子の真の枝の最上位に括弧のない `:` を書けなくし、組の型 `(a, b)` を持つ（「決めたことの記録」）。
7. **網羅しない選択肢の重大度**：決めた。緩い規則より厳しい規則の原則に従い、選ばれない選択肢（E03101）をエラーにする（「決めたことの記録」）。
8. **二つの上限の分け方と位置**：決めた。推奨のとおり、深さの上限（E04101）と手数の上限（E04100）を別のコードのエラーにし、位置を評価を始めた `.gm` の呼び出しにし、上限を超えた呼び出しは出力を返さない（「決めたことの記録」）。
9. **上限の値と数え方**：決めた。推奨のとおり、深さの上限を 10000、手数の上限を 100,000,000 とし、`.gm` からの一つの呼び出しごとに数え、`manifest.toml` で変えられない（「決めたことの記録」）。
10. **関数の末尾の `where` から等式の引数が見えるか**：決めた。見えない（「決めたことの記録」）。
11. **`where` の束縛の評価の時期**：決めた。`where` の束縛は遅延評価する（「決めたことの記録」）。これに伴い、`lazy` の語は付ける場所がなくなるので、使えない予約語（E01102）にした。自分自身の値を求める束縛は、循環を見つけた時点で E04102 とする。
12. **型クラスの余地の残し方**：決めた。なるべく余地を残す（「決めたことの記録」）。中身は「型クラスの余地」の節のとおりで、草稿の最初の案（三つの述語、予約語、`=>` を空けること）に、型の検査と評価器の形、組み込みの関数の型、データ型の比較の順を加えた。
13. **`import` の形**：決めた。`import "パス"` で、公開された名前を名前空間を付けずに取り込み、名前が重なればエラー（E02108）とする（「決めたことの記録」）。`module` の宣言は書かない。重なりを取り込んだ時点で誤りにすることと、取り込みが推移しないことは、この草稿の案である。
14. **パッケージと build-depends**：決めた。golem-eval には混ぜず、新しいパッケージ golem-emet を作る（「決めたことの記録」）。golem-emet は golem-syntax、golem-doc、golem-eval、peg-runtime に依存し、golem-driver と golem-lsp だけが golem-emet に依存する。
15. **diagnostic のコードの体系**：決めた。新しい接頭辞 `E` を作り、上 2 桁を段階とする（「決めたことの記録」）。段階の分け方（E01 から E07）は、この草稿の案である。
16. **言語の名前と拡張子**：決めた。Emet（拡張子 `.emet`、パッケージ golem-emet）とする（「決めたことの記録」）。ゴーレムの伝説で、ゴーレムの額に書いて動かす語が emet（真理）であり、Golem の見た目の回帰テストの描画器 shem と同じ由来の名である。
