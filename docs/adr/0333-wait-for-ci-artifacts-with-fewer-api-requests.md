# ADR 0333: CI の成果物を待つ問い合わせを減らし、利用上限の応答を待って再試行する

ステータス: 採択（未実装）

## 文脈

Golem の CI では、四つのジョブが同じビルドの異なる成果物を待つ。
`visual` は PDF、`wasm` は native 版との比較表、`editors-lsp` は実行ファイル、`verapdf` は適合宣言のある PDF を使う。
これらのジョブは、ビルド行列全体の終了を待たずに検査を始める（[ADR 0099](0099-visual-job-waits-only-for-visual-pdfs.md)、[ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md)、[ADR 0231](0231-run-the-lsp-and-the-editor-grammars-in-headless-neovim-and-helix.md)、[ADR 0244](0244-take-verapdf-off-the-critical-path-of-ci.md)）。

成果物がまだなければ、各ジョブは 10 秒ごとに、成果物の数と、それを上げるジョブの状態を GitHub API に問い合わせる。
[run 42892137240 の visual](https://github.com/tett23/golem/actions/runs/42892137240/job/130113951352) と [run 42905024634 の visual](https://github.com/tett23/golem/actions/runs/42905024634/job/130141516621) を含め、両実行の四つの待機ジョブで `API rate limit exceeded for installation` と HTTP 403 が記録された。
前者は失敗したジョブを再実行した試行でも同じ応答を受けた。
利用枠を消費した全リクエストの内訳、実際のリセット時刻、ほかのワークフローとの共有範囲は未確認である。

## 実装すること

成果物を 30 秒ごとに問い合わせ、存在すれば終了コード 0 で終える。
有効期限の切れた成果物は数えない。
成果物がないときだけ、最初の問い合わせと、その後 4 回の待機間隔ごとに、現在の試行のジョブ一覧を調べる。
`WAIT_INTERVAL` の指定があれば、30 秒の代わりにその値を使う。

ジョブの照合には従来の名前の規則を使う（[ADR 0165](0165-wait-pdfs-finds-the-job-under-a-caller-prefix.md)）。
該当するジョブが終わっていたら、成果物が最初の問い合わせと入れ違いで上がっていないか一度だけ確かめる。
成果物がなければ終了コード 1 とする。

API の応答は、同じ `gh api` 呼び出しに `--include` を付けて読み取る。
HTTP 429、または `gh` が利用上限と明示した HTTP 403 のときだけ、その問い合わせを待ってやり直す。
403 の識別には、実障害の `API rate limit exceeded` と `secondary rate limit` のどちらかを、大文字と小文字を区別せずに使う。
失敗したページがあれば、途中まで読んだジョブ一覧は破棄する。

待ち時間は次のように決める。

- 正の整数の `Retry-After` は秒数として読む。
- `X-RateLimit-Remaining` が 0 で `X-RateLimit-Reset` が現在以降の時刻なら、指定時刻の 1 秒後まで待つ。
- 両方があれば、長いほうを使う。
- どちらからも待ち時間が決まらなければ、同じ問い合わせで順に 60、120、240、480、600 秒待ち、それ以降は 600 秒ごとに試す。

元の応答と次の待ち時間をログに残す。
待機全体の上限は既存の `timeout -k 10 3600` に委ねる。
上限より長い待ち時間が返っても、期限より早く API を呼ぶために短縮しない。

## 実装しないこと

今回の対象は成果物を待つ処理である。
成果物の生成、ダウンロード、検査の失敗を再試行する機能は加えない。
権限、トークン、ジョブの依存関係、成果物名、待機時間の上限は変えない。
新しい実行を始めたり、別の実行にある成果物を代わりに使ったりしない。

## 不変条件

1. W1：同じ実行に期限内の成果物があれば成功し、最初からあればジョブ一覧を一度も読まない。
2. W2：成果物がなく、照合したジョブが 0 件または複数あれば失敗し、1 件が終了済みなら成果物を再度確認した結果で決める。
3. W3：利用上限を明示した応答の後は、指定された時刻より前に同じ API を呼ばない。
4. W4：再試行の対象外のエラーでは、同じ問い合わせをもう一度発行せず、失敗終了する。
5. W5：利用上限がなく API の所要時間を 0 とするモデルでは、成果物は公開後 30 秒以内、成果物を欠くジョブの終了は 120 秒以内に検出する。
6. W6：外側の待機上限に達すると、利用上限の再試行も終わる。

| 境界の入力 | 期待する結果 |
| --- | --- |
| 開始時に成果物がある | 成果物を 1 回問い合わせて成功 |
| 最後の問い合わせの 1 秒後に成果物ができる | 既定の間隔では、その 29 秒後に検出 |
| 成果物の問い合わせとジョブ終了の照合の間にアップロード | 最後の確認で成功 |
| 該当する名前が 0 件、または呼び出し元を含めて 2 件 | ジョブを選ばずに失敗 |
| HTTP 403、権限不足 | リセット時刻のヘッダーがあっても失敗 |
| 利用上限を示す HTTP 403、リセットは開始から 125 秒後 | 開始から 126 秒後に同じ問い合わせを再試行 |
| HTTP 429、`Retry-After: 65` | 同じ問い合わせを 65 秒後に再試行 |
| 利用上限が開始から 4000 秒後に解除される | 3600 秒の上限まで新たに問い合わせない |

## テスト設計

未コミットの試作は `scripts/visual/wait-pdfs.sh:35` の API 呼び出しと `scripts/visual/wait-pdfs.sh:80` の照合間隔を変えた。
`sh experiments/ci-wait/compare.sh` は基準コミットのスクリプトと試作に、同じ仮想時計、偽の gh、同じ応答を渡す。
結果を `experiments/ci-wait/results.tsv` に保存した。
表の回数は 1 ジョブが発行した gh の問い合わせの数であり、ジョブ一覧が 1 ページだった場合の API リクエスト数でもある。

| 入力 | 現行の回数 | 試作の回数 | 現行の検出時刻 | 試作の検出時刻 |
| --- | ---: | ---: | ---: | ---: |
| 開始から 1 秒で成果物を公開 | 3 | 3 | 10 秒 | 30 秒 |
| 301 秒で公開 | 63 | 15 | 310 秒 | 330 秒 |
| 1801 秒で公開 | 363 | 78 | 1810 秒 | 1830 秒 |
| 成果物を欠いたまま 61 秒でジョブ終了 | 17 | 8 | 70 秒 | 120 秒 |

現行に新しい期待値を当てると、長い待機の回数上限、利用上限からの復帰 3 件、外側の時間上限までの待機の 5 項目で失敗した。
この試験では、仮想時刻が 3600 秒に達したときに偽の sleep が 124 を返して、外側の timeout を模擬する。
試作では 15 シナリオすべてが通り、終了コードは 0 だった。
利用上限のない正常系では、API の呼び出しを減らす分、成果物やジョブの終了に気づくまでの時間が延びる。
本実装では W1 から W6 の仮想時計のテストを、既存の CI スクリプトの試験に組み込む。

インストール済みの gh でも、ローカルの HTTP サーバーとダミーのトークンで応答の読み方を確かめた。
`node experiments/ci-wait/gh-loopback.mjs` で、利用上限の 403 と待ち時間 1 秒を受けたケースは 2 リクエストで成功し、同じ待ち時間を持つ権限不足の 403 は 1 リクエストで失敗した。
2 ページのジョブ一覧に該当する名前が一つずつ出るケースでも、両方の名前を示して終了コード 1 になった。
実際の gh の結果は `experiments/ci-wait/gh-loopback.jsonl` に保存した。
既存の `sh scripts/visual/test.sh` は 181 件成功した。
障害が起きた GitHub の利用枠をこの試作で回避できるかは、本番の CI では確かめていない。

## トレードオフ

ポーリングをやめ、`needs` でジョブの完了を待てば、待機用の API リクエストはなくなる。
その代わり、成果物を使える時点と、依存先のジョブが終わる時点が離れる。
[ADR 0244](0244-take-verapdf-off-the-critical-path-of-ci.md) の調査では、適合宣言の PDF を上げた後にも `outputs` の処理が約 85 秒あった。

同じ四つの成果物の公開時刻を 120、180、240、301 秒、生成元ジョブの終了を 386 秒、行列全体の終了を 481 秒と置いて比較した。
`node experiments/ci-wait/dependencies.mjs` が計算した次の表は仮想時刻での比較であり、GitHub 上でジョブを分割して測った時間ではない。
依存先の終了通知とジョブの開始の間の待ち時間はすべて 0 とした。

| 待ち方 | 問い合わせ総数 | 公開から検出までの平均 | 最後の成果物の検出 |
| --- | ---: | ---: | ---: |
| 現行の 10 秒間隔 | 174 | 2.25 秒 | 310 秒 |
| 試作の 30 秒と 120 秒の間隔 | 41 | 7.25 秒 | 330 秒 |
| `needs: build` で行列全体を待つ | 0 | 270.75 秒 | 481 秒 |
| 生成元だけを独立させ、その終了を待つ | 0 | 175.75 秒 | 386 秒 |
| 四つの成果物だけを公開するジョブに分け、その終了を待つ | 0 | 90.75 秒 | 301 秒 |

この提案は、現在のビルドの分担を保ちながら、API リクエストを減らす案を選ぶ。
公開専用ジョブに必要なビルドや成果物の転送の費用は、表に含めていない。
また、別のワークフローの負荷や同時に始まるジョブの集中まで、この待機間隔で解消できるとは限らない。
ジョブを分割する案を採るには、実際の CI の公開時刻と分割後のビルド時間を別に測る必要がある。
