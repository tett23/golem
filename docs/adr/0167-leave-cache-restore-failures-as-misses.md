# ADR 0167: キャッシュの復元が egress の上限で失敗しても、再試行もタイムアウトの変更もしない

ステータス: 採択

## 文脈

[ADR 0009](0009-ci-speed.md) は、`build` ジョブで GHC、Hackage の索引、cabal の store、`dist-newstyle`、cddl の CLI をキャッシュすると決めた。
store のキャッシュが外れると、依存のパッケージをすべてビルドし直す。

### 実行 41915724203 で起きたこと

プルリクエスト #543 の CI の実行 41915724203（2026-11-04）で、`build (ubuntu-24.04, tests-rest)`（ジョブ 126874837533）の store の復元が途中で止まった。
ログの流れは次のとおりである。

```
21:24:28.47 Cache hit for: cabal-store-Linux-X64-ghc-9.10.3-b042b13a…
21:24:29.53 Received 94239559 of 102628167 (91.8%), 89.8 MBs/sec
            （同じ受信量の行が 1 秒ごとに 15 行続く）
21:24:44.76 ##[warning]Failed to restore: Egress is over the account limit.
21:24:44.76 Cache not found for input keys: cabal-store-Linux-X64-ghc-9.10.3-b042b13a…, cabal-store-Linux-X64-ghc-9.10.3-
```

`cabal build all peg-cli:exe:peg-hs` の手順は 16 分 23 秒かかった。
同じ実行のほかの六つの `build` のランナーでは、同じ手順は 2 秒から 6 秒で、ジョブは 1 分から 2 分で終わった。
実行の全体は、このジョブを待って約 18 分になった。
後片付けの手順は、復元できなかったキーで store を保存し直した（約 96MB、プルリクエストの範囲）。

この失敗は、ダウンロードが止まったまま時間切れになったものではない。
91.8% で受信が止まった 15 秒後に、キャッシュのサービスが「アカウントの egress の上限を超えた」と答え、`@actions/cache` はそれを警告にして外れとして扱った。
`@actions/cache` は、検証の誤り以外の復元の誤りを、すべて外れとして扱う（キャッシュは任意の高速化であるという方針による）。
5xx の応答は error、それ以外は warning として書く。
この行が warning なので、応答は 5xx ではなかった。

### どれほど起きているか

`ci.yml` の完了した最近の 400 の実行のうち、212 の実行のログを `gh run view --log` で取り、キャッシュの行を数えた（2026-11-05）。
新しい 150 の実行（2026-11-04 の 05:58 から 22:07）はすべて取り、残りの 250 の実行（2026-10-24 まで）は 4 つに一つを取った。

- キャッシュの手順を持つ実行は 177 だった。残りの 35 は、docs だけの変更でビルドを省いた実行と、取り消された実行である。
- `Cache hit for` の行は 4881、`Cache not found` の行は 97 だった。外れの大半は、`dist-newstyle` のようにコミットごとにキーが変わるキャッシュの、キーの一致しない復元である。
- `Failed to restore` は、実行 41915724203 の一回だけだった。store の復元に限ると、916 回のうちの一回である。
- `actions/cache` の README が書く、セグメントのダウンロードの時間切れ（`SEGMENT_DOWNLOAD_TIMEOUT_MINS`）による中断は、一回もなかった。

### egress の量

同じ 177 の実行で、復元を終えたキャッシュの大きさを足すと、一つの実行あたり平均で約 4.6GB だった。
2026-11-04 には、`ci.yml` の実行が 214 あった（このほかに `release.yml` の実行もある）。
この日だけで、キャッシュの復元はおよそ 1TB になる見込みである。
アカウントの egress の上限の値と、それを数える期間は、この ADR を書くときに確かめられなかった。
上限に届いたのが、この日の実行の多さによるものかは推測にとどまる。

## 実装すること

ワークフローは変えない。
キャッシュの復元が失敗したら、今と同じく外れとして扱い、依存をビルドし直す。

- `docs/roadmap.md` の「課題にしなかった事項」に、キャッシュの復元が egress の上限で失敗することがあり、この ADR の判断で手を加えていないことを一行で書く。
- 見直す条件は次のとおりとする。同じ警告（`Failed to restore: Egress is over the account limit.`）が、7 日のうちに二つ以上の実行で出たら、egress を減らす方法（キャッシュの数と大きさ、ランナーの数）を決める新しい ADR を書く。警告は実行の注釈に出るので、気付く手段はすでにある。

## 実装しないこと

### SEGMENT_DOWNLOAD_TIMEOUT_MINS を変えること

`SEGMENT_DOWNLOAD_TIMEOUT_MINS` は、止まったセグメントのダウンロードを指定の分数で打ち切り、外れとして進める（既定は 10 分）。
今回の失敗は、サービスの応答によって 16 秒で打ち切られており、この時間切れは働いていない。
値を下げても今回の失敗は防げず、遅いが進んでいるダウンロードを外れに変える危険だけが増える。
標本の 212 の実行にも、この時間切れで打ち切られた復元はなかった。

### 復元を再試行すること

store の手順を `actions/cache/restore` と `actions/cache/save` に分け、一回目が外れたら、少し待ってもう一度復元する形である。
次の理由で採らない。

- 利益が小さい。標本では 916 回に一回で、一回あたり約 15 分の損である。均すと、復元一回あたり約 1 秒になる。
- 再試行が役に立つ見込みが低い。失敗の原因はアカウントの egress の上限なので、上限が戻るまでの時間がわからないまま、上限を超えている最中に要求を重ねることになる。
- 外れと失敗を区別できない。`actions/cache` は失敗を外れとして返すので、出力（`cache-hit`、`cache-matched-key`）だけでは、キーの変わった本当の外れと区別がつかない。再試行は、freeze ファイルを変えたプルリクエストでも毎回走り、その手順の正しさを確かめるテストも要る。
- 手順が増え、[ADR 0009](0009-ci-speed.md) と [ADR 0045](0045-split-x86-build-and-pull-request-cache.md) が決めた、store の保存の条件を書き直すことになる。

### 復元の失敗でジョブを失敗させること

失敗を外れでなく誤りにすると、作者が実行し直せば数分で済む。
しかし、遅いが正しく通る実行を、失敗する実行に変える。
`ci` の判定が上流の一時的な状態で落ちることになり、[ADR 0157](0157-check-wasmtime-pin-against-advisories.md) がプルリクエストの CI でアドバイザリを照合しないとした理由と同じ理由で採らない。

### egress を減らすこと

一つの実行で約 4.6GB を復元する今の形は、上限に近づく原因になりうる。
ただし、上限の値が確かめられず、失敗は一回だけなので、減らす手段（キャッシュをまとめる、ランナーを減らす）の得失を今は比べられない。
見直す条件を満たしたときの ADR で扱う。

## テスト設計

ワークフローを変えないので、自動テストはない。
`docs/roadmap.md` の変更は、`sh scripts/ci/textlint.sh` と `adr-guard links` で確かめる。

## トレードオフ

- 同じ失敗がまた起きれば、その実行は 15 分ほど遅くなる。作者は待つか、実行をやり直す。標本の頻度では、およそ 200 の実行に一回である。
- 見直す条件は、警告の注釈を人が見て気付くことに頼る。注釈を数える仕組みは足さない。条件を満たしたことに気付かず、遅い実行が続く可能性は残る。
- 標本は 2026-10-24 から 2026-11-04 の 212 の実行で、新しい側に偏っている。egress の上限が日ごとの量に依存するなら、実行の多い日の失敗は、この標本の頻度より多い可能性がある。
