# ADR 0043: 表のファイルの大きさの上限

ステータス: 採択

## 文脈

`@table` は、CSV と TSV のファイルを読んで表にする（[golem-eval ADR 0004](../golem-eval/adr/0004-tsv-tables.md)）。
2026-10-18 のセキュリティ監査（[docs/audits/2026-10-18-security-audit.md](../audits/2026-10-18-security-audit.md)）の T1 で、ふつうの大きな表でも次のことがわかった。

- 読み込みは、TSV で入力の約 75 倍、CSV で約 130 倍から 160 倍のメモリを使う。CSV の読み手が `String` にしてから全体を `Either` の再帰で読むためである。
- PDF では 1 行あたり約 50 KB を使い、20 万行の表は 110 秒と 10.3 GB を使った。
- ファイルの大きさにも行の数にも上限がない。
- LSP は原稿の変更のたびに表のファイルを評価し直す。

組版する本の表が数万行になることは考えにくく、上限を設けても失うものは小さい。
一方、上限がなければ、clone した原稿の表でビルドする人のマシンを止められる。

## 実装すること

### 上限（G0288）

- 表のファイルは、大きさが 16 MiB（2^24 バイト）以下、行の数（見出しの行を含む）が 10,000 以下、1 行のセルの数が 256 以下とする。
- どれかを超えれば、新しいエラー G0288 を出す。位置は `@table` のブロックとし、メッセージは、ファイルのパスと、超えた上限（大きさ、行の数、セルの数のどれか）と、その値を述べる。
- 大きさはファイルを読む前に調べ、超えていればファイルの中身を読まない。
- 行の数とセルの数は読みながら数え、超えた時点で止める。残りは読まない。
- G0288 は dev と prod の両方でエラーである。評価の段階で出し、LSP も同じく出す。
- `cells=markup` を実装するときも同じ上限を使う。

### メモリ

- CSV と TSV の読み手は、`Text` のまま行ごとに読み、`String` を作らない。
- 一つの表の読み込みの割り当ては、ファイルの大きさの 16 倍以下とする。
- この変更は仕様を変えないが、上限と同じ変更で行う。

### ドキュメント

- `docs/diagnostics.md` に G0288 の節を足す。
- 仕様書と `docs/markup.md` の `@table` の節に、上限を書く。
- golem-eval の仕様書に、上限の値と数え方を書く。
- 利用者向けマニュアルの表の章と diagnostic の付録に、上限を書く。

## 実装しないこと

- 上限を `manifest.toml` で変えられるようにすること。必要になれば別の ADR で足す。
- PDF の組版での 1 行あたりのメモリの削減。行の数の上限で 10,000 行までは組めるが、組版の側の性能は別に調べる。
- LSP で表の評価をファイルが変わらないあいだ使い回すこと。性能の改善であり、別の ADR にする。
- `@import` や `@listing` のファイルの大きさの上限。表と違い、本文として組まれるので別の判断が要る。

## テスト設計

修正の前に失敗することを確かめてから実装する。

- golem-eval
  - 16 MiB を 1 バイト超える TSV が G0288 になり、メッセージに大きさの上限がある。16 MiB ちょうどの TSV は読める。
  - 10,001 行の TSV が G0288 になり、10,000 行は読める。
  - 257 セルの行を持つ CSV が G0288 になり、256 セルは読める。
  - 1 MiB の CSV の読み込みの割り当てが 16 MiB 以下である（`GHC.Stats` で測る）。
  - 既存の表の fixture の評価の結果が変わらない。
- golem-driver
  - 大きな表の原稿で `golem build --target text` が G0288 を出し、ビルドが 10 秒以内に終わる。
- golem-lsp
  - 大きな表の原稿を開くと、G0288 が `@table` の位置に出る。
- `docs/diagnostics.md` の G0288 の節は、golem-driver の既存のテストが確かめる。

## トレードオフ

- 10,000 行、256 列、16 MiB を超える表は組めなくなる。本の表としては十分だが、データの一覧をそのまま組む用途には足りないことがある。その場合は表を分ける。上限の変更を利用者が提案したときは、この ADR を書き換えず、新しい ADR で判断する。
- 上限は三つの値を同時に設ける。どれか一つ（大きさだけ）でもメモリは限れるが、行の数と列の数は組版の時間を限るために要る。
- 新しい diagnostic のコード G0288 を足す。G0285（表になりません）の理由にする選び方もあったが、上限は表の形の問題ではないので分けた。
