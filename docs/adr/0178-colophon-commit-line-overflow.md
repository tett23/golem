# ADR 0178: 奥付のコミットの行を版面に収める

ステータス: 採択

## 文脈

二つのマニュアルの奥付は、組んだコミットのハッシュを載せる（[docs/adr/0024](0024-manual-audiences-and-policy.md) の「奥付の版」）。
作業ツリーにコミットしていない変更があると、ハッシュの後に「（コミットしていない変更を含む）」が続く。
ロードマップの v0.1.0-rc4 の「奥付のコミットの行」は、このときコミットの行が版面の右にはみ出すとしている。

### 再現

`main`（`50b9fca8`）の `manual/` を作業用のディレクトリに写し、`manual/fonts` に取得済みのフォントを置いて組んだ（2026-11-06）。
`build-info.gm` は、`GOLEM_MANUAL_COMMIT` に 40 桁のハッシュと「（コミットしていない変更を含む）」をつないだ値を渡して `scripts/manual/build-info.sh` で書いた。
組んだ `golem` は、`50b9fca8` から作業用のディレクトリでビルドしたものである。

- 325 ページの奥付で、`50b9fca8…d2c（コミットしていない変更を含む）` が一行に組まれ、閉じ括弧が版面の右の端を越えて余白に出る。150dpi の PNG に描いて確かめた。
- `golem preflight` は、`back.gm:21` に「行が行長から 30.88mm はみ出しています（PDF の 325 ページ目）」（G09013）を出す。
- `GOLEM_MANUAL_COMMIT` にハッシュだけを渡した場合は、ハッシュが一行に収まり、`back.gm` の G09013 は出ない。

`scripts/manual/build.sh` は `golem build` の diagnostic が一つでもあれば失敗するが、はみ出す行は `golem build` では diagnostic にならず、プリフライトだけが報告する（仕様書の「行分割」）。
そのため、マニュアルの CI はこのはみ出しで止まらない。

### 原因

奥付は、コミットの値の全体を本文の中のコードにしている（[`manual/back.gm`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/manual/back.gm#L21-L22)、[`manual-dev/back.gm`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/manual-dev/back.gm#L21-L22)）。

```text
- コミット：\
  [code: [= build.commit]]
```

`build-info.sh` は、変更があるとき、「（コミットしていない変更を含む）」を `commit` の値そのものにつなげる（[`build-info.sh`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/scripts/manual/build-info.sh#L25-L31)）。
したがって、注記の和文もコードとして組まれる。

本文の中のコードは、空白と `/` の後でしか改行しない（仕様書の文字スタイル `code` の節、[golem-driver ADR 0017](../golem-driver/adr/0017-pdf-code-blocks.md)）。
`codePieces` は空白とタブのあいだの文字の連なりを一つの片にし（[`Japanese.hs`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/modules/golem-layout/src/Golem/Layout/Japanese.hs#L409-L422)）、`codeItems` はその片を欧文と和文の境目で箱に分けるが、箱のあいだの改行は `/` の後にしか許さない（[`Japanese.hs`](https://github.com/tett23/golem/blob/50b9fca8a0744f6f9d92808db231e6c04ac35d2c/modules/golem-layout/src/Golem/Layout/Japanese.hs#L649-L674)）。
コミットの値には空白も `/` もないので、ハッシュと注記の全体が改行できない一続きになる。
行分割は、一つの箱が行長より長い場合と同じく、行長からはみ出す行を作る。

ハッシュだけなら、コードの書体の 40 字は行長に収まる。
はみ出すのは、改行できない和文の注記がハッシュに続くからである。

### 同じ原因のほかのはみ出し

ハッシュだけで組んだ利用者のマニュアルでも、`golem preflight` は付録 E の 4 か所（269、276、286、287 ページ）に G09013 を出す。
269 ページを描いて確かめたところ、G03029 の項目の語の、和文のメッセージを入れたコード（`[hidden-folio] の gutter（…）が size（…）の半分（…）より小さいため、…`）が右にはみ出していた。
和文を含む長いコードが改行できないという原因は奥付と同じである。
ほかの三か所は描いて確かめていない。
これらは奥付の行ではないので、この ADR では直さない（「メンテナーが決めること」の 3）。

## 実装すること

### `build-info.gm` の変数（`scripts/manual/build-info.sh`）

コミットしていない変更があることを、ハッシュとは別の変数にする（「メンテナーが決めること」の 1）。

```text
%% scripts/manual/build-info.sh が書いたファイル。手で編集しない %%
@set edition = "0.1.0-rc3 の開発版"
@set commit = "0123456789abcdef0123456789abcdef01234567"
@set uncommitted = "（コミットしていない変更を含む）"
```

- `commit` は、変更の有無にかかわらず、`git rev-parse HEAD` の 40 桁のハッシュだけとする。
- `uncommitted` は、追跡しているファイルにコミットしていない変更があれば「（コミットしていない変更を含む）」、なければ空の文字列とする。変更の有無の判定（`git status --porcelain --untracked-files=no`）は今のとおりである。
- `GOLEM_MANUAL_COMMIT` があるときは、今のとおりその値を `commit` にし、`uncommitted` は空の文字列とする。Git のリポジトリの外では、変更の有無を読めないからである。
- 変数の名前に `-` は使えない（`@set commit-note = …` は G01010 になることを確かめた）ので、一語の `uncommitted` にする。

### 奥付（`manual/back.gm`、`manual-dev/back.gm`）

コードにするのはハッシュだけにし、注記は本文の文字として続ける。

```text
- コミット：\
  [code: [= build.commit]][= build.uncommitted]
```

注記は本文の和文として組まれるので、JLReq の禁則に従って字のあいだで改行できる。
三つの変数は、どれも奥付で使う。
使わない変数は lint の「使われていない `@set` 変数」になるという [docs/adr/0024](0024-manual-audiences-and-policy.md) の制約は、そのまま満たす。

試作として、写した `manual/` の `build-info.gm` と `back.gm` をこの形に書き換えて組んだ（変数の名前は試作では `note`）。
試作を組んだ `golem` は手元に入れてある 0.1.0-rc3 で、書き換える前の `manual/` からは、`50b9fca8` からビルドしたものと同じ PDF を出力することを確かめてある。

- 変更ありの値では、325 ページの奥付が `50b9fca8…d2c（コミットして` と `いない変更を含む）` の二行になり、版面に収まった。`golem preflight` は `back.gm` に G09013 を出さなかった。
- 変更なしの値（空の文字列）では、325 ページの 150dpi の PNG が、今の奥付で組んだものとバイト単位で一致した。PDF のバイト列は変わった。変わった箇所の中身は調べていない。
- `golem lint` の diagnostic は、書き換えの前後で同じだった。

### ドキュメント

- 仕様書のマニュアルの節の `commit` の説明を、ハッシュだけの `commit` と、変更の有無を表す `uncommitted` の二つに書き換え、この ADR へのリンクを付ける。
- 開発者のマニュアルの「奥付の版」（`manual-dev/part2/15-manuals.gm`）の `build-info.gm` の例、変数の説明、奥付の例を書き換える。「二つの変数」は「三つの変数」にする。
- [docs/manual-policy.md](../manual-policy.md) の奥付の項目を、`コミット：[code: [= build.commit]][= build.uncommitted]` の行に書き換える。
- `scripts/manual/build-info.sh` の冒頭の説明を書き換える。
- [docs/adr/0024](0024-manual-audiences-and-policy.md) のステータスの行を「採択→奥付のコミットの行の変数と組み方は [docs/adr/0178](0178-colophon-commit-line-overflow.md)」に変える。
- ロードマップの v0.1.0-rc4 から「奥付のコミットの行」を消す。

## 実装しないこと

- 本文の中のコードの和文を、字のあいだで改行できるようにすること。付録 E のはみ出しはこれで直るが、すべての本のコードの改行の規則が変わる（「メンテナーが決めること」の 3）。
- マニュアルの CI でプリフライトを走らせ、G09013 で止めること。付録 E のはみ出しが残っている今は、入れたとたんに CI が失敗する。
- 注記の文言を変えること、短縮したハッシュにすること。
- `GOLEM_MANUAL_COMMIT` に注記をつないだ値を渡したときに、注記を切り分けること。この環境変数は、リリースと見た目の回帰テストがハッシュだけを渡すために使っている。

## テスト設計

`scripts/manual/test.sh` の `build-info.sh` のテストを先に書き換え、今の実装で失敗することを確かめてから実装する。

- `expected` の補助を、三つの変数の行を持つファイルの内容に書き換える。
- タグのあるコミットと、`v` で始まるタグのないコミットで、`commit` がハッシュだけ、`uncommitted` が空の文字列であること。
- 追跡しているファイルに変更があるとき、`commit` がハッシュだけで、`uncommitted` が「（コミットしていない変更を含む）」であること。
- 追跡していないファイルだけがあるとき、`uncommitted` が空の文字列であること。
- `GOLEM_MANUAL_COMMIT` と `GOLEM_MANUAL_TAG` を渡したとき、`commit` がその値で、`uncommitted` が空の文字列であること。

奥付が収まることは、自動のテストにしない。
フォントを取得して実際に組まないと確かめられず、`scripts/manual/test.sh` はフォントを取得せずに動く。
実装の後に、次の手順で確かめ、プルリクエストに結果を書く。

1. 追跡しているファイルを一つ変えた作業ツリーで `sh scripts/manual/build.sh` を実行する。
2. 二つのマニュアルの PDF で `golem preflight` を実行し、`back.gm` の G09013 が出ないことを確かめる。
3. 奥付のページを `shem render` で描き、ハッシュと注記が版面に収まることを目で確かめる。

見た目の回帰テストは、マニュアルを `GOLEM_MANUAL_COMMIT` で組むので、`uncommitted` は空になる。
奥付のページの画像は変わらないはずである（上の試作で、変更なしの値の 325 ページが一致した）。

## トレードオフ

ハッシュだけをコードの書体で組み、注記は本文の書体で組むので、一つの欄の中で書体が変わる。
注記はハッシュの一部ではなく説明なので、本文の書体のほうが意味に合う。

注記の和文は、ハッシュの直後の行の途中で改行する。
注記を必ず次の行に送る組み方（強制改行や、注記を別の項目にする）は、変更がないときに空の行か空の項目が残る。
Golem の原稿には条件式がないので、変更の有無で行の数を変えられない。

`build-info.gm` の変数が一つ増えるので、マニュアルを組む手順の説明と、`build-info.gm` を自分で書いている人の手元のファイルが変わる。
`build-info.gm` は生成物で、`build.sh` が組むたびに書き直すので、手で書く人はいない前提である。

付録 E のはみ出しは残る。
奥付の行だけを直し、コードの改行の規則には触れない。

## 決めたことの記録

- **奥付のコミットの行を直すこと**（ロードマップ、v0.1.0-rc4 の「奥付のコミットの行」）：コミットしていない変更がある状態でマニュアルを組むと、奥付のコミットの行が版面の右にはみ出す。
- **すべての項目**（2026-11-07、メンテナー）：「推奨で問題ない」。「メンテナーが決めること」の 1 から 3 を、すべて推奨のとおりとした。

## メンテナーが決めること

すべて決めた（「決めたことの記録」）。

1. **直し方**：決めた。推奨のとおり、注記を `uncommitted` という別の変数にし、奥付ではハッシュだけをコードにする（「決めたことの記録」）。マニュアルの二つのファイルとスクリプト一つの変更で済み、組版の規則に触れない。退けた案の一つは、コードの中の和文を字のあいだで改行できるようにする案である。付録 E も直るが、すべての本のコードの改行が変わり、コードの中の禁則をどう扱うかを決め直す必要がある。二つめは、奥付のコミットの欄をコードにしない案である。注記は改行できるようになるが、識別子を `[code: ...]` で書くマニュアルの書き方（[docs/manual-policy.md](../manual-policy.md)）から外れ、ハッシュだけが本文の書体になる。三つめは、注記を `-dirty` のような短い欧文の印にする案である。収まりはするが、読み手は Git を知らない前提であり（[docs/adr/0024](0024-manual-audiences-and-policy.md)）、印の意味が伝わらない。
2. **変数の名前**：決めた。推奨のとおり `uncommitted` とする（「決めたことの記録」）。値の意味（コミットしていない変更）をそのまま表す。退けた案は `note` や `dirty` である。`note` は脚注と紛れ、`dirty` は Git の俗語で、マニュアルの方針の「Git を知らない読み手」に合わない。
3. **付録 E のはみ出しの扱い**：決めた。推奨のとおり、この ADR では直さず、ロードマップの v0.1.0-rc4 に「本文の中のコードの和文の改行」の項目を足す（「決めたことの記録」）。原因の中心はコードの改行の規則で、奥付とは直す場所が違う。退けた案は、この ADR でコードの改行の規則まで変える案である。理由は 1 の一つめと同じである。
