# ADR 0223: Emet の組み込みの関数と `++` が作る値の長さを、作る前に任意精度で求めて手数の残りと比べる

ステータス: 採択（未実装）

## 文脈

[ADR 0160](0160-emet-function-language-core.md) は、`.gm` からの一つの呼び出しが始めた評価に手数の上限（100,000,000 手）を置き、上限を超えたら E04100 とした。
手数は、簡約を一つずつ数えるほかに、`++` と、文字列とリストを作る組み込みの関数が作った値の長さも足す（「大きさの手数」）。
`s ++ s` を繰り返して、手数の小さいまま巨大な値を作ることを防ぐためである。

2026-11-06 と 2026-11-08 のセキュリティ監査（[docs/audits/2026-11-06-security-audit.md](../audits/2026-11-06-security-audit.md)、[docs/audits/2026-11-08-security-audit.md](../audits/2026-11-08-security-audit.md)）は、この仕組みが二つの形で働かないことを再現した。
どちらも重大度は中で、原稿から呼べる関数だけで起き、Wasm プラグインやファイルの権限を要らない。

- **E-01**：`List.range 1 18446744073709551616`（長さ 2^64）の大きさの手数が 0 に、長さ 2^63 では負の数になる。`List.take 3` と組み合わせた型検査済みの関数は、7 手で `[1,2,3]` を返した。同じ範囲を `List.length` で数える関数は、E04100 を返す前にヒープを使い果たした。
- **E-02**：`String.replace "a" x y` に 20,000 字ずつの `x` と `y` を渡すと、結果は 400,000,000 字になる。上限を超えるのに、E04100 を返す前にヒープを使い果たした。

### 二つに共通する原因

二つの発見は、別々の誤りに見えるが、原因は一つである。
組み込みの関数は、値と長さを組にして返し（[`Prim.hs:78-81`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Prim.hs#L78-L81)）、評価器はその長さを `Int` のまま手数に足してから（[`Eval.hs:327-329`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Eval.hs#L327-L329)）、次の簡約の前に上限と比べる（[`Eval.hs:172-175`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Eval.hs#L172-L175)）。
上限と比べるのは、値を作り、その長さを数えた後である。
しかも、長さも、それを足した手数も `Int` で表すので、64 ビットを超える長さは折り返す。

E-01 は後者の現れである。
`List.range` は長さを任意精度で求めてから `fromInteger` で `Int` にする（[`Prim.hs:41-43`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Prim.hs#L41-L43)）。
リストは遅延して作られるので、`List.take 3` は先頭の三つしか作らない。
E-02 は前者の現れであり、長さが `Int` に収まっていても、結果を作り終えるまで上限と比べない。
`Int` に収まるかを調べるだけでは、E-02 は直らない。
結果を作る前に長さを求めるだけでも、E-01 の折り返しは直らない。
したがって、この ADR は二つを一つの決定として扱う（「メンテナーが決めること」の 1）。

### 同じ形の組み込みの関数

[`Prim.hs`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Prim.hs) と [`Eval.hs`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Eval.hs) の、値を作るすべての操作を読んだ。
入力の長さの和より長い値を作れる操作（下の表の「増やす」）は、上限の手前で巨大な値を作れる。
入力が共有された値であれば、入力の長さを手数に数えたのは一度だけなので、延べの長さは手数を大きく超える。

| 操作 | 結果の長さ | 増やすか | 今の長さの数え方 |
| --- | --- | --- | --- |
| `List.range x y` | max(0, y − x + 1) | 増やす（引数は数二つ） | 任意精度を `Int` に折り返す |
| `String.replace from to s` | `from` が空なら \|s\|、そうでなければ \|s\| + c × (\|to\| − \|from\|)。c は `s` の中の重ならない `from` の数 | 増やす | 作ってから数える |
| `String.join sep xs` | Σ\|x\| + \|sep\| × max(0, n − 1)。n は `xs` の要素の数 | 増やす（区切りと、共有された要素） | 作ってから数える |
| `List.concat xss` | Σ\|xs\| | 増やす（共有された要素） | 作ってから数える |
| `++`（文字列）、`++`（リスト） | \|a\| + \|b\| | 入力の二倍まで。`a ++ a` で倍になる | 文字列は作ってから数える（[`Eval.hs:398-404`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Eval.hs#L398-L404)） |
| `String.fromChars xs` | `xs` の字の数 | 増やさない | 作ってから数える |
| `String.chars`、`String.split`、`String.lines`、`List.reverse`、`List.take`、`List.drop`、`String.trim`、`String.take`、`String.drop`、`String.fromChar` | 入力の長さ以下 | 増やさない | 作ってから数える |
| `String.fromNat`、`String.fromInt`、`String.fromRat` | 数の桁数。数は 2^4096 未満、小数点以下は 1000 桁まで | 増やさない（長さに定数の上限がある） | 作ってから数える |
| `List.length`、`List.at`、`String.length`、`String.startsWith` など | 0 | 作らない | 0 |

監査は `String.join`、`String.fromChars`、`List.concat` を「同じ形」として挙げ、個別には再現していなかった。
この ADR を書くために、`String.join` と `List.concat` を共有された値で再現した（「確かめたこと」）。
`String.fromChars` は、結果の長さが入力のリストの長さに等しく、入力はすでに手数に数えてあるので、増やす操作ではない。

### 確かめたこと

監査の再現コードと同じく、実際のパーサー、型検査、評価器を使った（`callFunctionCounted`、ヒープの上限 256 MiB、時間の上限 30 秒、`eeb70246`）。
次の二つの関数の `rep` は、同じ値を n 個並べたリストを末尾再帰で作る。

```text
rep :: Int -> String -> List String -> List String
rep 0 s acc = acc
rep n s acc = rep (n - 1) s (s : acc)
f :: Int -> String -> String
f n x = String.join "" (rep n x [])
```

| 関数 | 入力 | 結果 |
| --- | --- | --- |
| `String.join "" (rep n x [])` | `x` は 20,000 字、n = 10 | 成功、200,055 手 |
| 同上 | n = 20,000（結果は 400,000,000 字） | `Heap exhausted`、終了コード 251 |
| `List.length (List.concat (rep n xs []))` | `xs` は 20,000 要素、n = 10 | 成功、200,056 手 |
| 同上 | n = 20,000（結果は 400,000,000 要素） | `Heap exhausted`、終了コード 251 |

n = 20,000 の二つは、`rep` が数万手で終わり、上限を超えるのは結合の大きさの手数だけである。
それでも E04100 にならないのは、結合の結果を作ってから長さを数えるためである。

### wasm32 での `Int`

[ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md) の `golem.wasm` は、同じ評価器を wasm32 で動かす。
wasm32 の GHC の `Int` は 32 ビットである（[ADR 0202](0202-packages-that-do-not-build-for-wasm.md) の cborg の項）。
フィルタの手数の上限は `1 億 + 10000 × .gm のバイト数` を `Int` で求める（[`Gm.hs:159-160`](https://github.com/tett23/golem/blob/eeb70246124fc9cba002150078a47c54e29b512f/modules/golem-emet/src/Golem/Emet/Gm.hs#L159-L160)）。
32 ビットでは、204,749 バイト以上の `.gm` でこの値が 2^31 − 1 を超えて折り返す。
上限が負になれば、評価は最初の簡約の前に E04100 になる。
ネイティブの 64 ビットでは起きないので、[ADR 0199](0199-pdf-typesetting-as-wasm-reactor.md) が求める「golem.wasm の PDF と diagnostic はネイティブと同じ」が、大きな章のフィルタで崩れる可能性がある。
これはコードから読んだことで、wasm で動かして確かめていない。
手数の型を決め直すこの ADR で、あわせて扱う（「メンテナーが決めること」の 3）。

## 実装すること

### 長さを先に求める

- 値を作るすべての組み込みの関数と `++` について、結果の長さを、結果を作らずに引数だけから任意精度の整数（`Integer`）で求める関数を持つ。式は「同じ形の組み込みの関数」の表の「結果の長さ」のとおりである。`String.replace` の c は `Data.Text` の `count`（重ならない出現を左から数える。`replace` の置き換えと同じ数え方）で求める。
- 評価器は、組み込みの関数か `++` を当てるたびに、残りの手数 room = 上限 − 今の手数 − 1 を任意精度で求め、長さが room を超えれば、値を作らずに E04100 とする。超えなければ値を作り、今までと同じく 1 + 長さを手数に足す。
- 長さの関数は、作った値の長さと一致しなければならない（不変条件の S1）。一致すれば、上限の中で終わる評価の手数は今と変わらない。
- 組み込みの関数の型を、たとえば `runPrim :: Integer -> Text -> [PrimValue] -> Either PrimStop (PrimValue, Int)` のように、残りの手数を受け取り、超えるなら作らずに止まりを返す形にする。名前と形は実装に任せる。止まりの値を E04100 に変えるのは評価器であり、メッセージと位置は今の E04100 と同じにする。
- 長さの関数が引数を走査する手間（`Data.Text` の `length`、`count`、リストの `length`）は、引数がすでに手数に数えてあり、その長さに比例するので、手数に足さない。

### 手数の型

- 手数の数え上げと上限は、どのターゲットでも 64 ビットの `Int64` で表す（「メンテナーが決めること」の 3）。`stepLimit`、`evalCallLimited` の上限の引数、`evalCallCounted` が返す手数を `Int64` にする。
- `filterFuel` は任意精度で求め、`Int64` の最大値で頭打ちにする。
- 長さを足す前に room と比べるので、手数は上限 + 1 を超えない。上限 + 1 が `Int64` に収まる限り、加算は折り返さない。
- E04100 で止まった呼び出しが返す手数は、上限 + 1 とする。今は、止まった時点の手数（長さを足した後の値）を返す。この値は利用者に見えず、テストと仕事の測定にだけ使う。

### ドキュメント

- docs/golem-emet/specifications.md の「評価」に、長さを値を作る前に求め、残りの手数を超えれば作らずに E04100 とすること、長さを任意精度で求めること、手数と上限が 64 ビットであることを書き、この ADR にリンクする。「同じ形の組み込みの関数」の表の「結果の長さ」の列を仕様に写す。
- docs/specifications.md の Emet の節の手数の上限の項に、「組み込みの関数が作る値の長さは作る前に数える」と一文で足す。
- docs/diagnostics.md の E04100 の「意味」に、値を作る前に上限を超えることがわかれば、その値を作らずに止めることを書く。
- 利用者のマニュアルの関数の章で手数の上限を説明していれば、同じ一文を足す。手数の数え方は変わらないので、測った仕事の表は変えない。

## 実装しないこと

- 上限の値を変えること。100,000,000 手と、フィルタの `1 億 + 10000 × バイト数` は [ADR 0160](0160-emet-function-language-core.md) と [ADR 0162](0162-calling-emet-functions-from-gm.md) のままである。
- 大きさの手数の数え方を変えること。足す量は今と同じ「作った値の長さ」であり、変えるのは数える時期と型だけである。
- `List.range` を遅延したまま上限の外に置くこと（「メンテナーが決めること」の 2 の退けた案）。
- `.gm` に返した値の延べの大きさを数えること。`List.map` で同じ文字列を指す要素を百万並べた値を `.gm` に返すと、手数は百万の桁だが、意味論 IR の文字の延べの数はその文字列の長さ倍になる。結合の操作を通らないので、この ADR の対象ではない。再現は試していない。docs/roadmap.md の Emet の未決事項に一項として足す。
- プロセスの全体のメモリの上限（RTS の `-M`）。補助にはなるが、手数の上限を後から確かめる実装を直すことの代わりにはならない（監査の修正案）。
- `String.toNat` と `String.toInt` の、長い数字の並びを数にする手間。手数は 0 だが、入力の文字列はすでに手数に数えてある。手間が入力の長さの二乗になるかは調べていない。

## 不変条件

組み込みの関数か `++` の一回の適用について、引数を a、長さの関数を size(a)、作った値の長さを len(build(a)) と書く。
評価が適用の直前に使った手数を s、上限を L とする。

- **S1**：size(a) は、作った値の長さに等しい。すべての操作とすべての引数で、size(a) = len(build(a)) が成り立つ。
- **S2**：s + 1 + size(a) ≤ L なら、適用は値を作り、手数は s + 1 + size(a) になる。これは今の実装の手数と同じである。
- **S3**：s + 1 + size(a) > L なら、適用は値を作らず、評価は E04100 で止まる。止まるまでの時間と割り当ては size(a) によらず、引数の長さに比例する。
- **S4**：S2 と S3 の比較は数学の整数の比較であり、size(a) がどれほど大きくても（2^63、2^64、2^4097）、`Int64` の折り返しで判定が変わらない。
- **S5**：手数は上限 + 1 を超えない。E04100 で止まった呼び出しが返す手数は L + 1 である。
- **S6**：E04100 のコード、メッセージ、位置は、上限を超えたのが簡約か長さかによらず、今の E04100 と同じである。同じ入力からは、ネイティブと wasm32 のどちらでも、同じ diagnostic を返す。

境界の入力：

| 量 | 調べる値 |
| --- | --- |
| `List.range` の長さ | 0（y < x）、1、L − s − 1（ちょうど残り）、L − s（一つ超える）、2^31、2^32、2^63 − 1、2^63、2^64、2^4097 |
| 加算の境界 | L を `Int64` の最大値 − 10 にし、長さ 2^63 − 1 の範囲（今の `Int` の 1 + 長さが折り返す値） |
| `String.replace` | `from` が空、出現が 0、`to` が `from` より短い（結果が縮む）、結果がちょうど残り、一つ超える、400,000,000 字 |
| `String.join` | 要素が 0 個、1 個、区切りが空、区切りが長い、同じ要素の共有で 400,000,000 字 |
| `List.concat` | 空のリスト、空の要素、共有で 400,000,000 要素 |
| `++` | 空との結合、結果がちょうど残り、一つ超える |
| フィルタの上限 | 204,748 バイトと 204,749 バイトの `.gm`（32 ビットの `Int` の折り返しの境） |

## テスト設計

テストを先に書き、今の実装で失敗することを確かめてから実装する。
テストの名前には、S1 から S6 の番号を入れる。
golem-emet-test は [ADR 0207](0207-run-golem-emet-test-one-test-at-a-time-under-the-watchdog.md) の見張りの下で一つずつ走る。
時間の上限は [ADR 0073](0073-time-bounds-in-tests.md) のとおり、テストごとの 30 秒の時間切れとする。
割り当ては `System.Mem` の `setAllocationCounter` と `getAllocationCounter`（スレッドごとの割り当ての計数）で測り、64 MiB 以下を断言する。
今の実装では、どの拒否のテストも 64 MiB を大きく超えて割り当てるか、時間切れになる。

### golem-emet（`modules/golem-emet/test/LanguageSpec.hs` の「the limit of steps」）

- **S1**：hedgehog の性質のテストで、表のすべての操作について、小さい引数（文字列は 0 から 20 字、リストは 0 から 20 要素、範囲は −50 から 50）を作り、長さの関数の値と、作った値の長さが等しいこと。
- **S2、S3**：`f n = List.range 1 n` を `evalCallLimited` で上限 L を変えて呼ぶ。n と L を小さい範囲で数え尽くし、成功する呼び出しの手数を c としたとき、L = c で成功し、L = c − 1 で E04100 になること。`String.replace`、`String.join`、`List.concat`、`++` でも同じ形のテストを持つ。
- **S3、S4**：既定の上限で、長さ 2^63、2^64、2^4097 の `List.range` を `List.take 3` に渡す関数と、`List.length` に渡す関数が、どれも E04100 になり、割り当てが 64 MiB 以下であること。今は、`List.take 3` の関数が `[1,2,3]` を返すので失敗する。
- **S4**：上限を `Int64` の最大値 − 10 にした `evalCallLimited` で、長さ 2^63 − 1 の `List.range` が E04100 になること。
- **S3**：20,000 字の二つの引数の `String.replace "a" x y`（監査の E-02）、「確かめたこと」の `String.join` と `List.concat` の n = 20,000 が、E04100 になり、割り当てが 64 MiB 以下であること。今はヒープを使い果たす。
- **S5**：E04100 で止まった呼び出しの `evalCallCounted` の手数が、上限 + 1 であること。止まらない末尾再帰（今のテスト）と、長さで超える `List.range` の両方で確かめる。
- **S6**：長さで超える呼び出しの E04100 の位置とメッセージが、今の「a tail recursion that never stops is E04100」と同じ形（評価を始めた `.gm` の呼び出しの位置、関数の名前と行）であること。二度呼んで同じ diagnostic になること。
- 今の「the measured work is a third of the limit or less」の三つの仕事の手数が変わらないこと（S2）。

### golem-emet の Gm（フィルタ）

- **S6**：`filterFuel 204749` が 2,147,490,000 であり、`filterFuel` が `Int64` の最大値で頭打ちになること。ネイティブのテストなので、wasm32 の折り返しそのものは再現しない。

### 自動テストにしない確かめ方

- 実装の後に、監査の再現コード（[docs/audits/2026-11-08-evidence/emet-probe.hs](../audits/2026-11-08-evidence/emet-probe.hs)）の五つのモードを、ヒープの上限 256 MiB で走らせる。`cost` は型が変わるので書き直す。`take`、`length`、`replace` が E04100 になり、`control` が今と同じく E04100 になることを確かめ、プルリクエストに書く。
- wasm32 で 204,749 バイト以上の章にフィルタを当てる確かめは、golem.wasm を組める環境（x86-64 Linux）で、CI の wasm のジョブの fixture に足すかどうかを実装のときに決める。足さないなら、プルリクエストに確かめていないと書く。

## トレードオフ

`List.range 1 1000000000 |> List.take 3` のように、大きな範囲の先頭だけを使う関数は、今は動いているが E04100 になる。
評価は正格であると [ADR 0160](0160-emet-function-language-core.md) が決めており、範囲の全体を作る手数を数えるのが言語の意味である。
今その関数が動くのは、リストの遅延と折り返しが重なった結果である。
2^64 より短い範囲でも、上限を超える長さの範囲を作る関数は、`take` で先頭だけを使っていても E04100 になる。
`List.range 1 100000001` が今も E04100 なので、この点は今の振る舞いと一貫する。

組み込みの関数ごとに、長さの関数と値を作る関数の二つを持つことになる。
二つが食い違えば手数が変わるので、S1 の性質のテストで縛る。
長さの関数を持たず、作りながら数えて残りを超えた時点で打ち切る方法もある（監査の修正案の一つ）。
`Data.Text` の `replace` と `intercalate` は途中で止められないので、作る処理を自前で書くことになり、S1 に当たる一致を作る処理の中で保つことになる。

手数を `Int64` にすると、評価器の型が今の `Int` と変わり、golem-emet を呼ぶ側（golem-eval のフィルタ、テスト）の型も変わる。
ネイティブの 64 ビットでは `Int` と同じ幅なので、速さは変わらないと見込むが、測っていない。

## メンテナーが決めること

1. **ADR を一つにするか**：推奨は、E-01 と E-02 を一つの ADR で扱うことである。原因は一つ（長さを、値を作った後に、折り返す `Int` で数える）であり、直す場所も一つ（組み込みの関数と評価器の、手数を受け渡す形）である。どちらか一方だけを直しても、もう一方が残る（「二つに共通する原因」）。
   - 退けた案は、E-01（`List.range` の折り返し）と E-02（`String.replace` の確保）を別々の ADR にすることである。二つの ADR が同じ `runPrim` の型を別々に決め直すことになり、先に実装したほうの形が後のほうを縛る。
2. **長さを先に求める範囲**：推奨は、値を作るすべての組み込みの関数と `++` で、長さを先に求めることである。増やさない操作は、今のままでも入力の長さまでしか作らないが、規則を一つにすれば、組み込みの関数を足すたびに「増やすかどうか」を判断しなくて済む。
   - 退けた案の一つは、表の「増やす」操作（`List.range`、`String.replace`、`String.join`、`List.concat`、`++`）だけを直すことである。変える量は小さいが、`String.fromChars` のように境目の判断が要る操作が残る。
   - 二つめは、`List.range` を遅延したままにし、使った要素の数だけを手数に数えることである。評価が正格であるという [ADR 0160](0160-emet-function-language-core.md) の決定と食い違い、手数が「プログラムの意味だけで決まる」ことを、どこまで使ったかに依存させる。
3. **手数の型**：推奨は、手数と上限を `Int64` にし、長さと比較を `Integer` にすることである。`Int64` はネイティブでも wasm32 でも同じ幅なので、`filterFuel` の折り返しも同時に消え、評価の内側の繰り返しは今と同じく箱に入らない整数で数えられる。
   - 退けた案の一つは、手数も `Integer` にすることである。もっとも単純だが、簡約のたびに任意精度の加算をすることになる。速さを測っていない。
   - 二つめは、`Int` のまま、加算を飽和させることである。ネイティブでは足りるが、wasm32 の 32 ビットでは `filterFuel` が 2^31 − 1 で頭打ちになり、ネイティブと上限が変わる。
4. **止まった呼び出しが返す手数**：推奨は、上限 + 1 とすることである。長さで止めるときは長さを足さないので、今の「止まった時点の手数」はもう定義できない。上限 + 1 なら、簡約で止まったときの今の値と同じであり、どちらで止まったかによらない。
   - 退けた案は、s + 1 + size(a) を `Integer` で返すことである。`evalCallCounted` の型が `Integer` になり、使い道（測定とテスト）に対して大きすぎる。
5. **共有された値を `.gm` に返すときの大きさ**：推奨は、この ADR では扱わず、docs/roadmap.md の未決事項に足すことである。結合の操作を通らない別の経路であり、数え方（意味論 IR の延べの大きさを、返す時点で数えるか）を決める材料がない。
   - 退けた案は、`.gm` に返す値の延べの大きさを、この ADR で手数に足すことである。値を返す経路（コマンド、式、フィルタ）ごとに数え方を決めることになり、この ADR の原因と別の決定になる。
