# ADR 0351: 原稿の整形と再パースの往復を Lean で証明する

ステータス: 採択（未実装）

## 文脈

[Golem ADR 0310](0310-enumerate-parser-formatter-round-trips.md) は、見出しと短い段落について整形前後の構文木、冪等性、diagnostic の位置を検査する。
この検査を、原稿の開始規則から到達する文法全体と、原稿が参照する外部の表に広げる。
引数の全順列や任意回の繰り返しは Lean 4 のモデルで検証し、実装との対応は Golem のテストで確かめる。

## 調査した事項

[試作 PR #959](https://github.com/tett23/golem/pull/959) は、引用符を含むパスを持つ `@listing "a\"b"` に、固定した二つの引数 `lang=haskell` と `lines=1...3` を付けた。
この二種類から作る任意長の列を書き出して文字単位で読み戻すと、元の列になることを Lean 4.7.0 で帰納法により証明した。
二つの引数を一度ずつ使う両順序は実パーサーでも入力順に戻り、二度目の整形で原稿は変化しなかった。
試作は文法から引用文字列の選択肢順を読み込むが、二種類の引数の綴りは手で記述した。
任意の名前と値、コメント、評価器についてはこの試作で証明していない。

引用文字列の PEG の選択肢を逆順にした対照では、エスケープされた引用符で値が途中で閉じ、Lean の同じ定理が失敗した。
peg-hs で生成したパーサーでも、現行の順序で受理した文字列を逆順で拒んだ。
[証明ジョブ](https://github.com/tett23/golem/actions/runs/43032091788/job/130561453201) は Lean の準備に 5 秒、証明と対照の検証に 12 秒、ジョブ全体に 25 秒かかった。
ランナー待ちを含む経過時間は 6 分 6 秒だった。

現行の [引数検査](../../modules/golem-eval/src/Golem/Eval/File.hs) では、`uniqueKeys` が重複の G02077 を報告して後の出現を除き、`functionArgs` は未知の名前があると型検査へ進まない。

## 実装すること

### モデルと実装の対応

| Lean のモデル | 対応する Golem の処理と照合方法 |
| --- | --- |
| 順序付き選択、繰り返し、省略、トークン境界を持つ原稿パーサー | Golem が使う peg-hs 文法の規則を取り込む。実パーサーでは原稿を読み切った経路で採用した選択肢を記録する |
| コメントを含む具体構文木（CST）、ソース位置を除いた抽象構文木（AST）、書き出しと整形 | 原稿を実際のパーサーと fmt に通し、AST、CST 上のコメント、整形後のバイト列を照合する |
| 式の評価 | 原稿の式を評価し、呼び出された Emet 関数を評価する実装に対応させる。変数、関数、読み込んだ外部入力、評価の上限を同じにして値または失敗を照合する |
| 引数の検査と diagnostics の並べ替え | 名前、型、必須性、重複可否、宣言順、独立した誤りの報告条件、派生エラーの抑制条件、同位置の報告順を実装と共有する。具体例の期待値はテストに直接書く |
| 表の読み込みと整形 | 原稿と参照先の CSV または TSV を組にして実行し、セルの値と表ファイルのバイト列を照合する |

呼び出し先の Emet 関数は [Emet の文法](../../modules/golem-emet/grammar/Emet.hpeg) で読み、検査と名前解決を経た式を評価する。
Lean の評価規則を Golem.Emet.Core の式と Golem.Emet.Eval の各処理に対応付け、関数呼び出し、組み込み演算、評価上限を通る例で実装と照合する。

モデル生成時に取り込めない文法は、すべての判定可能な規則名と選択肢を示して CI を失敗させる。
共有できない引数規則も、命令名と不足する内容をまとめて報告する。
手書きの代用規則で通ったケースを検証済みに数えない。
証明には未証明の仮定として目的の性質や評価結果の一致を置かない。

各出現を残したまま独立した誤りを収集してから並べるよう、引数検査を変更する。
実装 PR では現行の diagnostic コードに対応する検査、仕様書、README を更新する。

### 検証する原稿

正しい原稿とは、構文エラーからの回復を使わずに読め、命令の必須引数、キーワード名、型、重複の検査を通る原稿である。
正しい原稿の定理とは別に、構文として読めるが引数検査に失敗する原稿にも、diagnostic の保存を示す。
型エラー、必須引数の不足、未知の名前、重複があっても fmt は整形する。
[Golem ADR 0339](0339-comments-in-arguments-and-manuscript-expressions.md) が定めた引用符不足はファイルを書き換えない。
同 ADR が定めるコメントの検査は、その記法の実装を前提とする。

## 不変条件

1. 任意の正しい引数列を原稿の文字列に書き出して再パースすると、名前、値、AST の種類、順序が元の列と一致する。文法が許すすべての名前と値を対象とする。
2. 任意の正しい表記の原稿を整形して再パースすると、位置を除く AST が一致する。本文の空白、引数の順序、CST に残るコメントの内容、引数との相対位置、コメント同士の順序を保存する。`StringLit` の値と種類を保つエスケープの変更は許す。
3. 任意の正しい原稿を二度整形した結果は一度目の結果とバイト単位で一致する。異なる入力を同じ綴りに統一する義務は、個別に表記を定めた整形規則に限る。
4. 任意の正しい引数列で、同じ記法内の独立な省略の全部分集合、繰り返しとの境界の直積、順不同のキーワードの全順列に対して 1 と 2 が成り立つ。繰り返し回数と重複のない引数列の長さに上限を置かない。
5. 同じ環境と上限で整形前後の式を評価すると同じ値または対応する評価失敗を得る。Emet の評価規則も Lean に記述し、式から値を得る過程を証明に含める。コメントは評価器に渡らない。
6. 任意の引数検査規則と構文として読める入力について、四種類の引数エラーのコード、件数、報告順は整形前後で一致する。diagnostic の開始と終了は、それぞれの原稿で、型エラーなら同じ引数の値、未知の名前は同じ出現の引数名、不足は同じ命令内の規定位置を指す。重複した引数はどちらも入力順に残し、間のコメントも保存する。値が等しい場合も重複の diagnostic は同じ出現を指す。
7. 繰り返せないキーワードを追加すれば、挿入位置や値によらず二度目以降の各出現に重複を一件ずつ報告する。未知の名前もこの数え方に従い、未知の名前そのものは各出現に一件報告する。指定済みの必須引数は値の型を誤っていても不足に数えない。
8. diagnostic は原稿順とし、同じ位置では未知の名前、重複、型エラーの順にする。同位置に複数の不足があれば宣言順に一件ずつ報告する。
9. 表の往復ではセルの値が一致する。一度目の整形結果は [Golem ADR 0186](0186-fmt-table-files.md) の BOM と改行の変換だけを施したバイト列と等しい。参照の引数順を変えても同じ形式で同じファイルを参照する限り表の整形結果は等しい。二度目には原稿と表のどちらも変わらない。
10. 正しい表の LF を一か所だけ単独の CR に変えたとき、整形前には G02082 を得る。修復後の表は破損させる前の表に一致し、次の整形で原稿と表は変わらない。

### 境界の入力

| 入力 | 判定 |
| --- | --- |
| 空の原稿、引数一つ、本文末のエスケープした空白 | 1〜3。意味を持つ空白を残す |
| 省略なしとあり、繰り返し0回、1回、2回以上 | 4。1回以上を要求する規則は1回と2回以上 |
| 引数間にコメントが二つ、順不同の引数が二つ | 2、4。両順序でコメントの内容と順序も保つ |
| 変数が整数か文字列に束縛された同じ式、Emet 関数経由の値、評価上限の直前と超過 | 5、6。評価の成功と失敗、型エラーの有無と範囲を実装と照合 |
| 未知の同名引数が三つ | 6〜8。三件の未知と二件の重複。同位置では未知が先 |
| 既知の必須整数引数が重複し二度目が文字列、別の必須引数二つが不足 | 6〜8。型違いを不足に数えず、欠けた二つを宣言順で報告 |
| BOM、CRLF、空セル、引用符内の改行、末尾の空白を持つ表 | 9。BOM と改行以外のバイトを保つ |
| 正しい表の LF 一つを単独の CR に変更 | 10。整形前の G02082 の範囲と件数、修復後の表と元の表の一致、二度目の両ファイルの一致 |

## テスト設計

テスト名に不変条件の番号を入れる。
実装に先立ち、期待する不変条件を破る入力または変更で失敗を確かめる。
実装では組み合わせを代表例でモデルと照合し、同じ値と異なる値の重複、隣接する重複と別の引数を挟む重複を含める。
単独の誤りに加え、独立した誤りが重なる入力でコード、開始、終了、件数、報告順を照合する。
整形で位置が動く例を含め、位置の期待値は整形前後それぞれの原稿から定める。

テスト用の生成器は Golem に置く。
開始規則から短い原稿を列挙し、上限内に現れない記法には最短の成立例を加える。
PR では各記法と省略と繰り返しの各境界を実際に通す。
新しい選択肢が受理に至る経路で一度も採用されなければ、生成時にその選択肢を使っていても失敗とする。

本文の長さは生成した文字列の Unicode 既定の拡張書記素クラスタ数で数える。
代表例には ASCII、鰍、𠮷、家族絵文字 👨‍👩‍👧‍👦、タイ語の กำ、アラビア語の بَ を含める。
1 クラスタの例は全列挙に入れ、เก と لا は 2 クラスタの境界例、ペルシア語の می‌روم は ZWNJ の保存を確かめる個別例とする。

期待する diagnostics の列を先に決められる壊し方について、該当するすべての箇所を元の原稿から一か所ずつ別々に壊す。
diagnostics の列全体を照合し、余分な報告、重複、欠落、順序の違いを失敗にする。
外部表の破損では原稿と参照先を一組にする。

PR と毎晩の main のいずれも、失敗後も全件を実行する。
失敗ごとの元の原稿、失敗した入力、再現コマンドを GitHub Actions の artifact に保存し、表を参照する場合は各原稿に対応する表ファイルも保存する。
PR は独立したジョブで並列実行し、workflow 全体の経過時間の目安を 5 分とする。
[Golem ADR 0281](0281-budgets-of-the-exhaustive-tests-and-what-moves-to-the-nightly-job.md) の従来の時間予算を理由に、この範囲の必須ケースを削らない。
採択時には同 ADR のステータスに、この範囲の予算の変更を記録する。
分割後も超える場合は待ち時間と実行時間の内訳を測って目安を見直す。
PR の列挙上限は測定後に固定して毎回同じ入力を使い、短い時間で打ち切らない。
毎晩は PR より大きい上限を使い、本文長と入れ子の深さの候補ごとに件数と所要時間を測って決める。

初回の列挙で発見した不具合は最小の再現原稿と修正を先に別 PR で入れ、列挙の PR は全件合格後にマージする。
毎晩の検査で見つけた不具合も、修正時に最小例を PR の回帰テストに加える。

## 実装しないこと

試作を根拠に peg-hs や Golem.hpeg の選択肢順を変えること、HTML 出力による往復判定、本文の全 Unicode 文字の総当たりは対象外とする。
改ページの Alloy モデルから Lean への移行は別の ADR に記録する。

## トレードオフ

Lean で一般に証明できるのはモデル上の性質である。
文法の取り込みと検査規則の共有は実装との差を小さくするが、評価器や整形器のモデルが実装に対応するかは別に検査する必要がある。
文法の変更で未対応になった箇所を一度に示し、実装で再現できる反例を残すことで、この差を調査できるようにする。
