# ADR 0338: ファイルとフォルダの改名に伴う参照の編集を Golem LSP が返す

ステータス: 採択

## 文脈

Aleph で章の原稿を改名しても、manifest.toml の章一覧や他の原稿の `@import` が古い名前を指していると、次のビルドでそのファイルを読めない。
Aleph の設計文書「ファイルツリーの右クリックからシートとフォルダの名前を変える」（`docs/adr/0070-rename-sheets-and-folders-from-tree.md`）は、ツリーからの改名、保護するファイル、開いたタブやノートの引き継ぎを定め、参照パスの更新を別の提案に送った。
Golem のファイルを指す記法やパスの規則は、コンパイラーと同じものを使いたい。

## 実装すること

### 改名前の問い合わせ

Aleph はプロジェクトごとに `workspace.fileOperations.willRename`、`didRename` と `workspace.workspaceEdit.documentChanges` の対応を申し出る。
Golem LSP は対応するファイル操作に登録し、`file` スキームのファイルとフォルダを対象にする。
関連するアセットには拡張子の決まらないものもあるため、対象の登録を原稿の拡張子だけに絞らない。
操作の対象がプロジェクトに属するかはサーバーでも検査する。

1. Aleph は改名元、新しい名前、既存の改名先、保護対象を確認する。開いた文書の最新の変更を LSP に送り、ファイルシステムを変更する前に `workspace/willRenameFiles` を送る。
2. Golem LSP は元と先の URI を受け取り、操作前の文書から参照先を解決する。編集が要るときは元の URI ごとの `TextDocumentEdit` を `WorkspaceEdit.documentChanges` で返す。編集がなければ `null` を返す。
3. Aleph は編集を検査してから、開いている文書にはエディターの編集として、閉じた文書にはファイルへの編集として適用する。参照の編集を適用してから改名する。サーバーから `RenameFile` は返さない。
4. 改名に成功した Aleph は同じ URI の組で `workspace/didRenameFiles` を一度送る。改名した文書と子孫の文書を旧 URI で閉じ、新 URI で最新の本文を開き直す。Golem LSP は旧 URI の索引と diagnostics を無効にしてプロジェクトを読み直す。改名後の通知から参照を二度編集しない。

この順序は [LSP の改名前の要求](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#workspace_willRenameFiles) と [改名後の通知](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#workspace_didRenameFiles) に従う。
フォルダを改名するときに Aleph が送る組はそのフォルダの一組だけである。

### 何を書き換えるか

各参照について、どの記法のどの値か、書いた文書とバイト範囲、元の基準ディレクトリ、解決した参照先を求める。
参照元と参照先の両方に改名を一度ずつ適用し、新しい参照元から同じ対象を指す綴りを求める。
今の綴りで同じ対象を指せるなら編集を省く。
範囲を交渉済みの位置エンコーディングに変換し、引用符、エスケープ、CSV の引用規則に従って値だけを書き戻す。

| 参照 | 解決と編集 |
| --- | --- |
| manifest.toml の章のパス | 文字列、入れ子配列、章テーブルの `file` を個々の出現位置で扱う。重複して指定した章は全箇所を直す |
| 原稿の `@import`、Emet の import | Golem の解決規則で対象を特定し、パス引数を編集する。名前空間や関数名を保つ |
| Golem のファイルを指す他の欄 | 画像、表、コード、書体、書誌、プラグイン、フィルター、Emet のファイル要求など、読み取り側がローカルパスと定めるリテラルを対象にする。URL、本文、パスを計算する式は置換しない |
| Aleph の plot.csv | Aleph がプロジェクトのプロットとして指定したファイルに限り、`file` 列をプロジェクトルート基準で解決する。シーン名、メモ、同じ文字列の別の列を保つ |
| Aleph の Markdown シートの Wiki リンク | Aleph が指定したシートの集合とワークスペースを使い、元のリンクがパスまたはファイル名で一意に指すとき、移動後も同じシートを指すようにする。見出し、ラベル、シートのタイトルによる指定を保つ |

Aleph 固有の二行は、Aleph がそのプロジェクトで対応する機能と対象ファイルを初期化設定で明示したときだけ有効にする。
普通の Golem プロジェクトに同名の CSV や Markdown があるだけでは解釈しない。
Aleph は現在、開いた .gm と .emet を LSP に同期する。
提案では、参照元として有効にした TOML、Markdown、プロットの未保存文書も本文と版を同期する。
プロジェクトのメンバーと Wiki の検索基準を提供できない場合は、検索範囲を推測せず、その形式の更新を利用できないことを Aleph に知らせる。
Wiki リンクは Aleph のシート集合と同じ範囲、元の基準と拡張子の有無で解決する。
フォルダ移動で参照元だけが移る場合も、相対リンクを照合する。
シート集合がそろわない場合、同名の候補が複数ある場合、式の評価が要る場合は対象を推測しない。
未解決の参照を編集できたものに数えない。
対応するクライアントでは、Aleph の旧 Wiki リンク書き換えフックから同じ範囲を編集しない。
タブ、ノート、ブックマーク、最近開いたファイルなど、Aleph 内部の状態は Aleph が引き継ぐ。

### ファイルの同一性と失敗時の扱い

URI はパスにデコードしてからプロジェクトの境界と各成分を比べる。
`章` の改名は `章外` に及ばない。
異なる綴りで同じ元を指す場合は既存の解決規則で判定し、ルートの外を指すパスやシンボリックリンクを経て外へ出る場所への編集を返さない。
旧 URI から新 URI への対応はすべて操作前の状態で確定する。
同じ組や同じ範囲の同じ編集は一つにまとめる。
親と子の指定に異なる行き先がある場合や、同じ範囲に異なる編集が生じた場合は要求全体をエラーにする。
ルート自体の改名でルート相対参照がすべてそのまま解決する場合は編集を返さず、Aleph がサーバーのプロジェクトルートを切り替える。
複数プロジェクトにまたがる移動は今回の対象外とする。

開いた文書は VFS の最新の本文と版を使い、閉じた文書はディスクから読む。
Aleph は開いた文書の版が応答の版と違えば編集を破棄し、最新の内容で問い合わせ直す。
閉じた文書の版は `null` とする。
Aleph は問い合わせ時に対象の文書の内容を記録し、応答が指す範囲を適用する直前に元の内容と照合する。
問い合わせ中に開閉やディスク上の変更があれば、対応する版と内容を取り直して再計算する。
開いているシートの未保存の内容はそのバッファーに残し、別の文書をまとめて保存しない。
改名対象の保存は Aleph の既存の保存手順に従う。

Aleph は同じ操作中に適用する編集、編集前の内容と版、完了した処理を記録する。
編集の途中かファイルシステムの改名で失敗したら、適用した箇所だけを逆順に戻し、成功の通知を送らない。
巻き戻し中に別の更新が見つかった文書は上書きせず、元の URI と適用済みの範囲を示して再読み込みする。
応答がタイムアウトした場合や機能がない場合は、参照更新まで完了したと表示しない。
Aleph は参照を更新する操作を中止し、既存の改名だけを行う操作を区別する。
改名後に接続が切れたらディスク上の改名を再実行せず、再接続時に現状から索引を作る。

## 実装しないこと

LSP サーバーからのディスクへの書き込み、ファイル監視で発見した外部の改名に対する自動置換、一致する文字列を全文検索して置き換える処理は加えない。
原稿のラベルや Emet のシンボルの改名には既存の `textDocument/rename` を使う。

## 不変条件

1. R1。更新後の参照を解決すると、元の参照先を一度移動した先に一致する。移動したフォルダに含まれない同名の接頭辞は変わらない。
2. R2。各編集は操作前の URI、位置、版を指す。同じ URI と範囲は一度だけ編集し、異なる出現はすべて残す。
3. R3。成功した操作は一度の改名と一度の事後通知を持つ。改名前の失敗では事後通知を送らず、他の編集を上書きしない。
4. R4。Aleph の機能を明示しないクライアントに、プロットや Wiki リンクを対象とする編集を返さない。

| 境界の入力 | 期待する結果 |
| --- | --- |
| 操作が空、または参照が 0 件 | `null` |
| 同じファイルを二つの位置から import | 二つの範囲を編集 |
| 同じフォルダの組が二度届く | 子孫の参照に一度だけ適用 |
| 親と子の行き先が矛盾 | エラー、編集は 0 件 |
| 応答待ちに未保存の文書が変化 | 旧版の応答を破棄 |
| 改名後の理解が変わらない相対リンク | 編集は 0 件 |
| ディスクの改名に失敗 | 自分の編集を戻し、完了した範囲を照合 |

## テスト設計

Golem のパーサーを呼ぶ試作で、章フォルダの改名、二つの import、似たフォルダ名、本文、重複、競合、未保存の本文などを調べる。
プロトコル試験では能力を申し出るクライアントで `initialize`、`willRenameFiles`、`didRenameFiles` の順と結果を記録する。
本実装では TOML の字句範囲、アセットの各欄、UTF-8 と UTF-16、URI 中の空白と非 ASCII 文字、版競合と書き込みの各段階の失敗を検査する。
Aleph 側では開いた子孫と閉じた文書の混在、同名の別ファイル、Wiki リンクの移動前後の解決、プロジェクトルートの改名を統合試験にする。

### 試作で確認した範囲

基準版 Golem の実行ファイルにファイル操作の能力を申し出ると、登録は空で、改名前の要求はエラー −32601 になった。
Golem LSP に試作用のハンドラーを加え、標準入出力上で同じクライアントを接続した。
サーバーは `file` スキームの改名前の要求と改名後の通知に登録した。
ディスクには import がない文書を版 7 で開くと、応答は未保存の本文にある二つの import への編集と、元の URI と版 7 を返した。
同じフォルダの組を重ねても編集は二つ、行き先が矛盾する組はエラー −32600 だった。
試験クライアントが編集を適用してディスクのフォルダを改名し、改名後の通知を送った後、同じ元パスをもう一度問い合わせると応答は `null` だった。

試作のハンドラーは UTF-16 と一つの開いた .gm の import に限った。
改名後の通知は受信するだけなので、索引の再構築を確認した結果には含めない。
Aleph の既存の Wiki リンク改名試験は 1 件通った。
TOML、プロット、Wiki リンクを含む LSP 応答、閉じた文書、複数ルート、ファイル操作失敗後の復元、Aleph とサーバーをつないだ操作は未検証である。
コマンドと結果は未コミットの試作の `experiments/lsp-file-rename/README.md` に残した。

## トレードオフ

改名後に旧パスを探す方式では、同名のシートのどれを指していたかを復元できない場合がある。
改名前にサーバーが対象を解決すると、エディター側に Golem の文法やパス解決を複製せずに済む。
一方で、閉じた参照元の読み取りが要求時間に加わり、プロジェクト全体の編集が完了したかを Aleph が管理する必要がある。
Aleph 固有の参照形式を加えるには、Aleph の解決規則との互換性を両方のテストで維持する費用も生じる。
