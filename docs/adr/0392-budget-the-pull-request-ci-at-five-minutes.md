# ADR 0392: プルリクエストの CI の時間を 5 分の予算にする

Status: accepted

## 文脈

CONTRIBUTING.md は、CI の実行時間を 5 分以内に保ち、プルリクエストの CI が 5 分を超えたら、ほかの作業を止めて CI を改善すると書いている。
しかし、この 5 分を決めた ADR は無い。
`docs/budgets.md` は、「この 5 分を決めた ADR は無いので、予算としてはこの一覧に載せない」と書き、予算にするときは何を測るかを ADR で決めるとしている。

tett23 は、2026-11-18 に次のとおり決めた。

- CI の 5 分を予算に加える。
- 測るのは、プルリクエストの `ci.yml` の実行の時間の中央値とする。ランナーの順番待ちは含めない。
- この ADR は、予算と測り方だけを決める。予算に収めるための CI の組み替えは、測った後に別の ADR で決める。

## 調査した事項

この節の値は、2026-11-18 に、origin/main の [`8f818497`](https://github.com/tett23/golem/tree/8f8184978a521cce45a4bbfe326bb4ef03346626) と GitHub の API で確かめた。

- `ci.yml` のジョブの依存（`needs`）は次のとおりである（[`ci.yml`](https://github.com/tett23/golem/blob/8f8184978a521cce45a4bbfe326bb4ef03346626/.github/workflows/ci.yml)）。
  - `changes`、`scripts-linux`、`editors` は、ほかのジョブを待たない。
  - `build`、`wasm`、`visual`、`release-scripts`、`scripts-macos`、`format`、`plugins`、`editors-lsp`、`verapdf` は `changes` を待つ。
  - `determinism` は `build` を待つ。`caches` は `changes`、`build`、`wasm` を待つ。
  - 必須のチェックの `ci` は、`caches` を除くすべてのジョブを待つ。
- 実行の作成から終わりまでの時間は、ランナーの順番待ちを含む。2026-11-17 には、macOS のランナーの順番待ちで、`scripts-macos` が 2 時間ほど始まらない実行がいくつもあった。
- 成功したプルリクエストの `ci.yml` の直近 40 回について、ジョブごとの `started_at` から `completed_at` までの秒を取った（`gh api repos/tett23/golem/actions/runs/<id>/jobs`）。`build` の 7 つのランナーは、最も長いものを `build` の秒とした。依存の順に秒を足して、`ci` が終わるまでの最も長い道の秒（下の「測り方」の値）を求めると、次のとおりだった。
  - `build` を省かなかった 31 回：最小 294 秒、中央値 491 秒、最大 718 秒。そのうち直近の 20 回の中央値は 509 秒である。
  - 文書だけの変更で `build` を省いた 9 回：中央値 170 秒。
- 今の CI は、この測り方で 5 分を超えている。

## 実装すること

### 予算

- プルリクエストの `ci.yml` の時間の中央値を、300 秒以下とする。
- 対象の実行は、`pull_request` の `ci.yml` の成功した実行のうち、`build` を省かなかったものの直近 20 回とする。文書だけの変更で `build` を省いた実行は、短いので数えない。
- CONTRIBUTING.md の、wasm のツールチェーンか freeze を替えるプルリクエストの例外（[ADR 0219](0219-frequency-of-the-wasm-job-and-its-uncached-runs.md)）は、そのまま残す。中央値で判定するので、例外の一回の実行は予算をほとんど動かさない。

### 測り方

一回の実行の時間は、ランナーの順番待ちを含めず、ジョブの依存をたどった最も長い道の秒とする。

- 各ジョブの秒は、`started_at` から `completed_at` までとする。省いたジョブ（`conclusion` が `skipped`）は 0 秒とする。マトリクスのジョブ（`build`）は、ランナーのうち最も長いものとする。
- 各ジョブの終わりの時刻を、そのジョブの秒と、待つジョブの終わりの時刻の最大との和とする。実行の時間は、`ci` の終わりの時刻とする。
- ジョブの依存は、測る時点の `ci.yml` の `needs` から読む。

### 計測のコマンドと一覧

- 上の測り方を、`scripts/ci/ci-critical-path.sh` に POSIX sh と jq で書く。直近 20 回の実行のジョブを `gh` で取り、各実行の秒の中央値を、標準出力の最後の行に一つの数として出す。20 回は偶数なので、中央値は真ん中の二つの平均とする。
- `docs/budgets.md` の「計測のコマンドで確かめる予算」の表に、この予算の行を足す。「ADR の無い目安」の段落を消す。
- CONTRIBUTING.md の 5 分の段落に、この ADR へのリンクと、測り方（中央値、順番待ちを含めない）を書く。

## 実装しないこと

- 予算に収めるための CI の組み替え（重いジョブを毎晩に移す、変更の無いパッケージのテストを省く、など）。測った後に別の ADR で決める。
- `bin/budget-check` を CI で動かすジョブ。どのイベントで動かすかは別の ADR で決める。
- `main` への push の実行と、毎晩のワークフローの予算。
- ランナーの順番待ちの時間の予算。

## 不変条件

以下で、`t(j)` をジョブ `j` の秒、`F(j)` をジョブ `j` の終わりの時刻とする。

- I1: どの実行でも、`F(j) = t(j) + max { F(d) : d は j の needs }` であり、needs が空なら `F(j) = t(j)` である。実行の時間は `F(ci)` である。
- I2: 省いたジョブの秒は 0 であり、マトリクスのジョブの秒はランナーの秒の最大である。
- I3: 実行の時間は、ジョブの始まりより前の順番待ちの時間によらない。
- I4: 計測のコマンドは、対象の実行の時間の中央値を、標準出力の最後の行に一つの数として出す。偶数個のときは真ん中の二つの平均である。

| 入力 | 期待 | 不変条件 |
| --- | --- | --- |
| needs の無いジョブだけの実行 | 実行の時間は `ci` の秒 | I1 |
| `changes` が 10 秒、`build` が 200 秒、`determinism` が 30 秒、ほかが 5 秒 | `ci` の終わりは 10 + 200 + 30 + `ci` の秒 | I1 |
| `build` を省いた実行 | `build` は 0 秒で、対象から外す | I2 |
| `build` のランナーが 100 秒と 300 秒 | `build` は 300 秒 | I2 |
| `scripts-macos` が 2 時間待ってから 60 秒で終わる | `scripts-macos` は 60 秒として数える | I3 |
| 実行の時間が 1、2、3、4 | 2.5 | I4 |
| 実行の時間が 1、2、3 | 2 | I4 |

## 受けいれ条件

- A1: `scripts/ci/ci-critical-path.sh` を動かすと、最後の行に一つの数を出す。実装の PR の本文に、その出力を書く。予算を満たすかどうかは問わない。

## テスト設計

テストの名前は `ADR 0392 I<n>: ` で始める。

- I1 から I4 は、`scripts/ci/ci-critical-path.sh` が、`gh` の代わりに JSON のファイルを入力に取れるようにして、境界の表の行をそれぞれ一つのケースとする。テストは、ほかの `scripts/ci` のテストと同じ置き場所と形で書く。
- `ci.yml` の `needs` の読み取りは、今の `ci.yml` から上の「調査した事項」の依存を読めることを確かめる。
- A1 は、実装の PR で一度だけ確かめる。

## トレードオフ

- 中央値で判定するので、一回だけ遅い実行は予算を破らない。そのかわり、遅い実行が続いてから予算の違反に気づく。
- 順番待ちを含めないので、ランナーの不足で開発が待たされる時間は、この予算では見えない。
- 今の CI はこの予算を超えているので、この ADR を入れた時点で予算の違反がある。収める組み替えは別の ADR で決める。
- 計測のコマンドは GitHub の API を使うので、ネットワークと `gh` の認証が要る。Actions のキャッシュの予算と同じである。
