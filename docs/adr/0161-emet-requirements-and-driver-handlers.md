# ADR 0161: Emet の関数の要求と driver のハンドラ

ステータス: 採択

## 文脈

[ADR 0160](0160-emet-function-language-core.md) は、`.emet` の関数を純粋なものとした。
しかし、社内の使い手が書きたい関数の多くは、手元の表や辞書を読む。
ルビの読みの一覧、用語の表、社内の表記の規則などである。
プラグインは同じ必要を、`manifest.toml` で渡すデータ（[docs/adr/0105](0105-plugin-data.md)）と、プラグインが宣言して受け取る本の文脈（[docs/adr/0121](0121-host-context-in-plugin-requests.md)）で満たしている。

言語の名前は、メンテナーの案の `.gmx` から Emet（拡張子 `.emet`）に変えた（[ADR 0160](0160-emet-function-language-core.md) の「決めたことの記録」）。

### 破棄した草案からの引き継ぎ

この ADR は、破棄した [docs/adr/0149](0149-gmx-requirements-and-driver-handlers.md) を引き継ぐ。
0149 は [PR #526](https://github.com/tett23/golem/pull/526) で誤って採択され、「メンテナーが決めること」に挙げた点はどれも「推奨のとおり」と記録されて [PR #533](https://github.com/tett23/golem/pull/533) で実装されたが、メンテナーは 2026-11-05 に取り下げ、実装を戻した（[PR #538](https://github.com/tett23/golem/pull/538)。[仕様書の「破棄した ADR」](../specifications.md#破棄した-adr)）。
[ADR 0160](0160-emet-function-language-core.md) と同じく、メンテナーが決めた点だけを「決めたことの記録」に書き、それ以外は「メンテナーが決めること」に挙げる。
本文は推奨の案で書いてある。

### メンテナーの案

メンテナーの案は、関数が処理系に求めるもの（**要求**）を、関数のシグネチャに書くことである。
最初の案は、型の後ろに `=>` を置く形だった。

```
pub inline/block docStyles :: Evaluated -> FileId -> Style => file
```

案の要点は次のとおりである。

- 代数的エフェクトを部分的に実装する。エフェクトを処理するハンドラは driver に集め、利用者はハンドラを書けない。型の上では、ハンドラを足す余地を残す。
- シグネチャを読めば、関数が driver に何を求めるかが分かる。wasm のモジュールが import でホストに求めるものを宣言するのと同じ形である。
- 未知の要求はエラーとする。
- コードを読み込めば、`manifest.toml` に足りない要求を見つけられる。ファイルがない場合はエラーとする。

例の型（`Evaluated`、`FileId`、`Style`）は Golem の内部の型であり（[`docStyles`](https://github.com/tett23/golem/blob/4f86b945b6e60913fc63e22c0bf4ec14e5114bed/modules/golem-driver/src/Golem/Driver.hs#L169-L170)）、`.emet` からは見えない。

2026-11-05 と 2026-11-06 に、メンテナーは次のことを決めた（「決めたことの記録」）。

- 要求の記法を Koka にならう。
- 要求を持つ関数を引数で渡せ、要求を合成する。
- 読むファイルの名前の表（破棄した 0149 の `[functions.data]`）を置かない。
- ファイルを読む要求は、`file` という種類だけでは不便なので、読むファイルの名前（プロジェクトのルートからの相対パス）を要求に含める。

Koka は、関数の型の矢印の後ろ、結果の型の前に、エフェクトの列（row）を書く（`int -> <console,exn> int`）。
エフェクトの列は合成でき、変数を持てるので、高階の関数は渡された関数のエフェクトをそのまま自分のエフェクトにできる（参考文献の Leijen 2014）。
この記法では `=>` を使わないので、`=>` は Haskell と同じく型クラスの制約のために空けておける（[ADR 0160](0160-emet-function-language-core.md) の「型クラスの余地」）。

プラグインのホストは、wasm の import を一切渡さない（[golem-plugin ADR 0001](../golem-plugin/adr/0001-wasm-host-and-abi.md)）。
プラグインが外のものを受け取る経路は、`golem_describe` で宣言した名前に限られ、宣言できる名前は閉じた一覧である。
一覧にない名前を宣言したプラグインは、読み込みの時点で G06105 になる（[docs/adr/0121](0121-host-context-in-plugin-requests.md)）。
案の「未知の要求はエラー」は、この規則を `.emet` の型に移したものと読める。

### 実装から分かったこと

戻した実装（[PR #533](https://github.com/tett23/golem/pull/533)）から、次が分かった。

- 要求の集合を関数の型（`Scheme`）の項として持つ形で、要求の検査を Hindley-Milner の型検査に載せられた（[`Types.hs`](https://github.com/tett23/golem/blob/ba6635adfc787a92a1c003a37650a5919a26e3eb/modules/golem-gmx/src/Golem/Gmx/Types.hs)）。この ADR は、集合に変数を足して、列の単一化に広げる。
- 「呼ぶ」の範囲を決める必要があった。実装は、引数の数が足りた呼び出しと、引数のない関数の参照を呼び出しとして扱った。この ADR も同じ範囲を呼び出しとする。
- 評価器はハンドラ（`Handlers`）を呼び出し側から受け取り、評価器のパッケージ（当時の golem-gmx）はファイルシステムに触れなかった。
- `[functions.data]` の名前の表は、データのファイルを一つ足すたびに、`manifest.toml` に名前とパスを、`.emet` に名前を書かせた。メンテナーはこれを煩雑とした。
- 読み込みの時点でデータのファイルをすべて読む形（[docs/adr/0120](0120-plugin-data-check-at-load.md) と同じ）は、ないファイルを関数を呼ぶ前に見つけ、評価のあいだにファイルシステムに触れずに済んだ。

## 実装すること

### シグネチャの要求

Koka と同じく、要求の列を矢印の後ろ、結果の型の前に書く（「決めたことの記録」）。

```haskell
pub inline reading :: String -> <file "data/words.tsv"> Inlines
lookupReading :: String -> <file "data/words.tsv"> Maybe String
total :: List Nat -> Nat
mapReadings :: (String -> e String) -> List String -> e (List String)
```

- 要求の列は `<` と `>` で囲み、要求をカンマで区切って並べる。
- ファイルを読む要求は、`file` と、読むファイルのプロジェクトのルートからの相対パスの文字列のリテラルを並べて書く（`file "data/words.tsv"`）。一つのファイルが一つの要求である。二つのファイルを読む関数は、`<file "data/words.tsv", file "data/terms.tsv">` と書く（「決めたことの記録」）。
- 列の最後に `|` と変数を書くと、開いた列になる（`<file "data/words.tsv"|e>`）。その関数は、書いた要求と、`e` に入るほかの要求を持つ。
- 要求の変数だけからなる列は、Koka と同じく括弧を付けずに変数だけを書く（`e String`）。矢印の後ろで、英小文字の識別子の後ろに型が続けば、その識別子を要求の変数として読む。`.emet` は高階の種を持たない（[ADR 0160](0160-emet-function-language-core.md)）ので、型の変数を型に当てる読み方と重ならない。
- 列を書かない矢印は、要求を持たない。要求を持たない関数は純粋である。
- 列の中の要求の順は意味を持たず、fmt が種類とパスの順に並べ替える。同じ要求を二度書くと E05102 とする。
- 要求の種類は、下の一覧の種類に限る。一覧にない種類は E05100 とし、プラグインの G06105 と同じく、知らない種類をすべて一つの diagnostic に並べ、メッセージに使える種類の一覧を添える。

### 列を書く矢印

`.emet` の関数の型は、Haskell と同じく引数を一つずつ取る矢印の連なりである。
要求は、関数の本体を評価したときに生じる。
本体を評価するのは、等式の引数の数（n）だけ引数を受け取ったときである。
メンテナーは、本体を評価する矢印にだけ列を書ける形を不便とし、規則を足して書ける位置を広げると決めた（「決めたことの記録」）。

- **本体の矢印**：n 個目の矢印には、本体の要求の列を書く。
- **戻り値の関数の矢印**：n 個目より後ろの矢印は、関数が返す関数の型の矢印である。そこに書いた列は、返した関数を呼んだときの要求である。等式の引数の数がシグネチャの矢印の数より少ない関数は、部分適用した関数を返す（`f x = g x`）。返した関数の要求は、その関数の型の列で検査する。
- **関数の型の引数**：引数の関数の型（`(String -> e String)`）の矢印にも、同じ規則で列を書く。
- **本体の前の矢印**：n 個目より前の矢印では何も評価しないので、列を書くと E05106 とする。
- **部分適用**：引数の足りない呼び出しは本体を評価しないので、要求を持たない。足りた時点で、n 個目の矢印の列の要求が生じる。
- **引数のない関数**：`config :: <file "data/config.tsv"> String` のように `::` の直後に列を書く。参照したときに要求が生じる。

[ADR 0160](0160-emet-function-language-core.md) の E02106（等式の引数の数がシグネチャと合わない）は、等式どうしで引数の数が違う場合と、等式の引数がシグネチャの矢印の数より多い場合を指す。
等式の引数がシグネチャの矢印の数より少ない場合は、上の「戻り値の関数の矢印」に当たり、誤りではない。

### 要求の一覧

v1 の一覧は `file` だけとする（「メンテナーが決めること」の 3）。

| 種類 | 使える操作 | ハンドラ |
| --- | --- | --- |
| `file "パス"` | `File.read "パス"` の型は `<file "パス"> String` | driver。`manifest.toml` に書いたファイルを、読み込みの時点で読む |

`File.read` は、プロジェクトのルートからの相対パスの文字列のリテラルを一つ受け取り、そのファイルの中身を文字列で返す。

- 引数は文字列のリテラルに限る。変数や式を渡すと E05107 とする。要求にファイルの名前を含めるので、読むファイルは型の検査の時点で決まっていなければならない。
- パスは、プロジェクトのルートからの相対パスに限る（「決めたことの記録」）。ルートの外、絶対パス、URL は G03003 とする。パスの検査は `resolveInRoot` で行う（[`resolveInRoot`](https://github.com/tett23/golem/blob/4f86b945b6e60913fc63e22c0bf4ec14e5114bed/modules/golem-project/src/Golem/Project/Paths.hs#L47-L48)）。原因が `@import` のルートの外と同じなので、コードを分けない。
- パスは正規化してから比べる。`data/./words.tsv` と `data/words.tsv` は同じ要求である。大文字と小文字だけが違うパスは、`@import` と同じく G03004 とする。
- 中身は UTF-8 として読む。不正なバイト列は E05103 とする。先頭の BOM は読み飛ばし、CRLF は受け付ける。`@table` の表のファイルと同じ扱いである（[golem-eval ADR 0004](../golem-eval/adr/0004-tsv-tables.md)）。
- 一つのファイルの大きさは、プラグインのデータと同じ 64 MiB までとし、超えれば E05105 とする。

本の文脈（書字方向、数の表記）、`meta` の値、文書構造（S1）の値を読む要求は、v1 では入れない。
入れるときは、この ADR の修正の ADR で一覧に足す。
一覧はプラグインの文脈の一覧（[docs/adr/0121](0121-host-context-in-plugin-requests.md)）と別に管理する。

### 要求の合成と伝わり方

要求は関数の型の一部であり、型の検査で確かめる。

- 関数の本体の要求は、本体の中の呼び出しの要求を合わせたものである。`file "data/words.tsv"` を要求する関数と、`e` を要求する引数の関数を呼ぶ本体は、`<file "data/words.tsv"|e>` を要求する。
- 本体の要求が、シグネチャの列に含まれなければ E05101 とし、位置は呼び出しを、メッセージは足りない要求を指す。シグネチャの列が開いていれば、変数が残りを受け取る。
- 要求を持つ関数を、引数として渡せる（「決めたことの記録」）。`List.map lookupReading words` は、`List.map :: (a -> e b) -> List a -> e (List b)` の `e` が `<file "data/words.tsv">` になり、呼び出しの全体がその要求を持つ。
- 組み込みの高階の関数（`List.map`、`List.foldl`、`String.map` など）は、渡された関数の要求をそのまま自分の要求にする型を持つ。
- 使わない要求をシグネチャに書いても誤りにしない。将来使う予定の要求を先に書くことを妨げないためである。その代わり、閉じた列に本体で使わない要求があれば、info（E05108）で知らせる（「決めたことの記録」）。位置はその要求、メッセージは関数の名前と要求である。info は `--verbose` を付けたときと LSP にだけ出る（[docs/adr/0104](0104-info-severity.md)）。開いた列の変数は、使わなくても知らせない。
- `where` の中の局所の関数は、シグネチャがなければ要求も推論する。推論した要求の変数は、型の変数と同じく一般化する。

要求の列は、利用者がハンドラを書けないので、同じ要求を二度持つ必要がない。
このため、Koka の列（同じ名前を重ねて持てる）と違い、要求の集合として扱う（「決めたことの記録」）。
型の推論は、Hindley-Milner の単一化に、列の単一化（開いた列の変数に足りない要求を入れる）を加えて行う（参考文献の Leijen 2005 と 2014）。
二つの要求は、種類とパスがどちらも等しいときに同じとする。

ハンドラは driver が持つものだけであり、`.emet` の中で要求を処理して消すことはできない。
列を型の項として持つので、利用者のハンドラは、後から列から要求を除く規則を足す形で入れられる（メンテナーの案の「型の上では拡張の余地を残す」）。

### `manifest.toml` での許可

関数に読ませるファイルは、`manifest.toml` の `[functions.requires]` の `file` に、ファイルの名前で並べる（「決めたことの記録」）。

```toml
[functions.requires]
file = ["data/words.tsv", "data/terms.tsv"]
```

- `[functions.requires]` のキーは要求の種類、値はその種類の要求の配列である。`file` の値は、プロジェクトのルートからの相対パスの配列である。省けば、関数はファイルを読めない。
- 読み込みの時点で、プロジェクトの `.gm` が `@import` で取り込む `.emet` と、`[[filters]]` が指す `.emet`（[ADR 0162](0162-calling-emet-functions-from-gm.md)）から、`import` でたどれるすべての `.emet` のすべての関数のシグネチャの要求を集め、`manifest.toml` にない要求があれば E05104 とする。位置は、その要求を書いたシグネチャである。メッセージには `manifest.toml` に足す行を書く。これが案の「コードを読み込めば、manifest に足りない要求を見つけられる」である。
- `[functions.requires]` に一覧にない種類のキーがあれば G03101 とする。
- `file` に書いたファイルがなければ G03102 とする。これが案の「ファイルがない場合はエラー」である。ルートの外のパスは G03003 とする。
- 関数を一つも呼ばない本でも検査する。誤りが見えるかどうかを、原稿に呼び出しを書いたかどうかで変えないためである（[docs/adr/0120](0120-plugin-data-check-at-load.md) と同じ理由）。

`manifest.toml` に読むファイルの名前を並べるので、本を作る側の責任者は、関数が読むファイルを `.emet` を開かずに確かめられる。
関数が新しいファイルを読むようになれば、`manifest.toml` の差分に現れる。
破棄した 0149 の `[functions.data]` と違い、`.emet` の側でもパスをそのまま書くので、名前とパスの対応の表は持たない。

### driver のハンドラ

- ハンドラは golem-driver に置く。golem-emet の評価器は、要求の操作に出会うと、評価を止めずに driver から渡されたハンドラの関数を呼ぶ。golem-emet はファイルシステムに触れない。
- `file` のハンドラは、読み込みの時点で `[functions.requires]` の `file` のファイルをすべて読み、評価のあいだはその値だけを返す。評価の途中でファイルシステムに触れない。プラグインのデータと同じく、評価を純粋に保ち、ファイルを並列に評価できるようにするためである。
- LSP は、`[functions.requires]` の `file` のファイルを、表のファイルと同じ仕組みで監視し、変われば評価し直す（[仕様書の「LSP」](../specifications.md#lsp)）。

### 誤りのコード

| コード | 重大度 | 原因 |
| --- | --- | --- |
| E05100 | エラー | シグネチャに一覧にない要求の種類がある |
| E05101 | エラー | シグネチャにない要求を使っている |
| E05102 | エラー | 一つの列に同じ要求を二度書いた |
| E05103 | エラー | 要求したファイルが UTF-8 として読めない |
| E05104 | エラー | シグネチャの要求が `manifest.toml` の `[functions.requires]` にない |
| E05105 | エラー | 要求したファイルが 64 MiB を超える |
| E05106 | エラー | 要求の列を、本体の前の矢印に書いた |
| E05107 | エラー | `File.read` の引数が文字列のリテラルでない |
| E05108 | info | シグネチャの閉じた列に、本体で使わない要求がある |
| G03101 | エラー | `[functions.requires]` に一覧にない種類のキーがある |
| G03102 | エラー | `[functions.requires]` の `file` のファイルがない |

E05100 と G03101 は、どちらも一覧にない種類だが、書いた場所と直す人が違う。
E05100 は関数の作者が `.emet` を、G03101 は本の設定の担当が `manifest.toml` を直す。
一つのコードに一つの原因の原則に従い、分ける。

`E` のコードは、[ADR 0160](0160-emet-function-language-core.md) の「型と評価の誤りのコード」が作る接頭辞の、段階 E05 である。
戻した実装は、要求の誤りに `G105` のコードを使っていたが、新しい接頭辞にしたので、`G10` の番号はどれも使わない。
G03101 と G03102 は、戻した実装が同じ意味で使っていた。
G03102 は、戻した実装では `[functions]` の `files` と `[functions.data]` のファイルがないことを表した。
宣言したファイルがないという原因が同じなので、同じ意味として使う。
戻した実装が別の意味で使った G03103 から G03107 も、この ADR と [ADR 0162](0162-calling-emet-functions-from-gm.md) では使わず、ほかの意味にも使い回さない。
その後の ADR はこの番号を飛ばして G03108 から使っている。

## 実装しないこと

- 利用者がハンドラを書くこと。
- 同じ名前を重ねて持つ列（Koka のスコープ付きの名前）。
- `file` のほかの要求（本の文脈、`meta`、S1 と S2 の値、時刻、乱数、ネットワーク、環境変数）。時刻、乱数、ネットワーク、環境変数は、決定性を壊すので今後も入れない。
- 評価の中で組み立てたパスのファイルを読むこと。`File.read` の引数は文字列のリテラルに限る。
- ディレクトリの中のファイルをまとめて要求すること（`file "data/*.tsv"` など）。
- ファイルへの書き込みと、ディレクトリの一覧。
- データを表として解釈すること。`File.read` は文字列を返し、分けるのは関数である。
- 関数ごとに許す要求を分けること。`[functions.requires]` はプロジェクトの全体で一つである。

## テスト設計

テストを先に書き、`File.read` と列の型がないためにコンパイルできないことを確かめてから実装する。

golem-emet のテストでは、次のことを確かめる。

- **記法**：`String -> <file "data/words.tsv"> Inlines`、`(a -> e b) -> List a -> e (List b)`、`<file "a.tsv", file "b.tsv"|e>` を読めること。同じ `file "a.tsv"` を二度書くと E05102、`<net>` が E05100 になり、メッセージに `file` が出ること。`data/./a.tsv` と `data/a.tsv` を同じ要求として E05102 にすること。
- **矢印**：引数が二つの等式を持つ関数のシグネチャ `String -> <file "a.tsv"> String -> Inlines` が E05106 になること。`f :: Nat -> (Nat -> <file "a.tsv"> String)` と `f x = g x`（`g` は引数が二つで `file "a.tsv"` を要求する）が通り、`f 1` は要求を持たず、`f 1 2` が要求を持つこと。
- **`File.read`**：`File.read "data/a.tsv"` の型が `<file "data/a.tsv"> String` であること。`File.read path` のように変数を渡すと E05107 になること。
- **伝わり方**：要求のある関数が `File.read` を呼べ、列のない関数から呼ぶと E05101 になること。`file "a.tsv"` を要求する関数を、`<file "b.tsv">` だけの関数から呼ぶと E05101 になり、メッセージに `file "a.tsv"` が出ること。引数のない要求つきの関数を参照しただけでも E05101 になること。部分適用だけでは要求が生じないこと。
- **合成**：`lookupReading` を `List.map` に渡した呼び出しが `file "data/words.tsv"` を要求し、それを持つ関数の中では通り、列のない関数の中では E05101 になること。純粋な関数を `List.map` に渡した呼び出しは要求を持たないこと。開いた列を持つ利用者の高階の関数に、要求を持つ関数と持たない関数の両方を渡せること。
- **推論**：シグネチャのない `where` の関数の要求が推論され、外の関数のシグネチャと突き合わされること。
- 使わない要求が誤りにならず、閉じた列なら E05108 の info になり、`--verbose` のない `golem check` には出ないこと。開いた列の変数を使わなくても info にならないこと。

golem-driver のテストでは、次のことを確かめる。

- `[functions.requires]` のない `manifest.toml` で、`@import` で取り込む `.emet` に `file "data/a.tsv"` を要求する関数があると、関数を呼ばない本でも E05104 になり、メッセージに足す行が出ること。`[[filters]]` だけが指す `.emet` でも E05104 になること。
- `[functions.requires]` の `net` のキーが G03101 になること。
- `file` に書いたファイルがないと、関数を呼ばない本でも G03102、ルートの外のパスが G03003、大文字と小文字だけが違うパスが G03004 になること。
- 不正な UTF-8 のファイルが E05103、64 MiB を超えるファイルが E05105 になること。BOM と CRLF のファイルを読めること。
- 同じファイルを二つの `.gm` の評価で読み、評価のあいだにファイルを書き換えても、二つが同じ値になること。並列と逐次で、出力と diagnostics が一致すること。

golem-lsp のテストでは、`[functions.requires]` の `file` のファイルを書き換えると、diagnostics が公開し直されることを確かめる。

## トレードオフ

要求にファイルの名前を含めるので、関数がどのファイルを読むかが、シグネチャと `manifest.toml` の両方で読める。
ないファイルは、関数を呼ぶ前に、読み込みの時点で見つかる。
その代わり、読むファイルは型の検査の時点で決まっていなければならず、パスを組み立てて読むことはできない。
章ごとに辞書のファイルを分けるような書き方では、ファイルごとに `File.read` を書き、シグネチャと `manifest.toml` にファイルを並べる。

ファイルを一つ足すと、`.emet` のシグネチャと `manifest.toml` の二か所を変える。
破棄した 0149 の `[functions.data]` と数は同じだが、どちらにも同じパスを書くので、名前とパスの対応を覚える必要はない。

要求の列は Koka の記法なので、Haskell を知る人には見慣れない形になる。
その代わり、要求を持つ関数を高階の関数に渡せ、`=>` を型クラスの制約のために残せる。
要求の変数を持たせ、列を書ける矢印を広げたので、型の推論と誤りのメッセージは、破棄した 0149 の具体的な集合だけの形より複雑になる。
要求に文字列のパスを含めるので、要求どうしの比較はパスの正規化に依る。

v1 の一覧が `file` だけなので、縦組みかどうかで漢数字にするような関数は書けない。
プラグインでは文脈として読めるので、使い手の要望が出た時点で、この ADR の修正で一覧に足す。

## 決めたことの記録

メンテナーが決めたことだけを書く。

- **要求をシグネチャに書くこと**（メンテナーの案）：関数が処理系に求めるものをシグネチャに書き、ハンドラは driver に集め、利用者はハンドラを書けない。型の上では拡張の余地を残す。未知の要求はエラーとする。コードを読み込んで `manifest.toml` に足りない要求を見つけ、ファイルがなければエラーとする。
- **`pub inline/block` の読み方**（2026-11-04、メンテナー）：「片方」と答えた。一つの関数には `inline` と `block` のどちらか一方だけを書く（[ADR 0162](0162-calling-emet-functions-from-gm.md)）。
- **`[functions.data]` をやめること**（2026-11-05、メンテナー）：「`[functions.data]` は煩雑なだけで不要そう」。`manifest.toml` に名前とパスの対応の表を置かない。
- **要求を持つ関数を渡せること**（2026-11-05、メンテナー）：「要求を持つ関数は引数で渡せてよい」。破棄した 0149 の、要求を持つ関数を値として渡せない規則をやめる。
- **要求の合成**（2026-11-05、メンテナー）：「要求を合成する」。本体の要求は、呼び出した関数の要求を合わせたものになる。
- **記法は Koka にならうこと**（2026-11-05、メンテナー）：「要求の記法は Koka のものを真似する」。要求の列を矢印の後ろ、結果の型の前に `<...|e>` の形で書く。
- **パスはルートからの相対パスだけ**（2026-11-06、メンテナー）：「相対パスだけにする。不便だったら直す」。
- **ファイルの名前を要求にすること**（2026-11-06、メンテナー）：「仮に file と置いているが、ファイル名とする」「file だけだと不便なので、tsv だったら実ファイル名を要求する」。要求を `file "data/words.tsv"` の形でファイルごとに書き、`manifest.toml` にもファイルの名前を並べる。`File.read` の引数を文字列のリテラルに限ることと、`[functions.requires]` の形は、この草稿の帰結である。
- **列を書く矢印を広げること**（2026-11-06、メンテナー）：「不便なので規則を増やす」。本体の矢印のほか、戻り値の関数の矢印と関数の型の引数の矢印にも列を書ける。本体の前の矢印を E05106 とすることは、この草稿の帰結である。
- **要求の集合**（2026-11-06、メンテナー）：「推奨で」。列を同じ要求を重ねて持てない集合として扱う。
- **v1 の要求の一覧**（2026-11-06、メンテナー）：「許容する」。v1 の要求は `file` だけとする。
- **使わない要求**（2026-11-06、メンテナー）：「許容する。info を出力する」。info を閉じた列に限ることは、この草稿の案である。
- **表の名前**（2026-11-06、メンテナー）：「問題ない」。`[functions.requires]` とする。

## メンテナーが決めること

採択の前に、次のことを決めてほしい。
本文は推奨の案で書いてあり、違う案を採れば書き換える。
決めた項目は、番号を変えないように残し、決めたことを書く。

1. **パスの基準**：決めた。プロジェクトのルートからの相対パスだけにする（「決めたことの記録」）。
2. **`manifest.toml` での許可**：決めた。読むファイルの名前を `manifest.toml` に並べる（「決めたことの記録」）。形は推奨の `[functions.requires]` の `file` の配列で書いた。採らなかった形は、`[functions]` の `requires = ['file "data/words.tsv"']` のように要求をシグネチャと同じ字句で書くことである。シグネチャと見た目が揃うが、TOML の文字列の中に引用符が入る。
3. **v1 の要求の一覧**：決めた。`file` だけにする（「決めたことの記録」）。
4. **使わない要求を許すか**：決めた。許し、info（E05108）を出す（「決めたことの記録」）。
5. **列を書く矢印**：決めた。本体の矢印に加え、戻り値の関数の矢印と関数の型の引数の矢印にも書ける（「決めたことの記録」）。
6. **`[functions]` の名前**：決めた。`[functions.requires]` とする（「決めたことの記録」）。
7. **要求を持つ関数を値として渡せるか**：決めた。渡せる（「決めたことの記録」）。
8. **`requires` のないデータを誤りにするか**：`[functions.data]` をやめたので、この問いはなくなった。
9. **列を名前の集合として扱うか**：決めた。集合として扱う（「決めたことの記録」）。
