# ADR 0034: 本文の中のコードの和文の字のあいだで改行できるようにする

ステータス: 採択（`wrap-mark` の既定は `"⏎"`（U+23CE）とした。二つのマニュアルのコードの書体の Noto Sans JP と Source Code Pro が U+21A9 の字形を持たず、Noto Sans JP が U+23CE を持つため。`↩` は和文の字のクラスに入り、Noto Sans JP で描くので、その書体が字形を持ち、同じく改行を表す記号の U+23CE を選んだ）→改行の印の幅で行があふれる候補の活きている節点、トレードオフの節の印の文、C2 の a_あ の文は [golem-layout ADR 0036](0036-record-what-the-implementation-of-0034-decided.md)、印の描き方、大きさ、位置、色は [golem-layout ADR 0042](0042-draw-the-wrap-mark-of-inline-code-small-and-light.md)、不変条件の C3 と C4 は [golem-layout ADR 0045](0045-break-inline-code-after-hyphens-and-full-stops-to-avoid-loose-lines.md) の J3 と J5

## 文脈

ロードマップの v0.1.0-rc4 に残る最後の項目は、「本文の中のコードの和文の改行」である（[docs/roadmap.md](../../roadmap.md)）。
本文の中のコード（文字スタイル `code`）は、空白、`/` の後、`_` の連なりの後でしか改行しない（[golem-driver ADR 0017](../../golem-driver/adr/0017-pdf-code-blocks.md)、[golem-layout ADR 0031](0031-line-breaks-after-low-lines-in-identifiers.md)）。
和文には空白がないので、和文を含む長いコードは、その全体が一つの改行できない並びになり、行長からはみ出す。
利用者のマニュアルの付録 E は、はみ出す六つの項目のメッセージの後ろを `…` で略して避けている（[docs/adr/0178](../../adr/0178-colophon-commit-line-overflow.md)、[docs/adr/0210](../../adr/0210-warn-overfull-lines-in-build.md)）。
はみ出す行は、`golem build` が G07105 の警告で報告する。

### 和文の並びは、一つの箱になる

コードの文字列は、次の三段で項目になる（origin/main の ed9aafba）。

1. [`codePieces`](https://github.com/tett23/golem/blob/ed9aafba3e0ffd788f921de86b261339d8f642cd/modules/golem-layout/src/Golem/Layout/Japanese.hs#L676-L686) が、空白とタブで区切った並びを一つずつ `PCode` にする。
2. [`codeItems`](https://github.com/tett23/golem/blob/ed9aafba3e0ffd788f921de86b261339d8f642cd/modules/golem-layout/src/Golem/Layout/Japanese.hs#L960-L982) が、`PCode` を `/` の後と `_` の連なりの後で部分に分け、各部分を欧文の字の並びと欧文でない字の並び（`T.groupBy sameSide`）に分けて、それぞれを一つの箱にする。
3. [`normalize`](https://github.com/tett23/golem/blob/ed9aafba3e0ffd788f921de86b261339d8f642cd/modules/golem-layout/src/Golem/Layout/Japanese.hs#L1218-L1230) は、コードの箱のあいだに、`/` の後の罰点 0 と `_` の後の罰点 100 だけを置く。和文と欧文の境にも、空きも罰点も置かない。

和文の字の並びは、何字続いても一つの箱である。
禁則も文字クラスも、コードの中では働かない。
本文の和文の字のあいだに罰点を置く [`between`](https://github.com/tett23/golem/blob/ed9aafba3e0ffd788f921de86b261339d8f642cd/modules/golem-layout/src/Golem/Layout/Japanese.hs#L1325-L1364) は、コードの箱どうしには呼ばれない。
ハイフネーション（[docs/adr/0222](../../adr/0222-line-breaking-points-the-invariants-did-not-decide.md)）も、`wordItems` を通らないコードには当たらない。

### 試作

作業用の worktree で、次の二つだけを変えた golem を作った（コミットしていない）。

- `codeItems` で、`code` の欧文でない字の並びを、字（基底の字と後に続く結合文字）ごとの箱にする。
- `normalize` で、隣り合う `code` の箱の、前の箱の最後の字と後の箱の最初の字がともに欧文でなければ、本文の `between` と同じ禁則（行頭禁則、行末禁則、分離禁止文字の連続）を判定し、禁則に当たらなければ `Penalty 0 0 NoHyphen` を置く。

この golem で同じ本を組むと、縦組みでも横組みでも diagnostic が一つも出なかった。
横組みの PNG で、句読点が行頭に来ないこと、`（` が行末に残らないことを目で確かめた。
E の段落の行は、試作の前と変わらなかった。

### HTML と EPUB

HTML と EPUB の `style.css` は、`pre` にだけ `white-space: pre-wrap` と `overflow-wrap: anywhere` を付け、本文の中のコード（`<code>`）には `white-space` も `word-break` も付けない（[`Golem.Html` の `css`](https://github.com/tett23/golem/blob/ed9aafba3e0ffd788f921de86b261339d8f642cd/modules/golem-html/src/Golem/Html.hs#L973-L976)）。
`<code>` の行を分けるのは、ブラウザーの既定の改行（Unicode の UAX #14 と CSS Text の `line-break: auto`）である。

Google Chrome 156.0.8078.80 の headless で、再現の本の横組みの HTML と、手で書いた HTML を描いて確かめた。

- `<code>` の中の和文の字のあいだで改行した。読点は行頭に来ず、`（` は行末に残らなかった。
- 和文と欧文の字の境（`あいうえお|foobar`、`foobar|かき`）でも改行した。
- 和文と ASCII の `"` のあいだ（`え"か`）では改行しなかった。
- 欧文の字だけの長い並び（`abcdefghijklmnop`）は改行せず、行長からはみ出した。

HTML は、既に和文の字のあいだで改行している。
PDF だけが、同じ原稿を一行に詰めてはみ出させている。

### 参照した組み方

仕様書の「仕様が不明瞭な場合」に従い、JLReq、InDesign、TeX の順に調べた。
InDesign と TeX の調べた結果は、「本文の中のコードの和文の改行」の節にまとめた（[TeX と InDesign との差異](../../differences-from-tex-and-indesign.md)）。

JLReq は、隣り合う二つの字のあいだで改行してよいかを、字のクラスの組の表で決める（付録 C の表 2、[文字間での分割の可否](https://www.w3.org/TR/jlreq/#possibilities_for_linebreaking_between_characters)）。
表 2 を PDF から描いて、欧文用文字（cl-27）の行と列を読んだ。

- 平仮名（cl-15）、片仮名（cl-16）、漢字等（cl-19）と cl-27 のあいだは、どちらの順でも空欄（分割可）である。
- cl-27 の後に、終わり括弧類（cl-02）、ハイフン類（cl-03）、区切り約物（cl-04）、中点類（cl-05）、句点類（cl-06）、読点類（cl-07）、繰返し記号（cl-09）、長音記号（cl-10）、小書きの仮名（cl-11）が来るところは分割不可である。どれも行頭禁則の字である。
- 始め括弧類（cl-01）の後は、cl-27 を含むどの字の前でも分割不可である。
- cl-27 の後に分離禁止文字（cl-08）が来るところと、cl-02、cl-06、cl-07 の後に cl-27 が来るところは、空欄である。
- cl-27 どうしのあいだは分割不可であり、ハイフネーションでだけ分けられる（付録 C の注記、[C.2](https://www.w3.org/TR/jlreq/#notes_a3)）。3.2.6 節も、欧文の単語をハイフネーションできる位置のほかで 2 行に分けないとする（[プロポーショナルな欧字を用いた和欧文混植処理](https://www.w3.org/TR/jlreq/#handling_of_western_text_in_japanese_text_using_proportional_western_fonts)）。

つまり JLReq では、和文と欧文の字の境は、和文の側の字の禁則に当たらない限り改行できる。
JLReq には、コードや等幅の書体の中の和文について定める節はない。

ASCII の記号がどのクラスに入るかは、JLReq の付録 A の表で次のように分かれる（[文字クラス一覧](https://www.w3.org/TR/jlreq/#character_classes)）。

- cl-27 の表は、U+0021 から U+007E までの ASCII の字をすべて、プロポーショナルな字として挙げる。
- `(`、`[`、`{` は cl-01 の表にも、`)`、`]`、`}` は cl-02 の表にも、全角の字形で挙がっている。付録 A の冒頭の注は、和文の組版ソフトウェアの多くがこれらの代わりに互換用の全角の字（U+FF08 など）を使うと書いている。`:`、`;`、`.`、`,`、`!`、`?`、`=`、`+` なども、同じく全角の字形で約物のクラスの表に挙がっている。
- `"`（U+0022）と `'`（U+0027）は、cl-27 の表にしかない。cl-01 と cl-02 に入る引用符は、`“`、`”`、`‘`、`’` である。
- 3.2.6 節の注は、プロポーショナルな欧字とアラビア数字を cl-27 として扱うと書く。和文との混植のために作った半角のアラビア数字は、連数字中の文字（cl-24）とする。

Golem の本文は、既に ASCII の字をすべて cl-27（`Western`）に分けている（[`charClass`](https://github.com/tett23/golem/blob/ed9aafba3e0ffd788f921de86b261339d8f642cd/modules/golem-layout/src/Golem/Layout/CharClass.hs#L38-L52)）。
全角の `（` や `。` が約物のクラスに入る。

## 実装すること

### 1. コードの和文の字の前後に、分割の候補を置く（golem-layout）

文字スタイル `code`（`lkCode` が真の見た目）の文字列で、隣り合う二つの字のうち少なくとも一つが和文の字（`lookClass` が `Western` でない字）であれば、そのあいだに `Penalty 0 0 NoHyphen` を置く。
和文の字どうしのあいだも、和文の字と欧文の字の境も、同じ規則で扱う。
ただし、本文の `between` と同じ禁則に当たるところには置かない。

- 後の字が行頭禁則の字（段落の禁則の強さ `ceKinsokuStrict` による）
- 前の字が行末禁則の字
- 二つがともに分離禁止文字

欧文の字は行頭禁則の字でも行末禁則の字でもないので、境で働く禁則は和文の側の字のものだけである。
これは、JLReq の表 2 の cl-27 の行と列と同じ結果になる（「文脈」の「参照した組み方」）。

字のクラスは、本文と同じく区間の言語で決める（`breakClass` と `startClass`、[docs/adr/0187](../../adr/0187-inline-language-switch.md)、[docs/adr/0211](../../adr/0211-record-what-implementations-decided-found-by-the-review-of-2026-11-08.md)）。
ASCII の字は、記号も含めてすべて欧文の字（JLReq の cl-27）とする。
`"`、`(`、`:`、`=` を、JLReq の約物のクラスとして扱うことはしない（「トレードオフ」）。
欧文の区間の中の両用の字（`…`、`“` など）は欧文の字とし、禁則の判定だけは本文と同じく和文のクラスで行う（docs/adr/0211）。

`codeItems` は、`code` の欧文でない字の並びを、字（基底の字と後に続く結合文字、[golem-driver ADR 0036](../../golem-driver/adr/0036-combining-characters.md)）ごとの箱にする。
箱の幅は、その字の `ceWordAdvance` にトラッキングを足した値とする。
欧文の字の並びは、今のとおり `/` の後と `_` の連なりの後で分けた部分ごとの箱のままとする。
`normalize` は、`code` の箱どうしのあいだで、前の箱の最後の字と後の箱の最初の字の少なくとも一方が和文の字であれば、上の候補を置く。

`/` の後と `_` の連なりの後で、後の字が和文の字のところは、次のようにする。

- 禁則に当たらなければ、候補を一つだけ置く。罰点は、`/` の後が 0、`_` の後が 100 である。上の候補を重ねて置かない。
- `_` の後では、空白で区切ったコードの最初と最後の連なりの後で改行しないという [golem-layout ADR 0031](0031-line-breaks-after-low-lines-in-identifiers.md) の除外によらず、候補を置く（`a_あ` の `_` の後など）。0031 の除外は、`_foo` や `foo_` のような識別子の端を分けないためのものであり、後に和文の字が続く `_` は識別子の端ではない。罰点は、`_` の連なりの後と同じ 100 とする。
- 後の字が行頭禁則の字（`a/。` の `。` など）であれば、今の候補も置かない。今は `。` の前で改行できるが、JLReq の表 2 は cl-27 と cl-06 のあいだを分割不可とする。

次のものは変えない。

- 欧文の字どうしのあいだ：今のとおり、空白、`/` の後、`_` の連なりの後だけで分ける。JLReq も cl-27 どうしのあいだを分割不可とする。
- コードの中の空き：和文の字のあいだにも、和文と欧文の字の境にも、アキ量のセットの空きを入れない（[golem-driver ADR 0017](../../golem-driver/adr/0017-pdf-code-blocks.md)）。境の候補は罰点だけであり、幅を持たない。行頭の始め括弧も、字形の持つ空きのまま組む。
- カーニング、ぶら下げ、突き出し、字幅の伸縮：コードには今のとおり当てない。
- コードの余白（[golem-driver ADR 0029](../../golem-driver/adr/0029-inline-code-background.md)）：今のとおり、コードの並びの最初の箱の前と最後の箱の後にだけ付ける。コードの中で改行しても、行の端に余白を足さない。空白で改行したときと同じである。
- 文字スタイル `url`：[golem-layout ADR 0018](0018-url-line-breaks.md) のままとする（「メンテナーが決めること」の 5）。
- 縦組み：和文の字は今のとおり正立、欧文の字の並びは回転する。候補の置き方は横組みと同じである。
- 改行した位置の印：空白でない候補で改行した行の行末に `wrap-mark` を描く（「実装すること」の 8）。

### 2. 罰点と設定

候補の罰点は 0 とする（「メンテナーが決めること」の 3）。
この振る舞いを止める設定は足さない（「メンテナーが決めること」の 4）。

### 3. G07105

G07105 の規則は変えない。
本文の中のコードがはみ出すのは、候補のあいだの欧文の並びが行長を超えるとき（長い識別子や URL）と、禁則で続いた字が行長を超えるときに限られる。

### 4. HTML と EPUB

変えない。
ブラウザーは既に `<code>` の中の和文の字のあいだで、禁則を守って改行している（「文脈」の「HTML と EPUB」）。
和文と英字の境でも、ブラウザーと PDF はともに改行する。
和文と ASCII の `"` の境（`え"か`）では、ブラウザーは改行せず、PDF は改行する。
この違いは残る（「トレードオフ」）。

### 5. 列挙の不変条件を、コードの並びに広げる

[docs/adr/0209](../../adr/0209-line-breaking-invariants-by-exhaustive-small-inputs.md) の `LineBreakEnum` に、コードの並びを足す（「メンテナーが決めること」の 7）。

- 部品：和文の `漢`、`あ`、`「`、`」`、`。`、`、`、`ー`、`ぁ`、`…`、欧文の `a`、`ab`、`/`、`_`、`"`、空白の 15。欧文の部品は、和文の部品と隣り合って境を作る。並び全体を `[code: …]` に入れ、前と後に置く字（`あ` と `い`）はコードの外に置く。
- 環境：禁則の強さと区間の言語（なし、`en`、`ja`）だけを掛ける。ぶら下げ、突き出し、字幅の伸縮はコードの箱に当たらないので掛けない。正規形は 0209 と同じく、`ー` か `ぁ` がなければ強い禁則だけ、両用の字がなければ区間なしだけとする。
- プルリクエストは段 2 まで（行の幅を 4 字まで）、毎晩のジョブは段 3 のすべてを調べる。段 2 の並びは 240（今の行分割の 552 の半分以下）であり、環境も少ないので、今の行分割の段 2（0209 の見込みで CI で約 3.5 秒）に 1 秒ほど足すと見込む。実装のプルリクエストで測り、範囲ごとの予算 10 秒（[ADR 0208](../../adr/0208-widen-lightweight-formal-methods.md) の 4）を超えるなら、行の幅を 3 字までにする。
- 0209 の不変条件 L1 から L13 を、コードの並びにも当てる。コードに当てはまらない不変条件（分綴、字幅の伸縮）は、0209 の述語の条件のとおり空に成り立つ。下の C1 から C7 を述語として足す。

### 6. 文書

- 仕様書の文字スタイル `code` の段落（「改行してよい位置を空白、`/` の後、`_` の連なりの後に限る」）に、和文の字のあいだと、和文と欧文の字の境でも、禁則に従って改行でき、罰点は 0 であること、ASCII の字はすべて欧文の字として扱うこと、`/` と `_` の後の候補も後の和文の字の行頭禁則に従うことを足し、この ADR へのリンクを付ける。
- 「本文の中のコードの和文の改行」の節（[TeX と InDesign との差異](../../differences-from-tex-and-indesign.md)）から、Golem の振る舞いが未実装であるという断りを消す。
- `docs/diagnostics.md` の G07105 の「主な原因」の「空白のない和文を、本文の中のコードに書いた」と、「直し方」の「本文の中のコードの和文は、空白を入れるか、コードの外に出す」を消し、「長い識別子を本文の中のコードに書いた。コードの欧文の並びは、空白、`/` の後、`_` の連なりの後でしか改行しない」に改める。`scripts/gen-embedded.sh` で `Golem.Driver.Explain.Embedded` を作り直す。
- 利用者のマニュアルの付録 E（`manual/appendices/e-errors.gm`）の六つの項目のメッセージを、「文脈」の表の全文に戻す（「メンテナーが決めること」の 6）。冒頭の、長いメッセージの後ろを `…` で略すという文を消す。G07105 の項目の、空白のない和文を書いた本文の中のコードが原因であることが多いという文を、`docs/diagnostics.md` と同じく改める。
- [docs/roadmap.md](../../roadmap.md) の v0.1.0-rc4 の「本文の中のコードの和文の改行」の項目を消す。
- [golem-driver ADR 0017](../../golem-driver/adr/0017-pdf-code-blocks.md) と [docs/adr/0210](../../adr/0210-warn-overfull-lines-in-build.md) のステータスの行に、この ADR へのリンクを足す。0210 には、付録 E の略を戻したことを書く。
- README の CI のジョブの表の `enum.yml` の行と、プルリクエストの CI の説明に、行分割の段がコードの並びも調べることを書く。

### 7. 出力の変化

和文を含む本文の中のコードを持つ段落が変わる。
二つのマニュアルの PDF と HTML（原稿の変更のぶん）、`scripts/visual/pages/manual.txt` と `manual-dev.txt` の参照、二つのマニュアルの決定性のハッシュが変わる。
試作では、ページ数は変わらず、利用者のマニュアルで 76 ページ、開発者のマニュアルで 4 ページの文字列が変わった（「文脈」）。
試作は和文と欧文の字の境に候補を置いていないので、この ADR の規則では、変わる段落がこれより増えうる。
境の候補は候補を足すだけなので、試作で収まった付録 E の六つの項目も収まると見込むが、組んで確かめてはいない。
golden、complex fixture、kanikosen などのほかの入力は、和文を含む本文の中のコードを持たないので変わらないと見込む。
実装のプルリクエストで、`scripts/visual/` の差分と決定性のハッシュの変化を確かめ、説明に書く。

### 8. 改行した位置の印

文字スタイル `code` に `wrap-mark`（文字列）を足す。
既定は `"↩"`（U+21A9）とする（「決めたことの記録」）。
空白でないコードの候補（和文の字の前後、`/` の後、`_` の連なりの後）で改行した行の行末に、その文字列をコードの文字スタイルで描く。
空白で改行した行には描かない。
印の幅は、候補の罰点の項目の幅に含め、印を描いた行も行長に収める。
`""` を書けば印を描かない。
HTML と EPUB には出さない。
二つのマニュアルのコードの書体が U+21A9 の字形を持つかを、実装のプルリクエストで確かめる。
持たなければ、書体の字形のある別の印を既定にし、その字と理由をこの ADR のステータスの行に足す。

## 実装しないこと

- **ASCII の記号を約物のクラスで扱うこと**：`"`、`(`、`:` などを cl-01 や cl-02 などとして禁則に掛けることはしない（「トレードオフ」）。
- **コードの欧文の並びの中の改行**：空白、`/` の後、`_` の連なりの後のまま。はみ出しそうなときだけどこででも分ける最後の手段（CSS の `overflow-wrap: anywhere` に当たるもの）も入れない（「メンテナーが決めること」の 1）。
- **文字スタイル `url`**：「メンテナーが決めること」の 5。
- **コードブロック**：収まる最後のシェイピングのクラスタの後で折り返す別の規則であり、変えない。
- **コードの中の空き**：和文の字のあいだや、行頭と行末の約物の空きを、アキ量のセットで調整しない。
- **止める設定**：「メンテナーが決めること」の 4。
- **HTML と EPUB の `style.css`**：変えない。

## 不変条件

「コードの候補」は、1 で置く `Penalty 0 0 NoHyphen` と、`/` の後と `_` の連なりの後の候補とする。
「和文の字」は `lookClass` が `Western` でない字、「欧文の字」は `Western` の字とする（区間の言語による）。
「禁則に当たる」は、後の字が行頭禁則の字（禁則の強さによる）、前の字が行末禁則の字、二つがともに分離禁止文字のどれかであることとする（字のクラスは `breakClass` と `startClass` による）。

- **C1**：`code` の文字列の中で隣り合い、どちらも空白でなく、少なくとも一方が和文の字である二つの字のあいだには、禁則に当たらない限り、コードの候補がちょうど一つある。禁則に当たれば、分割の候補が一つもない。
- **C2**：C1 の候補の罰点は、前の字が `_` なら 100、それ以外は 0 である。
- **C3**：`code` の文字列の中で隣り合う二つの欧文の字のあいだには、`/` の後と `_` の連なりの後の候補のほかに、分割の候補がない。
- **C4**：和文の字を含まない `code` の文字列の項目は、空白でない候補の罰点の項目が持つ印の幅を除けば、この ADR の前と同じである。
- **C5**：`url` の文字列の項目は、この ADR の前と同じである。
- **C6**：`code` の文字列の箱の字をつなぐと、空白を除いた元の文字列になる。コードの候補で分けた行の終わりに、ハイフンを描かない。
- **C7**：`code` の和文の字のそれぞれの箱の幅は、その字の `ceWordAdvance` とトラッキングの和である。コードの箱のあいだに glue を足さない。余白は、コードの並びの最初の箱の前と最後の箱の後にだけある。
- **C8 改行の印**：`code` の空白でない候補で分けた行の終わりには、`wrap-mark` の字がちょうど一つあり、その行は行長に収まる。空白で分けた行の終わりと、`wrap-mark` が `""` のときには、印がない。

境界の入力：

| 量 | 調べる値 |
| --- | --- |
| 和文の字の位置 | コードの最初、中ほど、最後、一字だけのコード |
| 隣の字 | 和文の字、英字（`a`）、数字（`1`）、ASCII の `"`、`(`、`)`、`=`、`/`、`_`、空白 |
| 禁則 | 読点、句点、始め括弧、終わり括弧、`ー`、`ぁ`（強い禁則と弱い禁則）、`……` |
| 境の禁則 | `（a`、`a）`、`a、`、`a。`、`aー`（強い禁則と弱い禁則）、`a/。`、`a_。` |
| `_` と和文 | `a_あ`（連なりが一つ）、`a_b_あ`、`_あ`（コードの最初の `_`） |
| 結合文字 | `か゛`（基底の字と結合文字が一つの箱） |
| 区間の言語 | なし、`en`（`…` と `“` が欧文の字）、`ja` |
| 組方向 | 横組み、縦組み |
| 余白 | 0、正（`padding` を持つ `code`） |
| 行の残りの幅 | 候補の前でちょうど終わる、禁則で候補がなく一字足りない |

## テスト設計

テストを先に書き、今の実装で失敗することを確かめてから実装する。
テストの名前には、C1 から C8 の番号を入れる。

- **C1**：`[code: 罫線を持つ]` の項目が、字ごとの箱と、そのあいだの罰点 0 になること。今は箱一つなので失敗する。`[code: あ、い]` は `、` の前に候補がなく、`[code: 「あ」]` は `「` の後と `」` の前に候補がないこと。`[code: あーい]` と `[code: あぁい]` は、強い禁則で `ー`、`ぁ` の前に候補がなく、弱い禁則で候補があること。`[code: ……]` の二字のあいだに候補がないこと。
- **C1 の境**：`[code: あa]`、`[code: aあ]`、`[code: あ1]`、`[code: え"か"]`、`[code: あ(い)]`、`[code: あ=い]` の、和文と欧文の字のすべての境に候補が一つあること。今は境に候補がないので失敗する。`[code: （a）]` は `（` の後と `）` の前に、`[code: a、]` と `[code: a。]` は約物の前に候補がないこと。`[code: aー]` は強い禁則で候補がなく、弱い禁則で候補があること。`[code: a/。]` と `[code: a_b_。]` は `。` の前に候補がないこと。今は `/` の後に候補があるので失敗する。欧文の区間の `“` が `あ` の前にあれば、`“` の後に候補がないこと。
- **C2**：`[code: a/あ]` の `/` の後の罰点が 0、`[code: a_b_あ]` の最後の `_` の後と `[code: a_あ]` の `_` の後の罰点が 100 で、どれも候補が一つだけであること。`[code: a_あ]` は今は候補がないので失敗する。`[code: あ_b]` の `あ` の後の罰点が 0 であること。
- **C3、C4**：`[code: a b/c_d]`、`[code: THIRD_PARTY_LICENSES/]` の項目が、今のテストのとおりであること。`[code: abc"def]` の中に候補がないこと。
- **C5**：[golem-layout ADR 0018](0018-url-line-breaks.md) のテストが、そのまま通ること。和文を含む URL（`[style url: https://例え.jp/日本語]`）の項目が、この ADR の前と同じであること。
- **C6、C7**：`wrap-mark = ""` の文字スタイルで、4 字の行に `[code: あいうえおかきくけこ]` を組み、行が 4 字、4 字、2 字に分かれ、どの行も `lineOverflow` が 0 で、行の字をつなぐと元の文字列になること。今は一行ではみ出すので失敗する。`[code: x = "日本語の文字列"]` を狭い行で組み、`"` の前後で分かれた行の字をつないでも元の文字列になり、行末にハイフンがないこと。`padding` を持つ `code` で、余白が最初と最後の箱にだけあること。縦組みで、和文の箱が正立（`KindText`）、欧文の箱が回転（`KindRotated`）であること。
- golem-typeset：付録 E の G03029 の全文を、利用者のマニュアルの書体と版面で組み、G07105 が出ないこと。今は出るので失敗する。和文を含むコードの箱の幅の和が、この ADR の前の一つの箱の幅と同じであること（Noto Sans JP で、コードのカーニングを切った状態）。
- **C8**：`wrap-mark` が既定のとき、`[code: あいうえおかきくけこ]` を 4 字の行に組むと、最後の行を除くどの行の行末にも `↩` がちょうど一つあり、最後の行にはないこと。`[code: a b c d e]` を空白で分けた行には印がないこと。`wrap-mark = ""` では、どの行にも印がないこと。印を描いた行の `lineOverflow` が 0 であること。今は `wrap-mark` がないので失敗する。
- 列挙：5 のコードの並びで、0209 の L1 から L13 と C1 から C8 が、プルリクエストの段のすべての入力で成り立つこと。
- マニュアル：`scripts/manual/build.sh` が、六つの全文を戻した二つのマニュアルを diagnostic なしに組むこと。

## トレードオフ

ASCII の記号を cl-27 として扱うので、`x = "日本語"` は `"` の後でも、`語` と `"` のあいだでも改行できる。
`"` が行末に残ることも、閉じる側の `"` が一字だけ次の行頭に来ることもある。
JLReq の表 2 は、どちらも分割可とする。
コードを読む人には、引用符と中身が行で分かれて見えることがある。

ASCII の記号を約物のクラスで扱わない理由は三つある。
一つめは、`"` と `'` が JLReq の cl-01 にも cl-02 にもないことである。
同じ字が開きにも閉じにも使われるので、字だけでは始め括弧か終わり括弧かを決められない。
二つめは、`(` や `:` を約物のクラスの表に挙げているのは全角の字形としてであり、JLReq 自身が、和文の組版では互換用の全角の字を使うのがふつうだと注記していることである。
コードの書体の `(` は、欧文の字形と欧文のベースラインを持つ。
三つめは、本文が既に ASCII の字をすべて cl-27 として扱っていることである。
コードだけ別の分け方にすると、本文で `日本"` の境で改行できるのに、同じ字の並びがコードの中では改行できなくなる。

ほかの組版系とは、記号の境で振る舞いが分かれる（[TeX と InDesign との差異](../../differences-from-tex-and-indesign.md)）。
pLaTeX は、ソースから推測すると、英字と数字との境では改行し、`"` や `=` との境では改行しない。
ブラウザーは、`え"か` の境で改行しなかった。
HTML と PDF の改行の位置は、英字と数字の境では一致し、`"` の境では一致しない。
`(`、`)`、`=` などとの境でブラウザーがどう改行するかは、確かめていない。

和文の字のあいだで改行すると、メッセージが二行にわたる。
付録 E の項目の語は、今は一行に収まるものだけである。
全文に戻すと、G03029 は 3 行になり、項目の語が説明の文より長く見える。
それでも、端末に出たメッセージの後ろの部分で付録 E を引けるようになる。

字ごとの箱にすると、和文の並びを一度にシェイピングしなくなる。
コードはカーニングを切っており、和文の字のあいだに合字や文脈による字形の置き換えはないと見込むが、確かめてはいない。
箱の幅の和が変わらないことを、テスト設計の golem-typeset のテストで確かめる。

コードの中の改行の位置に印を描かないので、行末で改行したコードが、空白の位置で分かれたのか、空白のない字のあいだで分かれたのかは、紙面からは分からない（「メンテナーが決めること」の 8）。

## メンテナーが決めること

1. **和文の字のあいだで改行するか**：推奨は、本文の和文と同じ禁則に従って改行することである。HTML は既にそうしており、JLReq も、和文の字のあいだの分割を文字クラスの組で決める。付録 E の六つの全文も収まる。
   - 退けた案の一つは、今のままとし、書き手に空白を入れるかコードの外に出すよう求めることである。メッセージを引用するコードに空白を足すと、原文と違う文字列になる。付録 E の略も残る。
   - 二つめは、はみ出しそうなときだけ、どの字のあいだでも分ける最後の手段を足すことである（CSS の `overflow-wrap: anywhere`）。欧文の識別子の途中で分かれ、分けた位置が規則で決まらない。行分割にもう一段が要る。
2. **和文と欧文の字の境で改行するか**：起草したときの推奨は、しないことだった。コードの欧文の字には、`"`、`(`、`:`、`=` のような構文の記号が多い。本文の規則で境に候補を置くと、`x = "` の後で `日本語"` を次の行へ送り、引用符が行末に残る、というのが理由だった。メンテナーは、JLReq に従うと決めた（「決めたことの記録」）。規則は「実装すること」の 1 に書いた。
   - 起草したときに退けた案の一つは、欧文の側の字が文字か数字のときだけ境に候補を置くことだった。HTML の改行に近づくが、文字と数字を記号と分ける新しい区分が要る。pTeX の `\xspcode` の既定（英字と数字だけが和文との境で空きと改行を許す）は、この案に近い。
   - 二つめは、すべての境に候補を置くことだった。引用符と括弧が行末に残る。決めた規則はこの案に近く、和文の側の字の禁則だけを除く。
3. **候補の罰点**：推奨は 0 である。本文の和文の字のあいだと、コードの `/` の後と同じ値である。コードの中の和文はメッセージや注釈であり、本文の和文と同じく字のあいだで分けるのがふつうである。
   - 退けた案は、`_` の後と同じ 100 にすることである。空白の位置のほうを好んで分け、空白のないメッセージでは、行の空きを大きくしてでも罰点を避ける。
4. **止める設定を足すか**：推奨は、足さないことである。和文を一つの並びのまま保ちたい用途が、二つのマニュアルにない。はみ出しは G07105 で知らせる。後から足しても、既定の振る舞いは変わらない。
   - 退けた案は、`[character-styles.code]` に、和文の字のあいだで改行するかどうかのキーを足すことである。HTML では `word-break: keep-all` に当たるが、使う人のいない設定を、PDF と HTML の両方で保つことになる。
5. **文字スタイル `url` にも当てるか**：推奨は、当てないことである。`url` の改行の位置は、url パッケージの字の一覧で決めている（[golem-layout ADR 0018](0018-url-line-breaks.md)）。開発者のマニュアルには和文を含む URL が 11 あり（仕様書の節へのリンクの `#` の後）、どれも今の規則で行長に収まっている。
   - 退けた案は、`url` にも当てることである。URL の区切りの字のほかに、節の名前の途中でも分かれる。0018 は、分ける位置を URL の区切りの字に限っている。
6. **付録 E の六つの項目**：推奨は、全文に戻し、冒頭の略の説明の文を消すことである。[docs/adr/0210](../../adr/0210-warn-overfull-lines-in-build.md) は、書き手が端末のメッセージの後ろの部分で付録 E を引けなくなることを、略のトレードオフとしていた。試作で、全文に戻しても diagnostic が出ないことを確かめた。
   - 退けた案は、略したままにすることである。略す理由がなくなり、付録 E の冒頭の説明の文も残ることになる。
7. **列挙を広げるか**：推奨は、5 のとおり、コードの並びを別の部品の組で足すことである。0209 は、規則が行の端で重なったときのバグを列挙で見つけるために作った。この ADR は、コードの中に禁則を持ち込むので、同じ種類のバグが起こりうる。
   - 退けた案の一つは、例のテストだけにすることである。禁則の字の組と、行の端の位置の組を、手で選んだ例では尽くせない。
   - 二つめは、今の 23 の部品の並びに、コードに入れるかどうかの環境を掛けることである。プルリクエストの段 2 の時間がほぼ倍になり、分綴の語のようにコードの中では一つの箱になる部品も、すべて組み直すことになる。

8. **コードの中の改行の位置に印を描くか**：推奨は、文字スタイル `code` に `wrap-mark`（文字列、既定 `""`）を足し、既定では印を描かないことである。空でなければ、空白でないコードの候補で改行した行の行末に、その文字列をコードの文字スタイルで描き、その幅を候補の罰点の項目の幅に含める。空白で改行した行には描かない。HTML と EPUB には出さない。
   - メンテナーは、技術書では改行の記号を入れて改行している本が多い気がする、と述べた。これはメンテナーの印象であり、技術書を調べて確かめてはいない。本文の中のコードの改行の印について書いた組版や出版社の資料は、見つからなかった。
   - 見つかった先例は、LaTeX の fvextra パッケージである。fvextra の文書は、本文の中のコード（`\Verb`）でも、空白での改行には印を付けず、`breakbefore`、`breakafter`、`breakanywhere` で足した位置での改行には、行末に印（既定は小さな `_⌋`）を付けると書いている。コードブロックの続きの行の行頭の印（`breaksymbolleft`）は、`\Verb` では働かない。印は、空白のない位置で分かれたことを示す。
   - Golem のコードブロックは、同じ役割の `[code]` の `wrap-mark` を持ち、既定は `""` である（[golem-driver ADR 0023](../../golem-driver/adr/0023-code-block-book-features.md)）。名前と既定をそろえると、書き手は一つの考え方で両方を設定できる。既定を空にすると、印を望まない本と二つのマニュアルの出力が変わらない。
   - 退けた案の一つは、印の機能を足さないことである。空白で分かれたのか、空白のない字のあいだで分かれたのかを、紙面で示す手段がなくなる。メンテナーの指摘と fvextra の先例がある。
   - 二つめは、既定で印を描くことである。和文のメッセージの字のあいだの改行にも印が付き、本文の和文の改行と見た目が分かれる。コードブロックの既定とも食い違い、二つのマニュアルの出力が変わる。
   - 三つめは、コードブロックの `[code]` の `wrap-mark` を、本文の中のコードにも当てることである。コードブロックの印を設定した本で、本文の中のコードの見た目も変わり、片方だけを設定できない。
   - 四つめは、空白での改行にも印を描くことである。印のない行末が空白の位置であるという手がかりがなくなる。
   - メンテナーは、既定で印を描くと決めた（「決めたことの記録」）。

## 決めたことの記録

- **「メンテナーが決めること」の 1、3、4、5、6、7**（2026-11-08、メンテナー）：推奨のとおりとした。
- **「メンテナーが決めること」の 2**（2026-11-08、メンテナー）：推奨を退け、JLReq に従って和文と欧文の字の境で改行することにした。メンテナーの言葉は次のとおりである。

  > 0034 JLReqに準拠して。

  同じ発言で、メンテナーは、技術書では改行の記号を入れて改行している本が多い気がする、とも述べた。
  これが「メンテナーが決めること」の 8 のもとになった。
  規則は「実装すること」の 1 に書いた。ASCII の字をすべて cl-27 として扱うことは、JLReq が `"` を約物のクラスに入れていないことと、本文の扱いに合わせて決めた（「トレードオフ」）。
- **「メンテナーが決めること」の 8**（2026-11-08、メンテナー）：推奨を退け、既定で印を描くことにした。メンテナーは、コードの改行はないと困るので、ひとまず改行の印を付けて進めるとした。規則は「実装すること」の 8 に書いた。印は、空白で改行した行には描かない。
