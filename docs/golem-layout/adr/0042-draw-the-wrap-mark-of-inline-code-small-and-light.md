# ADR 0042: 本文の中のコードの改行の印を、細い線の小さな矢印で淡く描く

ステータス: 採択

## 文脈

[golem-layout ADR 0034](0034-line-breaks-between-japanese-characters-in-inline-code.md) は、本文の中のコードを空白でない候補（和文の字の前後、`/` の後、`_` の連なりの後）で改行したとき、行末に文字スタイル `code` の `wrap-mark` を描くと決めた。
既定の印は `⏎`（U+23CE）である（[golem-layout ADR 0036](0036-record-what-the-implementation-of-0034-decided.md)）。
メンテナーは、組んだ PDF を見て、改行の印が大きすぎ、目立ちすぎると述べた。
この ADR の草案の最初の推奨（`⏎` の字形を 3/5 の大きさで淡く描く）を見て、白抜きでなくてよい、太くて目立ちすぎるとも述べた。

### 今の描き方

origin/main（`94b976e1`）の描き方は次のとおりである。

- 印は、コードの文字スタイルの見た目（`Look`）のまま、書体の字形として描く。大きさも色もコードの字と同じである（[`Draw.hs`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-typeset/src/Golem/Typeset/Draw.hs#L948-L959)）。
- 印の幅は、コードの字の大きさで測った印の送りであり、候補の罰点の幅として行分割に入る（[`Japanese.hs`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-layout/src/Golem/Layout/Japanese.hs#L1288-L1293)）。
- 既定の文字列は、組み込みの文字スタイル `code` が持つ（[`Style.hs`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-project/src/Golem/Project/Style.hs#L481)）。見た目への写しは [`Fonts.hs`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-typeset/src/Golem/Typeset/Fonts.hs#L453-L454) にある。
- 印の描画は、行のほかの箱と同じく、使った字形を持つ部分だけを描く（[`parts`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-typeset/src/Golem/Typeset/Draw.hs#L962)）。字形のない描画は捨てられる。
- 印は構造木に入らず、アーティファクトとして描く。

`⏎` は和文の字のクラスに入り、二つのマニュアルでは Noto Sans JP で描かれる。
Noto Sans JP の `⏎` は、送りが 1 em、字面が幅 0.906 em、高さ 0.926 em であり、仮想ボディのほぼ全体を占める。
字形は、矢印の輪郭を二重の線でかたどった白抜きである。
利用者のマニュアルの本文（13Q、3.25mm）では、印は 3.25mm 四方になる。
同じ行のコードの欧文の字（Source Code Pro）は、送りが 0.6 em（1.95mm）、大文字の高さが 0.66 em である。
印は、コードの欧文の字の 1.7 倍の幅を取り、大文字より 4 割高い。
色もコードの字と同じなので（マニュアルではスウォッチ `code`、CMYK 90/50/0/20）、行末で、コードの字より濃く大きなかたまりに見える。
白抜きの輪郭は二本の線でできているので、小さくしても線の量が減らず、太く見える。

印は字形なので、PDF から文字列を取り出すと、印の `⏎` も文字として出てくる。
PDFKit の `string` で数えた印は、利用者のマニュアルで 195 個（114 ページ）、開発者のマニュアルで 85 個（56 ページ）である。
印の多くは、付録 E（diagnostic の一覧）のメッセージと、脚注のコードで書いた URL の `/` の後にある。
4、8、291 ページが典型である（4 ページと 8 ページは脚注の URL、291 ページは付録 E の和文のメッセージ）。

### 先例

LaTeX の fvextra（[`fvextra.sty`](https://github.com/gpoore/fvextra/blob/b22ac9e0806479bfe69bf6f2fd2c052b50a3b5cf/fvextra/fvextra.sty#L2981-L3005)）は、`breakanywhere` と `breakafter` で足した位置で改行した行の末尾に、`breakanywheresymbolpre` と `breakaftersymbolpre` を置く。
既定は、どちらも `\,\footnotesize\ensuremath{_\rfloor}` である。
細い空き（`\,`）の後に、`\footnotesize` の数式の下付きの `⌋` を置く。
10pt の文書では、`\footnotesize` は 8pt、その下付きは 6pt なので、印は本文の 6 割の大きさの、細い線の鉤である。
コードブロックの続きの行の行頭の印（`breaksymbolleft`）の既定は、`\tiny`（10pt の文書で 5pt）の `\hookrightarrow` である（[2788 行目から 2792 行目](https://github.com/gpoore/fvextra/blob/b22ac9e0806479bfe69bf6f2fd2c052b50a3b5cf/fvextra/fvextra.sty#L2788-L2792)）。
どちらも、印を本文の字より明らかに小さく、細い線で描く。
色は、どちらの既定も本文と同じである。

Golem 自身にも、印の色を本文から外す先例がある。
コードブロックの `[code]` の `wrap-mark` は、`line-number-color`（行番号と同じ色）で描く（[`Flow.hs`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-typeset/src/Golem/Typeset/Flow.hs#L2600-L2607)）。
ただし `line-number-color` の既定はなく、本文の字の色になる。
強調の行の網の既定は、名前を持たないプロセスカラーの墨 15% である（仕様書の「コードブロック」の節）。
スウォッチを書かない本で既定の色を持たせるときに、名前のないプロセスカラーを使う先例である。

字形でない図形を、字の代わりに描く先例もある。
罫線の点線の点は、golem-pdf の `Disc` と `CurveFill`（塗った閉じた道）で描く（[golem-driver ADR 0028](../../golem-driver/adr/0028-rule-colour-and-style.md)）。
全角のダッシュの連なりも、字形でなく一本の線で描く（[docs/adr/0172](../../adr/0172-continuous-double-dashes.md)）。

### 書体の字形

二つのマニュアルが同梱する書体は、Noto Sans JP（Regular、Bold）、Noto Serif JP（Regular）、Source Code Pro（Regular）、Source Sans 3（Bold）、Source Serif 4（Regular）である。
Noto Sans JP にも Source Code Pro にも、Regular より細いウェイトは同梱されていない。
欧文の字のクラスに入らない字（`⌟` や `◂` など）は、和文の側の書体（コードでは Noto Sans JP）で描かれるので（[`charClass`](https://github.com/tett23/golem/blob/94b976e1fb59b59867e66195f2c8ca55a8f60b11/modules/golem-layout/src/Golem/Layout/CharClass.hs#L38-L52)）、印に使える字は実際には Noto Sans JP の字形に限られる。

CoreText で、矢印、技術記号、幾何学図形の区画（U+2190 から U+21FF、U+2300 から U+23FF、U+25A0 から U+25FF、U+2900 から U+297F、U+2B00 から U+2BFF）を引いた。

| 字 | 結果 |
| --- | --- |
| `↩`、`↪`、`↵`、`↲`、`↳`、`⤶`、`⌋` | どの書体も持たない |
| `⏎` | Noto Sans JP、Noto Serif JP。どちらも白抜き |
| `⤵`（U+2935） | Noto Sans JP、Noto Serif JP。Regular の線の曲がった矢印 |
| `←`、`↓`、`↙` など | 五つすべて。Regular の線の直線の矢印 |
| `◀`、`▼` など塗った三角 | Noto Sans JP、Noto Serif JP |
| `◂`、`▾` など小さな塗った三角 | Source Code Pro だけ。和文の側で描かれるので使えない |

改行を表す字で、線の細い字形はない。

### 試作

作業用の worktree で、origin/main（`94b976e1`）に、印の大きさ、行と直交する方向の位置、色を環境変数で変えられる箇所を足した golem を作った（コミットしていない）。
あわせて、字形の代わりに、塗った多角形（golem-pdf の `CurveFill`）で `↵` の形の矢印を描く箇所を足した。
多角形だけの描画が捨てられないように、`parts` の条件も試作で変えた。
大きさを変えると、印の幅（候補の罰点の幅）も同じ比で変わる。
字は、利用者のマニュアルの `style.toml` の `[character-styles.code]` に `wrap-mark` を書いて変えた。
利用者のマニュアルを PDF に組み、4、8、291 ページを shem（`scripts/visual/fetch-shem.sh` の版、v0.1.0-rc4）で PNG にした。
縦組みは、`golem new` の雛形にコードの書体と同じ段落を足した本で確かめた。

「大きさ」は、コードの字の大きさに対する比であり、図形では印の正方形の一辺である。
「線の太さ」の em は、コードの字の大きさである。
「中心」は、印の仮想ボディ（図形では正方形）の中心を、コードの字の大きさの仮想ボディの中心にそろえる位置である。
横組みでは、その中心は基準線より (`baselineRatio` − 1/2) em 上にある（`baselineRatio` は 0.88）。
「コードの色の 50%」は、コードの色のスウォッチの CMYK の各値を半分にしたプロセスカラーであり、コードに色がなければ墨 50% である。

v0 の PNG は、origin/main の golem で組んだ PDF を同じ shem で描いた PNG と、バイト列まで一致した。
試作の箇所は、環境変数がなければ出力を変えない。

組んだ結果は次のとおりである。
どの案でも、diagnostic は一つも出ず、ページ数は 376 のままだった。
「改行が動くページ」は、ページの文字列から印を除き、v0 と比べて違うページの数である。
どれも改行の位置だけが違い、文字の並びは同じだった。

| 案 | 改行が動くページ | 取り出した文字列の `⏎` |
| --- | --- | --- |
| v3 | 0 | 195 |
| v7 | 36 | 201 |
| v1、v2、v4、v5、v6、p1、p3、p4、p5 | 56 | 字形の案は 203、図形の案は 4 |
| v8、v9 | 55 | 字形の案なので印の字の数だけ出る |
| p2 | 68 | 4 |

図形の案で残る 4 個は、マニュアルの本文が `⏎` という字を説明している箇所である。
図形の印は、PDF から取り出す文字列に出ない。

印の幅が狭くなると、印の前の候補にもう一字入る行が出て、そこから段落の終わりまでの改行が動く。
291 ページの G03118 の見出しでは、v0 の `を書⏎` が、0.6 の案で `を書け` と印になる。

目で見た結果は次のとおりである。

- v1 と v2：大きさを 0.6 にすると、印の幅は欧文のコードの一字と同じになる。v2 の基準線では印が下に寄り、字の並びから落ちて見える。v1 の中心では、仮名と漢字の中心と並ぶ。
- v3：色だけを淡くしても、1 em の白抜きの輪郭が残り、大きさの印象は変わらない。
- v4：v1 を淡くしたもの。小さくはなるが、白抜きの二重の輪郭が残り、線の量が多い（メンテナーの「太くて目立ちすぎ」）。
- v5：v4 とほとんど同じに見える。青いコードの後で、灰色の印は色の系統が切れる。
- v6：0.5 では、白抜きの字形の形が脚注の大きさで読み取りにくい。
- v7：0.75 では、白抜きの輪郭がまだ目に付く。
- v8：`¬` は Source Code Pro で描かれ、コードの字と同じ太さの線になる。字として読めてしまい、論理否定の演算子と紛れる。
- v9：`↙` は軽いが、改行の印としてなじみがなく、向きが次の行の頭を指さない。
- g1：`⤵` は線が一本で軽いが、行の上へはみ出す曲線で、向きが「下へ続く」に見える。改行して行頭へ戻る意味にならない。
- g2：`◀` は塗った面が目立ち、コードの区切りの記号のように見える。改行の意味も持たない。
- p1：細い一本の線の `↵` になり、白抜きの v4 より明らかに軽い。形は脚注の大きさでも読める。
- p2：さらに軽いが、0.5 の幅では脚注で矢じりが小さく、p1 との差は、改行の動くページが増えるほどにはない。
- p3：p1 より線が太く、v4 に近い重さに戻る。
- p4：塗った矢じりは、開いた矢じりより先端が重く、印の左端に目が行く。
- p5：線は細いが、コードと同じ濃い色では、行末の細い線が字の続きに見える。

縦組みでは、図形を時計回りに 90 度回して描いた（行の方向の「下へ」が「左へ」に、「左へ」が「上へ」になる）。
次の行（左の行）へ移り、行頭（上）へ戻る向きになり、正立の字の並びの中で読めた。

## 実装すること

### 1. 既定の印を、字形でなく図形で描く（golem-typeset）

`wrap-mark` の値がちょうど `"⏎"` のとき、印は書体の字形でなく、次の図形で描く。
既定の `wrap-mark` は `"⏎"` のままなので、既定の印はこの図形になる。
利用者が `"⏎"` と書いた本も同じ図形になる。

図形は、一辺 W の正方形の中に置く。
W は、コードの字の大きさの 3/5 である。
正方形の中の座標を、左下を (0, 0)、右上を (1, 1) とし、横組みの向き（右が行の方向、上が行の上）で書く。
線の太さ t は、コードの字の大きさの 1/20 であり、正方形の座標では 1/12 である。

- 縦の線：中心線 x = 0.82、y = 0.30 − t/2 から y = 0.80 まで、幅 t の長方形。
- 横の線：中心線 y = 0.30、x = 0.12 + t から x = 0.82 + t/2 まで、幅 t の長方形。
- 矢じり：先端 (0.12, 0.30) から (0.36, 0.48) と (0.36, 0.12) への二本の線、幅 t。二本の向きは 3 対 4 対 5 の直角三角形の斜辺なので、線の両側の点は、平方根を使わず有理数で求まる。

各部分は、golem-pdf の `CurveFill`（制御点を両端に置いた直線の辺）で塗る。
新しい PDF の描画の命令は足さない。
座標は有理数で計算し、sp に変えるときに切り捨てる。
浮動小数点を使わないので、x86-64 と aarch64 で同じバイト列になる。

縦組みでは、正方形の中心を中心として、図形を時計回りに 90 度回して描く。
正方形は、印の位置から行の方向に W だけ取り、行と直交する方向は行の中心線に中心を置く。

### 2. 印の大きさを、コードの字の 3/5 にする（golem-layout、golem-typeset）

図形の印の幅（`Penalty` の幅）は W（コードの字の大きさの 3/5）とする。
`"⏎"` でない `wrap-mark` は、今までどおり字形で描き、その大きさをコードの字の大きさの 3/5 とし、幅を印の文字列の送りをその大きさで測った量とする。
比は、golem-layout に一つの定数（たとえば `wrapMarkScale = 3 / 5`）として置き、行分割と描画の両方がそれを使う。
印の幅は、今までどおり行分割に入れ、印を描いた行も行長に収める。

### 3. 印の中心を、コードの字の仮想ボディの中心にそろえる（golem-typeset）

横組みでは、図形の正方形の中心を、コードの字の基準線より (`baselineRatio` − 1/2) × コードの字の大きさだけ上に置く。
字形の印は、印の仮想ボディの中心が同じ高さに来るように、基準線を (1 − 3/5) × (`baselineRatio` − 1/2) × コードの字の大きさだけ上げる。
縦組みの正立の字形の印は、原点を今と同じ位置（印の仮想ボディの上辺の中央）に置く。
縦組みで回転する字形の印（欧文の字だけからなる印）は、回転した仮想ボディの中心が、同じ大きさのコードの回転した字の中心と、行と直交する方向でそろうように置く。
行の方向の位置は今と同じで、印の前に空きを足さない。

### 4. 印の色を、コードの色の 50% にする（golem-typeset）

印は、図形も字形も、コードの字の色のスウォッチの C、M、Y、K の各値を半分にした（端数は切り捨てる）、名前を持たないプロセスカラーで描く。
コードの字に色がなければ、墨 50% で描く。
色の付いた区間（`[color ...]`）の中のコードでは、その区間の色を半分にする。

### 5. 図形の印も、アーティファクトとして描く（golem-typeset）

図形の印は、今の字形の印と同じく、構造木に入れないアーティファクト（`/Artifact` の `Layout`）として描く。
字形を使わないので、ToUnicode にも `ActualText` にも何も足さない。
PDF から文字列を取り出しても、印は出てこない。
描画は、使った字形を持たない部分を捨てる今の `parts` の条件を、図形の印を持つ部分も残すように改める。
ほかの描画が残るか捨てられるかは変えない。

### 6. キーを足さない

印の大きさ、線の太さ、色を決めるキー（`wrap-mark-size`、`wrap-mark-color` など）は足さない。
大きさの比、線の太さ、色の比は、仕様書に書く固定の値とする。
`wrap-mark = ""` は、今までどおり印を描かない。

### 7. 文書

- 仕様書の「本文の中のコード」の節（`wrap-mark` の段落）に、既定の `"⏎"` を図形で描くこと、その形と大きさと線の太さ、ほかの字の印の大きさ、位置、色と、この ADR へのリンクを書く。
- 仕様書の行分割の列挙の段落の「改行の印は `⏎` で 1 em とする」を、印の幅を 3/5 em とする文に改める。
- 仕様書の、字形と使った書体の扱い（ToUnicode、使った字形の一覧）の節に、図形の印が字形を使わないことを書く。
- 利用者のマニュアルの付録 C の `wrap-mark` の行と、改行の印を説明する段落（付録 A、第 3 章）に、既定の印を細い線の小さな矢印として淡く描くことを書く。マニュアルの変更は ADR を要しない（メンテナーの方針）が、実装のプルリクエストに含める。
- [TeX と InDesign との差異](../../differences-from-tex-and-indesign.md) の改行の印の段落に、fvextra と同じく本文より小さく細く描くことを書き足す。
- 0034 のステータスの行に、「印の描き方、大きさ、位置、色は [golem-layout ADR 0042](0042-draw-the-wrap-mark-of-inline-code-small-and-light.md)」を足す。

## 実装しないこと

- コードブロックの `[code]` の `wrap-mark` の描き方は変えない。既定は `""` で、色は `line-number-color` で決まり、利用者が選ぶものだからである（「メンテナーが決めること」の 7）。
- `"⏎"` のほかの文字列を図形にしない。利用者が書いた字は、その書体の字形で描く。
- 図形の線を、PDF の線の描画（`S`）で描くことはしない。golem-pdf に線の太さと端の形の状態を足すことになり、`CurveFill` で足りる。
- 印の幅を行分割から外し、行長の外にはみ出させることはしない（「メンテナーが決めること」の 8）。
- HTML と EPUB は変えない。今も印を出さない。

## 不変条件

ここで「印」は、本文の中のコードの空白でない候補で改行した行の行末の `wrap-mark` の描画を指す。
「コードの大きさ」s は、印の前の箱の見た目の字の大きさ（`lkSize`）である。
大きさは sp の整数なので、3/5 倍などは切り捨てる。

- **W1 図形の印**：`wrap-mark` が `"⏎"` のとき、印の描画は `CurveFill` だけからなり、字形の描画を含まない。印の図形の点は、どれも一辺 ⌊s × 3/5⌋ sp の正方形の中にある。
- **W2 字形の印**：`wrap-mark` が `""` でも `"⏎"` でもないとき、印の字の大きさは ⌊s × 3/5⌋ sp に等しい。
- **W3 幅**：印を持つ候補の罰点の幅は、図形の印では ⌊s × 3/5⌋ sp、字形の印では印の文字列の送りを W2 の大きさで測った量に等しい。印を描いた行は行長に収まる（0034 の C8 は、この幅で成り立つ）。
- **W4 線の太さ**：図形の印の縦の線と横の線の太さは、⌊s/20⌋ sp と 1 sp 以内で等しい。
- **W5 位置**：横組みでは、図形の正方形の中心と、字形の印の仮想ボディの中心は、コードの字の基準線より (`baselineRatio` − 1/2) × s だけ上にある（1 sp の丸めを許す）。縦組みでは、その中心は、行と直交する方向で、行の中心線の上にある（1 sp の丸めを許す）。
- **W6 縦組みの向き**：縦組みの図形の印は、横組みの図形を正方形の中心のまわりに時計回りに 90 度回したものである。
- **W7 色**：コードの色のスウォッチが (c, m, y, k) なら、印の色は (⌊c/2⌋, ⌊m/2⌋, ⌊y/2⌋, ⌊k/2⌋) である。コードに色がなければ、印の色は (0, 0, 0, 50) である。
- **W8 アーティファクト**：印の描画は、どの構造の要素の内容にも入らず、アーティファクトの中にある。図形の印は、PDF の ToUnicode の対応と、取り出した文字列に何も足さない。
- **W9 印の文字列**：`wrap-mark = ""` では、印を持つ候補も印の描画もない。
- **W10 印のない段落**：印を持つ候補のない段落（印が空の段落、和文も `/` も `_` も持たないコードだけの段落、コードのない段落）の項目と描画は、この ADR の前と同じである。
- **W11 コードブロック**：コードブロックの折り返しの印の描き方、大きさ、色、幅は、この ADR の前と同じである。
- **W12 総インキ量**：印の色の総インキ量は、コードの色の総インキ量を超えない。
- **W13 決定性**：同じ入力から、x86-64 と aarch64 で、印の図形の座標が同じ sp になる。

境界の入力は次のとおりである。

| 入力 | 確かめる条件 |
| --- | --- |
| `wrap-mark = ""` | W9、W10 |
| 既定（`wrap-mark` を書かない） | W1、W3、W4、W5、W7、W8 |
| `wrap-mark = "⏎"` と書いた本 | W1（既定と同じ図形） |
| 字形の印が一字（`"→"`） | W2、W3、W5 |
| 字形の印が二字以上（`"->"`） | W2、W3（二字の送りの和を 3/5 で測る） |
| 字形の印が欧文の字だけ（`"\\"`）の縦組み | W5（回転した印） |
| 既定の印の縦組み | W5、W6 |
| コードの大きさが 5 でも 20 でも割り切れない sp | W1、W4（切り捨て） |
| コードに色がない | W7（墨 50%） |
| コードの色の値に奇数がある（`[45, 25, 0, 15]`） | W7（切り捨て） |
| コードの色が墨 100% | W7（墨 50%）、W12 |
| 印を除けば行長ちょうどに収まり、1 em の印ではあふれ、3/5 em の印では収まる行 | W3（その候補で改行できる） |
| 印の 3/5 em を足すと行長を 1 sp 超える行 | W3（その候補で改行しない） |
| `[code]` の `wrap-mark = "→"` を書いたコードブロック | W11 |
| 和文を含まないコードだけの段落 | W10 |
| タグ付きの PDF（PDF/UA の宣言のある本） | W8 |

## テスト設計

テストは、実装より先に書き、今の golem で失敗することを確かめる。

- **W1、W4、W5、W6、W7**（golem-driver の `PdfSpec`）：`[code: ...]` に和文の長いメッセージを書いた段落を、横組みと縦組みで組み、行末の印の描画が `CurveFill` だけからなること、点が正方形の中にあること、線の太さ、正方形の中心、縦組みの回転、色の演算子を確かめる。今は印が字形なので失敗する。色は、コードに色のない本と、`[character-styles.code] color` に奇数を含むスウォッチを書いた本の二つで確かめる。
- **W2**（golem-driver の `PdfSpec`）：`wrap-mark = "→"` の本で、印の字の大きさが 3/5 であることを確かめる。今は等倍なので失敗する。
- **W3**（golem-layout の `CodeJapaneseSpec`）：印を持つ罰点の幅が 3/5 em であることを確かめる。境界の表の、1 em の印ではあふれ 3/5 em の印では収まる行と、1 sp 超える行も確かめる。今は幅が 1 em なので失敗する。テストの `markWidth` を 3/5 em に改める。
- **W3 の列挙**（golem-layout の `LineBreakEnum`）：コードの並びの列挙の印の幅を 3/5 em にし、0034 の C1 から C8 と L7 がプルリクエストの段で通ることを確かめる。毎晩の段も、実装のプルリクエストで手元で一度走らせる。
- **W8**（golem-driver の構造木のテスト）：タグ付きの PDF で、印の描画がアーティファクトの中にあり、ToUnicode の対応と `renderPdfLeafTexts` の文字列に `⏎` がないことを確かめる。今は取り出した文字列に `⏎` が出るので失敗する。
- **W9、W10**：今の C4 と C8 のテスト（印が空のとき印がない、和文を含まないコードの項目が印の幅を除いて変わらない）がそのまま通ることを確かめる。
- **W11**（golem-driver の `PdfSpec`）：`[code] wrap-mark = "→"` と `line-number-color` を書いたコードブロックの印が、今と同じ字形、大きさ、色であることを確かめる。このテストは今も通り、実装の後も通ることを確かめる。
- **W12**：W7 の述語から従う。各値を切り捨てで半分にするので、和は元の和を超えない。W7 のテストで足りる。
- **W13**：図形の座標を求める関数を純粋な関数にし、有理数の入力に対する出力を固定の値と比べる単体テストを書く。CI の決定性の検査（x86-64 と aarch64 の `scripts/determinism`）でも確かめる。

目で見る変化は、実装のプルリクエストで確かめる。

- `scripts/visual` の参照の PNG は、本文の中のコードの印のあるページがすべて変わる。印が狭くなって改行の動くページも変わる。試作の p1 では、利用者のマニュアルで 56 ページの改行が動いた。変わったページを PR に挙げ、受け入れる。
- `scripts/determinism/hashes.txt` の入力に、空白でない候補で改行する本文の中のコードがあれば、ハッシュが変わる。変われば、受け入れて PR に書く。
- 二つのマニュアルを `scripts/manual/build.sh` で組み、diagnostic がないことを確かめる。

## トレードオフ

- 印が小さく細く淡くなるので、行末でコードが続くことに気づきにくくなる。コードの背景の網が行をまたいで続くことと、続く行の頭がコードの書体で始まることが、手がかりとして残る。背景を塗らない本では、手がかりは印だけになる。
- 線の太さは、コードの字の大きさの 1/20 である。利用者のマニュアルの本文（13Q）で 0.16mm、11Q で 0.14mm になる。これを墨 50% などの網で刷ると、オフセットの印刷では網点で線が途切れて見えることがある。試作は画面と PNG で確かめただけで、刷って確かめていない。
- 大きさ、線の太さ、色の比を固定するので、印を大きく濃く描きたい本は、それができない。必要になれば、キーを足す ADR を書く。
- `"⏎"` という値だけが図形になり、ほかの値は字形になる。値によって描き方が変わることを、仕様書とマニュアルに書く必要がある。
- 図形の印は、PDF から文字列を取り出しても出てこない。コードを PDF から写すとき、行末の `⏎` が混ざらなくなる。一方、印を文字として検索できなくなる。
- 図形の印は書体によらないので、コードの書体が `⏎` の字形を持たない本でも同じ印になる。
- 印の色は、名前を持たないプロセスカラーになる。`golem preflight` の使ったスウォッチの一覧には出ない。総インキ量はコードの色を超えないので（W12）、G09015 の検査の結果は変わらない。
- 特色を使える版（今は扱わない）では、半分にした CMYK は特色の網にならない。特色を足すときに、印の色の決め方を見直す。
- 印の幅が 1 em から 3/5 em になるので、印の前の候補で改行できる行が増え、既存の本の改行の位置が動く。利用者のマニュアルでは 56 ページの改行が動き、ページ数は変わらなかった。

## メンテナーが決めること

レビューのための PNG は、コミットしない。
案は「試作」の表の名前（v0 から v9、g1、g2、p1 から p5）で指す。

1. **印を何で描くか**：推奨は、既定の `"⏎"` を図形で描くこと（p1）である。マニュアルの書体には、改行を表す細い字形がない。図形なら、線の太さを決められ、書体の字形の有無によらない。
   - 退けた案の一つは、`⏎` の字形を小さく淡く描くこと（v4、この草案の最初の推奨）である。白抜きの二重の輪郭が残り、メンテナーは太くて目立ちすぎると述べた。
   - 二つめは、`⤵` の字形（g1）である。線は一本で軽いが、行の上にはみ出す曲線で、「下へ続く」に見え、行頭へ戻る意味にならない。
   - 三つめは、塗った小さな印（g2 の `◀`）である。塗った面が目立ち、改行の意味も持たない。小さな塗った三角（`◂`）は Source Code Pro にしかなく、和文の側の書体で描かれるので使えない。
   - 四つめは、`¬`（v8）と `↙`（v9）である。`¬` は論理否定と紛れ、`↙` は改行の印としてなじみがない。
   - 五つめは、Noto Sans JP の細いウェイトの `⏎` である。マニュアルは Regular と Bold しか同梱せず、細いウェイトでも白抜きの二重の輪郭は変わらない。
   - 六つめは、`wrap-mark` に図形を選ぶ値（真偽値や予約の名前）を足すことである。キーの型が変わり、`"⏎"` を図形にする今の案より設定が複雑になる。
2. **線の太さ**：推奨は、コードの字の大きさの 1/20（p1）である。
   - 退けた案の一つは 3/50（p3）である。v4 に近い重さに戻る。
   - 二つめは 1/25（p2）である。より軽いが、刷ったときに網点で途切れるおそれが増す。
3. **矢じり**：推奨は、開いた矢じり（p1）である。
   - 退けた案は、塗った矢じり（p4）である。先端が重く、印の左端に目が行く。
4. **印の大きさ**：推奨は 3/5（p1）である。fvextra の既定の印（10pt の文書で 6pt）と同じ比であり、印の幅が欧文のコードの一字と同じになる。
   - 退けた案の一つは 1/2（p2、v6）である。脚注の大きさで矢じりが小さく、改行の動くページも 68 に増える。
   - 二つめは 3/4（v7）である。印が大きく残る。
   - 三つめは大きさを変えないこと（v3）である。
5. **印の色**：推奨はコードの色の 50%（p1）である。コードの色の系統のまま淡くなり、コードの続きとして読める。色のない本では墨 50% になる。キーも、スウォッチの名前も要らない。
   - 退けた案の一つは、墨 50% に固定すること（v5）である。色を付けたコードの後で、色の系統が切れる。
   - 二つめは、コードの色のままにすること（p5）である。細い線でも、コードと同じ濃さでは字の続きに見える。
   - 三つめは、コードブロックの `line-number-color` を使うことである。既定がなく、色を書かない本では本文の色（墨 100%）になり、淡くならない。
   - 四つめは、印の色のキー（`wrap-mark-color`）を足すことである。メンテナーは、新しいキーより良い既定を好む。
6. **印の位置**：推奨は、中心をコードの字の仮想ボディの中心にそろえること（p1、v1、v4）である。
   - 退けた案は、基準線にそろえること（v2）である。印が下に寄り、字の並びから落ちて見える。
7. **コードブロックの印**：推奨は、この ADR では変えないことである。コードブロックの印の既定は `""` で、色は `line-number-color` で利用者が決める。
   - 退けた案は、コードブロックの印にも図形と 3/5 と 50% を当てることである。印を設定した本の出力が変わり、`line-number-color` で選んだ色が半分になる。
8. **印の幅を数えるか**：推奨は、今までどおり印の幅を行分割に入れることである。印を描いた行も行長に収まる。
   - 退けた案は、印を行長の外にはみ出させることである（ぶら下げに近い）。行長を超える描画は G07105 の検査とぶつかり、柱や傍注の領域に近づく。
9. **キーを足すか**：推奨は足さないことである。
   - 退けた案は、`wrap-mark-size`、`wrap-mark-weight`、`wrap-mark-color` を足すことである。印を消したい本は既に `wrap-mark = ""` で消せ、字は `wrap-mark` で変えられる。大きさや色を変えたいという要望は、まだない。

## 決めたことの記録

- **「メンテナーが決めること」のすべて**（2026-11-09、メンテナー）：推奨の p1（細い線の図形で描く印）を採り、ほかの点も推奨のとおりとした。v0.1.0-rc4 に入れる。
