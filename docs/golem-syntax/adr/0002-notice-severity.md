# ADR 0002: 重大度のお知らせ（notice）

ステータス: 採択→G02079 は [golem-parser ADR 0012](../../golem-parser/adr/0012-keep-trailing-escaped-space.md)、エラーと警告のあいだとお知らせどうしの並び順は [ADR 0003](0003-diagnostic-order.md)、notice の下の info と並び順の最後の段と `silence-info` は [docs/adr/0104](../../adr/0104-info-severity.md)

## 文脈

診断の重大度は、エラーと警告の二つである（[ADR 0001](0001-source-spans-and-diagnostics.md)）。
エラーはビルドを止め、警告は止めないが、警告は「出荷する前に直すべきもの」として扱われている。
実際、今の警告は三つしかない。
校正用のコメントの残り（G02005）、HTML と EPUB に同梱できないフォント（G03010、dev だけ）、参照されていないラベル（G05004、dev だけ）であり、どれも直す前提のものである。
マニュアルを組むスクリプト（`scripts/manual/build.sh`）も、警告を一つでも出せば失敗にしている。

ところが、Golem には「誤りではないが、書き手が知っておいたほうがよいこと」を伝える手段がない。
次のような場面がある。

- `style.toml` を置かないプロジェクトは、既定の体裁で組まれる。HTML と EPUB とプレーンテキストは組めるので、書き手は既定の体裁で組まれていることに気づかないまま進むことがある。
- ファイルの先頭の `@style-def` が `style.toml` の `body` を上書きすると、その章だけ字下げが変わる（[docs/adr/0014](../../adr/0014-in-file-settings.md)）。`style.toml` だけを読むレビューでは、この差に気づけない。
- 記法には、書けるが勧めない書き方がある。`@listing` はパスを位置引数でも `src=` でも受け付け（`Golem.Eval.File` の `listing`）、docs/markup.md の中でも二つの書き方が混ざっている。
- 効果のない書き方もある。本の最後の改ページは捨てられ、`keep` の段落の行頭のエスケープした空白（`\ `）は無視される。書き手の意図が黙って落ちる。

これらを警告にすると、`golem build` の出力が「直すべきもの」で埋まり、本当に直すべき警告が埋もれる。
黙っていると、書き手は気づく機会を失う。
エラーと警告の下に、直さなくてよいが知らせる重大度が要る。

記法と設定を変える手順にも、同じ穴がある。
これまで廃止した設定（`[emphasis]`、`[verse]`、`[sidenotes]` の `font` と `size`、見出しの `running-head`）は、廃止した版から直ちにエラー（G03006、G03019）になった。
v1 の前なので問題は小さかったが、配布を始めた後に同じことをすると、版を上げただけで手元の原稿が組めなくなる。
廃止する前に、まず廃止予定を知らせる段階を置きたい。

所有者の判断として、お知らせはお知らせだけが抑制でき、エラーと警告は抑制できないことが決まっている。
lint の警告を抑制しない方針（[golem-lint ADR 0001](../../golem-lint/adr/0001-lint-rules.md)）は、そのまま保つ。

## 実装すること

### 重大度の追加

`Severity` に `Notice` を加え、警告より下の重大度とする。
日本語の名前は「お知らせ」、英語の表記は `notice` とする。

お知らせは次の性質を持つ。

- 終了コードに影響しない。`isError` と `hasErrors` は変えないので、お知らせだけなら終了コードは 0 である。
- プロファイルで重大度が変わらない。dev でも prod でもお知らせのままであり、`profileDependentCodes` にお知らせのコードを入れない。
- 出力を変えない。お知らせを出すかどうかで、PDF、HTML、EPUB、プレーンテキストのバイト列は変わらない。
- 診断を出す段階は問わない。構文、評価、プロジェクト、文書の組み立て、レイアウト、出力のどの段階のコードもお知らせにできる。lint の規則（G05xxx）はお知らせにしない。lint は「ほぼ確実に誤りである記述」だけを扱うと決めているからである。

### お知らせのコードの一覧

お知らせのコードは、`Golem.Syntax.Diagnostic` の `noticeCodes :: [DiagnosticCode]` に一箇所で並べる。
`profileDependentCodes` と同じ置き方である。
お知らせを作るときは、新しい関数 `notice :: Text -> SrcSpan -> Text -> Diagnostic` を使う。
docs/diagnostics.md の重大度が「お知らせ」のコードと `noticeCodes` が一致することは、golem-driver のテストが確かめる（「テスト設計」）。
抑制の設定の検査（下の「抑制」）も、この一覧を使う。

### 表示

人が読む形式では、重大度を `notice` と書く。

```
chapters/01.gm:12:1: notice[G02065]: @listing の src= は廃止予定です。パスを最初の引数に書きます
  | @listing src=src/Main.hs lines=10-20
```

JSON の形式では、`severity` を `"notice"` とする。
ほかの欄は変えない。

LSP では、`DiagnosticSeverity` の `Information`（3）に写す。
`Hint`（4）を選ばないのは、エディタの多くが Hint を目立たない形（点線だけなど）で表示し、問題の一覧にも載せないからである。
お知らせは読んでもらうためのものなので、一覧に載る `Information` にする。

`golem explain` の案内の行（[golem-cli ADR 0005](../../golem-cli/adr/0005-explain-diagnostic-codes.md)）は、お知らせのコードも数える。
案内の行は、抑制した後に残った診断から作る。

### 並び順

`sortDiagnostics` の並べ方を変え、エラーと警告を先に、お知らせを後に並べる。
エラーと警告のあいだの順は今のまま（ファイル、位置、コード）とし、お知らせどうしも同じ規則で並べる。
人が読む形式と JSON の形式は、同じ順で出す。

お知らせを位置の順に混ぜると、お知らせの多いプロジェクトで、ビルドを止めたエラーが画面の外に流れる。
順の規則が一つ増えるだけで、決定性は保たれる。
これは [ADR 0001](0001-source-spans-and-diagnostics.md) の「診断はファイルの順、位置の順、コードの順で並べてから出力する」を変えるので、実装のときに [ADR 0001](0001-source-spans-and-diagnostics.md) のステータスに、重大度と並び順をこの ADR（[ADR 0002](0002-notice-severity.md)）が置き換えたことを、リンクとともに加える。

### コマンドごとの振る舞い

各コマンドは、自分が走らせる段階のお知らせを出す。

- `golem build`：すべての段階のお知らせを出す。PDF の組版の段階のお知らせ（G07xxx、G08xxx）は、PDF を組むときにだけ出る。
- `golem check`：出力を作らずに走らせる段階（構文、評価、プロジェクト、文書の組み立てと、`style.toml` だけで決まる版面の検査）のお知らせを出す。
- `golem lint`：今と同じく評価の診断を含めて出すので、評価と文書の組み立てのお知らせも出る。lint の規則そのものはお知らせを出さない。
- LSP：今と同じく、評価と文書の組み立ての診断を出す。お知らせは `Information` として載る。
- `golem fmt`、`golem inspect`、`golem explain`：診断を出さないか、今と変わらない。

### 抑制

抑制できるのはお知らせだけである。
エラーと警告を抑制する手段は、どこにも設けない。

抑制の手段は二つとする。

1. **マニフェストの設定**：`manifest.toml` に `[diagnostics]` の表を置き、`silence-notices` に抑制するお知らせのコードを並べる。

   ```toml
   [diagnostics]
   silence-notices = ["G02062", "G04007"]
   ```

   コードは大文字の `G` と 4 桁の数字で書く。
   並べたコードのお知らせは、`golem build`、`golem check`、`golem lint`、LSP のどれにも出ない。
   プロジェクトの方針としてリポジトリに残り、レビューで見える。
2. **CLI のオプション**：`golem build`、`golem check`、`golem lint` に `--no-notices` を設ける。そのコマンドの実行に限り、すべてのお知らせを出さない。人が読む形式と JSON の形式の両方に効く。

`silence-notices` は、次のどれかに当たるとエラー（G03024）とし、位置は `silence-notices` の値の中のそのコードとする。

- コードの形でない文字列（`"g262"`、`"all"` など）。
- `noticeCodes` にないコード。エラーと警告のコード、廃止したコード、存在しないコードがこれに当たる。

エラーと警告のコードを書いても抑制できないことを、黙って無視せずにエラーで伝える。
廃止したお知らせのコードをエラーにするのは、抑制の一覧に意味のない行が残り続けるのを防ぐためである。
版を上げてお知らせのコードが廃止になったら、利用者は一覧からその行を消す。
`silence-notices` がない場合と空の配列の場合は、何も抑制しない。
`[diagnostics]` の未知のキーは、マニフェストのほかの表と同じく G03001 とする。

設けない手段とその理由は次のとおりである。

- **マニフェストですべてのお知らせを抑制する値**（`silence-notices = "all"` など）：廃止予定のお知らせは、版を上げたときに利用者が記法の変更を知る唯一の経路である。プロジェクトの設定ですべてを止めると、その経路が恒久的に閉じる。一度の実行で止めたい場合は `--no-notices` を使う。
- **原稿の中の指示**（`%%` のコメントや `@` のコマンドで、そのファイルや行のお知らせを止めるもの）：記法を一つ増やすことになり、コメントに意味を持たせない今の規則とも合わない。ファイル単位で止めたい要求が具体的に出てきたら、別の ADR で決める。
- **`style.toml` の設定**：診断の扱いは体裁ではなく、プロジェクトの方針である。

LSP は、マニフェストの `silence-notices` に従い、抑制したお知らせを公開しない。
`Hint` に下げて残すことはしない。
CLI で見えないものがエディタでだけ見えると、どちらを正とするかで混乱するからである。
LSP には `--no-notices` に当たる設定を設けない。

### 廃止予定の手順

記法と設定のキーを廃止するときは、次の順に進める。

1. 廃止を決める ADR で、廃止予定のお知らせのコードを決める。メッセージは「〜は廃止予定です」で始め、代わりの書き方を続ける。docs/diagnostics.md の節の「直し方」に、書き換えの前と後の例を置く。
2. お知らせを出す版を、少なくとも一つの minor の版としてリリースする。プレリリース（`-rc` など）だけでは数えない。リリースノートの「変更」の項に、廃止予定の書き方を挙げる。
3. 次の ADR で、その書き方をエラーにする。エラーには新しいコードを割り当て、お知らせのコードは状態を「廃止」にする。番号は使い回さない。

v1 のリリースより前に廃止した設定（G03006 と G03019 で報告しているもの）は、今のままエラーとする。
すでに利用者の手元にない書き方のために、お知らせの段階を遡って設けることはしない。

### 最初のお知らせ

今の記法と設定を調べ、次の七つをお知らせとする。
既存の警告（G02005、G03010、G05004）は、どれも直すべきものなので、お知らせに移さない。

| コード | 種類 | 段階 | 出す条件 | メッセージ |
| --- | --- | --- | --- | --- |
| G02062 | 上書き | 評価 | ファイルの先頭の `@style-def character` か `@style-def paragraph` が、`style.toml` か組み込みのスタイルと同じ名前を定義した | `ファイルの中の定義が <種類> の <名前> を上書きしています` |
| G02063 | 一般的でない書き方 | 評価 | `[tcy: ...]` の中身が ASCII の数字だけからなる | `数の縦中横は [number-text <数> style=tcy] でも書けます` |
| G02064 | 効果のない書き方 | 評価 | `line-breaks = "keep"` の段落の行頭に、エスケープした空白（`\ `）がある | `行頭のエスケープした空白は無視されます。字下げには全角の空白を使います` |
| G02065 | 廃止予定 | 評価 | `@listing` のパスを `src=` で書いた | `@listing の src= は廃止予定です。パスを最初の引数に書きます` |
| G03023 | 既定の使用 | プロジェクト | プロジェクトルートに `style.toml` がない | `style.toml がないので、既定の体裁で組みます` |
| G04007 | 効果のない書き方 | 文書の組み立て | 見出しかリストの項目の `@number N` が、`@number` がなくても振られる番号と同じである | `@number <N> は自動で振られる番号と同じです` |
| G04008 | 効果のない書き方 | 文書の組み立て | 本の最後のブロックの後に改ページ（`@page-break`、`@column-break`）しかない | `本の最後の改ページは効果がありません` |

位置は次のとおりとする。
G02062 は `@style-def` の行、G02063 は `[tcy ...]` の全体、G02064 はエスケープの `\`、G02065 は `src=` の引数、G03023 は `manifest.toml` の先頭、G04007 は `@number` の行、G04008 は最後の改ページのコマンドの行である。

それぞれの理由は次のとおりである。

- **G02062**：ファイルの中の上書きは仕様どおりの使い方だが、`style.toml` を読んでも見えない体裁の差を作る。上書きでない新しい名前の定義には出さない。一つの `@style-def` に一つ出す。
- **G02063**：縦組みの PDF では、`[tcy: 10]` と `[number-text 10 style=tcy]` は同じ見た目になる。後者は数として扱われるので、書字方向に合わせて表記が決まり、プレーンテキストの縦書きと横書きでもそれぞれの表記で出る。docs/markup.md は数の縦中横に `[number-text ...]` を使うよう案内している。数字以外を含む中身（`!?` など）には出さない。
- **G02064**：docs/markup.md は、`keep` の段落で行頭のエスケープした空白も無視すると定めている。書き手は字下げのつもりで書くことが多く、黙って無視されると意図が落ちる。
- **G02065**：`@listing` だけが、パスを位置引数と `src=` の両方で受け付ける。`@figure` はパスを位置引数で書き、docs/markup.md のコードブロックの節の例も位置引数である。位置引数を正とし、`src=` を廃止予定にする。`@table` の `src=` は対象にしない（下の「実装しないこと」）。
- **G03023**：`style.toml` がなくても HTML、EPUB、プレーンテキストは組めるので、既定の体裁で組まれていることに気づきにくい。PDF はフォントの設定がないので G08007 で止まるが、そのときもお知らせを出す。原因を一つ先に示せるからである。
- **G04007**：番号を手で書かない理由（項目を入れ替えるたびに直す必要がある）は docs/markup.md にある。自動の番号と同じ `@number` は今は効果がないが、項目を入れ替えたときに番号を固定してしまう。番号は文書の組み立てで決まるので、この段階で判定する。リストの番号は `itemNumbers` で、見出しの番号は文書の組み立てで求めた番号と比べる。
- **G04008**：仕様は本の最後の改ページを捨てると定めている。書き手は白ページを作るつもりで書いた可能性がある。ファイルの末尾の改ページは次のファイルに効くので、本の最後のファイルのものだけを対象にする。

[golem-driver ADR 0017](../../golem-driver/adr/0017-pdf-code-blocks.md) は、この重大度を使って、コードの行の折り返し（G07030）とコードの書体の役割の欠け（G08008）をお知らせにする。
二つの ADR の番号が衝突しないよう、この ADR が G02062 から G02065、G03023、G03024、G04007、G04008 を、[golem-driver ADR 0017](../../golem-driver/adr/0017-pdf-code-blocks.md) が G02066、G07030、G07043、G08008 を使う。

### docs/diagnostics.md と explain の目録

- 「節の形」の重大度に「お知らせ」を加える。お知らせは終了コードに影響せず、`silence-notices` と `--no-notices` で抑制できることを書く。
- 「番号の区分」の後に、お知らせのコードの一覧と、廃止予定の手順を書く。
- 上の八つの節（G02062 から G02065、G03023、G03024、G04007、G04008）を足す。G03024 の重大度はエラーである。G02065 の節の「直し方」には、書き換えの前と後の例を置く。
- golem-driver の `Golem.Driver.Explain.Catalog` の `severities` に `"お知らせ"` を加える。目録の解析の規則（重大度の行は四つの値のどれか）は、この値を含めて検査する。

### データ構造の変更

```haskell
data Severity = Error | Warning | Notice
  deriving stock (Eq, Ord, Show)

noticeCodes :: [DiagnosticCode]

notice :: Text -> SrcSpan -> Text -> Diagnostic
notice code = diagnostic code Notice

-- 抑制を一箇所で行う。Nothing はすべてのお知らせを抑制する（--no-notices）
silenceNotices :: Maybe (Set DiagnosticCode) -> [Diagnostic] -> [Diagnostic]
```

`silenceNotices` は、重大度が `Notice` の診断だけを落とす。
エラーと警告は、引数によらず必ず残す。
マニフェストの型（golem-project）に `[diagnostics]` の `silence-notices` を表す欄（`Set DiagnosticCode`）を足す。

### ドキュメント

- docs/specifications.md の「構文木と診断」に、三つの重大度、お知らせの性質、並び順、抑制の手段と、抑制できるのはお知らせだけであることを書く。
- 同じく「CLI」の表の `golem build`、`golem check`、`golem lint` に `--no-notices` を加え、「プロジェクトの構成と import」のマニフェストの説明に `[diagnostics]` を加える。
- 同じく「意図的に採用しなかったもの」の lint の抑制の項に、お知らせの抑制は lint の警告の抑制ではないことを一文足す。
- 同じく「v1 の実装で次の段階以降に回した項目」に、`@table` の位置引数のパスを検討する項目を加える。
- docs/glossary.md に「お知らせ」を加える。
- README の CLI の説明に `--no-notices` を加える。
- 利用者のマニュアルの「検査と診断」の章に、お知らせの読み方と抑制の仕方を書く（[docs/adr/0024](../../adr/0024-manual-audiences-and-policy.md)）。

## 実装しないこと

- エラーと警告の抑制。どの手段でも設けない。
- マニフェストですべてのお知らせを抑制する値と、原稿の中でお知らせを抑制する指示（「抑制」）。
- プラグインのお知らせ。プラグインの応答の重大度は、今のとおり 0（エラー）と 1（警告）だけを受け付け、それ以外は「診断の重大度が不正です」とする。プラグインのコードは docs/diagnostics.md の外にあり、`silence-notices` で指せないからである。必要になったら、プラグインの ABI の変更として別の ADR で決める。
- 既存の警告をお知らせに移すこと。
- `@table` のパスを位置引数で書けるようにすること。`@table` は `src=` だけを受け付けるので、`@listing` と合わせるには記法の追加が要る。今後の実装項目に送る。
- 段落の先頭の全角の空白と `first-line-indent` の併用（二重の字下げ）のお知らせ。有用だが、[docs/adr/0006](../../adr/0006-paragraph-indent.md) が「指摘しない」と決めた事項であり、変えるには [ADR 0006](../../adr/0006-paragraph-indent.md) の該当部分を置き換える判断が要る。所有者の判断を待つ。
- 合成の太字と斜体を使ったことのお知らせ。`golem new` の雛形で `[strong: ...]` を使うだけで出るので、ほとんどのプロジェクトで常に出るお知らせになる。合成の太字は [golem-driver ADR 0004](../../golem-driver/adr/0004-pdf-emphasis-and-character-styles.md) と [ADR 0012](../../golem-driver/adr/0012-synthetic-bold-weight.md) が設計として採ったものでもある。
- 不要なエスケープ（`\a` のように、エスケープしなくても同じ意味になる文字の前の `\`）のお知らせ。`golem fmt` が取り除くので、お知らせは重複する（[golem-fmt ADR 0001](../../golem-fmt/adr/0001-formatter.md)）。
- 改行の様式のファイルの空行のお知らせ。青空文庫の形式の原稿では空行が多く、常に出るお知らせになる。
- お知らせの数の上限と、同じお知らせをまとめる表示。

## テスト設計

### 先に書いて失敗させるテスト

golem-syntax のテストで、次を確かめる。

- `Notice` が `Warning` より大きいこと（`Error < Warning < Notice`）。
- `hasErrors` が、お知らせだけの一覧で偽になること。
- `adjustForProfile` が、prod でもお知らせの重大度を変えないこと。`noticeCodes` と `profileDependentCodes` に共通のコードがないこと。
- `sortDiagnostics` が、位置の早いお知らせを位置の遅いエラーより後に並べること。エラーと警告は、今と同じく位置の順に混ざること。入力の順をシャッフルしても結果が同じであること（プロパティテスト）。
- `silenceNotices (Just s)` が、`s` にあるコードのお知らせだけを落とすこと。`s` にあるコードのエラーと警告は落とさないこと。
- `silenceNotices Nothing` が、すべてのお知らせを落とし、エラーと警告をすべて残すこと（プロパティテスト）。
- 人が読む形式の golden テスト：お知らせの見出しの行が `notice[G02065]` になること。
- JSON の形式の golden テスト：`"severity":"notice"` になり、お知らせが配列の後ろに並ぶこと。

golem-lsp のテストで、次を確かめる。

- お知らせが `DiagnosticSeverity_Information` で公開されること。
- マニフェストの `silence-notices` にあるコードのお知らせが公開されないこと。同じコードでも、ほかのコードのお知らせは公開されること。

golem-project のテストで、`silence-notices` の読み込みを確かめる。

- `["G02062"]` を読めること。
- `["G01001"]`（エラーのコード）、`["G02005"]`（警告のコード）、`["G02048"]`（廃止したコード）、`["G9999"]`（存在しないコード）、`["all"]`、`["g02062"]` が、それぞれその要素の位置で G03024 になること。
- 文字列で `"all"` と書いた場合（配列でない）が G03001 になること。
- `[diagnostics]` の未知のキーが G03001 になること。

golem-cli のテストで、次を確かめる。

- お知らせだけが出るプロジェクトで、`golem build`、`golem check`、`golem lint` の終了コードが 0 であること。`--profile prod` でも 0 であること。
- `--no-notices` で、お知らせが標準エラー出力から消え、エラーと警告は残ること。JSON の形式でも同じであること。
- お知らせだけが出たとき、`golem explain` の案内の行が出ること。`--no-notices` でお知らせを消したときは、案内の行も出ないこと。
- `golem build --no-notices` の出力のバイト列が、`--no-notices` なしの出力と同じであること。
- `golem fmt` と `golem explain` が `--no-notices` を受け付けず、使い方の誤り（終了コード 2）になること。

golem-driver のテストで、次を確かめる。

- docs/diagnostics.md で重大度が「お知らせ」のコードの集合が、`noticeCodes` と一致すること。
- 目録の解析が「お知らせ」を受け付け、「お知らせ」でも四つの値のどれでもない重大度（「情報」など）を拒むこと。

最初のお知らせの七つについて、それぞれ出る例と出ない例を golem-eval、golem-project、golem-doc のテストに置く。

- G02062：`@style-def paragraph body indent=1zw` で出る。`@style-def paragraph letter based-on=body` で出ない。`@style-def character bold font=heading`（組み込みの上書き）で出る。
- G02063：`[tcy: 10]` で出る。`[tcy: !?]` と `[tcy: 1a]` で出ない。`[number-text 10 style=tcy]` で出ない。
- G02064：`@style verse` の本体の行頭の `\ ` で出る。`keep` でない段落の行頭の `\ ` で出ない。行の途中の `\ ` で出ない。
- G02065：`@listing src=a.hs` で出る。`@listing a.hs` で出ない。出た場合も、取り込んだ内容は今と同じであること。
- G03023：`style.toml` のないプロジェクトで出て、位置が `manifest.toml` の先頭であること。`style.toml` のあるプロジェクトで出ないこと。
- G04007：最初の項目の `@number 1` で出る。三つ目の項目の `@number 3` で出る。三つ目の項目の `@number 5` で出ない。最初の見出しの `@number 1` で出る。`@nonumber` の見出しの後の見出しの `@number` は、`@nonumber` が番号を消費しないことを含めて判定すること。
- G04008：最後のファイルの末尾の `@page-break` で出る。最後でないファイルの末尾の `@page-break` で出ない。最後のファイルの末尾に `@page-break` と `@column-break` が続く場合に、二つとも出ること。

お知らせが出力を変えないことは、原稿を直さずに確かめる。
G03023 を除く六つのお知らせを出す原稿を一つ用意し、`silence-notices` に六つのコードを並べたマニフェストと並べないマニフェストで組み、四つのターゲットの出力が同じバイト列であることを確かめる。
G03023 は `style.toml` のないプロジェクトで、`--no-notices` の有無で HTML、EPUB、プレーンテキストの出力が同じであることを確かめる（PDF は G08007 で止まる）。
G02065 については、位置引数に書き換えた `@listing` の原稿でも、四つのターゲットの出力が同じであることを確かめる。
ほかの六つは、原因を直すと出力が変わりうるので（G02063 なら HTML の要素が縦中横から数に変わる）、この比較をしない。

### 自動テストにできないものの確かめ方

- Neovim で、お知らせが Information として表示され、問題の一覧に載ることを確かめる。`silence-notices` に加えると、保存の後に消えることも確かめる。
- 結果は、実装のプルリクエストのコメントに書く。

## トレードオフ

- 重大度を一つ増やすと、診断を出す側は、警告とお知らせのどちらにするかを判断する必要が出る。判断の基準を「直すべきか」の一つにする。直すべきものは警告、直さなくてよいものはお知らせである。迷うものはお知らせにしない。
- お知らせを後ろに並べると、同じファイルの診断が位置の順に並ばなくなる。エラーを見落とさないことを優先した。エディタは位置で表示するので、LSP では影響がない。
- 抑制をマニフェストのコードの一覧に限ると、ファイルごとや箇所ごとに止めたい場合に、プロジェクトの全体で止めるしかない。止め方の粒度を増やすと、記法かコメントに意味を持たせる必要があり、lint の警告を抑制しない方針との境界も曖昧になる。最初は粗い手段だけを置く。
- すべてのお知らせを止める手段を CLI にだけ置くので、CI のログを静かにしたい利用者は、CI のコマンドに `--no-notices` を書く必要がある。廃止予定を見落とす経路は CI のログに限られ、手元の `golem build` では見える。
- 廃止したお知らせのコードを `silence-notices` に残すとエラーにするので、版を上げたときに一覧の手直しが要ることがある。黙って無視すると、抑制の一覧が実際に何を止めているかわからなくなる。
- 廃止予定の期間を「一つの minor の版」と決めると、小さな記法の整理にも最低一回のリリースを待つことになる。版を上げただけで原稿が組めなくなることを避ける代価として受け入れる。
- G04007 と G04008 を文書の組み立ての段階に置くので、LSP でも出るが、ファイルを一つだけ開いた状態の LSP では、文書の全体を見ないと決まらない G04008 が出ないことがある。LSP は今もプロジェクトの全体を評価しているので、実際の差は小さいと見込む。
