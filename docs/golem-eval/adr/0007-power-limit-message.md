# ADR 0007: G02095 のメッセージを、計算の量の上限として書く

ステータス: 採択

## 文脈

[ADR 0006](0006-exact-power-limit-before-range.md) は、累乗の正確な計算に要るビットの数 `(m のビットの数 - 1) × |k|` が 2^20 を超える式を、エラー G02095 とした。
メッセージは次のとおりである。

```
累乗の計算が大きすぎます（正確な計算に要るビットの数 <n> が、上限の 1048576（2 の 20 乗）を超えます）
```

[ADR 0006](0006-exact-power-limit-before-range.md) の実装の後、メンテナーが別のセッションで規則の批評を受けた。
批評は、このメッセージが事象と合わないと指摘した。
G02095 が出るのは計算の量が多い場合であり、結果の値が大きい場合ではない。
たとえば `1.0000000000000002 ** 30000` の底は 1 + 2^-52 であり、`m` が 53 ビットなので `52 × 30000 = 1560000` が上限を超えて G02095 になる。
しかし、結果はおよそ 1 + 6.7 × 10^-12 であり、倍精度で普通に表せる。
メッセージの頭の「計算が大きすぎます」を読んだ書き手は、値の大きさを疑う。
メンテナーは、G02095 のメッセージを決めたときに「ユーザーが『大きい』とは何なのか迷ってはいけない」と求めており、括弧の中で量と上限を示した。
ただ、頭の句が値の大きさとも読めるので、迷いは残る。

### 批評のほかの指摘

批評はほかに四つの指摘と一つの私見を挙げた。
批評が読んだのは [ADR 0006](0006-exact-power-limit-before-range.md) の「文脈」の節にある、[ADR 0006](0006-exact-power-limit-before-range.md) が置き換えた前の規則（倍精度の見積もりによる判定）である。

- **前の規則の条件の文書とコードの食い違い（`E ≤ -1076` と `E < -1076`）**：[ADR 0006](0006-exact-power-limit-before-range.md) で見積もりごと消したので、当たらない。
- **見積もりの誤差が 1 未満であることへの依存**：同じく、[ADR 0006](0006-exact-power-limit-before-range.md) で判定を整数の演算だけにしたので、当たらない。
- **底が 0 の場合**：[ADR 0005](0005-float-overflow.md) と実装が決めている。指数が 0 なら 1、正なら 0、負なら G02003（0 での割り算）であり、[ADR 0006](0006-exact-power-limit-before-range.md) の判定には 0 でない底だけが来る。仕様書と markup.md にも書かれている。
- **結果の符号（負のゼロ）**：[ADR 0005](0005-float-overflow.md) は、負のゼロを正のゼロにすると決めている。結果がちょうど 2^-1075 になる負の底と奇数の指数の累乗（`(0 - 2.0 ** -215) ** 5`）では、`powRounded` の中で丸めた 0 に負の符号が付くが、続く `finite` が 0 を正のゼロにそろえるので、評価の結果は正のゼロになり、[ADR 0005](0005-float-overflow.md) のとおりである。回帰を防ぐテストを、ADR を起こさずに足す（プルリクエスト #281）。
- **丸めの方式**：[ADR 0005](0005-float-overflow.md) のテストと実装（`fromRational`）は、等距離なら偶数の側へ丸める。markup.md は「最も近い倍精度の値に一度だけ丸める」とだけ書き、等距離の扱いを書いていないので、負のゼロのテストと同じプルリクエスト（#281）で文書に足す。
- **私見（累乗の結果を有理数のまま保てば、倍精度の範囲の判定が要らなくなる）**：採らない。式の言語の数は、整数と倍精度の浮動小数点数の二つであり、浮動小数点数のリテラルは最も近い倍精度の値に読む（[ADR 0001](0001-expression-language-and-numerics.md)）。累乗だけ有理数を返すと、ほかの演算と本文への表記にまで有理数の型が広がり、数の仕組みの全体を変えることになる。

## 実装すること

### メッセージ

G02095 のメッセージを次のように改める。

```
累乗の正確な計算に要るビットの数 <n> が、上限の 1048576（2 の 20 乗）を超えます（結果の大きさによらない上限です）
```

- 頭に、上限を超えた量（ビットの数）を置く。「大きすぎます」の句を消し、値の大きさとの取り違えをなくす。
- 括弧の中で、この上限が結果の大きさと関係しないことを断る。
- `<n>` は今と同じく `(m のビットの数 - 1) × |k|` の値である。
- コード、重大度、判定の条件と順序は変えない。

直し方はメッセージに入れず、`docs/diagnostics.md` の「直し方」に書く。
底の桁を減らすという直し方は、十進の小数では役に立たないためである。
`1.1` も `1.0000001` も、倍精度の値の `m` は 50 ビットを超え、十進の桁を減らしても `m` のビットの数は減らない。
`m` が短いのは、`1.5` や `1.25` のように分母が 2 の累乗の小数だけである。
メッセージで「底の桁を減らしてください」と勧めると、書き手は十進の桁を減らして、同じエラーを受け取る。

### ドキュメント

- `docs/diagnostics.md` の G02095 の節の題を `累乗の正確な計算に要るビットの数が上限を超えます` とし、メッセージを改める。
  - 「意味」に、結果が倍精度で普通に表せる値でも出ることを、`1.0000000000000002 ** 30000` の例で書く。
  - 「直し方」に、十進の小数の底では `m` がおよそ 53 ビットになり、指数の絶対値の上限がおよそ 20000 になることを書く。
- 使い手のマニュアルの G02095 の項目（`manual/appendices/e-errors.gm`）のメッセージを改める。

## 実装しないこと

- 上限の値と判定を変えること。[ADR 0006](0006-exact-power-limit-before-range.md) のままとする。
- 累乗の結果を有理数のまま保つこと（「文脈」の私見）。
- 負のゼロの回帰を防ぐテスト。実装は [ADR 0005](0005-float-overflow.md) のとおりなので、この ADR に含めず、プルリクエスト #281 で足す。

## テスト設計

### golem-eval（`test/ExprSpec.hs`）

先にテストの期待を新しいメッセージに改め、今の実装で失敗することを確かめる。

- [ADR 0006](0006-exact-power-limit-before-range.md) の G02095 のテスト（「文脈」の表の四つの式、上限の境界）の期待するメッセージを、新しいメッセージに改める。
- `1.0000000000000002 ** 30000` が、`<n>` を 1560000 とする新しいメッセージの G02095 になる。結果が倍精度の範囲の内にある式でも G02095 になることを確かめる。

### golem-driver（`test/DiagnosticsSpec.hs`）

- G02095 の題とメッセージが、`docs/diagnostics.md` と一致する。今のカタログの検査が通ること。

## トレードオフ

- メッセージが長くなる。括弧の中の断りを消せば短くなるが、頭の句だけでは「上限」が何の上限かを読み違える余地が残る。
- 直し方をメッセージに入れないので、書き手は `golem explain G02095` で直し方を読む必要がある。直し方が底の種類で変わり、一文で正しく書けないためである。
- G02095 は v0.1.0-rc3 で入れたコードであり、まだリリースしていない。メッセージを変えても、既存の利用者の出力の比べには影響しない。
