# ADR 0017: コードの書体とコードブロックの組み方

ステータス: 採択→コードの改行の規則を文字スタイル `url` にも当てることは [golem-doc ADR 0005](../../golem-doc/adr/0005-bibliography-fields.md)

## 文脈

PDF のコードブロックは、本文と同じに組まれている（[仕様書の「v1 の実装で次の段階以降に回した項目」](../../specifications.md)の「PDF のコードブロック」）。
コードで確かめると、`Golem.Driver.Pdf` の `unitsOf` は、`CodeBlock` の各行を、本文の段落スタイルの見た目で字下げのない段落の単位（`UPara noIndent`）にしている。
このため、次のことが起きる。

- 本文の書体で組まれる。等幅の書体を指定する手段がない。
- 両端揃えになり、欧文の語はハイフネーションで分かれる。
- 行頭の空白が残らないので、字下げに意味のあるコード（Haskell、Python、YAML）の例が崩れる。
- 和文と欧文のあいだにアキ量のセットの空きが入り、約物の空きも本文の規則で詰められる。
- 一つのコードの行が版面の行長より長いと、本文の行分割で折り返される。

HTML と EPUB では、コードブロックを `<pre><code>` で出し、言語の名前があれば skylighting の class で色を付けている（[golem-html ADR 0001](../../golem-html/adr/0001-xhtml-serializer.md)）。
ただし、`pre` と `code` に書体の指定がなく、閲覧環境の既定の等幅の書体になる。

本文の中のコードの名前（`manifest.toml`、`golem build`）には、専用の記法がない。
利用者のマニュアル（`manual/`）は、`[character-styles.code]` に色だけを付けた文字スタイルを定義し、`[style code: manifest.toml]` と書いている。
本文の書体のままなので、`manifest.toml` がハイフネーションで `mani-` と `fest.toml` に分かれることがある。

所有者は、マニュアルのコードを、背景の色を付けて、コード用の等幅の書体で組むことを求めている（[docs/adr/0024](../../adr/0024-manual-audiences-and-policy.md)）。
仕様書の「PDF のコードブロック」の項は、これに加えて技術書の機能（行番号、キャプション、行の強調、注釈の印、差分、色分け、改ページの続きの表示など）を一つの ADR で扱うとしている。
この ADR は、そのうち、コードを正しく読める形で組むための中核だけを扱う。
技術書の機能は、どれも中核の組み方（行の置き方、背景、折り返し）の上に載るので、中核を先に固めてから別の ADR で決める。

キャプション（[ADR 0010](0010-caption-style.md)）と傍注（[ADR 0011](0011-sidenote-font.md)）は、組み込みの段落スタイルの `font` と `size` だけを使う組み方を採った。
コードブロックも、同じ形にする。
書体と大きさの書き方が段落スタイルと二通りにならず、`G0308`、`G0311`、使う役割の集め方（`usedRoles`）がそのまま使えるからである。

## 実装すること

### コードの書体の役割

コードの書体は、`style.toml` のフォントの役割 `code` で指定する。

```toml
[fonts.code]
latin = "fonts/SourceCodePro-Regular.otf"
ja = "fonts/NotoSansJP-Regular.otf"
```

役割の名前は今も自由に付けられるので、`[fonts]` の型は変えない。
`code` は、下の組み込みの段落スタイル `code` と文字スタイル `code` が既定で指す役割の名前である。

`[fonts.code]` がないのに、本にコードブロックかコードの文字スタイルの文字があれば、PDF は本文の役割で組み、お知らせ（G0808）を一つ出す（[golem-syntax ADR 0002](../../golem-syntax/adr/0002-notice-severity.md)）。
位置は `style.toml` の先頭（なければ `manifest.toml` の先頭）とする。
エラーにしないのは、`golem new` の雛形がコードの書体を持たず、コードを一つ書いただけで PDF が組めなくなるのを避けるためである。
警告にしないのは、本文の書体で組んだコードも読めるからである。
`code` の段落スタイルか文字スタイルの `font` を利用者が別の役割に変え、その役割が `[fonts]` にない場合は、今と同じ G0308 のエラーとする。

PDF は、本にコードブロックかコードの文字スタイルの文字があるときだけ、`code` の役割のフォントを読み込む。
使わない役割のフォントを読まない今の規則（仕様書の「フォント」の節）に合わせる。

### 組み込みの段落スタイル code

組み込みの段落スタイルに `code` を加え、コードブロックの書体、大きさ、背景、内側の余白を決める。
コードブロックは、常にこの段落スタイルで組む。

```toml
[color.swatches]
code-bg = { cmyk = [0, 0, 0, 8] }

[paragraph-styles.code]
size = "11Q"
background = "code-bg"
padding = "0.5zw"
```

| キー | 型 | 既定 | 意味 |
| --- | --- | --- | --- |
| `font` | 役割の名前 | `"code"` | コードの書体の役割 |
| `size` | 寸法 | 版面の文字の大きさ | コードの文字の大きさ。`zw` は版面の文字の大きさを一字とする |
| `background` | スウォッチの名前 | なし | 背景の色。書かなければ背景を塗らない |
| `padding` | 寸法 | `"0.5zw"` | 背景の内側の余白。`zw` はコードの文字の大きさを一字とする。上下と左右に同じ量を取る |

`code` は、ほかの段落スタイルと次の点で違う。

- `body` を根にしない。`based-on` を持たず、`[paragraph-styles.code]` に `based-on` を書くとエラー（G0306）とする。`body` の字下げ、正規表現スタイル、アキ量のセットを引き継がないためである。
- 書けるキーは上の四つだけである。ほかのキー（`indent`、`line-breaks`、`regex-styles`、`aki-set`、`kerning` など）を書くとエラー（G0306）とし、メッセージで書けるキーを示す。コードの組み方は下の「コードブロックの組み方」で固定する。
- ほかの段落スタイルの `based-on` に `code` を書くとエラー（G0313）とする。
- 原稿の `@style code` はエラー（G0266）とする。コードは ```` ``` ```` か `@listing` で書く。
- `background` と `padding` は、v1 では `code` の段落スタイルにだけ書ける。ほかの段落スタイルに書くとエラー（G0306）とし、メッセージで `code` にだけ書けることを示す。型は段落スタイルの全体に持たせ、実装を `code` に絞る（仕様書の「設計原則」の「広い型、狭い実装」）。InDesign の段落の背景色（段落の囲み罫と背景色）に当たる機能を、ほかの段落にも広げる余地を残す。
- `background` のスウォッチが `[color.swatches]` にない場合は、文字スタイルの `color` と同じく G0313 とする。`padding` が寸法として読めない場合と負の場合は G0306 とする。
- ファイルの先頭の `@style-def paragraph code ...` は、上と同じ四つのキーに限って書ける（[docs/adr/0014](../../adr/0014-in-file-settings.md)）。

`size` の `zw` を版面の文字の大きさで数えるのは、ほかの段落スタイルの `size` と同じ規則にするためである。
`padding` の `zw` をコードの文字の大きさで数えるのは、コードの大きさを変えたときに余白も同じ比で変わるほうが、見た目の釣り合いを保ちやすいからである。

### コードブロックの組み方

PDF では、コードブロック（```` ``` ```` と `@listing`）を次のように組む。

**行の置き方**。
コードの行の送りは、キャプションと同じく、本文の行送りと文字の大きさの比を保った値（コードの文字の大きさ × 行送り ÷ 版面の文字の大きさ）とする（[ADR 0010](0010-caption-style.md)）。
コードブロックは、コードの行の全体と上下の `padding` を収める最も少ない数の行の格子を占める。
その領域の中で、コードの行のまとまりを天地の中央に置く。
キャプションは余りを後ろに回すが、コードブロックは背景を塗るので、上下の余白をそろえる。
コードブロックの後の本文は、格子からずれない。

**背景**。
`background` があれば、占めた格子の行の領域を、そのスウォッチの CMYK の値で DeviceCMYK の矩形として塗り、その上に文字を描く。
領域の天地は、最初の格子の行の上の空き（行送りと文字の大きさの差の半分）から、最後の格子の行の下の空きまでとする。
領域の左右は、行の始まりの位置から行長の終わりまでとする。
リストの項目と定義リストの説明の中のコードブロックは、今と同じく項目の本文の始まりにそろえるので、背景もそこから始まる（[ADR 0013](0013-list-indents.md)）。
文字は、行の始まりから `padding` だけ内側から置く。

**空白とタブ**。
行頭と行の途中の空白（U+0020）は、詰めずにそのまま残し、`code` の役割の欧文のフォントの空白の送りで組む。
欧文のフォントがなければ、和文のフォントの空白の送りとする。
タブ（U+0009）は、行の文字の始まりから数えて、空白の送りの 2 倍ごとに置いたタブの位置のうち、次の位置まで進める。
タブの幅は 2 に固定し、設定のキーは設けない。
本の版面は、エディタの画面より行が短い。
字下げを浅くして、版面の行長に対してコードの文字に使える幅を残すためである。
2 は、多くのコードの整形の規約が使う字下げの幅の小さい側でもある。
タブの幅 2 は、コードブロックの中だけに当てる。
本文と、本文の中のコード（下の `[code: ...]`）のタブは、今の扱いのまま変えない。
和文の文字は空白の送りの整数倍とは限らないので、タブの位置を桁の数ではなく、行の始まりからの距離で決める。

**組み方の規則**。
コードの行には、本文の組み方の規則を使わない。

- 両端揃えにしない。行の始まりにそろえ、行の終わりは成り行きとする。
- ハイフネーションをかけない。
- アキ量のセットの空き（和欧間、約物の前後）を入れない。字送りは、フォントの送りのとおりとする。
- 禁則、ぶら下げ組、突き出し、字幅の伸縮（`protrusion`、`expansion`）を使わない。
- カーニングをかけない（`kerning = "none"` と同じ機能を足す）。`code` の役割の `features` は、ほかの役割と同じくシェイピングに渡す。
- 正規表現スタイルを当てない。

**長い行**。
行の始まりからの幅が、行長から左右の `padding` を引いた幅を超える行は、シェイピングのクラスタの境界で折り返す。
収まる最後のクラスタの後で折り返し、次の行に続ける。
折り返した続きの行は、元の行の行頭の空白とタブの幅に、空白の送りの 2 倍を足した位置から始める。
その位置から後に空白の送りの 8 倍の幅が残らない場合は、空白の送りの 2 倍の位置から始める。
折り返したことを示す印は描かない。
折り返した行のあるコードブロックごとに、お知らせ（G0730）を一つ出し、位置はコードブロックの始まりとする。
メッセージに折り返した行の数を含める。

エラーにしない理由は、`@listing` で取り込むファイルのように、利用者が行の長さを選べない場合があるからである。
黙って折り返さない理由は、シェルのコマンドのように、折り返しが意味を変えるコードがあるからである。
印の形（行末の `↩` など）は、技術書の機能の ADR で決める。

**行長の不足**。
行長から左右の `padding` を引いた幅が、コードの文字の大きさの 8 字分に満たないコードブロックはエラー（G0743）とし、位置はコードブロックの始まりとする。
リストの深い入れ子の中で起きうる。
8 字分は、段落スタイルの字下げ（G0725）とリスト（G0727）と同じ基準である。

**改ページ**。
コードブロックは、コードの行（折り返した続きの行を含む）のあいだで改ページしてよい。
ページに残る格子の行が、コードの一行と上下の `padding` を収めるのに足りなければ、ブロックを次のページから始める。
分けたそれぞれの部分は、上の規則で格子の行を占め、背景を部分ごとに塗る。
部分ごとに上下の `padding` を取り、背景はページの境で閉じる。
段組みの版面では、段の境も同じに扱う。
続きの表示（「続く」の印など）は描かない。
一行と上下の `padding` が一ページの行数に収まらない場合も G0743 のエラーとし、行長の不足とはメッセージで区別する。

**空行**。
コードの中の空行は、中身のない一行として残す。
コードブロックの先頭と末尾の空行も残す。

**縦組み**。
縦組みの本のコードブロックは、ほかの本文と同じく縦組みで組み、欧文は今の規則（UAX #50）で回転する。
タブの位置と折り返しは、行の方向（天から地）で測る。
横組みの囲みとして組む方式は、この ADR では扱わない。

### コードの文字スタイルと [code: ...]

組み込みの文字スタイルに `code` を加える。

| キー | 既定 |
| --- | --- |
| `font` | `"code"` |

文字スタイル `code` と、`based-on` をたどって `code` に行き着く文字スタイルの文字は、PDF で次のように組む。

- ハイフネーションをかけない。
- 改行してよい位置を、空白と、`/` の後に限る。`/` の後で改行しても、ハイフンを描かない。パスと URL がコードの名前の多くを占め、`/` の後で分けるのが慣用だからである。
- カーニングをかけない。
- 中の文字のあいだにアキ量のセットの空きを入れない。前後の文字との空きは、今と同じく、端の文字のクラスで決める。
- タブの幅 2 は当てない。タブは、本文のほかの文字と同じく今の扱いのままとする。

原稿には、`[code: ...]` を `[style code: ...]` の別名として加える。
`[strong: ...]` が `[style strong: ...]` の別名であるのと同じ形である（[docs/adr/0005](../../adr/0005-character-and-paragraph-styles.md)）。
中身は散文スロットなので、`]`、`|`、`[` は今と同じく `\` でエスケープする。

利用者が `[character-styles.code]` を書くと、書いたキーだけが組み込みの定義を上書きする。
今のマニュアルの `[character-styles.code] color = "code"` は、書体が `code` の役割になり、色はそのまま残る。

意味論 IR は変えない。
コードブロックは今の `CodeBlock` で、`[code: ...]` は `CharStyle "code"` で表す。
プラグインとの CBOR も変わらない。

### HTML と EPUB

`style.css` に次を書く。

- `code` の役割の `@font-face` を、ほかの役割と同じく書く。
- `pre` と `code` の `font-family` を `code` の役割の書体の並びにし、最後に `monospace` を置く。`code` の役割がなければ `monospace` だけとする。
- `pre` に `white-space: pre-wrap`、`overflow-wrap: anywhere`、`tab-size: 2`、`hyphens: none`、`font-kerning: none` を書く。PDF と同じく長い行を折り返し、タブの幅をそろえるためである。
- `[paragraph-styles.code]` の `background` があれば、`pre` の `background-color` をスウォッチの RGB の近似で書く。`padding` は `pre` の `padding` に、`zw` を `em` にして書く。`size` があれば、キャプションと同じく `pre` の `font-size` を版面の文字の大きさとの比の `em` で書く。
- 文字スタイル `code` は、`<code>` の要素で出す。組み込みの文字スタイル `strong` が `<strong>` になるのと同じ扱いである。`code` を `based-on` で引き継ぐ文字スタイルは、今と同じく `<span class="cs-名前">` で出し、CSS に `font-family` と `hyphens: none` を書く。

HTML の skylighting による色分けは、今のまま残す。
PDF の色分けは、技術書の機能の ADR で決める。

プレーンテキストの出力は変えない。

### 診断

この ADR が加えるコードは次のとおりである。
今のソースと docs/diagnostics.md で使っているコードは G0101 から G0261、G0301 から G0322、G0401 から G0406、G0501 から G0504、G0602 から G0611、G0701、G0702、G0721 から G0729、G0732 から G0735、G0741、G0742、G0801 から G0807 である。
[golem-syntax ADR 0002](../../golem-syntax/adr/0002-notice-severity.md) が G0262 から G0265、G0323、G0324、G0407、G0408 を使うので、それと重ならない番号を選んだ。

| コード | 重大度 | 段階 | 出す条件 | メッセージ |
| --- | --- | --- | --- | --- |
| G0266 | エラー | 評価 | 原稿に `@style code` がある | `code はコードブロックの段落スタイルです。コードは ``` か @listing で書きます` |
| G0730 | お知らせ | レイアウト | 版面の行長に収まらないコードの行を折り返した | `コードの行を折り返しました（<n> 行）` |
| G0743 | エラー | レイアウト | 行長から左右の `padding` を引いた幅がコードの文字の大きさの 8 字分に満たない、または一行と上下の `padding` が一ページに収まらない | `コードブロックの行長が足りません` または `コードブロックの一行が一ページに収まりません` |
| G0808 | お知らせ | 出力 | 本にコードがあり、`[fonts.code]` がない | `コードの書体の役割 code がないので、本文の書体で組みます` |

`[paragraph-styles.code]` のキーの誤り、`background` と `padding` のほかのスタイルでの使用、`code` の `based-on` は既存の G0306、スウォッチの欠けと `based-on = "code"` は既存の G0313 で報告する。
メッセージは、何がどこに書けるかを示す文言にする。
G0743 の行長の不足は、`style.toml` だけで決まる最上位のコードブロックについて、PDF をターゲットに含む `golem check` でも報告する（[ADR 0016](0016-output-and-layout-diagnostic-codes.md) の G0725 と同じ扱い）。

docs/diagnostics.md に四つの節を足し、「使っていない番号」の空きの一覧から G0730 を外す。
G0730 と G0808 は、[golem-syntax ADR 0002](../../golem-syntax/adr/0002-notice-severity.md) の `noticeCodes` に加える。

### データ構造の変更

```haskell
-- golem-project の段落スタイル
data ParagraphStyle = ParagraphStyle
  { -- 今の欄に加えて
    psBackground :: !(Maybe Text),      -- スウォッチの名前
    psPadding    :: !(Maybe Dimension)
  }
```

golem-layout の組版の単位に、コードブロックの行を表す種類を加える。
単位は、コードの一行（折り返す前の一行）を持ち、組み方の規則（両端揃えなし、ハイフネーションなし、アキなし、タブの位置）をこの種類に閉じ込める。
ページの割り付けでは、コードブロックを一つの塊として扱い、行のあいだでだけ分ける。
PDF の描画には、塗りの矩形の描画（DeviceCMYK の `re` と `f`）を加える。
意味論 IR と、プラグインの ABI は変えない。

### ドキュメント

- docs/specifications.md の「style.toml」に、組み込みの段落スタイル `code`、四つのキー、`code` の制限を書く。「フォント」に役割 `code` と、PDF がそれを読み込む条件を書く。組み込みの文字スタイルの一覧に `code` を加える。
- 同じく「v1 の実装で次の段階以降に回した項目」の「PDF のコードブロック」を書き換え、この ADR で扱った部分を除き、技術書の機能（行番号と開始の番号、ファイル名とキャプション、行の強調、注釈の印、差分の表示、PDF の構文の色分け、枠、折り返した印、改ページの続きの表示、`@listing` への同じ指定）と、本文のコードの背景の色を残す。
- docs/markup.md の「コードブロック」に、PDF の組み方の要点（空白とタブを残すこと、長い行を折り返すこと）を書く。「強調」の節の近くに `[code: ...]` を加える。
- docs/diagnostics.md に、上の四つの節を足す。
- 利用者のマニュアルと開発者のマニュアルのコードを、この ADR の組み方で組む（[docs/adr/0024](../../adr/0024-manual-audiences-and-policy.md)）。

## 実装しないこと

- 技術書の機能（行番号、キャプション、行の強調、注釈の印、差分、PDF の色分け、枠、折り返した印、改ページの続きの表示）。仕様書の「PDF のコードブロック」の項に残し、別の ADR で決める。
- 本文の中のコード（`[code: ...]`）の背景の色。一つの語が行をまたいで分かれたときの塗り方、ルビや圏点との重なり、縦組みでの向きを決める必要があり、コードブロックの背景とは別の問題になる。HTML と EPUB でも、媒体の差を作らないために `<code>` に背景を付けない。
- コードブロックごとに別の段落スタイルを付けること（`@style` や言語の名前で見た目を変えること）。
- タブの幅の設定。
- `background` と `padding` を `code` 以外の段落スタイルで使うこと。
- 縦組みの本で、コードブロックを横組みの囲みとして組むこと。
- `golem new` の雛形にコードの書体を加えること。雛形のフォントの取得（[golem-cli ADR 0003](../../golem-cli/adr/0003-new-project-page-and-fonts.md)）が増え、雛形の利用者の多くはコードを書かない。G0808 のお知らせで、書体を指定できることを伝える。
- コード用の合字（`liga`、`calt`）を止める既定。役割の `features` で `-liga` のように止められる。
- 段落の孤立行と泣き別れの制御。コードブロックは一行からページを分けてよい。

## テスト設計

### 先に書いて失敗させるテスト

golem-project のテストで、`style.toml` の読み込みを確かめる。

- `[paragraph-styles.code]` の `font`、`size`、`background`、`padding` を読めること。何も書かないときの既定が、`font = "code"`、`padding = "0.5zw"`、背景なしであること。
- `[paragraph-styles.code]` の `based-on`、`indent`、`line-breaks`、`regex-styles` が、それぞれ G0306 になること。
- `[paragraph-styles.quote]` の `background` と `padding` が G0306 になること。
- `[paragraph-styles.x] based-on = "code"` が G0313 になること。
- `background` のスウォッチがないとき G0313、`padding = "-1zw"` と `padding = "abc"` が G0306 になること。
- `size` が版面の文字の大きさを超えると G0311 になること。
- `@style-def paragraph code size=10Q` を読めること、`@style-def paragraph code indent=1zw` が G0306 になること。

golem-eval のテストで、次を確かめる。

- `@style code` が G0266 になること。
- `[code: manifest.toml]` が `CharStyle "code"` になり、`[style code: manifest.toml]` と同じ IR になること。

golem-layout と golem-driver のテストで、PDF の組み方を確かめる。
組版の結果は、ページごとの行と字の位置の一覧（今の PDF のテストが使う形）で比べる。

- 行頭の空白：行頭に空白を 4 つ持つ行の最初の字の位置が、行の始まりと `padding` に空白の送りの 4 倍を足した位置であること。
- 行の途中の空白の連続が、詰められずに数のとおり残ること。
- タブの範囲：段落の中の `[code: a\tb]` のタブが、コードブロックのタブの位置（空白の送りの 2 倍）に進まず、今と同じ扱いになること。
- タブ：`\tx`、`ab\tx`、`abcd\tx` の `x` が、どれも空白の送りの 2 倍（`abcd` では 6 倍）の位置に来ること。和文の字（幅が空白の送りの整数倍でない）の後のタブが、次のタブの位置に進むこと。
- 両端揃えにならないこと：行長より短い二つの語の行で、語のあいだが空白の送りのままであること。
- ハイフネーションがかからないこと：行長を超える長い英単語の行が、ハイフンを描かずにクラスタの境界で折り返されること。
- 和欧間の空きが入らないこと：`a漢b` の三字の送りの和が、フォントの送りの和に等しいこと。
- 折り返し：行長を超える行が、収まる最後のクラスタの後で折り返され、続きの行が元の行頭の空白の幅と空白の送りの 2 倍の位置から始まること。行頭の空白が深く、8 字分が残らない場合に、空白の送りの 2 倍の位置から始まること。G0730 が一つ出て、行の数がメッセージにあること。折り返しのないコードブロックで G0730 が出ないこと。
- 行の格子：本文 13Q、行送り 22H、`code` の `size = "11Q"`、`padding = "0.5zw"` の版面で、3 行のコードブロックが占める格子の行の数が、計算のとおりであること。コードブロックの直後の本文の行が、格子の上にあること。
- 天地の中央：占めた領域の上の余白と下の余白の差が、1sp 以内であること。
- 背景：`background` を書いたとき、PDF のページの内容に、スウォッチの CMYK の値の塗りの矩形が文字の前に描かれ、矩形の範囲が占めた格子の行の領域と一致すること。`background` を書かないとき、矩形が描かれないこと。
- 改ページ：ページの残りが 2 行のときに 5 行のコードブロックを置くと、前のページに入るだけの行が入り、残りが次のページに続き、背景が二つの矩形に分かれること。ページの残りに一行と上下の `padding` が入らないとき、ブロックが次のページから始まること。
- 段組み：二段組みの版面で、段の境でも同じく分かれること。
- リストの中：リストの項目の中のコードブロックの背景と文字が、項目の本文の始まりから始まること。深い入れ子で行長が 8 字分を切ると G0743 になること。
- 空行：先頭、途中、末尾の空行が、それぞれ一行として残ること。
- 縦組み：縦組みの版面で、行頭の空白とタブの位置が天からの距離で決まること。
- 書体：`[fonts.code]` があるとき、コードの字がそのフォントで描かれ、PDF にそのフォントが埋め込まれること。コードのない本では、`[fonts.code]` があっても埋め込まれないこと。`[fonts.code]` がないとき、本文の書体で組まれ、G0808 が一つ出ること。
- `@listing` で取り込んだコードが、```` ``` ```` のコードブロックと同じに組まれること。

文字スタイル `code` について、次を確かめる。

- `[code: manifest.toml]` を行末に置いたとき、ハイフネーションで分かれず、語の全体が次の行に送られること。
- `[code: modules/golem-driver/src/Golem/Driver/Pdf.hs]` が行末で `/` の後で分かれ、ハイフンが描かれないこと。
- `based-on = "code"` の文字スタイルでも同じに組まれること。
- `[character-styles.code] color = "x"` を書いたとき、書体が `code` の役割、色が `x` になること。

golem-html のテストで、次を確かめる。

- `style.css` に、`pre` と `code` の `font-family`（`code` の役割の書体の並びと `monospace`）と、`pre` にだけ `white-space: pre-wrap` と `tab-size: 2` が書かれること。`code` の規則に `tab-size` が書かれないこと。
- `background` があるとき `pre` の `background-color` が、`padding` が `em` で書かれること。ないときは書かれないこと。
- `[code: x]` が `<code>x</code>` になること。
- `[fonts.code]` がないとき、`font-family: monospace` だけになること。

golem-driver の診断の検査（docs/diagnostics.md とソースのコードの一致）が、四つのコードを足した後に通ること。

### 自動テストにできないものの確かめ方

- 利用者のマニュアルと開発者のマニュアル（[docs/adr/0024](../../adr/0024-manual-audiences-and-policy.md)）を組んだ PDF を開き、コードブロックの背景、等幅の書体、字下げ、折り返しを目で確かめる。Acrobat の出力プレビューで、背景が CMYK のプロセスカラーだけで塗られていることも確かめる。
- HTML を Safari と Chrome で開き、同じく確かめる。
- CI の `determinism` ジョブで、マニュアルのハッシュが x86-64 と aarch64 で一致することを確かめる。

確かめた結果は、実装のプルリクエストのコメントに書く。

## トレードオフ

- 段落スタイル `code` を `body` の鎖から外し、書けるキーを四つに限るので、ほかの段落スタイルと規則が揃わない。`body` の鎖に入れると、本文の字下げや正規表現スタイルがコードに漏れ、それを止めるキーが要る。キャプションと傍注も、使うキーを `font` と `size` に限っているので、限る形は前例に沿う。
- `background` と `padding` の型を段落スタイルの全体に持たせ、実装を `code` に限るので、`code` 以外に書いた利用者にはエラーで伝えることになる。黙って無視するより、仕様書の「未実装の機能はエラー」の方針に合う。
- 長い行を折り返すと、コードの見た目が元のファイルと変わる。エラーにすると、`@listing` の取り込みのように直せない場合に PDF を組めなくなる。お知らせで、折り返したことを書き手に伝える。
- タブの幅を 2 に固定するので、4 や 8 を前提にしたコード（Makefile や Go の一部の整形）は字下げが浅く見える。字下げの深さの比は保たれる。行長を節約することを、エディタでの見え方に近づけることより優先した。
- コードブロックが格子の行を単位に占めるので、`padding` の値によっては、上下の余白が指定より大きくなる。格子を保つことを、余白の正確さより優先した。
- 縦組みの本のコードは、欧文が回転した縦組みになり、読みにくい。和文の技術書は横組みが多く、縦組みの本にコードを載せる需要は小さいと見込む。
- `[fonts.code]` がないときに本文の書体で組むので、コードが等幅にならない本が、お知らせだけで通る。マニュアルのように見本とする本では、お知らせを含めて診断を出さないことを検査で求める（[docs/adr/0024](../../adr/0024-manual-audiences-and-policy.md)）。
- 組み込みの文字スタイル `code` を足すと、すでに `[character-styles.code]` を別の用途で定義しているプロジェクトでは、その文字の書体が `code` の役割に変わる。今の利用者はリポジトリのマニュアルだけであり、マニュアルは意図どおりになる。
