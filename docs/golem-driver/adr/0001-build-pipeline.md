# ADR 0001: ビルドのパイプライン

ステータス: 採択

## 文脈

ビルドは、プロジェクトの読み込み、構文解析、ファイル内評価（S0）、文書構造（S1）、各ターゲットの出力の順に進む。
各段階はそれぞれのモジュールが担い、golem-driver はそれらを順に呼び、並列に実行できる部分を並列にし、診断を集め、出力を書く。
並列に実行しても結果が逐次の実行と一致することは、決定性の規則（ADR docs/adr/0002）の要求である。

この ADR は、PDF を除く出力（HTML、EPUB、プレーンテキスト）までのパイプラインを定める。
レイアウト（S2）と PDF の段階は、レイアウトの ADR で加える。

## 実装すること

### 段階

1. golem-project でマニフェスト、`style.toml`、import のグラフを読む。プラグインはキャッシュから読み込む。
2. マニフェストから到達するすべてのソースファイルを構文解析する。ファイルごとに並列に実行する。
3. import のグラフのトポロジカル順序に従って、各ファイルを S0 で評価する。依存関係のないファイルは並列に評価する。
4. すべての S0 の結果をマニフェストの順に並べて、S1 を実行する。
5. マニフェストと `--target` で指定されたターゲットごとに出力を作る。ターゲットごとに並列に実行する。

ある段階で一つでもエラーがあれば、その段階の後には進まない。
ただし、同じ段階の中では、エラーのないファイルの処理を続け、診断をできるだけ多く集める。

### 並列性

- 並列に実行した結果は、完了の順ではなく、マニフェストの章の順とファイルの中の位置で並べ直してから次の段階に渡す。
- 診断は、ファイルの順、位置の順、診断コードの順で並べてから出力する。

### プロファイル

- dev と prod の二つのプロファイルがあり、既定は dev とする。
- プロファイルは、校正用のコメントの扱い（dev では出力し、prod では出力せず警告を出す）と、診断の重大度の調整（golem-syntax ADR 0001 の `adjustForProfile`）に使う。
- 出力の内容がプロファイルによって変わるのは、校正用のコメントだけとする。

### 出力先

- 出力はプロジェクトルートの `build/<ターゲット>/` に書く。
- 書き出す前に、そのターゲットの出力先のディレクトリを空にする。前回のビルドの古いファイルが残って、出力の一部と誤解されるのを防ぐためである。

### インターフェース

```haskell
build :: BuildOptions -> IO (ExitCode, [Diagnostic])

data BuildOptions = BuildOptions
  { optRoot    :: FilePath
  , optTargets :: Maybe [Target]   -- Nothing ならマニフェストの指定
  , optProfile :: Profile
  , optCheckOnly :: Bool           -- golem check：S1 まで実行し、出力を作らない
  }
```

## 実装しないこと

- レイアウト（S2）と PDF の出力。
- ビルドの結果のキャッシュと、変更のあったファイルだけを処理し直すインクリメンタルなビルド。
- ファイルの変更の監視。

## テスト設計

- 複数のファイルからなる原稿を、並列と逐次の両方でビルドし、出力と診断が一致することを確かめる。
- ファイルの処理の完了の順を無作為に変えても、出力と診断が一致することを確かめる。
- 構文エラーを含むファイルがあるとき、ほかのファイルの構文エラーも報告され、評価の段階に進まないことを確かめる。
- dev と prod で、校正用のコメントの出力と診断の重大度だけが変わることを確かめる。
- 前回のビルドの出力が、次のビルドの前に消されることを確かめる。

## トレードオフ

インクリメンタルなビルドを持たないので、一つのファイルを直しても全体をビルドし直すことになる。
v1 では正しさと決定性を優先し、速度が問題になってからキャッシュを ADR で検討する。
章ファイルが独立に評価できる設計なので、キャッシュは後から加えやすい。
