# 脆弱性診断（2026-11-06）

## 結論

新しく追加された Emet の評価器で、可用性に影響する問題を2件再現した。どちらも重大度は中とする。原稿から呼ばれる関数だけで発生し、Wasm プラグインやファイルアクセスの権限を必要としない。

| ID | 重大度 | 問題 | 確認結果 |
| --- | --- | --- | --- |
| E-01 | 中 | `List.range` の長さが `Int` に収まらず、手数制限を迂回する | コストが負数・0になる。型検査を通った評価と CLI で迂回を再現 |
| E-02 | 中 | `String.replace` が手数を確認する前に巨大な結果を確保する | 40,000文字の引数から400,000,000文字の生成を試み、128 MiB のヒープ上限で終了 |
| L-01 | 環境上の注意 | 取得設定は Wasmtime 49.0.5 だが、手元の取得済み依存は49.0.2 | ソースの更新だけでは既存の開発環境を更新できていない |

前回の SVG と CSL-JSON の問題は再現入力が拒否されるようになった。Wasmtime の修正版を取得する設定も入っている。前回レポートを上書きせず、現在の状態をこの記録に残す。製品コードの修正は行っていない。

## 対象・脅威モデル・方法

- 対象コミット：`50b9fca8a0744f6f9d92808db231e6c04ac35d2c`。
- 環境：macOS / aarch64、GHC 9.10.3、64ビットの `Int`。
- 開始時の追跡済みファイルに変更なし。既存の未追跡 `.claude/` は調査対象外。
- 攻撃者が `.gm`、`.emet`、設定、図版、参考文献を提供し、利用者がそれをビルドする状況を想定した。ネットワーク公開サーバーを前提にしていない。
- [前回の監査](2026-11-05-security-audit.md) からの変更を確認し、Emet の値生成と評価手数、File 要求のパス解決、SVG・CSL の修正、Wasmtime の取得と advisory workflow を中心に読んだ。
- Emet は実際のパーサー・型検査・評価器を使って再現した。コスト算出の単体試験だけで結論を出していない。
- 負荷試験の各プロセスには、GHC RTS の `-M128m` と外部からの5秒タイムアウトを設定した。子プロセス以外を停止させる負荷試験は行っていない。
- Python はツール内の一時実行にのみ使い、Python ソースファイルは成果物に含めない。

前回からの差分は1,115ファイルに及ぶ。この診断は重点レビューであり、差分全体、全依存ライブラリ、全ターゲットの網羅的な安全性検証ではない。

## E-01：リスト長の整数オーバーフローで評価手数を迂回する

### 根拠

[`Prim.hs:41–43`](../../modules/golem-emet/src/Golem/Emet/Prim.hs) の `List.range` は、任意精度の整数で求めた長さを `fromInteger` で `Int` に変換する。範囲の検査や飽和処理はない。

```haskell
Right (PL [PV (VInt i) | i <- [x .. y]], fromInteger (max 0 (y - x + 1)))
```

[`Eval.hs:327–329`](../../modules/golem-emet/src/Golem/Emet/Eval.hs) はこの値に1を加えて手数に使う。同ファイルの `loop`（172–180行）は `steps > limit` で上限を判定するため、折り返した値が通る。既定の上限は100,000,000手である。

### 再現結果

[再現コード](2026-11-06-evidence/emet-probe.hs) と [実行記録](2026-11-06-evidence/probe-results.txt) に結果を保存した。

| 範囲の長さ | 計上された生成コスト |
| --- | --- |
| 10 | 10 |
| 9,223,372,036,854,775,808（2^63） | -9,223,372,036,854,775,808 |
| 18,446,744,073,709,551,616（2^64） | 0 |

対照の `List.range 1 100000001` は E04100、100,000,004手で拒否された。それに対して、次の型検査済み関数は `[1,2,3]` を7手で返した。

```text
f :: List Int
f = List.take 3 (List.range 1 18446744073709551616)
```

[CLI 用の関数](2026-11-06-evidence/range.emet) を `main.emet` として配置し、原稿から次の形で呼ぶと、終了コード0で `3` が出力された。対照の拒否と合わせ、単に遅延評価で意図的に範囲のコストを省く仕様ではなく、上限の判定を迂回していることを確認した。

```text
@import main.emet as audit

[= audit.f()]
```

同じ巨大範囲を `List.length` で消費する関数は、E04100 を返す前に `Heap exhausted`、終了コード251となった。ヒープ上限は試験側で設定したものであり、製品がこの量で止めることを意味しない。

### 影響と修正案

短い関数定義をビルドするだけで、評価の手数制限が機能しなくなり、CPU・メモリを消費する。LSP も Emet の評価経路を使うが、LSP セッションの停止は今回実証していない。

長さを任意精度のまま残り予算と比較し、予算を超える場合はリストを渡す前に拒否する。コストの加算も含め、負数やオーバーフローが発生しない表現にする。`Int` に収まるかの検査だけでは、十分大きな値を加算したときの問題が残る。2^63、2^64、予算境界、加算の境界で、確保や走査の前に E04100 を返す回帰テストを追加する。

## E-02：文字列生成の後で手数制限を確認する

### 根拠

[`Prim.hs:62–64`](../../modules/golem-emet/src/Golem/Emet/Prim.hs) は `String.replace` を `text (T.replace from to s)` として実装する。`text`（81行）は結果の `T.length` をコストとして返す。この長さを知るには結果を生成する必要があり、その後に [`Eval.hs:327–329`](../../modules/golem-emet/src/Golem/Emet/Eval.hs) がコストを手数へ加算する。

この問題は E-01 の整数オーバーフローを必要としない。長さが `Int` に収まっていても、予算の確認より先にメモリを使う。

### 再現結果

次の型検査済み関数に、`x` として20,000個の `b`、`y` として20,000個の `a` を渡した。

```text
f :: String -> String -> String
f x y = String.replace "a" x y
```

入力は合計40,000文字だが、結果は400,000,000文字になる。100,000,000手の既定上限を超えるにもかかわらず、E04100 を返す前に `Heap exhausted`、終了コード251となった。再現プロセスには128 MiBのヒープ上限を付けた。上限なしでOSのメモリを枯渇させる試験は実施していない。

今回の直接の再現対象は `String.replace` である。`String.join` や連結にも生成後の長さ計測があるが、同じ影響をすべて実証したとは扱わない。

### 影響と修正案

小さい入力から大きな中間値を作り、ビルドの可用性を損なう。通常の入力からも使えるプリミティブなので、Wasm の導入や File 権限は不要である。

プリミティブに残り予算を渡し、置換回数と出力長をオーバーフローしない形で求め、確保前に拒否する。予算内の量だけを段階的に生成して打ち切る方法もある。プロセス全体のメモリ制限は補助策となるが、手数制限を後から確認する実装自体を直す必要がある。

## L-01：設定と手元の Wasmtime の版が一致しない

現在の [`scripts/fetch-wasmtime.sh:20`](../../scripts/fetch-wasmtime.sh) は49.0.5を指定する。一方、調査開始時の `third_party/wasmtime/include/wasmtime.h` は `WASMTIME_VERSION "49.0.2"`、`third_party/wasmtime/VERSION` も49.0.2だった。`cabal.project.local` はそのディレクトリを参照する。`cabal build` 単体は取得スクリプトを呼ばず、今回もその依存設定で成功した。

49.0.2 は aarch64 の既知サンドボックス逸脱 CVE-2026-115893 の影響範囲にあり、49.0.4で修正されたことを [公式アドバイザリ](https://github.com/bytecodealliance/wasmtime/security/advisories/GHSA-mghf-wjfp-p5xm) で再確認した。リポジトリの版指定の修正と、既存環境への適用は区別する必要がある。

これは49.0.5を取得する現在のリリース手順が脆弱という判定ではない。手元の依存を更新せずに作った実行ファイルについて、安全になったとは判断できないという運用上の注意である。今回はWasmを実行せず、依存アーカイブも変更していない。

利用前に文書化された `scripts/fetch-wasmtime.sh` を実行し、更新後の依存でクリーンな再リンクを行う。CI/release にも取得処理がある。加えて、ビルド開始時に想定版とローカル版の不一致を検出すると、既存環境での取り残しを防げる。新設の `.github/workflows/advisories.yml` は固定版を調べる仕組みであり、各開発端末の取得済みバイナリの版を検査するものではない。

## 検証コマンド

ビルドと再現コードのコンパイルは成功した。旧版のパッケージもローカルに登録されていたため、再現コードのコンパイルではパッケージを明示した。生成したバイナリは `/tmp` に置く。

```sh
cabal build golem golem-emet --offline
mkdir -p /tmp/golem-audit-20261106
cabal exec --offline -- ghc -O0 -rtsopts -hide-all-packages \
  -package base -package text -package golem-emet-0.1.0 \
  -package golem-eval-0.1.0 -package golem-syntax-0.1.0 \
  -outputdir /tmp/golem-audit-20261106 \
  -o /tmp/golem-audit-20261106/emet-probe \
  docs/audits/2026-11-06-evidence/emet-probe.hs
/tmp/golem-audit-20261106/emet-probe cost +RTS -M128m -RTS
/tmp/golem-audit-20261106/emet-probe control +RTS -M128m -RTS
/tmp/golem-audit-20261106/emet-probe take +RTS -M128m -RTS
runghc -XGHC2021 -XLambdaCase -XOverloadedStrings -XDerivingStrategies \
  -imodules/golem-svg/src docs/audits/2026-11-05-evidence/svg-probe.hs
```

`length` と `replace` はヒープ枯渇を観測するモードである。実行記録は5秒で子プロセスを停止する外部制御の下で取得した。再実行にも時間とヒープの両方の制限を付ける。上の `cost`、`control`、`take` は巨大な範囲を全走査しない。

CLI の確認には `modules/golem-driver/test/fixtures/bibliographies` を一時領域へ複製した。制御文字の再確認後、書誌データを空配列にし、章01を上記の呼び出し、章02を通常の短文へ置き換えて `golem build --target text` を実行した。最初の試行は `pub fn` でないため拒否されたが、公開形式を直した試行で成功した。両方の記録を残している。
