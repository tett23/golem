# ロードマップのレビュー（Fable 5.1、2026-10-20、origin/main）

Fable 5.1 による読み取りだけのレビューの要約と、メインのセッションでの検証。
ロードマップは変えていない。採るかどうかは tett23 が決める。

## 致命的とされた三点

1. **リファクタリングの安全網がない**（roadmap の rc4「リファクタリング」「見た目の回帰テスト」）
   - 「決定性の検査で確かめる」とあるが、`scripts/determinism.sh` は同じコミットの出力を x86-64 と aarch64 で比べるだけで、コミットをまたいで出力が変わったかは見ない。**検証済み**（スクリプトの冒頭のコメント）。
   - 提案：rc4 の最初に「コミット間の出力一致の検査」を置く。前のコミットの `determinism.sh` のハッシュの一覧を保存し、PR で比べて差があれば失敗にし、意図した変更は一覧の更新で明示する。費用は小さい。リファクタリングはその後に置く。
   - 提案：見た目の回帰テストは、目的を「意図した出力の変更の見た目のレビュー」と「手で確かめる項目の消化」に書き直す。
   - メインのセッションの所見：リファクタリングは「出力は変えず」なので、要るのはバイト列の一致であり、指摘は正しい。tett23 の判断（決定性を守る仕組みは v1 までに完成させる、rc4 の早い時期が安い）は、見た目の回帰テストを rc4 に置く理由としてはそのまま成り立つ。ハッシュの比較を先に足すかどうかが論点である。
2. **v1.0.0 が rc4 より重く、プレリリースを経ない機能が出る**
   - v1.0.0 の節は 20 項目で、rc4 より多い。「rc4 の直後に v1.0.0」なので、v1.0.0 で IR や ABI を変えると rc を経ずに出る。
   - 提案：v1.0.0 の項目を「互換を壊す（記法、IR、ABI、`style.toml` のキー、JSON の diagnostics）」と「足すだけ」に分け、前者を rc4（あふれたら rc5）、後者を v1.1 以降に置く。rc の最後の版と v1.0.0 の差をバージョン番号だけにする。
3. **1.0 で何を約束するかを決める項目がない**
   - 1.0 以降に互換を守る対象（原稿の記法、CLI、`style.toml`、出力のバイト列、プラグインの ABI と CBOR、JSON の diagnostics、diagnostic のコード、LSP）と、壊してよい条件を決める ADR がない。
   - 廃止の手順（「廃止予定の notice を少なくとも一つの minor のバージョンで出す」）が、0.1.0 の次が 1.0.0 なので宙に浮く。`@listing` の `src=`（G0265）をいつ消すかが決まらない。
   - 提案：v1.0.0 の先頭に「互換性の方針の ADR」を置く。

## 重要とされた点

4. **プラグインの ABI の順序**：rc4 の早い時期に二つのプラグイン（総ルビ、初出の語のルビ）を作るが、その後の rc4 の `*[式]` の引数の送り方と、v1.0.0 の複数段落の注、索引、引用が ABI を変える。ABI が変わると既存のプラグインは読み込めない。提案：ABI を変える項目、ABI の凍結の宣言、プラグインの順にする。「配布の形」は [golem-plugin ADR 0002](../golem-plugin/adr/0002-distribution-and-lock.md) に従うと書き、v2 の配布の仕組みと分ける。
5. **EPUB の決定性が v2**：仕様書は「EPUB の決定性はまだ保証しない」とするが、`Golem.Epub` は zip のエントリの時刻をすべて 0 で書き、CI は EPUB のハッシュも比べている。**検証済み**。提案：rc4 で「保証する」と決め直す ADR を書く。費用はほぼ文書だけ。
6. **diagnostics の判定の近似の監査が v1.0.0**：直すと diagnostic のコードが変わりうるので、1.0 の直前ほど高くつく。rc4 の早い時期に移す。rc3 の「既知の不具合を直す」は、仕様書の既知の不具合が空なので参照先がない。

## 中程度とされた点

7. rc4 の PDF の項目に、やることが書いていないものがある（「書体にない字」は現状の説明だけ、「脚注の多い本の組版の時間」は観察だけ、「出力インテントの条件」は仕様書の書き漏れなので今すぐ仕様書を直せばよい）。
8. rc4 が重すぎる。タグ付き PDF と PDF/A は v2 に移す提案。
9. v1 の PDF/X-4 の適合の確認（規格の本文との照合か商用のプリフライト）が未決事項にあり、どのバージョンにも載っていない。v1.0.0 の項目にする提案。
10. 「手で確かめる項目」が 20 件を超え、リリースの前にどれを必須にするかがない。画像化の仕組みが入った後に、PDF の見た目の項目をまとめて確かめる項目を rc4 に置く提案。

## 軽微とされた点

11. 矛盾と重複：「diagnostics の英語化」が v2 と「課題にしなかった事項」の両方にある。v1 と v2 の重複（柱とノンブル、段落スタイル、しおりとリンク、複数段落の注）。rc3 の「PDF」の見出しが空。
12. 後になるほど高くつく互換の問題が v2 にある：正規表現の Oniguruma への置き換え（v1 の方言が部分集合かを v1 の前に確かめる）、数式の TeX の記法（`$` などの予約を v1 の前に決める）、macOS の署名と公証（v1 の配布物は Gatekeeper で開けないことを README に書く）。
13. 実装済みに見える項目の点検：rc4 の未実装の項目は正しく未実装だった。例外は 5 の EPUB だけ。

## レビュアーが最初にやるとした三つ

1. rc4 の先頭を「コミット間の出力一致の検査」にし、リファクタリングをその後に置く。
2. v1.0.0 を「互換を壊す」と「足すだけ」に分け、前者を rc4（か rc5）に、後者を v1.1 以降に置く。v1.0.0 の最初の項目を「互換性の方針の ADR」にする。
3. ABI を変える項目をプラグインより前に並べ、EPUB の決定性を rc4 に移して「保証する」と決め直す。
