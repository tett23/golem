# ADR 0003: PDF/X-4 の検証ツール

ステータス: 採択

## 文脈

ADR 0002 は、CI で使う PDF/X-4 の検証ツールを実装の最初の段階で選び、その結果をこの ADR に記録すると定めた。
選ぶまでは、要件ごとの検査を Golem のテストとして書くことになっていた。

2026 年 10 月の時点で、自由に使える検証ツールを調べた。
PDF/X-4 の適合をコマンドラインで判定できるものは見つからなかった。

- veraPDF は PDF/A と PDF/UA の検証器であり、PDF/X を扱わない。
- Apache PDFBox の preflight は PDF/A-1b の検証器である。
- pdf-preflight（Ruby）は PDF/X-1a の規則を持つが、PDF/X-4 は持たない。
- pack-preflight はボックス、フォントの埋め込み、出力インテントなどを調べるが、作者自身が規格の検証器ではないと述べている。

PDF/X-4 を判定できるのは、Acrobat のプリフライトや callas pdfToolbox のような商用のツールに限られる。
商用のツールは CI に組み込めず、ライセンスの都合で誰の環境でも再現できない。

## 実装すること

- CI での PDF/X-4 の検証は、ADR 0002 の要件ごとの検査（golem-pdf のテスト）と、qpdf による構造の検査（`qpdf --check`）で行う。外部の PDF/X-4 の検証器は使わない。
- 印刷所に入稿する前の最終確認は、利用者が商用のプリフライトで行うものとし、README にそう書く。
- 自由に使える PDF/X-4 の検証器が現れた場合は、この ADR を改める ADR を作り、CI に加える。

## 実装しないこと

- 商用のプリフライトを CI で動かすこと。
- PDF/X-4 の全要件を Golem の中で汎用に検証すること。Golem が生成しうる要素に限って検査する。

## テスト設計

- ADR 0002 のテスト（出力インテント、XMP の `GTS_PDFXVersion`、`Trapped`、各ページの `TrimBox`、フォントの埋め込み、禁止される要素がないこと）を CI で実行し続ける。
- 出力の PDF が `qpdf --check` を通ることを CI で確かめる。

## トレードオフ

外部の検証器がないので、Golem の検査が見落とした要件は、印刷所のプリフライトで初めて見つかる。
自前の検査は Golem が生成しうる要素に絞れるが、規格の読み違いは検査にも同じように入り込む。
その危険は、商用のプリフライトでの確認を入稿の手順に含めることで補う。
